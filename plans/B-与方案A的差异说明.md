# 方案 B · 与方案 A 的差异说明

> 本文件回答三个问题：**B 比 A 多做了什么？改了什么？不用改什么？**
> 并给出从 A 到 B 的增量迁移路径与增量工作量估算。
>
> ⚠️ **核心结论先写在前面：从 A 到 B 是增量，不是重做。**
> 复用约 80% 代码，改动面小，且每一步都可独立验证、可随时停止。
>
> 配套：`plans/B-Agent开发指导.md`（主文档）· `plans/B-工具契约与粒度设计.md`（工具契约）· `plans/B-评估集与成本模型.md`（评估与成本）

## 二、新增部分（仅 B 有）

全部新增代码集中在两个新目录：`client/agent/` 与 `client/tools/`，加一个评估目录 `test/eval/`。

| # | 新增项 | 目录位置 | 职责 |
|---|---|---|---|
| 1 | **Agent 运行时** | `client/agent/runtime.js`、`model-client.js`、`context.js`、`token-budget.js` | 循环（接收指令 → 规划 → 调工具 → 观察 → 汇报）；轮次/墙钟/token 三重上限；模型接入抽象；每轮从**落盘状态**重建上下文；预算熔断 |
| 2 | **工具封装层** | `client/tools/registry.js`、8 个工具文件、`validate.js`、`audit.js` | 把既有 `adapters/` 与 `safety/` **包装**成 8 个粗粒度业务工具；参数校验（不信任模型传参）；每次调用落审计 |
| 3 | **提示词与版本管理** | `client/agent/prompts/system.p-*.md`、`index.js` | 系统提示词正文；语义化版本；历史版本并存不覆盖；`prompt_version` 与 `prompt_digest` |
| 4 | **评估集与评估流程** | `test/eval/`（`dataset/`、`run-eval.js`、`reports/`） | 脱敏评估集；离线 runner（不依赖 CDP/真账号）；混淆矩阵与误批率报告；基线对比 |
| 5 | **决策记录与成本监控** | `client/agent/planner.js` + `instances/<ID>/decision_log.jsonl` + `tool_audit.json` | 每次决策落盘（`decision_id`、`model.version`、`prompt_version`、`usage` 等）；成本指标与告警 |
| 6 | **对话界面** | `client/ui/`（Agent 面板） | 自然语言输入；汇报展示；**决策明细并列展示**（`decisions` 与 `blocked[]` 对照，可核对） |

**六个新增项的目录职责边界**（三条硬约束）：

1. `client/agent/` **不得**`require('ws')`、不得直接操作 CDP、不得直接 `fs.writeFileSync`。
2. `client/tools/` **不得**出现 `data-e2e` 选择器字符串（选择器只能定义在 `client/platform/selectors.js`）。
3. `test/eval/` **不得**被生产代码 `require`（评估代码只用于离线跑分）。

## 三、需要改造的部分

改造共 **5 处**，且每一处都是"加一层"或"开个口"，**不是重写**。

### 3.1 🔧 `client/safety/`：新增对 Agent 意图的拦截

**为什么必须改**：Agent 是一个新的、**不可信的**调用方。它可能（因模型幻觉或被提示注入）请求超限、
请求候选外内容、请求扩大批次。方案 A 时期的 `safety/` 只面对"代码自己发起的发送"，
不需要考虑"调用方本身是恶意的"这种情况。

**改动内容**：

| 新增能力 | 位置 | 说明 |
|---|---|---|
| 候选外内容拦截 | `approve-batch.js`（工具层调用 `safety/similarity.js` 与候选集校验） | `draft_id` 必须在本批次 `draft_options` 内，否则 `AGENT_DRAFT_NOT_IN_CANDIDATES` |
| 批次过期拦截 | 同上级 | `expires_at_ms` 到期即拒绝，返回 `AGENT_BATCH_EXPIRED` |
| **二次独立校验** | `approve-batch.js` 重新调用 `safety/guard.js` + `circuit.js` + `similarity.js` | ⚠️ **不信任 Agent 的审批结果**，对每条批准项独立重跑全部校验 |
| 观察期硬拦 | `review-batch.js` / `approve-batch.js` | `sending_enabled=false` 时 `review_batch` 返回空批次、`approve_batch` 返回 `POLICY_SENDING_DISABLED` |
| 参数越权拦截 | `client/tools/validate.js` | 拒绝未知字段；`max_items` 按服务端策略上限截断 |

> ⚠️ **关键点**：这些校验是**新增的第二道**，不是替换原有的那道。
> 原有护栏（`scheduler` 的频控/随机间隔、`publish-verifier` 的成功判定、熔断）**一行不改**，
> 且仍然在发送执行时强制生效。**Agent 审批通过 ≠ 放松任何护栏。**

**改动量**：小。大部分逻辑是"在既有函数外面加一层校验与返回码映射"，`safety/` 内部算法不变。

### 3.2 🔧 `client/adapters/`：暴露"预筛候选"能力

**为什么必须改**：方案 A 中"筛候选"是**流水线的内部步骤**——采集进来、规则筛过、
直接进入发送流程，中间结果不需要对外暴露。方案 B 需要把这个中间结果**交给 Agent 审批**，
所以必须有一个明确的出口。

**四个新增出口**（新增方法，不改原有方法）：

| 出口 | 位置 | 供哪个工具 | 返回内容 |
|---|---|---|---|
| `listPendingCandidates({source_type, max_items})` | `adapters/collect.js` | T-06 `review_batch` | 已过规则筛选、待审批的候选线索（含 intent、excerpt、draft_options） |
| `listLeads({intent, region, date_from, date_to, keyword, source_type, limit})` | `adapters/collect.js` | T-01 `query_leads` | 只读线索库查询（**脱敏摘要**，不含 `sec_uid`/昵称） |
| `listFailures({lead_id, send_id, batch_id, date_from, date_to, limit})` | `adapters/collect.js` | T-08 `explain_failure` | 失败归因记录（`reason_code` 闭集） |
| `enqueueApproved({batch_id, items})` | `adapters/reply-*.js` 统一入口 | T-07 `approve_batch` | 把批准项投递到发送队列（返回 `queued_send_ids`） |

**三条实现约束**：

1. 出口方法**只读或只入队**，不实现任何 CDP 操作；真正的发送仍走原有 adapter 主体逻辑。
2. 返回结构必须**白名单构造**（显式挑字段），⚠️ **禁止 `return {...row}` 全量透传**——那是隐私泄漏最常见的入口。
3. `enqueueApproved` 入队时**不生成 `send_id`**；`send_id` 仍由发送执行层在发送前生成并落盘（红线 2）。

**改动量**：小到中。约等于"在既有流水线里加 4 个导出函数 + 一次字段白名单整理"。

### 3.3 🔧 审计：扩展为记录 Agent 决策（红线 3 的扩展）

**为什么必须改**：红线 3 要求审计能回答"当时实际生效的策略是什么、用户是否主动调高过、系统是否拒绝过"。
方案 B 引入模型决策后，必须再多回答一个问题：**"当时为什么发了这一句？"**
没有这个记录，模型或提示词一更新，历史决策就无法复现（这是 B 的两个特有风险之一）。

**改动内容**（🆕 全部为**新增**，不修改既有审计字段）：

| 新增记录 | 位置 | 字段 |
|---|---|---|
| 决策记录 | `instances/<ID>/decision_log.jsonl` | **字段见 `plans/B-工具契约与粒度设计.md` §五**：`decision_id`、`decided_at_ms`、`batch_id`、`input_summary`、`candidates_offered`、`decisions[]`、`model{provider,model,version}`、`policy_version`、`prompt_version`、`usage`、`latency_ms` |
| 工具审计 | `instances/<ID>/tool_audit.json` | 工具名、`args_digest`、`ok`、阻断码、`latency_ms`、`prompt_version` |
| 配置审计（复用既有） | 走既有 `POST /api/v1/audit/config-changes` | `field_key:"agent.enabled"`、`"agent.prompt_version"`、`"agent.allow_generated_drafts"` |
| 计数上报（复用既有） | 走既有 `POST /api/v1/usage/report` | `agent_tool_calls{tool,code}`、`agent_decisions{approve,reject,skip}`、模型标识哈希 |

**三条硬性约束**：

1. **不新增服务端接口**——决策留痕挂到既有的 `usage/report` 与 `audit/config-changes` 上。
2. **只传哈希与计数**——`provider|model|version` 取 `hmac(privacy_salt, …)` 前 16 hex；
   `prompt_version` 与 `policy_version` 是明文（非隐私且举证必需）。**绝不上传评论原文、回复原文、`sec_uid`。**
3. ⚠️ `agent_*` 计数属**新增上报字段**，`shared/protocol.md` §7.5 的白名单会校验它。
   按 §8.1「新增可选请求字段」流程：**服务端先上线支持**，在此之前 Agent 计数只落本地审计。

**改动量**：小。既有审计机制（本地/服务端双写、哈希化上报）**完全复用**，只是多写两个本地文件与三个计数。

### 3.4 🔧 前端：新增对话界面，**保留原图形界面**

**为什么保留原图形界面**（⚠️ 这一条不是可选项）：

| 理由 | 说明 |
|---|---|
| **降级路径** | Agent 不可用、超预算、误批率超标时，商家必须仍能完成回复 → 见 `plans/B-Agent开发指导.md` §4.6 的 L1~L4 |
| **部分操作更适合表单** | 批量配置关键词、编辑话术池、查看流水台账、卡密兑换——用表单比"跟 Agent 说"更精确高效 |
| **合规与心理预期** | 不是所有商家都愿意让模型参与决策；`docs/需求规格.md` FR-2.5 的默认档位是**半自动** |
| **举证需要** | 审计导出的操作界面沿用既有 UI |

**新增内容**：

| 新增 | 说明 |
|---|---|
| 对话面板 | 自然语言输入 + 汇报展示（复用既有 UI 的设计 token 与暗色主题，保持"按键简洁高级"） |
| 决策明细视图 | ⚠️ **必须并列展示** `decisions[]` 与 `blocked[]`——让商家能看出"批准了但被安全校验拦下了"，避免误以为"Agent 批准 = 一定发出" |
| 降级状态条 | 明确显示当前降级级别（L1~L4）与原因，**不许静默降级** |
| Agent 设置页 | 总开关（**默认关闭**）、模型配置、`allow_generated_drafts`（**默认关闭**）、预算 |

**改动量与约束**：
① 前端仍为**原生 DOM、无框架、无构建**（`shared/术语与选型基准.md` §3.3）；
② 既有页面**不改结构**，只新增导航入口与面板；
③ 本地 API 仍绑 `127.0.0.1` + 会话令牌 + CORS 白名单（修复 D-6 的成果不得回退）。

### 3.5 🔧 看板：新增 Agent 相关指标

**口径约束**：新增指标**不得改变既有指标口径**（`docs/需求规格.md` FR-4.3 要求客户端与服务端口径一致）。
既有指标（截流总量、已回复人数、回复条数、回复成功率、分来源明细、失败原因分布、积分消耗、近 7 日趋势）
**全部保持不变**，新增指标单列。

**新增指标**：

| 指标 | 定义 | 风险方向 |
|---|---|---|
| **审批通过率** | `approve` 条数 ÷ 被审批（approve+reject+skip）条数 | ⚠️ **必须标注口径**（见下） |
| **误批率** | 已发送条目中标注为不该回复的比例（**需人工抽检**） | ⚠️ **>8% 即停用 Agent** |
| **误拒率** | 应回复条目中被 `reject` 的比例 | 低风险 |
| **跳过率** | `skip` 占比 | 过高 = Agent 没在工作 |
| **每条成本** | 每条成功回复的摊薄 token 成本 | 占比 >15% 需优化 |
| **话术池命中率** | `source:"template"` 占比 | <70% 时成本上升 |
| **工具阻断计数** | 按阻断码聚合（`blocked[]`） | 突增说明模型在越权 |
| **降级触发次数** | L1~L4 各级次数 | 可用性指标 |

> ⚠️ **"审批通过率"必须写明口径，否则会得出相反结论。**
> 本项目统一为：**`approve` 条数 ÷ 被审批条数**（Agent 对送来的候选放行了多少）。
> 另一种口径"成功发送数 ÷ 批准数"衡量的是**安全护栏的拦截强度**，含义完全不同，**不得混用**。
> 看板上应同时展示 `blocked[]` 计数，让商家能区分"Agent 没批"与"批了但被系统拦下"。

## 四、不需要改动的部分

**明确列出原样复用的资产。改动面小是本方案可执行的关键前提。**

| 资产 | 状态 | 说明 |
|---|---|---|
| `license-server/` **全部**（`api/`、`domain/`、`store/`、`crypto/`、`admin/`） | ✅ **一行不改** | B 不新增服务端接口；策略下发、计费、卡密、看板、审计留存全部复用 |
| `shared/protocol.md` 契约 | ✅ **不改**（仅需增补两个可选字段，见 §6 注意） | 认证、签名、心跳、计费、审计、错误码全部复用 |
| `shared/lib/`（`protocol.js`、`stable-stringify.js`、`errors.js`） | ✅ **一行不改** | 双端共享契约常量 |
| `client/core/`（`cdp.js`、`browser-host.js`、`ipc.js`） | ✅ **一行不改** | Agent **永远不碰 CDP**——这正是工具粒度设计的核心 |
| `client/platform/`（选择器注册表、页面模型、`publish-verifier.js`） | ✅ **一行不改** | 抖音 DOM 知识与成功判定逻辑不受影响 |
| `client/license/`（`auth.js`、`heartbeat.js`、`reporter.js`、`sign.js`） | ✅ **一行不改** | 心跳、策略 ack、离线补报、停机逻辑不变 |
| `client/host/store.js` | ✅ **一行不改** | 单写者 + 原子写的实现复用（B 只是多几个调用方） |
| `client/host/scheduler.js` | ✅ **一行不改** | 频控、随机间隔、熔断、活跃时段全部复用 |
| `client/host/api.js` | ✅ **基本不改** | 仅新增 Agent 相关路由（`/api/agent/*`） |
| `client/safety/` 的**算法** | ✅ **不改** | `guard.js` / `similarity.js` / `circuit.js` / `audit.js` 的内部逻辑不变（只在外面加一层调用与返回码映射） |
| `test/`（fixtures 离线回归、`run.js`） | ✅ **不改** | 既有测试全部继续通过（这是回归门槛） |
| `legacy/` | ✅ **不动** | 仍为只读存档 |
| 三条红线的**实现机制** | ✅ **不改** | Agent 是红线的**新受约束方**，不是红线的修改者 |

**可以这样理解**：方案 B 只在"业务动作如何被触发"这一层做了加法——
**从"用户点按钮触发"变成"用户下指令 → Agent 审批 → 代码触发"**，
而"业务动作本身怎么做、发送护栏怎么拦、结果怎么计费与审计"**完全没有变**。

## 五、增量工作量估算

### 5.1 估算表

**假设**（⚠️ 估算的前提，请按实际团队规模折算）：

- 1 名熟悉本项目的全栈开发（Node + 原生前端）；
- 已完成方案 A，团队已熟悉 `adapters/` / `safety/` / `store.js`；
- 有可用的模型 API 与测试账号；
- 不含等待审批、真机验证排队、商务沟通的时间。

| # | 模块 | 增量人日 | 说明 |
|---|---|---|---|
| 1 | 工具层（8 个工具 + registry + validate + audit） | **4–6** | 只读 3 个简单；`review_batch`/`approve_batch` 最重（含二次校验与幂等） |
| 2 | Agent 运行时（循环 + 上限 + 中断 + 降级分支） | **3–5** | 含三重上限与 L1~L4 降级 |
| 3 | 模型接入抽象（内置 `node:https` 自研适配器） | **1–2** | 不引 SDK；含厂商字段归一化 |
| 4 | 提示词工程（首版 + few-shot + 版本管理 + 反复调试） | **3–5** | 调试占大头，需要评估集支撑 |
| 5 | `adapters/` 四处读取型出口 | **1–2** | 加导出 + 字段白名单整理 |
| 6 | `safety/` 的 Agent 意图拦截层 | **1–2** | 加一层校验与阻断码映射 |
| 7 | 状态落盘与决策记录（含工具审计） | **2–3** | 经 `store.js`；含 schemaVersion |
| 8 | 对话界面 + 决策明细视图 + 降级状态条 | **3–5** | 原生 DOM，无框架；复用既有设计 token |
| 9 | 评估集（200 条：抽样 + 脱敏 + 标注 + 复核） | **4–6** | ⚠️ 主要是**人力**成本，不是编码成本 |
| 10 | 评估 runner + 报告生成 | **2–3** | 离线，不依赖 CDP |
| 11 | 成本监控与告警 | **1–2** | 指标接入看板 + 预算熔断 |
| 12 | 看板新增 Agent 指标 | **2–3** | 含人工抽检误批率的操作流程 |
| 13 | 降级路径实现与故障注入测试 | **2–3** | 四级降级逐一实测 |
| 14 | 上线前检查清单逐项验证（含真机验证） | **3–5** | 真机验证不可压缩 |
| | **合计** | **32–52 人日** | |

### 5.2 与方案 A 的比例

**假设方案 A 自身的规模**（基准，用于计算比例）：

| 方案 A 阶段 | 人日量级（估算） |
|---|---|
| P0 移 `legacy/` + fixtures + 选择器骨架 | 3–5 |
| P1 契约 + 授权中心 + 客户端登录 | 12–18 |
| P2 core + platform + 评论适配器 + **真机验证门** | 15–22 |
| P3 弹幕 + 私信适配器 | 8–12 |
| P4 双端看板 + 上报补报 | 6–9 |
| P5 卡密 + 管理后台 + 套餐 + 多实例隔离 | 8–12 |
| P6 UI 精修 + 文档 + 72h 长稳 | 6–10 |
| **方案 A 合计** | **58–88 人日** |

**增量比例**：

```
                        32–52 人日
B 相对 A 的增量比例 = ─────────────────  ≈ 36% ~ 59%
                        58–88 人日
```

**结论**：**B 相对 A 的增量约为 A 自身的 30%–50%。**
（区间上沿出现在"A 做得精简、B 把评估集做重"的组合；下沿出现在"A 做得扎实、工具层复用度高"的组合。）

> ⚠️ **三条估算纪律**：
> ① **不要把"Agent 层"当成一个独立项目来估**——它没有独立部署、独立数据库、独立发布流程，
> 全部是客户端内的进程内模块。若估算结果显著超过 50%，通常说明方案被理解成了"另建一套系统"。
> ② **评估集（第 9 项）是人力成本而非编码成本**，容易被低估；200 条 × （标注 + 复核）≈ 4–6 人日。
> ③ **提示词调试（第 4 项）与评估集（第 9/10 项）必须同时进行**，
> 否则调试没有依据，实际耗时会显著超出上表（这是最常见的工作量失控点）。

### 5.3 增量成本（非人力）

| 项 | 说明 |
|---|---|
| 模型 token 费用 | 开发期评估与调试消耗；见 `plans/B-评估集与成本模型.md` §五 |
| 评估集标注人力 | 已在 §5.1 第 9 项计入 |
| 服务端 | **零增量**（不新增接口、不新增存储；`agent_*` 计数复用既有上报通道） |
| 分发体积 | **零增量**（不引第三方 SDK；模型调用用内置 `node:https`） |

## 六、迁移路径

**核心原则：增量式，不是重做。每一步都可独立验证、可随时停止，且停下来时系统仍然可用。**

### 第 1 步：先实现只读工具，验证 Agent 能读数据

| 项 | 内容 |
|---|---|
| **做什么** | `client/tools/registry.js` + `validate.js` + `audit.js` + T-01 `query_leads` / T-02 `get_stats` / T-03 `get_account_health` + `client/agent/` 最小运行时 + 最小对话界面（只读问答） |
| **改动面** | 新增 `client/agent/`、`client/tools/`；`adapters/collect.js` 加 `listLeads()` 出口 |
| **验证方式** | ① 单元测试：schema 校验、未知字段拒绝、审计落盘；② 真机问 5 个问题（"今天回复了几条""现在能不能发""还剩多少额度"），数字与图形界面看板**逐项一致** |
| **继续下一步的判据** | ① 工具清单恰好 3 个、无任何写操作；② `query_leads` 返回**不含** `sec_uid`/昵称（代码断言）；③ `get_account_health` 数值与 `policy.json` 一致（非自行推算）；④ 每次调用都有审计记录 |
| **停止条件** | 若 Agent 连"读数据"都不稳定（频繁调错工具、数字对不上），说明提示词或工具描述有问题——**先解决再往下，不要带着问题加写操作** |

### 第 2 步：实现 `review_batch` / `approve_batch`，**不做 LLM 生成**，验证核心假设

| 项 | 内容 |
|---|---|
| **做什么** | T-06 + T-07；`adapters/` 暴露 `listPendingCandidates()` / `enqueueApproved()`；`safety/` 加 Agent 意图拦截层；候选由**纯规则**生成（话术池匹配 + 相似度检测），**不接任何 LLM 生成**；决策记录落盘 |
| **改动面** | 新增 2 个工具；改 `adapters/collect.js`、`adapters/reply-*.js`、`safety/` 外层；`ui/` 加决策明细视图 |
| **验证方式** | ① 构造边界用例使 7 个阻断码各触发一次（`AGENT_DRAFT_NOT_IN_CANDIDATES`、`AGENT_BATCH_EXPIRED`、`POLICY_DAILY_CAP`、`POLICY_SENDING_DISABLED`、`POLICY_CIRCUIT_OPEN`、`SAFETY_SIMILARITY_BLOCKED`、`SAFETY_INTERVAL_TOO_SHORT`）；② 真机跑一批真实候选走完整链路（审批 → 入队 → 发送 → 结果回报）；③ 断网/重启后批次仍可续；④ 同一 `batch_id` 重复提交验证幂等 |
| **继续下一步的判据** | ① **手工篡改 `draft_id` 为候选外值，必须 `blocked`**；② 同 `batch_id` 重复提交 → 返回首次结果，**不重复发送**；③ 观察期下 `review_batch` 返回空批次、`approve_batch` 返回 `POLICY_SENDING_DISABLED`；④ 发送仍走完整护栏（`send_id` 发送前落盘、平台响应体判成功、审计双写）；⑤ **商家实际试用后反馈"愿意用"** |
| **⚠️ 这一步为什么不做 LLM 生成** | 方案 B 有一个**与 LLM 能力无关**的假设：**商家接受"Agent 替我做审批"这个形态**。即使 Agent 只做规则级审批，形态是否被接受也是同一个问题。而 LLM 生成内容恰恰是风险最高（可能被判内容级 spam）、成本最高、最难回退的一块。**先用纯规则把形态与链路验证完，在最小风险下回答"这条路走不走得通"。** |
| **停止条件** | 若商家反馈"不愿意让 Agent 审批"或"还不如自己点"→ **到此为止**。此时投入仅为工具层的一部分，且已交付的只读问答仍有价值；**不要因为已经投入就继续加 LLM** |

> ⭐ **第 2 步是整个迁移路径的关键决策点。** 它用最小的成本验证最大的不确定性。
> 前两步完成后，系统已经是一个**可用的、有价值的**产品（对话式查询 + Agent 审批），
> 即使后面三步全部不做，也不算白做。

### 第 3 步：引入 `analyze_comments`（第一个 LLM 能力）

| 项 | 内容 |
|---|---|
| **做什么** | T-04 + 24h 缓存 + 意图闭集校验；同步建立**评估集 V1**（≥200 条，脱敏 + 标注 + 复核） |
| **改动面** | 新增 1 个工具；`client/agent/` 加模型实际调用；新增 `test/eval/` |
| **验证方式** | 跑评估集出意图分类准确率报告与混淆矩阵；用方案 A 的**实际关键词规则配置**跑同一份评估集做基线对比 |
| **继续下一步的判据** | ① 整体准确率 **≥85%**；② **`complaint` 召回率 ≥95%**（漏判为询价会导致在投诉下自动回复，风险最高）；③ 相对规则基线的召回增益**可量化**（例如询价类召回 55%→91%）；④ 缓存命中时零 token 消耗（实测）；⑤ 未知意图一律落 `unknown`，不得自由文本 |
| **停止条件** | 若**增益不足**（例如询价召回只提升 5 个百分点）→ **说明规则已够用，不应继续上 LLM**。这是评估集最重要的一次决策输出，且它是**在花钱之前**得到的结论 |

### 第 4 步：建评估集与成本监控

| 项 | 内容 |
|---|---|
| **做什么** | 评估 runner + 报告生成 + 成本看板 + 预算熔断 + 四级降级实现 + 每周人工抽检误批率的流程 |
| **改动面** | `test/eval/run-eval.js`；`client/agent/token-budget.js`；`ui/` 加成本与降级展示；看板新增 Agent 指标 |
| **验证方式** | ① 用两版提示词跑同一评估集，能产出**可对比**的报告（含逐项差值）；② 成本看板数字与实际 token 账单核对一致；③ 四级降级逐一故障注入实测（断网 / 改错 API Key / 预算设 0 / 人工急停） |
| **继续下一步的判据** | ① 评估集已脱敏（逐条人工确认）；② **误批率 <5%**（硬门槛 ≤8%）；③ 每条成功回复摊薄成本占单价 **<15%**；④ 降级实测生效且**状态在 UI 可见**；⑤ 决策记录可按 `batch_id` 导出并人工复核 |
| **停止条件** | 若误批率 >8% 且经两轮提示词整改仍不下降 → **停用 Agent、回退方案 A**（见 §7）。此时不建议进入第 5 步：内容生成会让风险进一步上升 |

### 第 5 步：最后引入 `draft_replies`

| 项 | 内容 |
|---|---|
| **做什么** | T-05 + `allow_generated_drafts` 开关（**默认关闭**）+ 生成候选的相似度检测强制 + 生成候选进池的复核流程 |
| **改动面** | 新增 1 个工具；`ui/` 加开关与复核入口；话术池加"待复核"区 |
| **验证方式** | ① 构造**语义雷同但字面不同**的生成内容，验证相似度检测能拦下；② 人工评审生成候选的可用率；③ 确认 `similarity_checked:false` 的候选不会出现在任何 `draft_options` 中 |
| **完成判据** | ① `similarity_checked:false` 的候选**不出现**在任何 `draft_options`；② 商家未显式开启时**没有任何** `source:"generated"` 候选；③ 生成候选人工评审通过率 ≥70%；④ 未复核不得进入长期话术池 |
| **停止条件** | 内容风控风险最高。若生成候选的可用率低或相似度拦截率异常高，**保持 `generated` 永久关闭**也是完全可接受的结论——话术池匹配已经能覆盖 ≥80% 的场景 |

### 6.1 迁移路径示意

```
A 完成
  │
  ├─ 1. 只读工具 ──────────── ✓ 验证"Agent 能看数据"
  │
  ├─ 2. review/approve ⭐ ─── ✓ 验证"审批式 Agent 这个形态被接受"  ← 关键决策点
  │      先不做 LLM 生成          走不通就停在这里，已交付物仍有价值
  │
  ├─ 3. analyze_comments ──── ✓ 验证"LLM 有可量化增益"           ← 花钱决策点
  │
  ├─ 4. 评估集 + 成本监控 ─── ✓ 验证"误批率与成本都可接受"
  │
  └─ 5. draft_replies ─────── ✓ 最后一个做（内容风控风险最高）
```

**每一步都是"加上去"，不是"重做前面"。任何一步停下来，系统都仍然可用**
（区别只是 Agent 能力少一层，图形界面始终完整）。

### 6.2 迁移期间的三个注意点

| # | 注意点 |
|---|---|
| 1 | **不要提前改 `safety/`**。第 1 步不需要动 `safety/`；过早改动会让方案 A 的既有测试出现假失败。**按步骤改** |
| 2 | **`agent_*` 上报字段需服务端先上线**（`shared/protocol.md` §8.1 的"新增可选请求字段"流程）。在此之前 Agent 计数**只落本地审计**，不要为了上报而擅自扩白名单 |
| 3 | **评估集要早做**。第 3 步就要有 V1，不要等到第 4 步——否则第 3 步的"增益是否可量化"根本无法回答，会退化成"感觉好像好一点" |

## 七、不建议做 B 的情况

**明确列出停止条件。命中任意一条，都不应该做方案 B——这不是技术能力问题，是适用性问题。**

| # | 情况 | 为什么不该做 | 该怎么判断 |
|---|---|---|---|
| **1** | **规则召回率已足够** | 若方案 A 跑一个月后，导出的真实评论里"规则抓不住的意图"占比很低（例如 <10%），上 LLM 的收益极小、成本与复杂度却是确定的 | 用 §六 第 3 步的基线对比方法量化：询价类召回若只提升 <10 个百分点，就属于这一类 |
| **2** | **定价空间无法覆盖 token 成本** | 按成功条数计费时，token 成本占比 >30% 即不可持续；无论产品多好，亏钱的方案不能上 | 按 `plans/B-评估集与成本模型.md` §5.4 测算；**注意分母要用"成功回复单价 × 计费成功率"**，被风控拒绝的发送收不到钱但 token 已花掉 |
| **3** | **团队无 LLM 应用经验** | 评估集、提示词版本管理、成本监控、误批率抽检——这四项都不是"会调 API"就能做好的。缺少这些，方案 B 会变成"上线后无法判断好坏、无法安全迭代"的黑盒 | 自查：能否独立完成一份含混淆矩阵与误批率的评估报告？不能则先补齐能力 |
| **4** | **P2 真机验证门未通过** | G-1~G-5 是**方案 A 与 B 的共同前提**（B 用同一套 CDP 驱动）。A 走不通，B 一样走不通，且 B 还多一层成本 | `shared/术语与选型基准.md` §5.2 的 G-1~G-5；**未通过则先修 A，不要用 B 绕过** |
| **5** | **商家不接受模型参与决策** | 方案 B 的核心假设就是"商家接受 Agent 替我审批"。若商家明确反对（合规要求、内部制度、心理顾虑），后面的工作全部作废 | 第 2 步就会暴露；不必先投入 LLM 部分 |
| **6** | **真机数据量太小** | 评估集依赖真实评论。若月评论量只有几十条，既建不出可信的评估集，也说不清"规则抓不住多少" | 估算：月真实评论量 <300 条时，评估集建设周期会拉长到不可接受 |
| **7** | **误批率无法压到 8% 以下** | 误批会真实发出且无法撤回。>8% 意味着每 100 条回复里有 8 条以上不该发——这在商家账号上是不可接受的风险 | 第 3/4 步即可测出；**两轮整改无效就应停用 Agent 并回退方案 A**（这是成熟决策，不是失败） |
| **8** | **合规/客户合同禁止数据出本机** | 方案 B 需要把评论摘要发给第三方模型服务。若客户合同或行业合规明确禁止，则不可实施（除非改用可私有化部署的模型，成本另算） | 逐条核对客户合同与 `docs/需求规格.md` FR-6 的责任边界；⚠️ 即使允许，也要按主文档 §7.4 做脱敏 |
| **9** | **无人力维护评估集** | 评估集会腐化：平台语言在变、商家业务在变。没有持续维护，半年后它测的就不是线上的东西了 | 至少需要"每季度复核 + 每次改提示词必重跑"的稳定投入承诺 |

> ### 最后一条建议
>
> **先完成方案 A，跑满一个月，导出真实评论数据，再回来读这一节。**
> 那时候你手上有真实数字，判断"要不要做 B"会从"讨论"变成"算一道题"。
> 方案 A 本身可独立交付与商业化，方案 B 是增值升级项、不是必需项。
