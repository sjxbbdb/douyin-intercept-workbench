# 方案 C · 工作流包契约

> **这是"专业分化"能不能成立的唯一关键文档。**
>
> 如果工作流包只是"一份配置文件"，那么每来一个行业就要改一次核心代码——那是工具，不是平台。
> 如果工作流包是"可以执行任意代码的插件"，那么三条红线全部失守——每个包都是一个绕过护栏的后门。
>
> 本文档定义这条线在哪里，并给出完整的包契约。
>
> 配套：`plans/ADR-001-Agent优先与框架选型.md`（定位与框架）· `plans/B-工具契约与粒度设计.md`（工具粒度）·
> `plans/D-重构迁移与验收.md`（现有代码如何迁移）

---

## 一、什么是工作流包

### 1.1 定义

> **工作流包（Workflow Pack）= 一个专业领域的全部"业务知识"，以声明式方式描述。**
> 它回答"这个行业里，什么样的人值得接、什么话不能说、什么算成功"，
> **不回答**"怎么点按钮""能发多少条"。

| 工作流包定义 | 工作流包**不**定义 |
|---|---|
| 线索判据（什么信号值得接） | 日发送上限、最小间隔 |
| 业务规则（什么情况该走什么流程） | 观察期是否禁发 |
| 话术池与选择策略 | 如何判定平台发送成功 |
| 合规边界（本行业的额外禁语/禁场景） | 任何浏览器操作方式 |
| 成功定义（什么算这一步做成了） | 计费资格判据 |
| 领域术语表（供模型理解行话） | 审计字段与隐私边界 |

### 1.2 一个具体对比

同样是"客户问多少钱"，三个行业的工作流包给出**完全不同的行为**：

| | 本地生活（团购） | 家居定制 | 教育培训 |
|---|---|---|---|
| **线索判据** | 问"有没有优惠""几个人" | 问"多少钱一平""什么时候量房" | 问"几岁能上""多少钱一期" |
| **必须收集** | 就餐人数、时间 | 房型、面积、城市 | 学员年龄、基础 |
| **合规禁语** | 不得承诺具体折扣 | 不得承诺工期与总价 | ⚠️ **不得承诺升学/提分效果** |
| **高风险信号** | 差评、投诉 | 工期质疑 | 价格敏感 + 效果追问 |
| **话术风格** | 直接、促单 | 专业、先问需求 | 谨慎、先建立信任 |
| **成功定义** | 留下联系方式 | 约到量房 | 约到试听 |

**这六行差异，就是"专业分化"的全部内容。** 核心代码一行不改，只换包。

## 二、🔴 三条不可违背的约束

> 这三条决定了"插件化"是平台的扩展机制，还是红线的漏洞。

### 约束 1：工作流包是**声明式**的，不是可执行代码

**允许**：JSON / YAML 声明、Markdown 提示词片段、模板字符串、正则表达式。

**禁止**：❌ JavaScript 文件、❌ `eval` / `new Function`、❌ 任何形式的动态代码执行。

**理由**：一旦工作流包能执行代码，它就能：
- 提高自己的日上限（破红线 1）
- 直接构造"计费成功"的上报（破红线 2）
- 跳过审计写入（破红线 3）

**而工作流包的来源是第三方（渠道商、合作方、甚至客户自己定制）**，不可能逐个审计其代码安全性。
声明式是唯一能同时做到"可扩展"与"可审计"的形态。

> ⚠️ **"只让可信的人写包"不是可接受的答案。** 项目定位是平台，平台的前提就是**作者不可信**。

### 约束 2：工作流包**不得**触碰硬规则

红线 1 的所有数值（`daily_max`、`min_interval_ms`、`content_similarity_max`、`active_hours`）
由服务端 `tier_table` 下发，**工作流包无权读写**。

**校验点**：包加载时，若声明中出现下列键名，**直接拒绝加载**并报 `PACK_FORBIDDEN_KEY`：

```
daily_max · min_interval_ms · content_similarity_max · active_hours
sending_enabled · collect_only · tier · circuit_* · balance · credits
confirm_signal · platform_status_code · verdict · billing_*
```

> 这是**键名黑名单 + 契约白名单双重校验**（见 §四），不是"提示作者不要写"。

### 约束 3：工作流包的作用范围是**单向收窄**

工作流包只能让系统**更保守**，不能更激进：

| 维度 | 允许 | 禁止 |
|---|---|---|
| 可回复的线索范围 | **收窄**（只处理某类意图） | 扩大 |
| 话术可用范围 | **收窄**（限定子集） | 引入服务端策略外的内容 |
| 时间窗 | **收窄**（在自己的活跃时段内再限） | 超出 `active_hours` |
| 风险场景 | **新增禁语/禁场景** | 移除任何既有禁令 |
| 批次规模 | **调小** | 调大 |

> **实现方式**：核心把"服务端策略"与"包声明"做**交集**运算，
> 而不是"包声明覆盖策略"。见 §五 的加载流程。

## 三、目录与文件结构

```
packs/
├── _template/                     ← 新包的起点（复制这个目录改名）
│   ├── pack.json                  包清单（必填，契约见 §四）
│   ├── prompts/
│   │   ├── system.md              该领域的系统提示词片段
│   │   └── classify.md            意图分类提示词
│   ├── scripts/                   话术池（声明式，非代码）
│   │   ├── price_inquiry.md
│   │   └── ...
│   ├── glossary.json              领域术语表（供模型理解行话）
│   └── README.md                  这个包面向谁、怎么用
│
├── douyin-intercept/              ← 内置包 1：抖音截流（现有产品能力）
│   └── ...
└── <your-domain>/                 ← 你的领域
    └── ...
```

**硬约束**：

| # | 约束 | 理由 |
|---|---|---|
| 1 | 包目录下**不得出现 `.js` / `.mjs` / `.cjs` 文件** | 约束 1。加载时扫描，发现即 `PACK_CONTAINS_CODE` 拒绝 |
| 2 | 包**不得** `require` 任何模块 | 同上 |
| 3 | 包**不得**声明 URL / 网络地址 | 防止包偷偷外传数据（破红线 3 隐私边界） |
| 4 | 包内的模板**不得**包含变量插值以外的逻辑 | 防止模板引擎被当作代码执行 |
| 5 | 包的 `pack.json` **必须**声明 `schema_version` | 契约会演进，无版本号无法安全升级 |

## 四、`pack.json` 契约

### 4.1 完整字段

```jsonc
{
  "schema_version": "1.0",
  "pack_id": "douyin-intercept",          // 唯一标识，[a-z0-9-]+，全局唯一
  "pack_version": "1.0.0",                 // 语义化版本
  "display_name": "抖音截流自动回复",
  "domain": "local-life",                  // 领域分类，用于统计与筛选
  "author": "…",                           // 作者（举证用）
  "min_core_version": "3.0.0",             // 要求的最低核心版本

  // ── 线索判据 ──────────────────────────────
  "lead_criteria": {
    "intents": ["price_inquiry", "feature_inquiry", "purchase_intent"],  // ⚠️ 必须是闭集内的值
    "required_signals": [],                // 必须同时具备的信号（交集，不是并集）
    "exclude_signals": ["complaint", "irrelevant"],   // ⚠️ 只能增加，不能移除核心默认排除项
    "min_confidence": 0.7                  // 低于此置信度不入批（只能 ≥ 核心下限）
  },

  // ── 必须收集的信息（供 Agent 追问，不是硬性拦截） ──
  "required_fields": [
    { "key": "region",  "label": "城市",   "ask_if_missing": true },
    { "key": "budget",  "label": "预算",   "ask_if_missing": false }
  ],

  // ── 业务规则 ──────────────────────────────
  "rules": [
    {
      "rule_id": "r-holiday-delay",
      "when": { "signal": "complaint" },
      "then": { "action": "never_reply", "reason": "负面评论不自动回复" }
    }
  ],

  // ── 合规边界（本领域额外禁令） ──────────────
  "compliance": {
    "forbidden_phrases": ["保过", "包上岸", "百分之百"],
    "forbidden_topics": ["升学率", "提分承诺"],
    "disclaimer": "本回复由自动化系统发送"
  },

  // ── 话术池 ────────────────────────────────
  "scripts": {
    "dir": "scripts/",
    "selection": "semantic_match",         // semantic_match | round_robin
    "max_candidates_per_lead": 3           // 只能 ≤ 核心上限（5）
  },

  // ── 成功定义（⚠️ 见 §五，本字段只描述"业务成功"，不改计费） ──
  "outcome": {
    "goal": "collect_contact",             // 业务目标，用于汇报与统计
    "milestones": ["replied", "contact_collected", "appointment_booked"]
  },

  // ── 提示词 ────────────────────────────────
  "prompts": {
    "system": "prompts/system.md",
    "classify": "prompts/classify.md",
    "prompt_version": "p1.0.0"             // ⚠️ 必须显式声明，纳入审计（红线 3）
  },

  "glossary": "glossary.json"
}
```

### 4.2 字段合法性总表

| 字段 | 必填 | 核心的校验动作 | 违规码 |
|---|---|---|---|
| `schema_version` | ✅ | 必须等于核心支持的版本 | `PACK_SCHEMA_UNSUPPORTED` |
| `pack_id` | ✅ | `[a-z0-9-]+`、不与已加载包重复 | `PACK_ID_INVALID` / `PACK_ID_DUPLICATE` |
| `min_core_version` | ✅ | ≤ 当前核心版本 | `PACK_CORE_TOO_OLD` |
| `lead_criteria.intents` | ✅ | **每个值必须在 `intent` 闭集内** | `PACK_INTENT_UNKNOWN` |
| `lead_criteria.exclude_signals` | — | **必须是核心默认排除集的超集** | `PACK_EXCLUDE_NARROWED` |
| `lead_criteria.min_confidence` | — | ≥ 核心下限 | `PACK_CONFIDENCE_TOO_LOW` |
| `rules[].then.action` | ✅ | **必须在动作闭集内** | `PACK_ACTION_UNKNOWN` |
| `scripts.max_candidates_per_lead` | — | ≤ 核心上限 | `PACK_LIMIT_EXCEEDED` |
| `prompts.prompt_version` | ✅ | 非空（审计必需） | `PACK_PROMPT_VERSION_MISSING` |
| 任意键名 | — | 不在 §二 约束 2 的黑名单内 | `PACK_FORBIDDEN_KEY` |
| 目录内容 | — | 无 `.js`/`.mjs`/`.cjs` | `PACK_CONTAINS_CODE` |
| 任意字符串值 | — | 无 URL / 网络地址 | `PACK_EXTERNAL_REFERENCE` |

**动作闭集**（`rules[].then.action`）——**这是包能产生影响的全部方式**：

| 动作 | 含义 | 是否可能收窄为"不发送" |
|---|---|---|
| `never_reply` | 该线索永不自动回复 | ✅ 更保守 |
| `require_human` | 必须人工确认后才可发送 | ✅ 更保守 |
| `defer` | 延迟处理（如非工作时间） | ✅ 更保守 |
| `prefer_script` | 优先使用指定话术 | — 仅影响选择 |
| `ask_field` | 让 Agent 追问某字段 | — 仅影响话术 |

> ⚠️ **闭集里没有"发送"这个动作。** 发送永远由核心代码决定，包只能在"不发"方向上加约束。

## 五、核心如何加载与执行（三条运算规则）

```
① 服务端下发策略（tier_table 推导）           ← 权威，不可协商
   daily_max / min_interval / active_hours / sending_enabled …

② 工作流包声明（本领域约束）                  ← 单向收窄
   intents / exclude_signals / forbidden_phrases / rules …

③ 引擎装载：包清单解析成 Agent 任务序列       ← 编排
   ┌────────────────────────────────────────────────────┐
   │ LangGraph 状态图（节点固定，包只影响配置与分支）      │
   │                                                    │
   │  START → 采集 → 分类(包提示词) → 包规则过滤          │
   │                                    ↓               │
   │                            候选池（已过规则层）      │
   │                                    ↓               │
   │         Agent 审批（模型）→ choose script          │
   │                                    ↓               │
   │         🔴 硬闸门节点（代码 if，不可跳过）           │
   │            · sending_enabled? （观察期禁发）        │
   │            · 未超 daily_max?                       │
   │            · 满足 min_interval?                    │
   │            · 相似度未超阈值?                        │
   │            · 不命中 forbidden_phrases?             │
   │                                    ↓               │
   │         执行发送（既有 adapters，走完整护栏）        │
   │                                    ↓               │
   │         平台响应体判定 → 审计双写 → 计费            │
   │                                    ↓               │
   │         按包 outcome 汇报里程碑                     │
   └────────────────────────────────────────────────────┘

交集规则（三条，实现时逐条测试）：
   · 意图范围    = 核心默认集 ∩ 包声明 intents
   · 排除集      = 核心默认排除集 ∪ 包声明 exclude_signals     ← 并集！只会更严
   · 数值上限    = min(核心上限, 包声明值)                     ← 取小！只会更严
```

### ⚠️ 三条最容易写反的运算（失败方向都是"放行"）

| 运算 | 写反的后果 |
|---|---|
| 排除集用**交集** | 包声明 `exclude_signals: []` 就能把"投诉不回复"这条核心禁令**取消掉** |
| 数值上限用**并集/取大** | 包声明更大的批量上限即可放大发送量 |
| 意图范围用**并集** | 包能引入核心未授权的意图类型 |

> **这三条必须各有独立测试用例，且测试必须断言"更激进的值被拒绝"**，
> 而不是只断言"合法值被接受"。见 `plans/D-重构迁移与验收.md` 的验收项。

## 六、🔴 闸门必须断言（本 ADR §3.3 的强制落地）

**背景**：实测中，用 LangGraph 的累积型 reducer 表达"清空 decisions"时，
返回 `[]` 被 reduce 成"追加零个元素"，**观察期仍然放行了 1 条**。
失败方向是"放行"——这是最危险的方向。

**由此确立规范**：

> ### 每一个安全闸门节点，必须配一条"闸门关闭时下游收到 0 条"的测试。

| 闸门 | 测试要求 |
|---|---|
| 观察期禁发 | `sending_enabled=false` → 下游 `execute` 收到的条数 **=== 0** |
| 日上限 | 构造 `daily_max + 1` 条候选 → 下游收到 **=== daily_max** |
| 最小间隔 | 两条候选间隔 < `min_interval_ms` → 第二条**不出现**在下游 |
| 相似度 | 两条近似文案 → 后者**不出现在** `draft_options` |
| 包禁语 | 文案命中 `forbidden_phrases` → **不流入** 下游 |

**断言强度要求**：断言"下游为空/被截断"，**不得**只断言"闸门函数自己返回了什么"。
因为缺陷恰恰可能出在**闸门与下游之间的状态传递**上（本次实测即是此例）。

## 七、计费模型：一个必须现在处理的冲突

### 7.1 冲突是什么

| 需求 | 计费口径 | 现状 |
|---|---|---|
| 需求 2（自动回复） | **按成功回复条数**（`credit_per_reply_milli = 1000` = 1 积分/条） | ✅ 已实现 |
| 需求 5（自动剪辑） | 需求原文："也是消耗积分制" | ⚠️ `docs/需求规格.md` FR-5 标注"本期不做，只留接口"，并预留 `price_table.video_edit`（默认 0） |

**问题**：自动剪辑**没有"平台确认成功"这个信号**。
红线 2 的判据（`verdict=sent_confirmed` + `confirm_signal=platform_response` + `platform_status_code=0`）
是为"发送"设计的，**套不到"渲染出一个视频"上**。

如果直接复用，会发生两种坏结果之一：
- 剪辑失败也算计费（违背红线 2 的精神：不对失败计费）
- 剪辑无法计费（需求 5 落空）

### 7.2 结论：红线 2 的范围需要**明确界定**，而不是硬套

> **红线 2 的准确表述应为**：
> 「**可观测平台结果的动作**（如发送），只对平台确认成功计费；
> **不可观测平台结果的算力动作**（如视频渲染），按**实际消耗的算力**计费，
> 且必须能在事后用客观证据复现该次消耗。」

| 动作类别 | 计费依据 | 佐证 |
|---|---|---|
| `send`（发送类） | 平台响应体（`status_code=0`） | 已有：`publish-verifier` |
| `compute`（算力类，如剪辑） | **实测资源消耗**（token 数 / 渲染时长 / 输出字节） | 🆕 需新增：消耗证明（见 §7.3） |
| `llm`（推理类） | 上游 API 返回的 `usage` | 已有：`decision_log` 的 `usage` 字段 |

### 7.3 「消耗证明」——算力类计费的必要条件

算力类动作要计费，必须落盘一份**可复核的消耗记录**，否则又是"客户端说用了多少就多少"：

```jsonc
{
  "action_kind": "compute",
  "action_id": "cmp-…",              // 幂等键，动作开始前生成（与 send_id 同理）
  "kind": "video_edit",
  "started_at_ms": …,
  "finished_at_ms": …,
  "outcome": "succeeded",            // succeeded | failed | cancelled
  "evidence": {
    "output_bytes": 12345678,        // 产物大小
    "output_sha256": "…",            // 产物哈希（可复核"确实产出了东西"）
    "cpu_ms": 45210,                 // 实测占用的 CPU 时间
    "wall_ms": 187400                // 实测墙钟耗时（≈3 分钟，含排队与 I/O 等待）
  },
  "usage": { "llm_prompt_tokens": 0, "llm_completion_tokens": 0 },
  "billed_units": 3                  // 折算的计费单位数（由服务端核算，客户端只提议）
}
```

**四条约束**：
1. `action_id` **必须在动作开始前生成并落盘**（与 `send_id` 同理，红线 2 的幂等要求）
2. `outcome != "succeeded"` **一律不计费**（失败不收费的原则延伸到算力类）
3. `billed_units` 由**服务端**根据 `price_table` 核算，客户端只上报证据
4. `output_sha256` 是"确实产出了产物"的客观证据，防止"空跑也计费"

### 7.4 本期要做与不做的

| 项 | 本期 |
|---|---|
| `action_kind` 字段进入契约（`send` / `compute` / `llm`） | ✅ **做**（现在改契约，比以后改便宜） |
| 服务端计费按 `action_kind` 分派 | ✅ **做**（先只实现 `send`，另两类返回 `BILLING_KIND_NOT_ENABLED`） |
| `price_table` 迁移 | ✅ **做**（含 `send_reply` / `video_edit` / `llm_tokens` 三类单价，后两类默认 0） |
| 自动剪辑功能本身 | ❌ **不做**（维持 FR-5 的"只留接口"） |

> ⚠️ **本节的结论需要甲方确认**：需求 5 的计费口径（按次 / 按秒 / 按输出时长）
> 属商业定价决策，本文档只保证**契约能承载**，不代替定价。

## 八、验收标准

工作流包机制算"完成"，必须同时满足：

- [ ] `packs/_template/` 可被复制改名后**直接加载成功**（无需改核心任何文件）
- [ ] 加载一个含 `.js` 文件的包 → 报 `PACK_CONTAINS_CODE` 并**拒绝加载**
- [ ] 加载一个声明 `daily_max` 的包 → 报 `PACK_FORBIDDEN_KEY` 并**拒绝加载**
- [ ] 加载一个 `intents` 含闭集外值的包 → 报 `PACK_INTENT_UNKNOWN`
- [ ] 包声明 `exclude_signals: []` → 核心默认排除（`complaint`/`irrelevant`）**仍然生效**
- [ ] 包声明 `max_candidates_per_lead: 99` → 实际被截断到核心上限
- [ ] 包声明 `forbidden_phrases` → 命中该短语的文案**不流入**发送环节（§六 断言强度）

- [ ] 包的 `prompt_version` 出现在审计记录中（红线 3）
- [ ] 卸载包后，其话术池与规则**不再被任何路径引用**（无残留）
- [ ] §五 的三条"写反运算"各有独立测试，且断言"更激进的声明被拒绝"

## 九、给包作者的最短说明（模板 README 的正文）

> 你要做的不是写程序，是**把你们行业的业务知识写成声明**。
>
> 1. 复制 `packs/_template/`，改成你的领域名
> 2. 填 `pack.json`：哪些意图值得接、哪些必须排除、有什么不能说的话
> 3. 在 `scripts/` 里写话术（一个意图一个文件，多准备几条）
> 4. 在 `prompts/` 里告诉模型"我们这个行业的人怎么说话"
> 5. 改 `prompt_version`，然后加载试跑
>
> **你不需要、也不能**关心：一天能发多少条、间隔多久、怎么判断发送成功。
> **这些是平台的安全底线，不属于任何一个行业。**
