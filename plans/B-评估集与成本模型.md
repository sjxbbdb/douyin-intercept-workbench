# 方案 B · 评估集与成本模型

> 本文件回答方案 B 的两个"能不能上线"的问题：**效果能不能量化？成本能不能承受？**
> 配套：`plans/B-工具契约与粒度设计.md`（工具契约）· `plans/B-Agent开发指导.md`（主文档）
> 前置：方案 A 已跑通并已积累真实运行数据。

---

## 一、为什么需要评估集

### 1.1 模型输出不确定 → 传统单元测试测不了决策

方案 A 的行为是确定的：给定评论与规则，命中与否、取哪条话术、发还是不发，都能写出断言。
方案 B 引入了模型，同一个输入在两次调用里可能给出不同答案——**这不是 bug，是模型的性质**。

于是出现一个尴尬的处境：

```
传统单测能测的：  工具的参数校验、安全拦截、幂等、落盘、缓存 TTL、审计字段完整性
传统单测测不了的：这条评论该不该回？这个话术选得对不对？这个意图判对了没有？
```

### 1.2 ⚠️ 困境：回归测试只能测工具，测不了决策

`node test/run.js` 可以保证「`approve_batch` 会拒绝候选外的 `draft_id`」，
但它**永远无法告诉你**「Agent 把一条投诉判成了询价」。

后果是：**改一个字的提示词、换一次模型版本、调一次 temperature，都没有任何客观依据判断是变好还是变坏。**
只能靠"感觉好像好一点"，而上线的是真实账号——试错成本由商家的账号承担。

### 1.3 评估集的作用

**一句话**：把"模型决策质量"这个不可测的东西，变成一个**可重复、可对比、可回归的数字**。

| 用途 | 说明 |
|---|---|
| 改提示词前后对比 | 提示词从 p-1.0.0 升到 p-1.1.0，准确率是升还是降，有数字 |
| 换模型 / 换模型版本前后对比 | 换模型不再靠感觉，指标掉了就不换 |
| 换工具 schema 后回归 | 字段语义变了，评估集能立刻暴露质量下降 |
| 上线前的准入门槛 | 误批率不达标就不上线（§7 检查清单） |
| 上线后的持续监控 | 定期重跑，指标漂移即告警 |

> ⚠️ **没有评估集就不应该改提示词。** 这是本文件最重要的一条纪律。

## 二、评估集设计

### 2.1 数据来源：从真实评论中抽样

| 项 | 要求 |
|---|---|
| 来源 | 方案 A 运行期实际采集到的真实评论（**不是凭空编造**） |
| 为什么用真实的 | 编造的样本会遗漏真实语言习惯（错别字、方言、火星文、表情符号、"多少钱？？？"、"111"） |
| ⚠️ **脱敏是硬要求** | 见 §2.6。**不得含真实用户信息**——这是红线 3 的适用范围 |

**建议同时纳入一部分"困难样本"**（规则明确抓不住的）：

```
"这个能便宜点吗？我在南京，预算3000左右"  ← 询价+地域+预算，规则需配三个关键词
"贵不贵"                                  ← 询价，字面无"价"字关键词也常见
"有没有货"                                ← 购买意向，规则常漏
"上次买的坏了"                            ← 售后，容易被误当投诉
"骗子商家 大家别买"                        ← 投诉，必须高召回
"111" / "打卡" / "沙发" / 广告链接         ← 无关
```

### 2.2 规模建议

| 阶段 | 规模 | 说明 |
|---|---|---|
| 起步（评估集 V1） | **200 条** | 够跑出可信的整体准确率，也能覆盖各意图类别 |
| 稳定（评估集 V2+） | **300–500 条** | 每发现一类新的错误模式就补样本 |
| 上限 | 不建议超过 1000 条 | 人工标注成本上升，边际信息量下降；改为按类别分层抽样 |

> **规模怎么定**：若某类别只占 5%，200 条里只有 10 条——该类别指标噪声极大。
> 这也是 §2.5 的分布要求不按真实分布、而按**评测需要**设置的原因。

### 2.3 标注方式

**每条样本标注三样东西**（不标注"标准答案文案"）：

| 标注项 | 取值 | 说明 |
|---|---|---|
| **期望意图** | `intent` 闭集之一 | `price_inquiry` / `feature_inquiry` / `purchase_intent` / `support_inquiry` / `complaint` / `irrelevant` / `unknown` |
| **是否值得回复** | `worth_replying: true/false` | 这一条是否应该被 `approve` |
| **可接受的话术特征** | 字符串数组，如 `["直接报价","引导私信"]` | ⚠️ **不是精确文案** |

> ⚠️ **为什么话术只标"特征"不标"精确文案"**：
> 一条评论往往有多条话术都合适，标成唯一答案会把合理的选项判为错误，让指标失真。
> 标注"可接受特征"后，评审者按特征判断候选是否合格（§4.2）。

**可选的第四项**：`note`（标注人备注，例如"这条是边界情况，判 unknown 也可接受"）。
边界样本允许标注多个可接受意图，例如 `acceptable_intents: ["support_inquiry","complaint"]`。

### 2.4 目录与格式

```
test/eval/
├── dataset/
│   ├── v1.jsonl              评估集本体（一行一条，便于 diff 与追加）
│   ├── v1.labels.json        标注（与本体分离，防止误改数据）
│   └── README.md             构建说明：抽样时间、脱敏方法、标注人、复核人
├── run-eval.js               评估 runner（离线，不需要真账号/CDP）
├── prompts/                  被评估的提示词快照（与 client/agent/prompts/ 对应）
└── reports/
    ├── 2026-09-20_p-1.0.0_<model>.json    评估报告
    └── 2026-09-20_p-1.0.0_<model>.md      可读版报告
```

**`v1.jsonl` 单条结构**（⚠️ 已是脱敏后的内容）：

```json
{
  "sample_id": "ev-0001",
  "source_type": "comment",
  "excerpt": "这个能便宜点吗？我在南京，预算3000左右",
  "region_hint": "南京",
  "collected_at_ms": 1756800000000,
  "context": { "is_repeat_user": false, "recent_replied_count": 0 }
}
```

> `context` 字段用于还原 Agent 决策时会看到的最小上下文（是否已回复过该用户等），
> 但**不含**任何用户标识（无 `sec_uid`、无 `user_key_hash`、无昵称）。

**`v1.labels.json` 单条结构**：

```json
{
  "ev-0001": {
    "expected_intent": "price_inquiry",
    "acceptable_intents": ["price_inquiry"],
    "worth_replying": true,
    "acceptable_draft_traits": ["直接报价", "引导私信详聊", "说明价格区间"],
    "annotator": "A", "reviewer": "B", "reviewed_at_ms": 1756886400000, "note": ""
  }
}
```

### 2.5 类别分布要求

**建议分布**（合计 100%）与理由：

| `intent` | 建议占比 | 理由 |
|---|---|---|
| `price_inquiry` | **30%** | 最高频、商业价值最高，也是规则最容易漏的一类（"贵不贵"无"价"字） |
| `feature_inquiry` | **20%** | 次高频，且常与询价混在一起（"有什么功能，多少钱"），能测出多意图分辨能力 |
| `purchase_intent` | **10%** | 转化价值最高，但表达方式少、相对好判，占比不必高 |
| `support_inquiry` | **5%** | 频次低，但**误判为投诉或询价的代价不对称**（回复错话术会激化矛盾），需保留少量样本 |
| `complaint` | **10%** | ⚠️ **刻意超额采样**。真实占比可能只有 2-3%，但漏判会导致在投诉下自动回复（公关风险 + 账号风险），必须用足够样本量把召回率测准 |
| `irrelevant` | **15%** | 灌水与广告占比真实较高，且是"要不要回"的主要误批来源 |
| `unknown` | **10%** | 语义不明、信息严重不足的样本；用于验证"拿不准落 unknown / skip"的行为 |
| 合计 | **100%** | |

**为什么 `complaint` 要超额采样**：评估集的分布**服从评测需要，不服从真实分布**。
若按真实分布（3%）采样，200 条里只有 6 条投诉——召回率的分母太小，一次漏判就让指标跳 17 个百分点，
测出来的数字没有意义。**指标要准，样本就必须够。**

**每条样本还应带一个"是否值得回复"的标注**，其分布建议约为 `true:false = 6:4`，
用于评估 `approve_batch` 的误批率（§3.3）。`complaint` 与 `irrelevant` 全部标 `worth_replying: false`。

### 2.6 构建流程

```
① 抽样   从方案 A 生产数据抽取真实评论（按 intent × source_type 分层）
            ↓  导出时即做第一轮字段裁剪：只留 excerpt / region / 时间
② 脱敏   ⚠️ 关键步骤，逐条执行：
            · 删除 sec_uid / uid / 昵称 / 头像 URL / conversation_id / video_id / comment_id
            · 手机号、微信号、QQ 号、邮箱、车牌、身份证号 → 替换为 <PHONE> / <WECHAT> 等占位符
            · URL → <URL>；昵称式 @提及 → <AT>；地域只保留到"市"一级（与真实工具一致）
            · 人工抽检 10% 复核，确认无可反查用户的片段
③ 标注   由 1 人标注（intent + worth_replying + 可接受话术特征）
④ 复核   由另 1 人复核；不一致的样本讨论定稿，仍不一致则标 acceptable_intents（多值）或剔除
⑤ 冻结   写入 dataset/，记录构建说明（抽样时间、脱敏方法、标注人、复核人）
            ⚠️ 冻结后不修改；要改就建 v2
```

**四条纪律**：① **脱敏在标注之前做**，标注人不接触未脱敏原文（否则标注人会成为隐私暴露面）；
② 评估集不进公开分支（含真实评论语义），或只进受控私有仓库；③ 评估集与提示词分目录存放，避免误改；
④ **数据集冻结、报告不冻结**——每次评估生成带日期的报告，历史报告保留。

## 三、评估指标

### 3.1 `analyze_comments`（T-04）：意图分类

| 指标 | 定义 | 目标值 | 说明 |
|---|---|---|---|
| **整体准确率** | 判定意图 == `expected_intent` 的比例 | **≥ 85%** | 主指标 |
| **`complaint` 召回率** | 真实为投诉中被正确判为投诉的比例 | **≥ 95%** | ⚠️ 见下，最高优先级 |
| **`complaint` 精确率** | 判为投诉中真的是投诉的比例 | ≥ 60% | 允许误判为投诉（保守方向），不苛求 |
| **`irrelevant` 召回率** | 真实无关中被正确识别的比例 | ≥ 85% | 决定有多少灌水进入审批 |
| **`unknown` 使用率** | 判为 `unknown` 的比例 | 5%–15% | 过低说明模型在硬猜；过高说明提示词没说清 |
| **`extracted` 字段可用率** | `region`/`budget` 等抽取字段非空且正确的比例 | ≥ 80% | 辅助指标，不作为准入 |
| **缓存命中率**（工程指标） | 24h 内重复查询命中缓存的比例 | 监控项 | 直接决定成本，见 §5.3 |

**混淆矩阵关注点**（按风险排序）：

| 真实 \ 预测 | 最危险的错误 | 后果 | 处置 |
|---|---|---|---|
| `complaint` → `price_inquiry` | ⚠️⚠️ **最高危** | 在投诉下自动回复报价话术 → 公关事故 + 平台风控 | `complaint` 召回率 ≥95% 是**硬门槛**；同时预筛层由代码排除 `complaint`（双保险） |
| `complaint` → `feature_inquiry` | ⚠️ 高危 | 同上 | 同上 |
| `irrelevant` → `price_inquiry` | ⚠️ 中危 | 对灌水内容发报价 → 浪费额度、内容像 spam | 提高 `irrelevant` 召回 |
| `price_inquiry` → `complaint` | 低危（保守方向） | 少回一条，商家损失一次机会 | 可接受，不专项优化 |
| `price_inquiry` → `unknown` | 低危 | 该回没回 | 通过降低 `unknown` 使用率改善 |
| `purchase_intent` → `price_inquiry` | 低危 | 话术可能略偏，但仍在正确方向 | 不专项优化 |

> ⚠️ **不对称性是这个项目的核心**：少回一条的代价是"少赚一次"，回错一条的代价是"账号风险 + 公关事故"。
> 因此所有指标都允许"宁可保守"的偏差，**唯独 `complaint` 的召回不给折扣**。

### 3.2 `draft_replies`（T-05）：候选质量

| 指标 | 定义 | 目标值 |
|---|---|---|
| **候选可用率** | 输出的候选中至少有一条被人工评审判为"可用"的线索占比 | ≥ 90% |
| **人工评审通过率** | 被评审为"可用"的候选数 ÷ 候选总数 | ≥ 70% |
| **话术池命中率** | 由话术池（而非 LLM 生成）提供的候选占比 | **≥ 80%**（⚠️ 同时是成本指标，见 §5.3） |
| **相似度拦截率** | 生成候选中被 `similarity_checked=false` 拦掉的比例 | 监控项；>30% 说明提示词或话术池需要调整 |
| **生成候选进池率** | 经复核后进入长期话术池的生成候选占比 | 监控项（低是正常的，不必追求高） |

**评审"可用"的判定标准**（三条全满足才算可用）：

1. 语义与评论匹配（例如问价格就答价格，不答功能）；
2. 语气不冒犯、不像机器人（无"亲""宝贝"式过度营销腔）；
3. 不含承诺性表述（不承诺效果、不承诺不封号、不承诺绝对价格）。

### 3.3 `approve_batch`（T-07）决策质量：误批率与误拒率

| 指标 | 定义 | 目标值 | 风险等级 |
|---|---|---|---|
| **误批率** | 被 `approve` 且**实际发出**的条目中，标注为 `worth_replying=false` 的比例 | **≤ 5%（硬门槛 ≤8%）** | ⚠️⚠️ **最高** |
| **误拒率** | 标注为 `worth_replying=true` 的条目中被 `reject` 的比例 | ≤ 25% | 低 |
| **跳过率** | 被 `skip` 的条目占比 | 5%–20% | 中（过高等于 Agent 没在工作） |
| **非候选外提交率** | `approve` 中 `draft_id` 不在候选内的比例 | **必须为 0** | 工程正确性，不是质量指标 |

> ### ⚠️ 误批率为什么是最高优先级，以及"可接受的误批率上限"
>
> **误批会真实发出。** 误拒只是"少发一条"——商家少一次触达机会，可以人工补。
> 误批是"发错一条"——它消耗真实额度、写入真实审计、可能触发平台风控、可能引发公关事故，
> **且无法撤回**（评论已发出）。两者的代价完全不对称。
>
> **可接受上限**：
> - **≤ 5%** 为常规准入线；
> - **5%–8%** 为可上线的边界（需同时满足：`complaint` 召回 ≥95%、有每日人工抽检、误批即停用 Agent 并回退方案 A）；
> - **> 8% 不得上线**，必须回到提示词与工具设计上整改。
> - 误批率**超过 8% 且经两轮整改仍不下降**时，应重新评估方案 B 是否适合本项目（见 `plans/B-与方案A的差异说明.md` §7）。

**误批率的正确计量口径**（⚠️ 容易算错）：

```
分母 = 被 approve 且进入 queued_send_ids 的条数（不是"被 approve 的条数"）
分子 = 其中 annotations.worth_replying === false 的条数

为什么分母不含被安全校验拦下的？因为那些没有真实发出，不构成风险。
为什么分母不含 reject/skip？因为它们没有产生发送。
```

### 3.4 端到端：商家满意度代理指标

无法直接测"商家满意"，用可观测的代理指标：

| 代理指标 | 定义 | 目标值 | 含义 |
|---|---|---|---|
| **审批通过率** | `approve` 数 ÷ 批次数（**口径见下方警告**） | 40%–70% | 过低说明预筛质量差或 Agent 过保守；过高要警惕误批 |
| **商家推翻率** | 商家人工把 Agent 的 `approve` 改成不发（或反之）的比例 | **≤ 10%** | 最接近"满意度"的指标，需 UI 支持一键推翻 |
| **降级触发频次** | Agent 不可用/超预算次数 | 每千条 ≤ 1 次 | 可用性指标 |
| **单次交互完成率** | 未因轮次/超时/预算中断的交互占比 | ≥ 90% | 见主文档 §4.2 |
| **重复交互率** | 同一任务商家需要第二次下指令的比例 | ≤ 15% | 反映 Agent 一次说清的能力 |

> ⚠️ **"审批通过率"必须写清口径，否则会得出相反结论。**
> 本项目建议统一为：**审批通过率 = `approve` 条数 ÷ 被审批（approve+reject+skip）条数**，
> 即"Agent 对送来的候选放行了多少"。
> 另一种常见口径是"成功发送数 ÷ 批准数"，它衡量的是**安全护栏的拦截强度**（越低说明被拦越多），
> 两者含义完全不同。看板上必须标注口径，且**不得混用**（`docs/需求规格.md` FR-4.3 要求口径一致）。

## 四、评估方法

### 4.1 离线评估流程

```
node test/eval/run-eval.js --dataset v1 --prompt p-1.0.0 --model <provider/model>
   │
   ├─ ① 加载 v1.jsonl（脱敏样本），逐条构造与线上一致的最小上下文
   ├─ ② 调用 analyze_comments 的同款逻辑（复用同一提示词与 schema，不另写一套）
   ├─ ③ 对 worth_replying=true 的样本，跑 draft_replies 生成候选
   ├─ ④ 用同一模型模拟 approve_batch 决策（⚠️ 只做决策，不真实发送）
   ├─ ⑤ 比对标注，计算 §3 的全部指标
   └─ ⑥ 输出 reports/<date>_<prompt>_<model>.{json,md}
```

**五条实现要求**：① **评估必须复用生产提示词与工具 schema**，不得另写"评估版提示词"（否则测的不是线上的东西）；
② **评估不发送任何内容**——`approve_batch` 在评估模式下只返回决策结果、不入队（避免污染真实数据）；
③ 评估**离线、可重复**：不依赖 CDP、不依赖真账号；④ 记录 `model.version` 与 `prompt_version`，
报告文件名即含这两项（否则报告无法比较）；⑤ 报告保留历史、不覆盖，否则无法回答"三个月前那次调整是不是真的变好了"。

**报告必备内容**：整体准确率 + 混淆矩阵 + 各类别精确率/召回率 + 误批率/误拒率 + token 消耗与摊薄成本 +
与上一版报告的**逐项差值**（差值比绝对值更重要）。

### 4.2 人工评审流程与评分标准

自动化指标无法覆盖的两件事：**话术是否得体**、**决策是否合理**。因此每次评估必须配一轮人工评审。

| 项 | 做法 |
|---|---|
| 抽样 | 从评估结果中随机抽 **50 条**（不足 50 则全评）；**必含全部误批样本** |
| 评审人 | 1 名产品/运营 + 1 名熟悉商家业务的人；两人独立评，不一致处讨论 |
| 盲评 | 评审时**不告知**该条来自哪个提示词版本，避免先入为主 |
| 评分维度 | ① 意图判对了吗 ② 该不该回 ③ 选的话术是否得体 ④ 有没有更好的候选存在 |
| 记录 | 每条给出 `pass / fail` + 一句话理由（理由要具体，例如"报价话术但评论在问发货"） |
| 输出 | 人工通过率 + 全部 `fail` 样本清单（这张清单是改提示词的**第一手输入**） |

> ⚠️ **人工评审的重点是"错在哪"，不是"得几分"。** 那张 `fail` 清单直接决定下一版提示词怎么改。### 4.3 基线对比：证明 LLM 有增益

**必须做基线对比，否则无法回答"为什么不用方案 A 的关键词规则"。**

| 对比项 | 方案 A 基线 | 方案 B |
|---|---|---|
| 意图判定 | 关键词整词包含匹配 | LLM 语义理解 |
| 话术选择 | 模板随机轮换 | 从候选池按语义选 |
| 该不该回 | 黑白名单 + 规则排除 | Agent 语义判断 |

**基线实现要点**：① 用**方案 A 实际使用的规则配置**（关键词表 + 黑白名单）跑同一份评估集；
② 同一套标注、同一套指标口径（**口径不同则对比无意义**）；③ 报告必须给出**可量化的增益**，例如：

```
意图分类召回率：规则 62%  →  LLM 88%   （+26pt）
询价类召回：    规则 55%  →  LLM 91%   （+36pt，即"贵不贵"这类无关键词的表述）
投诉类召回：    规则 95%  →  LLM 96%   （+1pt，说明规则在投诉上已够用——这是有用的结论）
误批率：        规则 12%  →  LLM 4%    （-8pt）
```

> **若增益不足**（例如询价召回只提升 5pt），说明规则已够用，**不应上方案 B**——
> 这是评估集最重要的一次决策输出，且它是**在花钱之前**得到的结论。

### 4.4 何时必须重跑评估

| 触发条件 | 必须重跑 | 额外要求 |
|---|---|---|
| 提示词版本变更（`prompt_version` 主/次版本） | ✅ | 主版本变更还需人工复核 + 更新本文档记录 |
| 提示词修订版本（措辞微调） | ✅（可只跑自动化） | 自动化指标下降则视为次版本变更处理 |
| 换模型 / 换模型版本 | ✅ | ⚠️ 换模型**必须**重跑，且必须更新报告中的 `model.version` |
| 改工具 schema（字段增删改） | ✅ | 重点看参数校验与决策质量是否退化 |
| 改话术池结构或相似度阈值 | ✅ | 重点看候选可用率与命中率 |
| 换 `temperature` | ✅ | 决策类任务改动 temperature 影响显著 |
| 平台改版导致线索质量变化 | 建议 | 评估集本身可能需要重建（建 v2） |
| 每季度定期 | ✅ | 防漂移；模型服务端也可能静默更新 |

> ⚠️ **`temperature` 是评估的一部分，不是无关紧要的旋钮。** 建议固定为 **0.2**，
> 并在报告中记录该值——否则两次报告不可比。

## 五、成本模型

### 5.1 成本项拆解

| 成本项 | 说明 | 是否会随对话轮数增长 |
|---|---|---|
| ① **系统提示词 + 工具定义** | **每轮推理都要重新传一遍**的固定成本 | ❌ 每次调用固定，但**每轮都重复支付** |
| ② **上下文** | 状态摘要 + 线索摘要 + 历史工具返回 | ✅ 随轮数累积增长 |
| ③ **推理输出** | 模型的决策输出（JSON 或汇报文本） | ✅ 略增 |
| ④ **工具调用往返** | 每次工具调用的返回内容也进上下文 | ✅ 显著增长（批次的 `draft_options` 很长） |

**关键认识**：③ 是显性成本，① 才是主要成本。
系统提示词 + 工具 schema 通常有数千 token，**它被重复支付的次数等于推理轮数**——
这正是批处理能省 5-10 倍的根本原因（§5.3）。

**计价变量**（⚠️ **不写具体厂商价格，按实际报价填入**）：

| 变量 | 含义 | 填入方式 |
|---|---|---|
| `P_IN` | 输入 token 单价（元 / 千 token） | 按所选厂商**当前报价**填写 |
| `P_OUT` | 输出 token 单价（元 / 千 token） | 同上 |
| `R_CACHE` | 上下文缓存命中的输入折扣系数 | 若厂商支持 prompt caching，取实际折扣（常见 0.1–0.5）；不支持则填 1 |
| `P_FIXED_TOKENS` | 系统提示词 + 工具定义 token 数 | **实测**（用实际提示词与 schema 计数） |
| `N_ROUNDS` | 单次交互的工具调用轮数 | 实测（主文档 §4.2 上限 12，典型 3–5） |
| `N_BATCH` | 一批处理的线索条数 | `review_batch` 的 `max_items`，典型 10–20 |
| `CTX_TOKENS` | 每轮上下文（状态摘要 + 线索 + 工具返回） | 实测 |

> ⚠️ **模型价格会变动，且各家计价方式不同（是否区分缓存读写、是否有阶梯价、是否按批次计价）。
> 本文件的测算必须在使用时按最新报价重新代入，不要沿用任何历史数字。**
> 建议在 `test/eval/pricing.json` 里维护一份带 `updated_at` 的价格变量表，
> 每次出成本报告时核对一次；超过 90 天未更新则在报告中标注"价格可能过期"。

### 5.2 单次交互 token 测算

**三档估算**（假设：`P_FIXED_TOKENS ≈ 3000`；每轮上下文增长 ≈ 1500；输出 ≈ 300）：

| 档位 | 假设 | 推理轮数 | 单次交互输入 token | 单次交互输出 token |
|---|---|---|---|---|
| **乐观** | 话术池高命中、批次 20 条、轮数 3、缓存全命中 | 3 | `3000 + 3×1500 ≈ 7500`（缓存命中后按 `R_CACHE` 折算） | `3×300 ≈ 900` |
| **典型** | 批次 10 条、轮数 4、部分缓存命中 | 4 | `3000 + 4×1500 ≈ 9000` | `4×300 ≈ 1200` |
| **保守** | 批次 10 条、轮数 6、无缓存、含 `draft_replies` 生成 | 6 | `3000 + 6×1500 ≈ 12000`（另加生成候选的调用） | `6×300 ≈ 1800` + 生成候选输出 |

**单次交互成本**：

```
cost_interaction = (P_IN  × in_tokens  × R_CACHE_effective
                  + P_OUT × out_tokens) / 1000
```

> 说明：`R_CACHE_effective` 是"被缓存覆盖的输入占比 × `R_CACHE` + 未被覆盖的占比"。
> 若厂商不支持缓存，取 1。**不要把缓存折扣当作必然**，保守测算时按 1 计。

### 5.3 ⚠️ 每条回复的摊薄成本：逐条推理 vs 批处理

| 设计方式 | 推理次数 | 每条回复的 token 成本 | 相对成本 |
|---|---|---|---|
| ❌ **逐条推理**（每条单独决策） | 1 次/条 + 多轮工具调用（约 3–4 轮/条） | `cost_interaction(N=1) / 1` | **基准 × 1** |
| ✅ **批处理 20 条** | 1 次决策覆盖 20 条，约 4 轮 | `cost_interaction(N=20) / 20` | **基准 × 1/10 ~ 1/5** |

**为什么差 5–10 倍**（逐步说明）：

```
逐条推理（20 条）：
  每条都要传一次  系统提示词(3000) + 工具定义 + 上下文 + 工具往返
  ≈ 20 × (3~4 轮 × 约 3000~4500 token)  ← 固定成本被支付了 20 次

批处理（20 条）：
  系统提示词与工具定义只传 1 次（后续轮次仍会带，但被同一批 20 条共享）
  ≈ 4 轮 × 约 3000 + 20 条的线索摘要（一次性）
  固定成本被支付了 4 次，且分摊到 20 条上
```

**摊薄成本公式**：

```
cost_per_reply = cost_interaction(N = N_BATCH) / N_BATCH

其中 cost_interaction 的输入 token 里：
  · 固定部分（系统提示词 + 工具定义）        ≈ P_FIXED_TOKENS × N_ROUNDS
  · 可变部分（线索摘要 + 工具返回，随 N 增长）≈ k × N_BATCH + CTX_BASE × N_ROUNDS
```

**三个立竿见影的降本手段**（按收益排序）：

| 手段 | 效果 | 实现位置 |
|---|---|---|
| ① 批处理（`max_items` 用满） | **5–10 倍** | 主文档 §8.1 + 提示词"优先批量" |
| ② 提高话术池命中率（目标 ≥80%） | 命中即不调 LLM，**近似线性** | 主文档 §8.3 |
| ③ 上下文缓存 + `analyze_comments` 24h 缓存 | 输入成本降低（取决于 `R_CACHE`） | 主文档 §8.2 |

> ### ⚠️ 结论
> **成本能否接受，取决于是否做了批处理设计。**
> 按逐条推理实现，成本高出 5–10 倍**且没有任何必要**——批处理的决策质量不会更差
> （同一批线索在一次推理里对比，反而更一致）。
> 若在测算中发现"成本不可接受"，**第一件事是检查是否真的走的是批处理**，
> 而不是先去谈涨价。

### 5.4 与定价的关系

本项目按**成功回复条数**计费（`credit_per_reply`，见 `shared/protocol.md` §6.1）。因此：

```
token 成本占比 = cost_per_reply(元) / 单条成功回复的收入(元)
```

**建议阈值**：

| 占比 | 判定 | 处置 |
|---|---|---|
| **< 15%** | ✅ 健康 | 正常推进 |
| 15% – 30% | 🟡 可接受但需优化 | 优先做 §5.3 的三个降本手段；暂不上新功能 |
| 30% – 50% | 🟠 危险 | 必须优化后再扩大使用范围；考虑限制 Agent 适用范围（如只对询价类启用） |
| **> 50%** | ❌ 不可持续 | **停止推广**；要么调整定价，要么限制功能（关闭 `draft_replies`、只保留意图分析），要么放弃方案 B |

**四个必须写进测算表的假设**（否则数字没有意义）：

1. 单条成功回复的对商收入（由定价决定，**需按商务实际配置填入**）；
2. 话术池命中率（影响是否调用 LLM 生成）；
3. 批次大小 `N_BATCH`；
4. 是否启用上下文缓存及其折扣。

> ⚠️ **不要用"平均单价"估算，要用"成功回复单价"。**
> 因为只有 `verdict=sent_confirmed` 才计费（红线 2），
> 被风控拒绝、超上限、跳过的发送**收不到钱**，但它们的 token 成本已经花掉了。
> 因此实际占比 = `cost_per_reply / (单价 × 计费成功率)`——**计费成功率低于 100% 会放大成本占比**。

### 5.5 成本监控

**上线后必须监控的指标**：

| 指标 | 粒度 | 告警阈值（建议） |
|---|---|---|
| 每条成功回复的摊薄成本 | 日 | 连续 3 日 > 预算的 1.5 倍 |
| 每日 token 总消耗 | 日 | > 日预算 |
| 单次交互 token P95 | 小时 | > `max_tokens_per_interaction` 的 80% |
| 工具调用轮数 P95 | 小时 | > 8 轮（说明模型在兜圈子） |
| 话术池命中率 | 日 | < 70% |
| `analyze_comments` 缓存命中率 | 日 | < 50% |
| 模型服务错误率（超时/5xx） | 小时 | > 5% → 触发 L1 降级 |
| **误批率**（人工抽检） | 周 | **> 8% → 立即停用 Agent 并回退方案 A** |

**监控数据来源**：

- token 与轮数：`decision_log.jsonl` 的 `usage` / `latency_ms` + `tool_audit.json` 计数
- 话术池命中率：`draft_replies` 的候选 `source` 分布（`template` vs `generated`）
- 误批率：需要**人工抽检**（每周从已发送中随机抽 20–30 条复核），无法纯自动得到

> ⚠️ **"误批率"必须靠人工抽检**，因为真实世界没有标注。这是上线后唯一的风险发现手段，不能因为"麻烦"而省掉。
> 建议固定为每周一次，抽检清单直接复用 §4.2 的评审标准。另：上述指标中的"模型服务错误率""成本超预算"
> 属于**运营监控**，不改变既有计费口径；`agent_*` 计数上报需服务端先支持字段（见主文档 §12.3 冲突项 C-6）。

## 六、降级与熔断

### 6.1 成本超预算时的降级策略

**逐级降级，不一次性关闭**（对应主文档 §4.6 的 L1/L2/L3）：

| 级别 | 触发 | 动作 | 影响 |
|---|---|---|---|
| **L0 正常** | — | 全部工具可用 | — |
| **L1 限流** | 单次交互 > 预算 80% | 注入"请尽快收敛"提示；不改变可用工具 | 汇报可能略简 |
| **L2 关闭生成** | 当日累计 ≥ 日预算 | 关闭 T-05 `draft_replies`；候选只来自话术池 | 覆盖率下降，成本显著下降 |
| **L3 关闭分析** | 连续 3 日超预算 | 再关闭 T-04 `analyze_comments`（改用方案 A 的规则意图判定） | 回到纯规则候选 |
| **L4 回退方案 A** | 误批率 >8% 或成本持续不可控 | **完全停用 Agent**，人工在图形界面按方案 A 流程操作 | 功能不缺失，只是没有语义理解 |

> ⚠️ **L4 是产品能力的一部分，不是失败。** 保留完整图形界面正是为了让这一步永远可行
> （这也是主文档 §1.3 中"`client/ui/` 保留"的原因）。
> 降级必须**在 UI 上可见**：明确显示当前级别、原因、恢复条件，不许静默降级。

### 6.2 模型服务不可用时的行为

| 故障 | 检测方式 | 行为 |
|---|---|---|
| 请求超时 | 请求级超时（建议 30 秒） | 退避重试 1 次（2 秒）；仍失败 → 本次交互以 L1 降级结束，**不执行未审批的发送** |
| 鉴权失败 / 配额耗尽 | HTTP 401 / 429 | **不重试**（重试无意义），立即进入 L2 并提示用户"模型服务不可用，已切回人工审批" |
| 服务端 5xx | HTTP 5xx | 退避重试（1s/2s/4s，上限 60s）；连续 3 次失败 → L2 |
| 返回格式不符（无 `tool_call` 且文本不可解析） | 解析失败 | 重试 1 次；仍失败则**终止本次交互并汇报**，不猜测模型意图 |
| 网络中断 | 连接错误 | 按既有离线降级逻辑（`shared/protocol.md` §9.3 同思路）：Agent 停用，采集与人工审批继续 |

**三条不可动摇的底线**：

1. **模型不可用时绝不"猜"着执行**——宁可停在人工审批，也不要让模型不可靠的输出流向发送队列。
2. **模型不可用不影响发送护栏**——`approve_batch` 的二次校验、频控、相似度、熔断全部由本地代码执行，与模型无关。
3. **模型不可用不影响计费与审计**——凡是真实发生的发送，明细照常上报与计费（红线 2 不因 Agent 故障而改变）。

### 6.3 质量下降的自动告警

| 告警 | 数据来源 | 阈值 | 处置 |
|---|---|---|---|
| **误批率上升** | 每周人工抽检 | > 5% 预警；> 8% 停用 | 停用 Agent → 回退方案 A → 分析 `fail` 清单 → 修正提示词 → 重跑评估集 |
| 意图分类质量漂移 | 抽样重跑评估集（月度） | 整体准确率下降 > 5pt | 检查模型版本是否变化（对比 `model.version` 记录） |
| `unknown` 使用率异常 | `analyze_comments` 结果分布 | > 25% | 提示词或模型退化；也可能是真实线索质量下降 |
| `skip` 率异常 | `decision_log.jsonl` | > 40% | Agent 变得过度保守，等于没在工作；检查提示词第 5 条 |
| 工具被拦次数激增 | `tool_audit.json` 的阻断码计数 | 较基线翻倍 | 模型在尝试越权或参数总传错；检查提示词与 schema 描述 |
| 轮数 P95 上升 | `decision_log.jsonl` | > 8 轮持续 3 天 | 模型在兜圈子，成本将上升；检查提示词收敛性 |

> ⚠️ **模型服务端可能静默更新模型**。因此"用户侧无任何改动但质量下降"是**真实可能发生的场景**，
> 月度重跑评估集是发现它的唯一手段。发现后应记录 `model.version` 的变化作为证据。
