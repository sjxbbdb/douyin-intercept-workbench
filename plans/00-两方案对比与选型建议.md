# 两方案对比与选型建议

> 本文件帮助决策者选择实施方案。**结论：先做方案 A，验证底座后再决定是否叠加方案 B。**

---

## 一、两方案是什么

两套方案共用**同一个底座**，区别只在"能力如何被编排"。

```
                 ┌──────────────────────────────────────────┐
                 │  共用底座（两方案都必须实现，工作量相同）    │
                 │                                          │
                 │  授权中心：账号/积分/套餐/卡密/看板         │
                 │  接口契约：shared/protocol.md             │
                 │  安全策略：tier_table 服务端下发           │
                 │  审计留痕：配置变更 + 发送明细              │
                 │  计费：按成功条数，send_id 幂等            │
                 │  CDP 驱动：core + platform + adapters     │
                 └──────────────────┬───────────────────────┘
                                    │
                    ┌───────────────┴───────────────┐
                    ▼                               ▼
        ┌───────────────────────┐       ┌───────────────────────┐
        │  方案 A：完整工具链路    │       │  方案 B：专用 Agent    │
        │                       │       │                       │
        │  图形界面             │       │  对话界面             │
        │  固定流水线           │       │  Agent 编排工具        │
        │  关键词规则匹配        │       │  LLM 语义理解          │
        │  话术模板随机轮换      │       │  LLM 从候选池选择       │
        │  零 LLM 成本          │       │  可变 token 成本        │
        └───────────────────────┘       └───────────────────────┘
```

**关键认识**：方案 B ≈ 方案 A + Agent 层。**B 不能跳过 A 的底座。**

## 二、能力对比

| 维度 | 方案 A：完整工具链路 | 方案 B：专用 Agent |
|---|---|---|
| **交互方式** | 图形界面（填表单、点按钮、看表格） | 自然语言下指令，Agent 编排 |
| **意图理解** | 关键词匹配（命中任意一个字即触发） | LLM 语义理解 |
| **典型能力差距** | "贵不贵"与"多少钱"字面不同 → **抓不住** | 两者识别为同一意图「询价」 |
| **线索结构化** | 原文整条保存 | 可抽取地域/预算/时间等字段 |
| **多轮对话** | 不支持（发一条固定话术即结束） | 可来回协商 |
| **异常处理** | 预定义分支（失败即熔断/跳过） | 可尝试替代路径 |
| **话术来源** | 模板库随机轮换 | LLM 从**候选池**中选择（不得自由生成，见下） |
| **可预测性** | 高（确定性） | 中（模型输出有随机性） |
| **可测试性** | 高（可写单元测试） | 中（需评估集打分） |
| **单位成本** | 固定（服务器带宽） | 每条约 1 次推理调用，可摊薄 |
| **开发工作量** | 基准 | 基准 × 1.3 ~ 1.5 |
| **上线后的调试难度** | 低（行为可复现） | 中（需区分"工具坏了"还是"模型选错了"） |

### 一个具体的对比场景

假设某条评论是：**"这个能便宜点吗？我在南京，预算3000左右"**

| | 方案 A | 方案 B |
|---|---|---|
| 是否命中 | 只有当商家把"便宜""南京""3000"都配成关键词才命中 | 理解意图为「询价 + 地域 + 预算」 |
| 线索记录 | 整条原文存入 | `{intent:询价, region:南京, budget:3000}` |
| 回复 | 模板轮换取一条 | 从候选池选最匹配"议价"场景的一条 |
| 后续跟进 | 人工翻记录 | 可按意图+地域筛选 |

## 三、成本对比

### 方案 A

| 项 | 成本 |
|---|---|
| 推理 | **0** |
| 服务器 | 授权中心（低配 VPS 即可，见部署指南） |
| 客户端 | 商家本机资源 |

### 方案 B

token 成本取决于**工具粒度**（这是方案 B 成败的关键，详见 `plans/B-评估集与成本模型.md`）：

| 设计方式 | 每条回复的推理次数 | 相对成本 |
|---|---|---|
| ❌ 逐条推理（agent 每条单独决策） | 1 次/条 + 多轮工具调用 | **基准 × 1** |
| ✅ 批处理（一次决策处理一批） | 1 次 / 20 条 | **基准 × 1/10 ~ 1/5** |

**结论：方案 B 的成本能否接受，取决于是否做了批处理设计。** 若按逐条推理实现，成本会高出 5-10 倍且无必要。

## 四、风险对比

| 风险 | 方案 A | 方案 B |
|---|---|---|
| **抖音改版导致定位失效** | 中（选择器集中，改一处即可） | 同 A（共用底座） |
| **账号封禁** | 中（靠安全护栏） | 中（同 A，**Agent 不得绕过硬规则**） |
| **模型产出内容被判定为营销** | 低（模板可控） | **中**（LLM 生成内容字面不同但语义可能雷同，可能绕过"相似度"检测） |
| **决策不可复现导致无法举证** | 低（行为确定） | **中**（必须落盘决策记录，见下） |
| **成本失控** | 无 | 中（token 波动） |
| **调试困难** | 低 | 中 |

### ⚠️ 方案 B 的两个特有风险（必须在设计中解决）

**风险 1：LLM 生成内容可能绕过内容级风控检测**

现有安全机制要求"与近期已发内容相似度超过 85% 即拒绝发送"，这是为了避免内容级 spam。但 LLM 可以生成**字面完全不同、语义相同**的话术——相似度检测挡得住字面，**挡不住语义**。而平台判定 spam 看的是模式。

**对策（已写入方案 B 设计）**：Agent **不得自由生成话术**，只能**从候选池中选择**。候选池由商家提供并经相似度检测。这样既保留语义匹配能力，又使内容可控、可审计。

**风险 2：决策不可复现，影响举证能力**

红线 3 要求审计能回答"当时为什么发了这句"。若决策来自模型，必须落盘：输入摘要、候选列表、选中项、模型版本号、策略版本号、决策耗时与成本。否则模型更新后无法复现历史决策。

**对策（已写入方案 B 设计）**：每次决策写结构化记录，纳入现有审计体系（复用红线 3 的机制）。

## 五、选型建议

### ✅ 推荐路线：先 A，后评估 B

```
阶段 1：实施完整方案 A（P0~P6）
        ↓
        ├─ 验证底座：裸 CDP 能否稳定驱动抖音（P2 验证门 G-1~G-5）
        ├─ 积累数据：真实意图分布是怎样的？哪些意图规则抓不住？
        └─ 确认成本承受力：每条回复的定价空间有多大？
        ↓
阶段 2：用数据决定是否叠加 B
        ↓
        ├─ 若"规则抓不住的意图"占比低 → 继续用 A，不值得上 LLM
        ├─ 若占比高 且 定价空间足够 → 实施方案 B
        └─ 若不确定 → 先只对"话术选择"这一小步用 LLM（成本可控、风险最低）
```

### 四条支持"先做 A"的理由

1. **B 的底座就是 A**。A 的工作量不是"额外成本"，而是 B 的必要前提。反过来做行不通。
2. **A 能在无 LLM 依赖下回答最关键的问题**：裸 CDP 驱动抖音这条路到底走不走得通？如果走不通（G-1 登录态不可用、G-3 风控拦截严重），方案 B 也救不了——因为 B 用的是同一套 CDP 驱动。
3. **只有先跑起来 A，才知道 B 该做什么**。空想"哪些意图规则抓不住"没有意义；跑一个月后导出的真实评论数据才能告诉你答案。
4. **A 可以独立商业化**。A 完成即可交付渠道商（见 `docs/合作方须知.html`），B 是增值升级项，不是必需项。

### 什么情况下可以直接做 B

- 已有明确数据表明关键词规则召回率低到不可接受
- 定价空间足以覆盖 token 成本（且已按批处理设计）
- 团队有 LLM 应用经验，能承担评估集与成本监控的额外工作

**即便如此，仍建议先完成 A 的 P0~P2 与真机验证门。**

## 六、如果两条路都要，工作如何组织

两方案的**文档与代码是分层复用的**：

| 资产 | A | B | 说明 |
|---|---|---|---|
| `shared/protocol.md` 契约 | ✅ 必需 | ✅ 复用 | B 的 Agent 调用工具走同一套权限与审计 |
| `client/core/` CDP 层 | ✅ | ✅ 复用 | 不变 |
| `client/platform/` 选择器与页面模型 | ✅ | ✅ 复用 | 不变 |
| `client/adapters/` 适配器 | ✅ | ✅ 复用 | **B 把 adapters 包装成工具** |
| `client/safety/` 护栏 | ✅ | ✅ 复用 | **B 不得绕过，且要额外拦 Agent 的越权意图** |
| `client/license/` 授权通信 | ✅ | ✅ 复用 | 不变 |
| `client/ui/` 图形界面 | ✅ | 部分复用 | B 增加对话界面 |
| Agent 层（工具封装、提示词、评估集） | — | 🆕 新增 | 仅 B 有 |

**共享程度约为 80%。** 这意味着：先做 A 不会浪费工作；从 A 转到 B 是**增量**，不是重做。

## 七、决策清单

请决策者确认以下问题后再开工：

| # | 问题 | 影响 |
|---|---|---|
| 1 | 是否接受"先 A 后评估 B"的路线？ | 决定是否立即投入 Agent 层开发 |
| 2 | 若直接做 B：是否接受"话术只能从候选池选，不得自由生成"？ | 关系到内容风控与举证能力，**不建议放弃** |
| 3 | 若做 B：是否接受批处理式工具设计（成本差 5-10 倍）？ | 决定 token 成本量级 |
| 4 | 是否有可用的抖音测试账号（**建议专门小号**）？ | 无此则 P2 验证门无法通过，方案 A 无法完成 |
| 5 | 目标部署环境是否确认为现有 VPS（与 sing-box 共存）？ | 决定服务端部署方案 |
