> 回答一个问题：**现有 34,000 行代码，在"专用 Agent"定位下，哪些留、哪些改、哪些新写。**
>
> 原则：**这是重新定位，不是重新开发。** 现有代码的主体是资产，不是沉没成本。
>
> 配套：`docs/项目章程.md`（定位锚点）· `plans/ADR-001-Agent优先与框架选型.md`（为什么改）·
> `plans/B-Agent开发指导.md`（Agent 层主文档）· `plans/B-工具契约与粒度设计.md`（工具粒度）

## 一、先回答"要不要推倒重来"

### 1.1 不推倒。理由是可测量的

| 模块 | 行数 | 在新定位下的角色 | 处置 |
|---|---|---|---|
| `client/core/`（CDP、浏览器宿主、IPC） | 3,827 | 与"是不是 Agent"**完全无关**的底层能力 | ✅ **一行不改** |
| `client/platform/`（选择器、页面模型、成功判定） | 2,104 | 抖音平台知识，与架构无关 | ✅ **一行不改** |
| `client/safety/`（护栏、相似度、熔断、审计） | 2,994 | **新定位下更重要**（要拦 Agent 越权） | 🔧 新增一层拦截 |
| `client/license/`（心跳、上报、验签、停机） | 2,715 | 与服务端通信，与架构无关 | ✅ **一行不改** |
| `client/adapters/`（采集、回复、私信） | 2,289 | 被工具层包装；同时是**降级路径** | 🔧 新增 4 个只读/入队出口 |
| `client/host/`（存储、队列、调度、本地 API） | 4,799 | 状态落盘与节奏控制，与架构无关 | 🔧 新增 Agent 路由 |
| `client/ui/`（商家面板） | 1,842 | **降级路径**（Agent 不可用时必须仍能干活） | 🔧 新增对话界面 + 配置页 |
| `license-server/`（授权、计费、后台、CLI） | 12,459 | 服务端权威，与客户端架构无关 | 🔧 计费增加 `action_kind` 分派；新增业务规则下发 |
| `shared/lib/` | 1,051 | 双端契约常量 | 🔧 增加业务规则校验常量 |
| `test/`（628 项） | 16,002 | **回归门槛** | ✅ 全部保留，必须继续绿 |

**合计复用：约 33,000 / 34,000 行 = 97%。**

> ### ⚠️ 真正的结论
>
> **这次要写的代码很少（约 3,000–4,000 行），要改的"定位"很多。**
> 危险的不是工作量，是**把"改定位"误当成"改代码"**，从而去做无谓的重写。
>
> 反过来说：如果实施者认为需要重写 `client/core/` 或 `license-server/`，
> 说明他把这次定位修正理解成了"换框架重做"，需要立即回看本文件 §一。

### 1.2 那 3% 的"错误"在哪

原先的定位错误**没有体现在代码里**，而体现在**默认值与优先级**上：

| 体现位置 | 原状（工具定位） | 改为（Agent 定位） |
|---|---|---|
| Agent 总开关 | 默认关闭 | **默认开启**；关闭后退化为工具链路 |
| 交互主入口 | 图形界面（填表单、点按钮） | **对话界面**；图形界面成为降级路径与精细操作入口 |
| 意图理解 | 关键词整词匹配 | **Agent 语义理解**（"贵不贵"＝"多少钱"） |
| 线索 | 存原文 | **抽取结构化字段**（诉求/地域/预算），可筛选跟进 |
| 业务规则 | 硬编码 / 界面零散配置 | **商家配置 → 服务端下发**（数据，不是代码） |
| 计费口径 | 只有"按成功条数" | 按 `action_kind` 分派（为自动剪辑预留） |

**所以这次修正的主要产物是文档与契约，代码改动集中且清晰。** 这对项目是好事：**纠正得早。**

```
client/
├── agent/                    🆕 Agent 运行时
│   ├── graph.js              状态图定义（节点固定位置）

│   ├── classify.js           批量意图分类（闭集枚举，不自由文本）
│   ├── extract.js            结构化字段抽取（诉求/地域/预算/紧迫度）
│   ├── worth-replying.js     值不值得回（含置信度门槛）
│   └── cache.js              24h 缓存（显著降本）
│
├── tools/                    🆕 工具层（包装既有模块，不重新实现）
│   ├── registry.js           工具清单唯一来源
│   ├── validate.js           参数校验（zod）
│   ├── audit.js              每次调用落审计
│   └── t01…t10*.js           10 个工具（契约见 B-工具契约与粒度设计.md）
│
├── core/       ✅ 不改       CDP / browser-host / ipc
├── platform/   ✅ 不改       selectors / page-* / publish-verifier
├── adapters/   🔧 加 4 出口   collect / reply-comment / reply-danmaku / send-dm
├── safety/     🔧 加一层      guard / similarity / circuit / timing / audit
├── license/    ✅ 不改       keys / sign / http / state / auth / heartbeat / privacy / reporter
├── host/       🔧 加路由      store / queue / scheduler / instances / api / main
└── ui/         🔧 加两页      对话界面 + 决策明细 + 降级状态条 + **业务规则配置页**

license-server/               🔧 计费分派（action_kind）+ 业务规则下发
```

**目录约束（继续有效，且新增两条）**：

1. ⚠️ `client/agent/` **不得** `require('ws')`、不得直接操作 CDP、不得 `fs.writeFileSync`
   （落盘一律经 `host/store.js`，保持"单写者"）
2. 🆕 ⚠️ `client/agent/` **不得**包含任何安全数值字面量——只能从 `gates.js` 读
   （`gates.js` 自身也只能从策略对象读，不得有默认值）
3. 🆕 ⚠️ `client/understanding/` **不得**直接发送或入队——它只产出判断结果，不产生副作用

### P11 · 意图理解与评估集（**本阶段的核心："专业"从这里开始**）

> ### ⚠️ 为什么这是核心，而不是工具层
>
> 定位说"专用 Agent 要在截流这件事上足够专业"。**"专业"的全部可验收内容都在这一层**：
> 能不能认出"贵不贵"就是"多少钱"、能不能从一句话里抽出地域和预算、
> 能不能判断这条值不值得回。
>
> 工具层只是"怎么发"，这一层是"**该不该发、发什么**"。
> **先把这一层做对，工具层才有意义。**

| # | 任务 | 产出 |
|---|---|---|
| 1 | 建**评估集 V1**（≥200 条真实评论，脱敏 + 标注 + 复核） | `test/eval/dataset/` |
| 2 | 用**现有关键词规则**跑同一份评估集，得出**基线** | 基线报告 |

| 5 | `understanding/cache.js`：24h 缓存 | 缓存命中时零 token（实测） |
| 6 | 评估 runner + 报告生成（离线，不依赖 CDP） | `test/eval/run-eval.js` |

**验收**（细则见 `docs/项目章程.md` §七）：
- [ ] 意图识别准确率 **≥ 85%**
- [ ] **`complaint` 召回率 ≥ 95%**（漏判为询价会导致在投诉下自动回复，风险最高）
- [ ] 相对关键词基线的**增益可量化**（例如询价类召回 55% → 91%）
- [ ] 未知意图一律落 `unknown`，**不得自由文本**

- [ ] `test/eval/` **不被任何生产代码 require**

> ### ⚠️ 本阶段有一个**提前停止条件**
>
> 若第 2 步的基线显示"关键词已经够用"（例如询价召回已达 85%），
> 或第 3 步的增益不足（只提升 <10 个百分点）→
> **说明不该继续上 LLM，应停下来重新评估整个方案。**
>
> 这是评估集**最重要的输出**，而且它是在**大规模花钱之前**得到的结论。
> 能得到这个结论，评估集就没有白做。

## 六、这次定位修正给项目留下的一条通用教训

> ### 把"用户说的一个词"直接翻译成一个架构，是这类项目最贵的错误。

两次修正的代价对比：

| | 我读成 | 实际 | 代价 |
|---|---|---|---|
| 第一次 | "要做 agent" → 加一层 agent（默认关闭、界面为主入口） | Agent 是承载形态 | 撤回三个默认值 + 全套文档 |
| 第二次 | "专业分化程度较高" → 要支持多个行业 | 在截流这件事上判断得准 | 撤回一整套插件机制与三份文档 |

**两次错在同一个地方：注意力在"技术上能不能扩展"，而不在"用户到底要什么"。**

**规范（已写入 `shared/AI协作开发指引.md`）**：
定位类词汇（专用 / 平台 / 通用 / 智能）在被翻译成架构之前，
**必须先问清楚它修饰的是业务领域还是技术能力。**

> ### 还有一条更实用的推论
>
> **两次修正的行动成本之所以还能接受，是因为每次都是"文档与默认值"层面的改动，
> 而不是"拆掉代码重写"。**
> 这不是运气——是因为代码被组织成了"机制（几乎不变）+ 业务（可配 + 平台知识隔离）"两层，
> 定位变了只需要改默认值与配置，不需要动 `core/`、`platform/`、`license-server/`。
>
> **分层的真正收益不在于好看，而在于"定位改错时不用重写"。**
