>
> 原则：**这是重新定位，不是重新开发。** 现有代码的主体是资产，不是沉没成本。
>
> 配套：`plans/ADR-001-Agent优先与框架选型.md`（为什么改）· `plans/C-工作流包契约.md`（包契约）·
> `plans/B-工具契约与粒度设计.md`（工具粒度，继续有效）

## 一、先回答"要不要推倒重来"

### 1.1 不推倒。理由是可测量的

| 模块 | 行数 | 在新定位下的角色 | 处置 |
|---|---|---|---|
| `client/core/`（CDP、浏览器宿主、IPC） | 3,827 | 与"是不是 Agent"**完全无关**的底层能力 | ✅ **一行不改** |
| `client/platform/`（选择器、页面模型、成功判定） | 2,104 | 平台知识，与架构无关 | ✅ **一行不改** |
| `client/safety/`（护栏、相似度、熔断、审计） | 2,994 | **新定位下更重要**（要拦 Agent 越权） | 🔧 新增一层拦截 |
| `client/license/`（心跳、上报、验签、停机） | 2,715 | 与服务端通信，与架构无关 | ✅ **一行不改** |
| `client/adapters/`（采集、回复、私信） | 2,289 | 被工具层包装；同时是**降级路径** | 🔧 新增 4 个只读/入队出口 |
| `client/host/`（存储、队列、调度、本地 API） | 4,799 | 状态落盘与节奏控制，与架构无关 | 🔧 新增 Agent 路由 |
| `client/ui/`（商家面板） | 1,842 | **降级路径**（Agent 不可用时必须仍能干活） | 🔧 新增 Agent 面板 |
| `license-server/`（授权、计费、后台、CLI） | 12,459 | 服务端权威，与客户端架构无关 | 🔧 计费增加 `action_kind` 分派 |
| `shared/lib/` | 1,051 | 双端契约常量 | 🔧 增加包契约常量 |
| `test/`（628 项） | 16,002 | **回归门槛** | ✅ 全部保留，必须继续绿 |

**合计复用：约 33,000 / 34,000 行 = 97%。**

> ### ⚠️ 真正的结论
>
> **这次要写的代码很少（约 3,000–4,000 行），要改的"定位"很多。**
> 危险的不是工作量，是**把"改定位"误当成"改代码"**，从而去做无谓的重写。
>
> 反过来说：如果实施者认为需要重写 `client/core/` 或 `license-server/`，
> 说明他把这次定位修正理解成了"换框架重做"，需要立即回看本文件 §一。

### 1.2 那 3% 的"错误"在哪

原先的定位错误**没有体现在代码里**，而体现在**默认值与优先级**上：

| 体现位置 | 原状（工具定位） | 改为（Agent 定位） |
|---|---|---|
| Agent 总开关 | **默认关闭**（`plans/B-与方案A的差异说明.md` §3.4） | **默认开启**；关闭后退化为工具链路 |
| 交互主入口 | 图形界面（填表单、点按钮） | **对话界面**；图形界面成为降级路径与精细操作入口 |
| 工作流边界 | 硬编码在 `adapters/`（采集→回复→私信） | **由工作流包声明**，核心不预设 |
| 计费口径 | 只有"按成功条数" | **按 `action_kind` 分派**（为需求 5 预留） |
| 文档第 0 层 | "抖音自动回复工具" | **"可承载多种专业工作流的 Agent 平台"** |

**所以这次修正的主要产物是文档与契约，代码改动集中且清晰。** 这对项目是好事：**纠正得早。**

**目录约束（继续有效，且新增两条）**：

1. ⚠️ `client/agent/` **不得** `require('ws')`、不得直接操作 CDP、不得 `fs.writeFileSync`
   （落盘一律经 `host/store.js`，保持"单写者"）
2. 🆕 ⚠️ `client/agent/` **不得**包含任何安全数值字面量——只能从 `gates.js` 读
   （`gates.js` 自身也只能从策略对象读，不得有默认值）
3. 🆕 ⚠️ `client/packs/` **不得** `require` 任何 `packs/` 目录下的文件
   （包是数据，不是模块——一旦包被 `require`，约束 1 就事实上失效了）

## 六、本次修正给项目带来的一条通用教训

> ### 把"以后要加的东西"设计成"现在可以不加"，但不能设计成"以后要重做"。

原方案的错误不在于"先做工具链路"这个顺序本身——**顺序是对的**。
错误在于把 Agent 定位成**后续叠加的一层**（"B ≈ A + Agent 层，共享 80%"），
而不是**一开始就存在的承载形态**。

两者的差别在**默认值与优先级**上，而不在代码量上：

- "叠加一层" → Agent 默认关闭、图形界面是主入口、工作流边界硬编码
- "承载形态" → Agent 默认开启、对话是主入口、工作流由包声明

**代价对比**：在代码写完 34,000 行之后修正 = 改约 3,000 行 + 3 份文档。
如果等到有第二个客户时再修正 = 拆掉并重写所有领域的硬编码逻辑。

**这个教训应当写进 `shared/AI协作开发指引.md`：定位类决策的默认值，比功能实现更难改。**
