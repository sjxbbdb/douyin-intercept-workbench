# ADR-001 · 项目定位修正：Agent 优先 + 框架选型 + 插件化

> **状态**：已采纳（2026-09-19）
> **取代**：原"先做方案 A，验证底座后再决定是否叠加方案 B"的路线（该文档已删除）
> **影响面**：项目定位、路线图、依赖白名单、目录结构、验收口径

---

## 一、被修正的判断

原先的判断是：**先做完整工具链路（方案 A），跑一个月拿到数据，再决定是否叠加 Agent（方案 B）。**

这条判断基于三个前提，其中**第一个前提是错的**：

| # | 原判断的前提 | 实际 |
|---|---|---|
| 1 | 目标产品是"抖音自动回复工具" | ❌ **错**。目标是**承载专业分化程度较高的自动化工作流的 Agent**。"回评论"只是第一个工作流，不是产品本身 |
| 2 | 两个方案是"同一产品的两种实现" | ❌ **错**。不是两种实现，是**两种产品定位**：一个是工具，一个是工作流平台 |
| 3 | Agent 是可选增值项 | ❌ **错**。Agent 是**承载形态**，不是功能 |

**结论**：把 Agent 当成"以后再加的一层"，等于把平台当成工具来做。方向错误，越晚纠正代价越大。

## 二、重新定义项目

### 2.1 一句话定位（修正后）

> **一个可承载多种"专业分化工作流"的 Agent 平台。**
> 每个专业领域（本地生活、家居、教育、房产、医美…）是一**个工作流包**：
> 它定义该领域的**线索判据、业务规则、话术策略、合规边界、成功定义**，由 Agent 编排执行。
> 「抖音截流自动回复」是**内置的第一个工作流包**，不是产品的全部。

### 2.2 这个定义改变了什么

| 维度 | 工具定位（原） | 工作流 Agent 平台（修正后） |
|---|---|---|
| 扩展方式 | 改代码、加 `if` | **加载新的工作流包**，不改核心 |
| 能力边界 | 回评论 / 回弹幕 / 发私信 | 由工作流包定义，核心不预设 |
| Agent 角色 | 可选审批者 | **主控**：理解意图 → 选工作流 → 编排步骤 → 执行 → 汇报 |
| 规则与模型 | 规则为主，模型可选 | **模型决定"做什么"，代码决定"能不能做"** |
| 交付形态 | 一个工具 | 平台 + N 个领域包 |
| 验收口径 | 功能清单 | **工作流包的可插拔性与隔离性** |

### 2.3 三条红线在新定位下的位置（**不变，且更严格**）

红线不是"工具定位的产物"，是**平台的底座契约**。新定位下它们的作用范围扩大：

| 红线 | 工具定位下 | 平台定位下 |
|---|---|---|
| ① 安全上限服务端下发 | 约束客户端 | 约束客户端 **+ 约束每一个工作流包**。工作流包**无权**提高任何上限 |
| ② 只对平台确认成功计费 | 约束计费 | 不变。**且计费模型必须能承载不同工作流的不同成功定义** |
| ③ 审计记录真实生效值 | 记录策略值 | **+ 记录"哪条工作流的哪一步、由哪个决策产生"** |

> ⚠️ **插件化不得成为绕开红线的通道。**
> 工作流包是**声明式的**，不是"可以执行任意代码的插件"。
> 详见 `plans/C-工作流包契约.md` §二。

## 三、框架选型（实测，非推断）

### 3.1 实测数据

在两个干净目录各装一次，Node v24.18.0 / npm 11.16.0：

| 框架 | 版本 | 新增包 | node_modules 体积 | 直接依赖 | CommonJS `require` |
|---|---|---|---|---|---|
| **`@langchain/langgraph`** | 1.4.16 | 22 | **47.6 MB** | 4 | ✅ **可用** |
| `@mastra/core` | 1.67.0 | **152** | **104.4 MB** | **36** | 未测（体积已否决） |

**关键发现：`@langchain/langgraph` 可以在 CommonJS 下直接 `require()`，不需要构建步骤。**

它的 `package.json` 里 `exports["."]` 同时提供 `import` 与 `require` 两个条件：

```json
".": {
  "import": { "default": "./dist/index.js"  },
  "require": { "default": "./dist/index.cjs" }
}
```

实测（`node -e`，`.cjs` 文件，无任何编译）：

```
✅ require 成功，耗时 4891 ms
导出数量： 94
关键导出： Annotation, Command, CompiledStateGraph, END, GraphInterrupt,
          INTERRUPT, MemorySaver, START, Send, StateGraph, interrupt
```

> ⚠️ **这一条推翻了原有依赖白名单的立论基础。**
> `AGENTS.md` §2.14 与 `shared/术语与选型基准.md` §3.3 把 `ws` 定为唯一依赖，
> 理由是"引入依赖需要构建步骤 / 破坏可行性"。该理由对 `puppeteer` 成立
> （它给浏览器打自动化指纹，**是这个项目绝不能用它的真正原因**），
> 但对"框架类依赖需要构建"是**不成立的**。
> **白名单应当按理由而不是按习惯维护。**

### 3.2 选型结论

> ## 采用 `@langchain/langgraph` 作为 Agent 编排框架。
> 拒绝 `@mastra/core`。

四条理由：

| # | 理由 |
|---|---|
| 1 | **体积差 2.2 倍、依赖数差 9 倍**。104 MB / 152 个包要装到**商家的 Windows 电脑**上，而客户端是要分发的。47 MB / 22 个包已属可接受上限 |
| 2 | **依赖树越深，供应链风险越大**。Mastra 直接依赖里含 `posthog-node`（遥测）、`execa`、`croner`、`xxhash-wasm`、`@modelcontextprotocol/server` 等 36 个。任何一个出安全问题都要跟着发版 |
| 3 | **LangGraph 的模型正是这个项目需要的**：状态图 + **检查点（checkpointer）**。项目要求"任务状态必须落盘、进程崩溃后必须能续"（`plans/B-工具契约与粒度设计.md` §五），检查点就是这个能力的原生实现，而不是自己写一套 |
| 4 | **图的节点边界天然吻合红线**。硬规则（观察期禁发、日上限、最小间隔）可以做成**图上的独立节点**，位置固定、不可跳过、可单独测试——比散落在流程里的 `if` 更容易证明"它真的拦住了" |

### 3.3 ⚠️ 实测中发现的一个必须写进规范的陷阱

用 LangGraph 复刻"观察期禁发"时，第一版实现**没有拦住**：

```js
decisions: Annotation({ reducer: (a, b) => (b ? a.concat(b) : a), default: () => [] })
// ...
.addNode('policy_gate', (s) => !sendingEnabled
    ? { decisions: [], traces: ['gate: POLICY_SENDING_DISABLED'] }   // ❌ 打算清空
    : { traces: ['gate: 通过'] })
```

**执行结果：观察期下仍然有 1 条进入入队环节。**

原因：`decisions` 用了**累积型 reducer**（`concat`），返回 `[]` 被 reduce 成
`[...原有, ...[], ]` —— **不是清空，是追加了零个元素**。
改成替换型 reducer（`(a, b) => b ?? a`）后归零正确。

> ### 🔴 由此确立一条硬规范
>
> **凡是用框架原语表达"安全闸门"的地方，必须写一条断言"闸门生效"的测试。**
> 闸门是"不通过就不往下走"，而框架的 reducer / 状态合并语义可能把"清空"
> 变成"什么也没发生"——**失败方向恰好是"放行"**，这是最危险的方向。
>
> 这条测试的要求写在 `plans/C-工作流包契约.md` §六，纳入验收。

**修复后实测**（`sendingEnabled = false`）：

```
· prefilter: 已剔除 complaint
· agent: 批准 1 条
· gate: POLICY_SENDING_DISABLED（观察期，全部拒绝）
· execute: 入队 0 条
✅ 观察期 decisions 归零，红线 1 成立
```

## 四、依赖白名单修正

### 4.1 修正后的白名单

| 依赖 | 位置 | 理由 |
|---|---|---|
| `ws` | 客户端 | CDP 与 IPC 的 WebSocket 实现（自主实现已证明需要 ~500 行且易错） |
| `@langchain/langgraph` | 客户端 | Agent 编排框架（本 ADR §3） |
| `zod` | 客户端 | ⚠️ langgraph 的 **peer dependency**，工具参数校验需要。**必须显式安装**，不能依赖其被间接带入 |
| ~~`@langchain/core`~~ | 客户端 | ⚠️ 同为 peer dependency。**评估后决定**：若仅用 `StateGraph` 与 `Annotation` 则不装；一旦需要消息/模型抽象则必须装。**装与不装都要写进 `package.json`，不留隐式依赖** |

### 4.2 仍然明确禁止

| 禁止 | 理由（**理由，不是习惯**） |
|---|---|
| `puppeteer` / `playwright` | 给浏览器打自动化指纹，且**用不上商家已登录的账号**——直接破坏方案可行性 |
| `@mastra/core` | 体积与依赖树（本 ADR §3.2） |
| 任何需要**构建步骤**才能运行的依赖 | 客户端要在商家 Windows 上以"解压即用"分发（`client/启动.cmd`），无构建链 |
| 服务端（`license-server/`）的任何新依赖 | 服务端已用 `node:sqlite` + 原生 `node:http`，**零依赖**是它最大的运维优势（`docs/部署指南-服务端.md`） |

> ⚠️ **服务端零依赖这条不因本次修正而放宽。** Agent 跑在客户端，服务端不需要框架。

### 4.3 白名单的维护规则（新增）

白名单条目必须写成 **`依赖名 + 理由 + 禁止替代品的理由`** 三项。
只写"只允许 ws"这种形式，会在下次遇到"理由不适用"的情况时无法判断该不该放行——
本次 `langgraph` 的矛盾就是由此产生的。
