# ADR-001 · Agent 优先、框架选型与依赖白名单修正

> **状态**：已采纳（2026-09-19）
> **取代**：原"先做工具链路（方案 A），跑一个月拿到数据再决定是否叠加 Agent（方案 B）"的路线
> **影响面**：项目定位、路线图、依赖白名单、目录结构、验收口径
>
> ⚠️ **本 ADR 记录两次修正。** 第一次把项目从"工具"改为"Agent 承载"（有效）；
> 第二次**撤回了同一次修正中"多领域平台 + 工作流包机制"的过度设计**（见 §二）。
> 两次都保留在案，因为**犯错的原因比结论更有价值**。

## 一、第一次修正：Agent 是承载形态，不是可选叠加层

### 1.1 被修正的判断

原判断：**先做完整工具链路，跑一个月拿到数据，再决定是否叠加 Agent。**

这条判断基于三个前提，其中两个是错的：

| # | 原前提 | 实际 |
|---|---|---|
| 1 | 目标产品是"抖音自动回复工具" | ❌ **错**。目标是**一个 Agent**，不是一个带规则引擎的工具 |
| 2 | 两个方案是"同一产品的两种实现" | ❌ **错**。不是两种实现，是**两种能力上限** |
| 3 | Agent 是可选增值项 | ❌ **错**。Agent 是**承载形态** |

**结论**：把 Agent 当成"以后再加的一层"，等于把能力上限锁死在规则引擎上。

### 1.2 这个修正改变了什么（**具体在默认值上，不在代码量上**）

| 体现位置 | 原状（工具定位） | 改为（Agent 定位） |
|---|---|---|
| Agent 总开关 | 默认关闭 | **默认开启**；关闭后退化为工具链路（降级路径） |
| 交互主入口 | 图形界面（填表单、点按钮） | **对话界面**；图形界面成为降级路径与精细操作入口 |
| 意图理解 | 关键词匹配 | Agent 语义理解（"贵不贵"＝"多少钱"） |
| 线索 | 存原文 | 抽取结构化字段（地域/预算/诉求），可筛选跟进 |

> ### ⚠️ 教训一：定位类决策错在**默认值**上，而默认值比功能难改
>
> "叠加一层"与"承载形态"的差别，落到代码上只是三个默认值。
> 但它们决定了产品的能力上限。
> **代价对比**：写完 34,000 行之后再改 = 改约 3,000 行 + 文档；
> 等到有真实客户时再改 = 拆掉重写全部业务逻辑。

## 二、第二次修正：撤回"多领域平台 + 工作流包机制"

### 2.1 我当时怎么读错的

原话是"承载**专业分化程度较高**的自动化工作流"。

我读成了：**"要支持多个行业"** → 于是设计了"工作流包"（插件）机制：
每个行业一个包，包含线索判据、业务规则、话术池、合规边界，核心代码不预设任何行业。

**实际意思是**：**"这一个 Agent 在截流这件事上要足够专业"** ——
即判断得准（读懂意图、判断价值、多轮跟进），而不是能装很多行业。

### 2.2 正确的读法

> **"专用"修饰的是业务领域，不是技术能力。**

| 是 | 不是 |
|---|---|
| 只做截流与自动回复**这一个领域** | ❌ 不是"什么都能聊"的通用助手 |
| 在该领域内具备**专业深度** | ❌ 不是"支持加载多个行业"的平台 |
| 业务规则由商家配置、服务端下发（**数据**） | ❌ 不是插件机制 |

### 2.3 "专业"体现在哪（这才是可验收的东西）

客户问「这个能便宜点吗？我在南京，预算3000左右」：

| | 关键词规则 | 本 Agent |
|---|---|---|
| 是否响应 | 三个词**都**配成关键词才命中 | 识别为「议价 + 地域 + 预算」 |
| 线索 | 存原文 | `{诉求:议价, 地域:南京, 预算:3000}`，可按维度筛 |
| 回复 | 模板池随机取一条 | 按"议价"场景从该场景候选池中选 |
| 多轮 | 发一条即结束 | 可追问"您想要哪个型号" |

**验收指标见 `docs/项目章程.md` §七**：意图识别准确率 ≥85%、
投诉召回率 ≥95%、相对关键词基线的增益可量化、误批率 <5%、成本占单价 <15%。

### 2.4 撤回的东西

| 撤回项 | 原设计 | 现方案 |
|---|---|---|
| `plans/C-工作流包契约.md` | 包契约、违规码、三条交集运算 | **删除** |
| `client/packs/` 加载器与校验 | 加载 / 校验 / 拒绝 | **不做** |
| `packs/<domain>/` 目录 | 每行业一个包 | **不做** |
| `pack.json`（`schema_version` / `pack_id` / 动作闭集） | 通用声明式语言 | **不做** |
| 三层骨架（平台 / 领域 / 运维） | 三层 | **两层**（机制层 / 业务层） |
| `FR-P6 工作流包机制` | 可插拔性需求 | 改为 **`FR-P6 业务规则可配`** |
| 验收项"必须存在第二个包" | 可插拔性的唯一证据 | **删除** |
| 真机验证门 G-7（包隔离） | 换包验证 | **删除** |

**保留的**：Agent 运行时、工具层、硬闸门、降级路径、决策记录、
`action_kind` 计费分派、以及全部三条红线。**这些都与此错误无关。**

### 2.5 为什么不做插件的四条理由（**留档，防止将来重复设计**）

| # | 理由 |
|---|---|
| 1 | **定位不是平台。** 本项目只做截流自动回复一件事。支持"加载任意行业"是另一件事，会拖慢真正的目标 |
| 2 | **抽象会吃掉正确性。** 为了让"任意行业"能表达，包契约不得不做成通用声明式语言——而通用声明式的表达力**一定弱于**为截流场景专门设计的配置 |
| 3 | **没有证据表明需要。** 没有任何真实客户要求过"接入第二个行业"。为假设需求付出的抽象成本是确定的，收益是想象的 |
| 4 | **可配置已经够了。** 商家要改的是**话术和判据**，那用配置就能解决，不需要"加载代码之外的能力" |

> ⚠️ **将来真的要做第二个平台（如快手），那是那时的决定，不是现在的设计约束。**
> 若那天到来，正确的做法是**先看两个平台的实际差异**再抽象，
> 而不是现在凭想象设计一套通用语言。

### 2.6 教训二：**不要把用户说的一个词直接翻译成一个架构**

- 第一次：把"要做 agent"做成"加一层 agent"
- 第二次：把"专业分化程度较高"读成"要支持多个行业"

**两次错在同一个地方：注意力放在"技术上能不能扩展"，而不是"用户到底要什么"。**

> **规范**：定位类词汇（专用 / 平台 / 通用 / 智能）在被翻译成架构之前，
> **必须先问清楚它修饰的是业务领域还是技术能力。**

## 三、框架选型（实测，非推断）

**这一节与两次定位修正无关，结论始终有效。**

### 3.1 实测数据

在两个干净目录各装一次，Node v24.18.0 / npm 11.16.0：

| 框架 | 版本 | 新增包 | node_modules 体积 | 直接依赖 | CommonJS `require` |
|---|---|---|---|---|---|
| **`@langchain/langgraph`** | 1.4.16 | 22 | **47.6 MB** | 4 | ✅ **可用** |
| `@mastra/core` | 1.67.0 | **152** | **104.4 MB** | **36** | 未测（体积已否决） |

**关键发现：`@langchain/langgraph` 可以在 CommonJS 下直接 `require()`，不需要构建步骤。**

它的 `package.json` 里 `exports["."]` 同时提供 `import` 与 `require` 两个条件：

```json
".": {
  "import": { "default": "./dist/index.js"  },
  "require": { "default": "./dist/index.cjs" }
}
```

实测（`.cjs` 文件，无任何编译）：

```
✅ require 成功，耗时 4891 ms
导出数量： 94
关键导出： Annotation, Command, CompiledStateGraph, END, GraphInterrupt,
          INTERRUPT, MemorySaver, START, Send, StateGraph, interrupt
```

> ⚠️ **这一条推翻了原有依赖白名单的立论基础。**
> 原白名单把 `ws` 定为唯一依赖，隐含理由是"引入依赖需要构建步骤"。
> 该理由对 `puppeteer` 成立（它给浏览器打自动化指纹，**是这个项目绝不能用它的真正原因**），
> 但对"框架类依赖需要构建"是**不成立的**。
> **白名单应当按理由而不是按习惯维护。**

### 3.2 选型结论

> ## 采用 `@langchain/langgraph` 作为 Agent 编排框架。拒绝 `@mastra/core`。

| # | 理由 |
|---|---|
| 1 | **体积差 2.2 倍、依赖数差 9 倍**。104 MB / 152 个包要装到**商家的 Windows 电脑**上，而客户端是要分发的 |
| 2 | **依赖树越深，供应链风险越大**。Mastra 直接依赖含 `posthog-node`（遥测）等 36 项。任何一个出安全问题都要跟着发版 |
| 3 | **LangGraph 的模型正是这个项目需要的**：状态图 + **检查点**。项目要求"任务状态落盘、崩溃后能续"，检查点就是这个能力的原生实现 |
| 4 | **图的节点边界天然吻合红线**。硬规则可做成**图上的独立节点**，位置固定、不可跳过、可单独测试——比散落在流程里的 `if` 更容易证明"它真的拦住了" |

### 3.3 回退方案（若框架在客户端集成受阻）

**退回自研最小状态机（约 300 行），接口不变，其余全部不受影响。**
这是选择"图 + 固定节点"而非"框架深度绑定"的原因。

## 四、⚠️ 实测发现的框架陷阱（**已写成硬规范**）

用 LangGraph 复刻"观察期禁发"时，第一版**没有拦住**：

```js
decisions: Annotation({ reducer: (a, b) => (b ? a.concat(b) : a), default: () => [] })
// ...
.addNode('policy_gate', (s) => !sendingEnabled
    ? { decisions: [], traces: ['gate: POLICY_SENDING_DISABLED'] }   // ❌ 打算清空
    : { traces: ['gate: 通过'] })
```

**执行结果：观察期下仍然有 1 条进入入队环节。**

原因：`decisions` 用了**累积型 reducer**（`concat`），返回 `[]` 被 reduce 成
`[...原有, ...[]]` —— **不是清空，是追加了零个元素**。
改成替换型 reducer（`(a, b) => b ?? a`）后归零正确。

**修复后实测**（`sendingEnabled = false`）：

```
· prefilter: 已剔除 complaint
· agent: 批准 1 条
· gate: POLICY_SENDING_DISABLED（观察期，全部拒绝）
· execute: 入队 0 条
✅ 观察期 decisions 归零，红线 1 成立
```

> ### 🔴 由此确立的硬规范
>
> **凡是用框架原语表达"安全闸门"的地方，必须写一条断言"闸门生效"的测试。**
>
> 闸门是"不通过就不往下走"，而框架的 reducer / 状态合并语义可能把"清空"
> 变成"什么也没发生"——**失败方向恰好是"放行"，这是最危险的方向**。
>
> **断言强度要求**：断言**下游**的输入（"下游收到 0 条"），
> **不得**只断言闸门函数自己返回了什么。
> 因为缺陷恰恰可能出在**闸门与下游之间的状态传递**上（本次即是此例）。

## 五、依赖白名单修正

### 5.1 修正后的白名单（客户端）

| 依赖 | 用途 | 为什么允许它而不是替代品 |
|---|---|---|
| `ws` | CDP WebSocket | 自研需正确处理分帧、掩码、背压、ping/pong、重连、半开连接。这是"要求稳定"最不该自己写的部分 |
| `@langchain/langgraph` | Agent 编排（状态图 + 检查点） | 实测 22 包 / 47.6 MB，CommonJS 直接可用无构建。**不用 `@mastra/core`**：152 包 / 104.4 MB |
| `zod` | 工具参数校验 | ⚠️ langgraph 的 **peer dependency**。工具层必须校验模型传入的参数（不信任模型传参），**必须显式声明，不留隐式依赖** |

### 5.2 服务端依赖：零（**不放宽**）

服务端已用 `node:sqlite` + 原生 `node:http`，零依赖是它最大的运维优势。
**Agent 跑在客户端，服务端不需要框架。**

### 5.3 仍然明确禁止

| 禁止 | 理由（**理由，不是习惯**） |
|---|---|
| `puppeteer` / `playwright` | 给浏览器打自动化指纹，且**用不上商家已登录的账号**——直接破坏方案可行性 |
| `@mastra/core` | 体积与依赖树（§3.1） |
| 任何需要**构建步骤**才能运行的依赖 | 客户端要在商家 Windows 上以"解压即用"分发（`client/启动.cmd`） |
| 服务端任何新依赖 | §5.2 |

### 5.4 白名单的维护规则（新增）

白名单条目必须写成 **`依赖名 + 理由 + 禁止替代品的理由`** 三项。
只写"只允许 ws"这种形式，会在下次遇到"理由不适用"的情况时无法判断该不该放行——
本次 `langgraph` 的矛盾就是由此产生的。

| # | 待决事项 | 为什么不在本 ADR 决定 |
