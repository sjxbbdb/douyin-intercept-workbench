## 一、这个项目是什么

一套**抖音互动自动化工具**，帮助商家自动回复视频评论、直播间弹幕与私信，并把互动中的意向客户沉淀为线索名单。采用「客户端 + 授权中心」两段式架构，按**成功回复条数**计费。

驱动方式为 Chrome 远程调试协议（CDP），使用商家本机**已登录的**专用 Chrome，因此登录态真实可用。

## 二、⚠️ 先读这一段：三条不可违背的红线

在写任何代码之前，请先理解并接受以下三条。**它们不是建议，是产品存在的前提。**

### 红线 1：安全上限由服务端下发，客户端不可绕过

**背景**：这个工具的价值来自"发得多"，而账号被封的原因也是"发得多"。这两个目标根本对立。

因此产品定位是**「控制节奏，让账号活得久」**，不是"发得越多越好"。所有安全上限（日发送量、最小间隔、活跃时段、内容相似度）**由服务端权威下发，客户端只能调低不能调高**。

- 权威数值见 `shared/protocol.md` §4.6 的 `tier_table`（**全系统唯一来源**）
- 越权上报 → 服务端返回 `POLICY_VIOLATION(409)` 并拒绝
- 新账号前 3 天为**观察期，日上限为 0**（只采集、不发送），客户端**不可跳过**

> **如果实现时放宽了这些限制，整个项目就失去了核心价值，且会产生真实的账号封禁损失。**

### 红线 2：只对平台确认成功的发送计费

计费依据**仅有** `POST /api/v1/audit/sends` 的逐条明细，且必须**同时**满足：

```
verdict = sent_confirmed
且 confirm_signal = platform_response      ← DOM 判断不算，必须拿到平台响应
且 platform_status_code = 0
且 未超当日策略上限
且 该 send_id 未计费过
```

失败、被风控拒绝、被跳过、超上限的发送**一律不计费**。

> **特别注意**：绝不允许"DOM 上看起来发出去了"就判定成功。旧代码中曾出现"编辑器消失即判定已发送"的错误（把页面崩溃记为成功），必须避免。空响应 = 风控拒绝，不得标记成功。

### 红线 3：审计留痕必须记录"真实生效的策略值"

每次发送与配置变更都要留痕，且审计必须记录**实际生效的策略版本与生效值**，而不只是用户设置值。

原因：纠纷时需要能回答"该账号当时实际生效的策略是什么、用户是否主动调高过、系统是否拒绝过"。**只记设置值无法自证。**

- 隐私边界：**只上传哈希与计数，绝不上传评论原文、回复内容原文、用户隐私字段**
- 审计本地与服务端双写，客户端不可篡改服务端副本

更多合规要求见 `shared/安全与合规要求.md`。

### 关于 `legacy/`

原项目是**别人的半成品**，存在 14 项已确认缺陷（含硬编码绝对路径导致在非原作者机器上跑不通、队列竞态丢任务、控制台裸奔可被跨站调用等）。完整清单见 `docs/需求规格.md` §七之二。

**处置决定：完全重写。** 但——旧代码**不删除**，已移入 `legacy/` 作为**只读行为规格参考**。

**为什么必须保留**：旧代码里含有用真账号在真页面上反复试错换来的**抖音 DOM 知识**（例如：页面上同时存在隐藏与可见两个 `comment-list`，只能用可见的那个；`scrollIntoView` 之后虚拟列表会重渲染，必须延迟再读按钮坐标否则拿到 0×0）。这些知识**无法凭空复现**，且每次试错都消耗真实账号风险。

**使用方式**：

1. 新实现的每个 DOM 交互原语，都要在 `legacy/` 中找到对应实现逐条对照
2. 已提取的知识点见 `shared/已知陷阱与平台知识.md`（**写 DOM 代码前必读**）
3. 离线回归测试见 `shared/测试策略.md`

**⚠️ 硬约束**：`legacy/` **只读**，不得被任何生产代码 `require`。这是验收项之一。

## 五、两套方案：先选一条路

本项目提供**两套完整方案**，底座相同，上层不同。

```
                    ┌─────────────────────────────┐
                    │  共同底座（两方案都必须实现）  │
                    │  授权中心 · 接口契约 · 审计    │
                    │  安全策略下发 · 计费 · 数据看板 │
                    └──────────┬──────────────────┘
                               │
                 ┌─────────────┴─────────────┐
                 ▼                           ▼
        ┌─────────────────┐         ┌─────────────────┐
        │  方案 A          │         │  方案 B          │
        │  完整工具链路     │         │  专用 Agent      │
        │                 │         │                 │
        │  固定流水线      │         │  Agent 编排      │
        │  规则匹配        │         │  LLM 语义理解    │
        │  零 LLM 成本     │         │  可变 token 成本  │
        │  确定、可测      │         │  灵活、需评估集   │
        └─────────────────┘         └─────────────────┘
```

| | 方案 A：完整工具链路 | 方案 B：专用 Agent |
|---|---|---|
| **一句话** | 把现有工具能力重构为完整可交付产品 | 在 A 的底座上加一层对话式智能体 |
| **交互** | 图形界面，填表单、点按钮 | 自然语言下指令，Agent 编排工具 |
| **意图理解** | 关键词匹配（任意字命中） | LLM 语义理解，能识别"贵不贵"＝问价格 |
| **话术** | 模板库随机轮换 | 从候选池中由 LLM 选择（**不得自由生成**，见方案 B 文档） |
| **线索** | 原文保存 | 可抽取结构化字段（地域/预算/时间） |
| **成本** | 固定（服务器带宽） | 每条约 1 次推理调用，需成本模型 |
| **可测性** | 高（确定性，可写单测） | 中（需评估集打分） |
| **风险** | 低 | 中（模型不确定性需额外护栏） |
| **建议** | **先做 A**，验证底座 | A 稳定后再叠加 |

**详细对比与选型建议**：`plans/00-两方案对比与选型建议.md`
**方案 A 开发指导**：`plans/A-工具链路开发指导.md`
**方案 B 开发指导**：`plans/B-Agent开发指导.md`

> **强烈建议先实施方案 A。** 理由：A 的底座（授权中心、契约、审计、安全策略）是 B 的必要前提，且 A 可在无 LLM 依赖下验证"裸 CDP 驱动抖音"这条路是否真的走得通。若 A 都跑不通，B 无从谈起。

## 八、技术选型（速查）

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | **Node.js ≥ 22.5**（客户端与服务端均要求） | 服务端需 `node:sqlite` |
| 语言 | **纯 JavaScript**（不用 TypeScript，无构建步骤） | 零构建便于商家分发；如需 TS 需自行评估 |
| CDP WebSocket | **`ws`** | 唯一允许的第三方依赖。自研 WS 需处理分帧/背压/重连/半开连接，是"要求稳定"最不该自己写的部分 |
| HTTP 服务 | **Node 内置 `http`** | 够用 |
| 服务端存储 | **`node:sqlite`（内置）** | 真事务、零依赖。已实测可用 |
| 客户端存储 | **JSON 文件 + 单写者 + 原子写** | 见 `shared/开发规范.md` |
| 密码哈希 | **内置 `crypto.scrypt`** | 够用 |
| HMAC | **内置 `crypto.createHmac`** | 够用 |
| 前端 | **原生 DOM，无框架** | 保持单文件分发，无构建 |
| 并行/async | Promise + async/await | 无 async 库 |

**明确不引入**：`puppeteer-core`、`playwright`（理由见 `shared/术语与选型基准.md` §三）
