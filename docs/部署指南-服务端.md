# 授权中心服务端（license-server）部署指南

> 厂商（甲方）自运维文档。目标：**在已运行代理服务的 VPS 上部署，与现有服务共存**。除 `<...>` 处需替换，所有命令可直接复制（bash / Linux）。客户端（商家本机 Windows）不在本文范围，见 §6.5。
> **本版对应两项设计变更**：① 计费由"按小时"改为**按成功回复条数**（`credit_per_reply`，心跳不再计费）；② 新增**安全策略服务端下发**（§3.3）与**审计留痕**（§5.4、§5.5、§5.6）。

**基准环境**：Ubuntu 22.04.5 / 2 核 3GB / 50GB NVMe；现有 sing-box v1.14.1 占 **443/tcp**（Reality）与 **8443/udp**（Hysteria2）；ufw 放行 22、443、8443；fail2ban 已启用。本文给授权服务分配 **127.0.0.1:18080**（应用）+ **9443/tcp**（HTTPS 对外）。

```bash
bd=/opt/dy-license
rc="sudo -u dylicense env HOME=/opt/dy-license node $bd/cli.js"
```

### 1.5 资源要求与容量预估

| 资源 | 最低 | 建议 | 说明 |
|---|---|---|---|
| 内存 | 192MB 可用 | **384MB 可用** | sing-box 通常 < 150MB；授权服务 `MemoryMax=384M`（§4） |
| 磁盘 | 2GB 空闲 | **8GB 空闲** | 审计明细持续增长，见 §5.6 |
| CPU / IOPS | 1 核 / — | 共享 2 核 / NVMe | `CPUQuota=60%` 兜底；**不要放 NFS** |

```bash
df -h / && df -i / && free -m      # 要求：/ 可用 ≥ 8GB、可用内存 ≥ 384MB
```

**按条计费的实际写入量**（每条成功回复 = 1 条明细 + 1 条台账；客户端每 300s 批量上报）：10 商家×300 条/日 ≈ 0.03 行/秒；50 商家 ≈ 0.17 行/秒；100 商家×500 条/日 ≈ 0.58 行/秒。**不足 1 行/秒，NVMe 上毫无压力——批量事务下 SQLite 可跑 5000+ 行/秒。** 真实风险是①逐条自动提交的 fsync 次数、②WAL 无限增长、③明细长期累积吃满磁盘，分别由 §5.3（两次）与 §5.6 解决。

## 3. 配置项清单

### 3.1 选 `.env`（KEY=VALUE），理由

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **`.env`** | systemd `EnvironmentFile=` 原生支持；可脱敏；换环境不改代码 | 值只有字符串，需自行解析类型 | ✅ 采用 |
| `config.json` | 结构清晰、可嵌套 | **密钥明文躺在代码目录**，易被一起打包提交 | ❌ |

约定：只写 `KEY=VALUE`，**不写 `export`、不加引号**（systemd 的 `EnvironmentFile` 不解析 shell）；敏感值用十六进制/字母数字生成，规避转义。

| 配置项 | 含义 | 默认值 | 推荐值 | 敏感 |
|---|---|---|---|---|
| `HOST` / `PORT` | 应用监听 | `127.0.0.1` / `18080` | 有反代就绑回环；直连才 `0.0.0.0` | 否 |
| `PUBLIC_BASE_URL` | 客户端实际访问地址 | `https://license.example.com:9443` | 必须与证书一致 | 否 |
| `TRUST_PROXY` | 信任 `X-Forwarded-For`（限流/白名单取真实 IP） | `1` | 反代后 `1`；直连必须 `0` | 否 |

| `DB_BUSY_TIMEOUT_MS` | `SQLITE_BUSY` 等待毫秒 | `8000` | `8000`（按条计费写入更频繁） | 否 |

| `DB_SYNCHRONOUS` | 提交落盘强度 | `NORMAL` | **`NORMAL`**（WAL 下安全且快）；`FULL` 写吞吐降 3~5 倍，仅"绝不能丢已确认扣费"时用 | 否 |

| `OFFLINE_GRACE_HOURS` | 断网宽限（期间不发送不扣费，恢复后补报补扣） | `24` | `24` | 否 |

| `LOG_FORMAT` | `json` / `text` | `json` | `json` | 否 |

### 3.3 安全策略的存放方式：**数据库表**，不放 `.env`

账号等级、各操作类型日上限、最小间隔、活跃时段、熔断阈值是**业务数据**：要能按账号单独调、要留痕、要带版本号下发。放 `.env` 有三个硬伤——改一个商家的限额要重启全服、无法留痕、无法按账号差异化。因此：

- **`policy`**：按 `account_id` 一行，存当前生效策略（DDL 见 §5.4）。
- **`policy_history`**：每次变更插一条，留改前/改后 JSON + 操作人 + 时间 + 原因，是"谁把谁的限额改了"的举证依据。
- **`.env` 只提供"建表初始默认值"与"字段缺失时的兜底值"**，迁移时把下表默认值写入每个新账号。
- **下发机制**：心跳响应携带 `policy_version` + 完整策略体；客户端只记版本号，落后即**整体替换**（不做字段合并，避免新旧混合）。策略一改 `policyVersion+1`，客户端最迟下一个心跳（≤60 秒）生效。失败计 `policy_push_fail`（§8.3）。

**策略默认值（迁移时写入 `policy` 表）**

> ⚠️ **本节已按 `shared/protocol.md`（`protocol_version=2`）重写（2026-09-18）**
>
> 原版使用 `level`（`basic`/`standard`/`vip`）、`daily_total_max`、`min_interval_comment_sec` 等字段，与 v2 契约**完全不同**。契约是唯一权威，字段名与取值必须一致，否则策略下发与越权校验全部失效。

| 字段（v2 契约） | 含义 | 默认值 | 可配 |
|---|---|---|---|
| `account_tier` | 账号等级，**按天数自动推进** | 见下表四级 | ❌ 不可手工指定 |
| `limits.<source>.daily_max` | 各渠道日上限（`source` ∈ `comment`/`live_danmaku`/`dm`） | 见下表 | ✅ 但**只能调低** |
| `limits.<source>.min_interval_ms` | 各渠道最小间隔（**毫秒**） | 见下表 | ✅ 但**只能调高**，且须落在 `min_interval_ms_range` 内 |
| `limits.<source>.content_similarity_max` | 内容相似度上限（**超过即拒绝**） | `0.85`（`dm` 为 `0.75`） | ✅ 但**只能调低** |
| `active_hours` | 活跃时段（单窗口，本地时区偏移 `tz_offset_minutes`） | `[["08:00","23:00"]]` | ✅ 但**只能调短** |
| `circuit_breaker` | 熔断参数（失败率阈值 / 窗口 / 平台拒绝阈值 / 冷却） | `0.4` / `20` / `3` / `1800000ms` | ✅ |
| `idle_pause_ms` | 空闲停扣阈值 | `7200000`（2 小时） | ✅ |
| `policy_hash` | 策略哈希，客户端 ack 存证用 | 服务端计算 | ❌ |

**四级 `tier_table`（权威值，来自 `shared/protocol.md` §4.6）**

| 等级 | 天数 | comment | live_danmaku | dm | 说明 |
|---|---|---|---|---|---|
| `observation` | 1–3 | **0** | **0** | **0** | `sending_enabled=false`，只采集不发送 |
| `warm_up` | 4–7 | 10 | 10 | 3 | — |
| `ramp_up` | 8–14 | 25 | 25 | 8 | — |
| `stable` | 15+ | 30 | 30 | 10 | 合计 **70**，套餐积分折算基数 |

`min_interval_ms_range`：`comment` 60000–180000 / `live_danmaku` 30000–90000 / `dm` 300000–900000

> ⚠️ **重要**：`tier_table` 是**全系统唯一来源**。`stable_daily_max_total`（70）、`plan.credits`（12600）、`min_plan_credit`（12600）与 `quota_notice` 文案中的全部数字**必须由该表实时推导，禁止硬编码**，否则改上限后会出现"界面写每日 70 条、套餐却按旧值折算"的错误告知。
>
> 三条写死在服务端、不参与下发：`circuit_policy`（命中风控/空响应即硬停）、验证码/滑块出现即停、全局急停开关。
>
> 客户端**只能更保守**，四个方向的判定见 `shared/安全与合规要求.md` §2.2。

### 3.4 生成密钥与初始密码（敏感项）

```bash
openssl rand -hex 32                                # HMAC_SECRET
echo "/admin-$(openssl rand -hex 3)"                # 后台随机路径
openssl rand -base64 15 | tr -d '/+=' | cut -c1-18  # 初始管理员密码
openssl rand -base64 24                             # 备份加密口令（§9.6）
sudo -u dylicense sed -i "s|^HMAC_SECRET=.*|HMAC_SECRET=$(openssl rand -hex 32)|" /opt/dy-license/.env
sudo -u dylicense sed -i "s|^ADMIN_INIT_PASSWORD=.*|ADMIN_INIT_PASSWORD=$(openssl rand -base64 15 | tr -d '/+=' | cut -c1-18)|" /opt/dy-license/.env
sudo chmod 600 /opt/dy-license/.env && sudo grep -E '^(HMAC_SECRET|ADMIN_INIT_PASSWORD)=' /opt/dy-license/.env   # 抄进密码管理器
```
**保管要求**：`HMAC_SECRET` 客户端也持有一份 → 存密码管理器，**不进 git、不发群/邮件**；文件 `600` 且属主 `dylicense`，不额外复制第二份；一旦疑似泄漏，立刻按 §9.5 轮换并 `$rc session revoke --all`。

## 5. 数据库初始化、写入调优与数据保留

### 5.1 建议：**自动迁移 + 迁移前自动备份**

- 首次启动按 `schema_meta` 建表并从 `schema_version=1` 依次迁移。
- 每次启动：库版本 < 代码期望版本 → **先自动备份**，再单事务迁移；失败回滚并 `exit 1`（systemd 记录）。
- 库版本 > 代码期望版本（代码被回滚过）→ **拒绝启动**并打印错误，防止旧代码写坏新结构。
- 逃生开关：`DY_LICENSE_SKIP_MIGRATE=1`（跳过自动迁移）、`DY_LICENSE_ALLOW_DOWNGRADE=1`（允许旧代码开新库，仅救援用）。

```sql
CREATE TABLE IF NOT EXISTS schema_meta (          -- 单行表，防并发歧义
  id INTEGER PRIMARY KEY CHECK (id = 1), schema_version INTEGER NOT NULL, app_version TEXT NOT NULL,
  applied_at TEXT NOT NULL,     -- ISO8601 UTC
  checksum TEXT NOT NULL        -- 迁移集合 sha256，防"同号不同内容"
);
```
迁移约定（写进代码，别手工做）：① 连接后立刻设 §5.3 的 PRAGMA；② 每个迁移一个 `BEGIN IMMEDIATE … COMMIT`，内含 DDL 与 `schema_meta` 更新；③ **DDL 只做加法**（`ADD COLUMN`、`CREATE TABLE/INDEX IF NOT EXISTS`），不删列不改类型——回滚旧代码仍能跑；④ 迁移前落一份 `backups/pre-migrate-<ver>-<ts>.db`。

```bash
$rc db migrate && $rc db version && $rc db check   # check = integrity_check + foreign_key_check
# 手工触发等价于：systemctl stop dy-license; $rc db migrate; systemctl start dy-license
```

### 5.2 备份：**绝不要 `cp` 正在写入的 db**

WAL 模式下已提交数据可能还在 `license.db-wal` 里，`cp license.db` 会缺数据甚至得到 `database disk image is malformed`。三种正确做法：

```bash
TS=$(date -u +%Y%m%dT%H%M%SZ)
# A) VACUUM INTO（推荐：一条命令，产物已整理为单文件）
sudo -u dylicense sqlite3 /opt/dy-license/data/license.db "PRAGMA wal_checkpoint(TRUNCATE); VACUUM INTO '/opt/dy-license/backups/license-$TS.db';"
# B) sqlite3 .backup（在线备份，无需停服）  C) 应用内置（node:sqlite 的 backup()，零外部依赖）
sudo -u dylicense sqlite3 /opt/dy-license/data/license.db ".backup '/opt/dy-license/backups/license-$TS.db'"
$rc db backup --out /opt/dy-license/backups
sudo -u dylicense sqlite3 /opt/dy-license/backups/license-$TS.db "PRAGMA integrity_check;"   # 校验
```
> 没装 `sqlite3`：`sudo apt-get install -y sqlite3`（Ubuntu 22.04 自带 3.37，支持 `VACUUM INTO`）。**必须带 `sudo -u dylicense`**：`data/` 是 `0700`；用 `sudo sqlite3` 会生成 root 属主的 WAL 文件反而把库搞坏。

```bash
sudo tee /etc/cron.d/dy-license-backup >/dev/null <<'CRONEOF'
20 3 * * * dylicense /usr/bin/sqlite3 /opt/dy-license/data/license.db ".backup '/opt/dy-license/backups/license-$(date -u +\%Y\%m\%d).db'" >/dev/null 2>&1
40 3 * * * dylicense find /opt/dy-license/backups -name 'license-*.db*' -mtime +14 -delete >/dev/null 2>&1
CRONEOF
sudo chmod 644 /etc/cron.d/dy-license-backup
```
> `/etc/cron.d` 里 `%` 必须写成 `\%`（上面已转义）。**不要**动或覆盖 `/etc/cron.d/vps-maintenance`（现有代理的自动更新任务）。

**恢复步骤**（顺序不能变）：
```bash
sudo systemctl stop dy-license
sudo -u dylicense cp -a /opt/dy-license/data/license.db /opt/dy-license/backups/before-restore-$(date -u +%Y%m%dT%H%M%SZ).db   # 服务已停，cp 安全
sudo -u dylicense sqlite3 /opt/dy-license/backups/license-20260918.db "PRAGMA integrity_check;"                              # 校验备份可用
sudo -u dylicense cp /opt/dy-license/backups/license-20260918.db /opt/dy-license/data/license.db
sudo rm -f /opt/dy-license/data/license.db-wal /opt/dy-license/data/license.db-shm   # ★ 必须删，否则旧 WAL 覆盖新库
sudo chown dylicense:dylicense /opt/dy-license/data/license.db* && sudo chmod 600 /opt/dy-license/data/license.db
sudo systemctl start dy-license && $rc db version && $rc db check
```
季度演练（在 `/tmp` 做，别动生产库）：`mkdir -p /tmp/restore-drill && sudo -u dylicense cp <备份> /tmp/restore-drill/t.db`，再跑 `sqlite3 /tmp/restore-drill/t.db "PRAGMA integrity_check; SELECT schema_version,app_version FROM schema_meta;"`。

### 5.3 SQLite 写入调优（按条计费后必须做的四件事）

**① 每个连接建立后立即设 PRAGMA**（PRAGMA 是连接级的）：
```sql
PRAGMA journal_mode=WAL;                 -- 读写不互斥，单写多读
PRAGMA synchronous=NORMAL;               -- WAL 下进程崩溃不丢已提交事务；仅断电可能丢最后几个
PRAGMA busy_timeout=8000;                -- 写冲突时等待而非直接抛 SQLITE_BUSY
PRAGMA foreign_keys=ON;
PRAGMA wal_autocheckpoint=4000;          -- 约每 16MB WAL 触发一次检查点
PRAGMA journal_size_limit=67108864;      -- 检查点后把 WAL 文件截回 ≤64MB
PRAGMA cache_size=-24576;                -- 24MB page cache（对应 DB_CACHE_MB）
PRAGMA temp_store=MEMORY;
```
**② 批量事务写明细——最重要的一条。** 一次上报（最多 `REPORT_BATCH_MAX=500` 条，典型 10~100 条）必须包在**一个事务**里，禁止逐条 autocommit：
```js
db.exec('BEGIN IMMEDIATE')
try { for (const r of rows) insertStmt.run(...); db.exec('COMMIT') }
catch (e) { db.exec('ROLLBACK'); throw e }
```
**吞吐量级差**：逐条提交（每次 commit 一次 fsync）在 2 核 NVMe VPS 上约 **100~300 行/秒**；每 100 行一个事务约 **5000~20000 行/秒**。我们实际峰值不足 1 行/秒——"按条计费"压不垮 SQLite，**只有写错模式才会**。
**③ 会计台账不要和审计明细走同一事务。** `ledger`（钱）必须与余额同事务、同步落盘；`send_log` / `audit_config_changes`（证据）允许延迟、批量，甚至按 §5.6 降级丢弃。**钱的优先级永远更高。**
**④ 长事务禁令。** 挂着的写事务会让 WAL 无限增长、服务端持续 `SQLITE_BUSY`，排查一律只读：
```bash
sudo -u dylicense sqlite3 -readonly /opt/dy-license/data/license.db "select count(*) from send_log;"
sudo -u dylicense sqlite3 /opt/dy-license/data/license.db "PRAGMA journal_mode; PRAGMA synchronous; PRAGMA busy_timeout;"
ls -lh /opt/dy-license/data/    # WAL 应稳定在几十 MB 内，不应无限增长
```

### 5.4 审计表结构（发送明细 + 策略留痕）

```sql
-- ⚠️ 本节已按 shared/protocol.md（v2）与 shared/开发规范.md 重写（2026-09-18）
-- 原版存在三处与规范冲突：① 时间用 ISO8601 文本（应为整数 Unix 毫秒）；
-- ② credit_delta 用 REAL 浮点（禁止用浮点存金额）；③ 缺 policy_ack_log
-- （契约硬要求，用于证明"客户端确认应用了哪一版策略"）。

-- 发送明细：纠纷举证与计费的核心证据。完整字段以 shared/protocol.md §4.8 为准
CREATE TABLE IF NOT EXISTS send_log (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  account_id        INTEGER NOT NULL,
  instance_id       TEXT    NOT NULL,
  send_id           TEXT    NOT NULL,          -- 幂等键与计费键，客户端发送前生成
  source_type       TEXT    NOT NULL,          -- comment | live_danmaku | dm
  target_hash       TEXT,                      -- 目标哈希（视频/直播间/会话）
  user_key_hash     TEXT,                      -- 对方用户哈希，绝不上传 sec_uid 原文
  user_key_type     TEXT,
  content_hash      TEXT,                      -- 回复内容哈希，绝不上传原文
  verdict           TEXT    NOT NULL,          -- sent_confirmed | sent_confirmed_dom | rejected | skipped | failed
  confirm_signal    TEXT,                      -- platform_response | dom_stable | none
  platform_endpoint TEXT,                      -- 闭集白名单：comment/publish、im/send 等
  platform_status_code INTEGER,
  failure_reason    TEXT,
  billing_status    TEXT    NOT NULL,          -- billed | unbilled_failed | unbilled_risk_control
                                               -- | unbilled_over_limit | unbilled_insufficient_credit
                                               -- | unbilled_dom_only
  charged_milli     INTEGER NOT NULL DEFAULT 0,-- ⚠️ 整数毫单位，禁止 REAL
  applied_policy_version INTEGER,
  policy_snapshot_json   TEXT,                 -- 实际生效的策略值（非用户设置值）
  sent_at_ms        INTEGER NOT NULL,          -- 客户端事件时间（已按 clock_skew_ms 校准）
  received_at_ms    INTEGER NOT NULL,          -- 服务端接收时间（权威）
  client_version    TEXT,
  device_id         TEXT,
  report_id         TEXT,                      -- 批次幂等键
  UNIQUE(account_id, send_id)                  -- ⚠️ 计费幂等的根本保证
);
CREATE INDEX IF NOT EXISTS idx_send_acc_time ON send_log(account_id, sent_at_ms);
CREATE INDEX IF NOT EXISTS idx_send_billing  ON send_log(billing_status, sent_at_ms);
CREATE INDEX IF NOT EXISTS idx_send_verdict  ON send_log(verdict, sent_at_ms);

-- 配置变更审计：回答"用户是否主动调高过、系统是否拒绝过"
CREATE TABLE IF NOT EXISTS audit_config_changes (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  change_id      TEXT    NOT NULL UNIQUE,
  account_id     INTEGER NOT NULL,
  instance_id    TEXT,
  changed_at_ms  INTEGER NOT NULL,
  source         TEXT    NOT NULL,     -- user | server_policy | default
  actor          TEXT,                 -- local_user | license_server | admin:<name>
  field_key      TEXT    NOT NULL,     -- 如 limits.dm.daily_max
  old_value      TEXT,
  new_value      TEXT,
  applied        INTEGER NOT NULL,     -- 1/0，是否实际生效
  reject_code    TEXT,                 -- 被拒时的错误码，如 POLICY_VIOLATION
  policy_version INTEGER,
  received_at_ms INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_cfg_acc_time ON audit_config_changes(account_id, changed_at_ms);

-- 策略版本历史（每次调整留一条，量极小，长期保留）
CREATE TABLE IF NOT EXISTS policy_history (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  policy_version INTEGER NOT NULL,
  account_id     INTEGER,              -- NULL 表示全局默认策略
  before_json    TEXT,
  after_json     TEXT    NOT NULL,
  operator       TEXT    NOT NULL,
  reason         TEXT,
  created_at_ms  INTEGER NOT NULL      -- ⚠️ 整数毫秒
);
CREATE INDEX IF NOT EXISTS idx_polhist_ver ON policy_history(policy_version);

-- 当前生效策略（每账号一行；全局默认行 account_id IS NULL）
CREATE TABLE IF NOT EXISTS policy (
  account_id     INTEGER PRIMARY KEY,
  policy_version INTEGER NOT NULL DEFAULT 1,
  account_tier   TEXT    NOT NULL DEFAULT 'observation',
  policy_hash    TEXT    NOT NULL,
  policy_json    TEXT    NOT NULL,
  updated_at_ms  INTEGER NOT NULL
);

-- ⚠️ 契约硬要求：证明"客户端确认应用了哪一版策略"，是责任划分的关键证据
CREATE TABLE IF NOT EXISTS policy_ack_log (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  account_id         INTEGER NOT NULL,
  instance_id        TEXT    NOT NULL,
  policy_version     INTEGER NOT NULL,
  policy_hash        TEXT    NOT NULL,
  account_tier       TEXT    NOT NULL,
  account_day_index  INTEGER NOT NULL,
  applied_limits_json TEXT   NOT NULL,   -- 客户端上报的实际生效上限（须 ≤ 策略值）
  first_ack_at_ms    INTEGER NOT NULL,
  last_seen_at_ms    INTEGER NOT NULL,
  UNIQUE(account_id, instance_id, policy_version)
);
CREATE INDEX IF NOT EXISTS idx_ack_acc ON policy_ack_log(account_id, last_seen_at_ms);
```
> **隐私约束**：`target_hash` / `user_key_hash` / `content_hash` **只存哈希**（HMAC + `privacy_salt`，不得用无盐哈希）；**禁止**存储评论原文、回复原文、`sec_uid` 原文、Cookie、完整手机号（需求 NFR-7、红线 3）。
>
> **计费约束**：`charged_milli` 为整数毫单位，**禁止 REAL**（浮点误差会导致台账对不上）。时间一律整数 Unix 毫秒（`_ms`）。
>
> **证据约束**：`policy_snapshot_json` 必须记录**实际生效值**而非用户设置值——这是"只记设置值无法自证"的落地要求。

### 5.5 数据保留策略：明细 → 聚合 → 归档

| 数据 | 保留 | 理由 |
|---|---|---|
| `send_log` + `audit_config_changes`（明细） | `AUDIT_KEEP_DAYS=60` 天 | 举证窗口通常 1~2 个月；量最大 |
| `usage_report`（原始批次） | `USAGE_KEEP_DAYS=90` 天 | 幂等去重与对账；聚合完成即可清 |
| `stats_daily`（日聚合） | `STATS_KEEP_DAYS=400` 天 | 保留一年同比，**清理明细后看板数字不丢** |
| `policy_history` | `POLICY_HISTORY_KEEP_DAYS=730` 天 | 每次改动一行，量极小，长期留 |
| `ledger` / `credit`（钱） | **永久，绝不清理** | 财务凭证 |

**清理作业**（优先做成服务内置定时任务，随服务生命周期、有日志、不与 CLI 抢锁；cron 兜底）：
```bash
sudo tee /etc/cron.d/dy-license-retention >/dev/null <<'CRONEOF'
10 4 * * * dylicense /usr/bin/node /opt/dy-license/current/cli.js audit prune --yes >/dev/null 2>&1
20 4 * * * dylicense /usr/bin/node /opt/dy-license/current/cli.js db checkpoint >/dev/null 2>&1
30 4 * * * dylicense /usr/bin/node /opt/dy-license/current/cli.js audit usage >/dev/null 2>&1
CRONEOF
sudo chmod 644 /etc/cron.d/dy-license-retention
```
实现要点：① **小批删除**（每批 `LIMIT 5000` 循环），避免巨大事务长时间持锁；② 每批之间 `PRAGMA wal_checkpoint(TRUNCATE)`；③ **先聚合后删除**（`stats_daily` 落库才删明细）；④ 删除前校验该窗口"明细条数 vs 聚合条数"，不一致就**跳过并告警**，不要盲删。

### 5.6 磁盘占用估算与降级策略

```
每日新增 ≈ 明细条数/日 × 250 B × 1.8      # 250B/行（含索引，meta_json 按 120B 估）；1.8 为 WAL/碎片/页开销系数
明细稳态 ≈ 每日新增 × AUDIT_KEEP_DAYS      # 有清理就不会无限增长
总量     ≈ 明细稳态 + 聚合(≈80B/行) + 台账(≈150B/行) + WAL(≤DB_WAL_SIZE_LIMIT_MB) + 备份(库大小 × 14)
```

| 规模（`AUDIT_KEEP_DAYS=60`） | 明细稳态 | 聚合(400天) | 台账 | 合理预留 |
|---|---|---|---|---|
| 10 商家 × 300 条/日 | ≈80 MB | ≈12 MB | ≈2 MB | **1 GB** |
| 50 商家 × 300 条/日 | ≈405 MB | ≈58 MB | ≈9 MB | **2 GB** |
| 100 商家 × 500 条/日 | ≈1.35 GB | ≈200 MB | ≈30 MB | **4 GB** |
| 200 商家 × 500 条/日 | ≈2.7 GB | ≈400 MB | ≈60 MB | **8 GB** |

> 50GB 盘上预留 8GB 很安全（现有代理几乎不占磁盘）。**最易被忽略的是备份**：库涨到 1GB，备份目录就是 14GB —— 每月核对 `du -sh /opt/dy-license/backups`。

```bash
$rc audit usage                                   # 各表行数与占用
df -h / && du -sh /opt/dy-license/data /opt/dy-license/backups
sudo -u dylicense sqlite3 -readonly /opt/dy-license/data/license.db "select 'send_log',count(*) from send_log union all select 'cfg_change',count(*) from audit_config_changes union all select 'usage',count(*) from usage_report union all select 'ledger',count(*) from ledger;"
```

**磁盘满时的降级策略：先停明细，绝不停服务。** 服务一停，**策略下发、会话续期、扣费、卡密兑换全部停摆**——商家直接不可用，恢复后还要处理大量补报；而明细只是审计证据。所以降级顺序固定：

| 磁盘使用率 | 动作 |
|---|---|
| `≥ DISK_WARN_PCT` 75% | 告警；把 `AUDIT_KEEP_DAYS` 临时降到 `30`；立即跑一次 `audit prune` |
| `≥ DISK_DEGRADE_PCT` 88% | **降级模式**：停止写入 `send_log` / `audit_config_changes` / `usage_report`，保留 `ledger`、`credit`、`policy`、`policy_ack_log`；清理改每小时一次；上报返回 `202 Accepted` + `degraded:true` |
| `≥ DISK_HARD_PCT` 95% | **拒收新明细**：返回业务码 `disk_full`，客户端把明细囤进本地 `pending_reports.json`（**不当作失败丢弃**）；拒绝新建登录会话，只保留续期；`ledger` 仍可写 |
| 出现 `SQLITE_FULL` | 立即 `VACUUM INTO` 到别处 + `wal_checkpoint(TRUNCATE)`；`/` 确无空间时先删 `backups/` 最旧备份腾地方（备份可再生，业务数据不能） |

**为什么不是"先停服务"**：停服把可降级的运维事件升级成全量故障；且停服期间客户端持续累积补报，恢复瞬间形成写入尖峰，更容易把库搞坏。建议内置护栏（别只靠人盯）：
```js
const used = diskUsedPct('/')
if (used >= cfg.DISK_HARD_PCT && isDetailWrite) return res.accepted({ degraded: 'disk_full' })
if (used >= cfg.DISK_DEGRADE_PCT) detailWriteEnabled = false
```
人工应急：`$rc audit prune --keep-days 7 --yes && $rc db checkpoint` → `find /opt/dy-license/backups -name '*.db' -mtime +3 -delete` → `sudo journalctl --vacuum-size=128M` → `df -h / && $rc db check`。

## 6. HTTPS 与反向代理

### 6.1 为什么必须 HTTPS

客户端是纯 HTTP 客户端，登录密码、会话 token、**HMAC 签名密钥**都在请求/响应里。明文 HTTP 等于把这些直接暴露在同链路上（商家本机可能在公司网关/公共 WiFi 后）。**生产不接受 HTTP 直连。**

### 6.2 方案对比与端口规划

| | A. 反代 + 证书 | B. Node 直接监听 |
|---|---|---|
| 端口 | 应用 `127.0.0.1:18080`，Caddy/Nginx `9443/tcp` | Node `0.0.0.0:9443` + `https.createServer` |
| 证书续期 | ✅ 内建 / certbot timer | ❌ 自写钩子 + 重启服务 |
| 限流 / IP 白名单 / 访问日志 | ✅ 代理层统一做 | ❌ 全写进应用 |
| 与现有 443 冲突 | 不冲突 | 需自行处理，抢 80 还会打断续期 |
| 结论 | ✅ **推荐** | 仅临时联调 |

| 用途 | 端口 | 归属 |
|---|---|---|
| sing-box Reality / Hysteria2 | 443/tcp / 8443/udp | 现有，**不动** |
| 授权应用 | 127.0.0.1:18080 | 新增，仅回环 |
| 授权 HTTPS / 证书 HTTP-01 | **9443/tcp** / 80/tcp | 新增 / 空闲，仅签发时使用 |

### 6.5 方案 B（先跑通）与客户端连接方式

```bash
sudo -u dylicense mkdir -p /opt/dy-license/tls && cd /opt/dy-license/tls
sudo -u dylicense openssl req -x509 -newkey rsa:2048 -nodes -days 90 -keyout key.pem -out cert.pem \
  -subj "/CN=license.example.com" -addext "subjectAltName=DNS:license.example.com,IP:$(curl -sS ifconfig.me)"
sudo chmod 600 /opt/dy-license/tls/key.pem && sudo ufw allow 9443/tcp
```
`.env` 改 `HOST=0.0.0.0` + `TLS_CERT=/opt/dy-license/tls/cert.pem` + `TLS_KEY=/opt/dy-license/tls/key.pem`，让 `server.js` 在设置这两个变量时用 `node:https` 起服务。补证书：装 Caddy（§6.3）→ `.env` 改回 `HOST=127.0.0.1` → `PUBLIC_BASE_URL` 换新域名 → `systemctl restart dy-license`。

客户端存的就是 `PUBLIC_BASE_URL`：
```json
{
  "server": "https://license.example.com:9443",
  "serverFingerprint": "sha256/AbCd...=",
  "hmacSecret": "与服务端 HMAC_SECRET 相同",
  "deviceId": "本机生成的稳定 UUID",
  "reportIntervalSec": 300,
  "policyVersion": 1
}
```

| 场景 | server 写法 | 证书校验 |
|---|---|---|
| Caddy/Nginx + 正式证书（推荐） | `https://license.example.com:9443` | 正常校验证书链，无需额外配置 |
| 自签证书（临时） | `https://<VPS_IP>:9443` | 必须固定 `serverFingerprint`（`openssl x509 -in cert.pem -noout -fingerprint -sha256`），否则拒绝连接 |
| 纯 HTTP | ❌ 禁止 | 客户端应直接拒绝非 `https://` 地址 |

**给甲方的三条硬要求**：① 客户端只接受 `https://`；② 自签证书必须固定指纹；③ 换域名/换证书后给商家发新 `server` 配置，**不要靠"忽略证书错误"兜底**。


## 8. 监控与日志

### 8.1 日志格式与轮转

```json
{"ts":"2026-09-18T07:21:03Z","level":"info","evt":"heartbeat.ok","account":"demo001","policyVersion":4,"pendingReports":12}
{"ts":"2026-09-18T07:21:05Z","level":"info","evt":"report.batch","account":"demo001","rows":37,"charged":37,"balance":4463,"ms":18}
{"ts":"2026-09-18T07:22:10Z","level":"warn","evt":"policy_push_fail","account":"demo002","sentVersion":4,"ackVersion":2}
{"ts":"2026-09-18T07:23:00Z","level":"error","evt":"disk.degrade","usedPct":88.4,"mode":"drop_detail"}
```
**脱敏硬约束**：不打印 `password`、`token`、`HMAC_SECRET`、完整手机号、评论原文；`sec_uid` 只记哈希。
**日志量**：`info` 下每商家每轮上报约 1 行、每次心跳约 1 行 → 100 商家约 2900 行/日/来源 × 250B ≈ 1.5MB/日，可忽略。**`LOG_LEVEL=debug` 会按明细逐条打印**（100 商家 × 500 条/日 ≈ 15MB/日），排障后必须改回 `info`。

```bash
sudo mkdir -p /etc/systemd/journald.conf.d
sudo tee /etc/systemd/journald.conf.d/99-dy-license.conf >/dev/null <<'JEOF'
[Journal]
SystemMaxUse=512M
SystemMaxFileSize=64M
MaxRetentionSec=30day
JEOF
sudo systemctl restart systemd-journald && journalctl --disk-usage
```
用文件日志（`logs/`）时加 `/etc/logrotate.d/dy-license`，内容为 `daily / rotate 14 / maxsize 50M / missingok / notifempty / compress / delaycompress / copytruncate / su dylicense dylicense`，验证：`sudo logrotate -d /etc/logrotate.d/dy-license`（`-d` 只演练）。

### 8.2 健康检查端点

| 端点 | 鉴权 | 作用 | 返回 |
|---|---|---|---|
| `GET /healthz` | 无 | 存活：HTTP 栈在服务 | `200 {"ok":true,"uptime":1234}` |
| `GET /readyz` | 无（仅回环）/ Bearer | 就绪：DB 可读写、迁移完成、时钟偏移、磁盘状态 | `200 {"ok":true,"schema":1,"dbMs":0.8,"diskPct":41}` / `503` |
| `GET /metrics` | **必须**鉴权或仅内网 | 计数指标：心跳、扣费条数、拒绝数、上报积压、策略下发失败、审计表行数 | `200 text/plain` |
| `GET /version` | 无 | 版本与最低客户端版本 | `200 {"app":"1.0.0","minClient":"0.1.0"}` |

健康检查**不要**放 `/api/v1/` 下（会被鉴权/限流中间件拦）；`/metrics` 上公网必须加鉴权。

### 8.3 关键告警点

| 告警 | 阈值 | 检查命令 |
|---|---|---|
| 登录失败激增 / 账号锁定 | 5 分钟 > 30 次 / 出现 `login.lock` | `journalctl -u dy-license --since "5 min ago" \| grep -c 'login.fail'` |
| **上报积压** | pending > 200 持续 15 分钟 | `$rc stats --days 1 \| grep -i backlog`；`journalctl -u dy-license \| grep -c report.reject` |
| **审计表增长异常** | 日增 > 预期 2 倍或 > 200MB | `$rc audit usage`；`du -sh /opt/dy-license/data` |
| **策略下发失败** | 24h > 20 次，或单账号 ack 落后 > 2 个版本 | `journalctl -u dy-license --since "24 hours ago" \| grep -c policy_push_fail`；`$rc policy push --status` |
| 余额告警 | 剩余可发条数 < `MIN_BALANCE_ALERT_REPLIES` | `$rc stats --days 1 \| grep -i low` |
| 磁盘降级 / 磁盘占用 | 出现 `disk.degrade`/`disk.full` / `/` > 80% | `journalctl -u dy-license \| grep -E 'disk\.(degrade\|full)'`；`df -h /` |
| 服务重启 / 内存 | `NRestarts > 0` / `MemoryCurrent > 300M` | `systemctl show dy-license -p NRestarts -p MemoryCurrent` |
| DB 异常 / `SQLITE_BUSY` | `integrity_check` 非 ok / 10 分钟 > 5 次 | `$rc db check`；`journalctl -u dy-license --since "10 min ago" \| grep -c SQLITE_BUSY` |

```bash
sudo tee /usr/local/bin/dy-license-check.sh >/dev/null <<'CHECKEOF'
#!/usr/bin/env bash
set -u
FAIL=0
curl -fsS --max-time 5 http://127.0.0.1:18080/healthz >/dev/null || { echo "healthz FAIL"; FAIL=1; }

[ "${PF:-0}" -gt 5 ] && { echo "policy_push_fail=$PF"; FAIL=1; }
USED=$(df --output=pcent / | tail -1 | tr -dc '0-9')
[ "$USED" -gt 80 ] && { echo "磁盘使用 ${USED}%"; FAIL=1; }
[ "$FAIL" -eq 0 ] && echo OK || echo ALERT
exit $FAIL
CHECKEOF
sudo chmod 755 /usr/local/bin/dy-license-check.sh && sudo /usr/local/bin/dy-license-check.sh
echo '*/5 * * * * root /usr/local/bin/dy-license-check.sh >/dev/null 2>&1 || logger -t dy-license-alert "授权服务健康检查失败"' | sudo tee /etc/cron.d/dy-license-healthcheck >/dev/null
sudo chmod 644 /etc/cron.d/dy-license-healthcheck
```

**9.1 防火墙（只加不删）**
```bash
sudo cp /etc/ufw/user.rules /root/ufw-user.rules.bak.$(date -u +%Y%m%d)   # 先备份规则，再看现状
sudo ufw status numbered
sudo ufw allow 9443/tcp comment 'dy-license https'                        # 只新增
sudo ufw allow 80/tcp comment 'acme http-01'                              # 仅签证书期间
sudo ufw status verbose
```
四条禁令：❌ 不 `ufw --force reset`、不 `ufw disable`、不重排规则顺序；❌ 不动已有的 22/tcp、443/tcp、8443/udp；❌ 不 `iptables -F`；❌ 不改 `sshd_config` 后无条件 `systemctl restart ssh`。

**9.2 SSH 保持密钥登录**
```bash
sudo sshd -T | grep -Ei '^(permitrootlogin|passwordauthentication|pubkeyauthentication|port)'
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak.$(date -u +%Y%m%d)  # 改前备份
sudo sshd -t && sudo systemctl reload ssh        # 用 reload 而非 restart，并保留一个已登录会话
sudo systemctl is-active fail2ban && sudo fail2ban-client status sshd
```

**9.3 管理后台暴露面（优先级从高到低）**：① **SSH 隧道**（§7 末）——后台只听 `127.0.0.1`，公网零暴露，**首选**；② `ADMIN_IP_ALLOW=<你的固定公网IP>/32` + 反代 `allow/deny`（§6.4 已给示例）；③ 必须公网可用时：随机 `ADMIN_PATH` + 强制 HTTPS + `ADMIN_SESSION_TTL_HOURS=12` + 独立强密码。
```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://license.example.com:9443/admin/   # 必须 404/403
```

**9.4 限流（登录防爆破）**：应用层 `RATE_LIMIT_LOGIN_PER_MIN=10`（按 IP）+ `LOGIN_FAIL_LOCK_TIMES=5` / `_MINUTES=10`（按账号，FR-1.5）；代理层 Caddy/Nginx 限流（§6.3/§6.4），与应用层独立计；登录固定加 200–500ms 随机延迟，账号不存在与密码错误统一提示"账号或密码错误"（停用/到期才单独提示）。
```bash
sudo journalctl -u dy-license --since "1 hour ago" | grep 'login.fail' | awk -F'"ip":"' '{print $2}' | cut -d'"' -f1 | sort | uniq -c | sort -rn | head
```

**9.5 HMAC 密钥轮换（客户端不断服）**
```bash
NEW=$(openssl rand -hex 32); echo "新密钥（安全渠道发给商家客户端）: $NEW"
sudo -u dylicense sed -i "s|^HMAC_SECRET_PREV=.*|HMAC_SECRET_PREV=$(grep '^HMAC_SECRET=' /opt/dy-license/.env | cut -d= -f2-)|" /opt/dy-license/.env
sudo -u dylicense sed -i "s|^HMAC_SECRET=.*|HMAC_SECRET=$NEW|" /opt/dy-license/.env   # 旧值留在 PREV，两端都接受
sudo chmod 600 /opt/dy-license/.env && sudo systemctl restart dy-license
sudo journalctl -u dy-license --since "24 hours ago" | grep -c signature_mismatch      # 灰度观察 24 小时
sudo -u dylicense sed -i 's|^HMAC_SECRET_PREV=.*|HMAC_SECRET_PREV=|' /opt/dy-license/.env   # 全量换完后清空 PREV
sudo systemctl restart dy-license
```
**顺序不能反**：清 PREV 前必须确认客户端都已换新密钥，否则它们会立刻"签名校验失败"并停机。建议每 12 个月轮换一次，或**怀疑泄漏立即轮换**。

**9.6 备份加密**
```bash
sudo apt-get install -y age && age-keygen -o /root/age-key.txt && chmod 600 /root/age-key.txt
AGE_PUB=$(grep 'public key:' /root/age-key.txt | awk '{print $NF}'); TS=$(date -u +%Y%m%d)
sudo -u dylicense sqlite3 /opt/dy-license/data/license.db ".backup '/tmp/dy-$TS.db'"
age -r "$AGE_PUB" -o /opt/dy-license/backups/license-$TS.db.age /tmp/dy-$TS.db
shred -u /tmp/dy-$TS.db 2>/dev/null || rm -f /tmp/dy-$TS.db
sudo chown dylicense:dylicense /opt/dy-license/backups/license-$TS.db.age
age -d -i /root/age-key.txt -o /tmp/restore.db /opt/dy-license/backups/license-$TS.db.age   # 恢复时解密
```
上面把明文库放在 `/tmp` 只是中转，完成后**必须立即 `shred -u`**（已包含在命令里）；若中途失败，补跑 `sudo rm -f /tmp/dy-*.db`。备份含全部账号、台账与审计明细，泄漏 = 数据泄漏。**私钥与备份不要放同一台机器**，至少 `scp` 一份到本地保管。

**9.7 加固自检**
```bash
sudo ss -tulnp | grep -E ':(18080|9443)\b'     # 18080 必须是 127.0.0.1 而非 0.0.0.0
sudo stat -c '%a %U:%G %n' /opt/dy-license/.env /opt/dy-license/data /opt/dy-license/backups
sudo systemctl is-active fail2ban; sudo ufw status | head -5; $rc db check
```

## 10. 升级与回滚

### 10.1 版本发布流程

```bash
V=1.0.1
sudo -u dylicense mkdir -p /opt/dy-license/releases/$V
sudo rsync -a --delete /tmp/license-server-$V/ /opt/dy-license/releases/$V/
sudo chown -R dylicense:dylicense /opt/dy-license/releases/$V && sudo find /opt/dy-license/releases/$V -type f -exec chmod 640 {} \;
sudo -u dylicense node --check /opt/dy-license/releases/$V/server.js && sudo -u dylicense node --check /opt/dy-license/releases/$V/cli.js
$rc db backup --out /opt/dy-license/backups            # 迁移前必做
sudo ln -sfn /opt/dy-license/releases/$V /opt/dy-license/current
sudo systemctl restart dy-license && sleep 2
sudo systemctl is-active dy-license && curl -sS --max-time 5 http://127.0.0.1:18080/version; echo && $rc db version
```

### 10.2 停机升级 vs 蓝绿

| 方案 | 适用 | 代价 | 建议 |
|---|---|---|---|
| **停机升级（切软链 + restart）** | 本场景 | 2~5 秒不可用；客户端心跳/上报自动重试，不影响计费正确性 | ✅ **采用** |
| 蓝绿双实例 | 高频发布 | **SQLite 单写者，两实例不能同时写一个库**；需独立 DB + 同步，复杂度极高 | ❌ 不建议 |

发布窗口建议凌晨 03:00–05:00（北京时间）；升级前后各跑一次 §12.3 的代理自查。

### 10.3 schema 迁移回滚策略

1. **迁移只做加法**（§5.1）→ 旧代码能读新库，回滚只需切回旧代码，**不用回滚数据库**。
2. 回滚前看 `$rc db version`：`schema_version` 大于旧代码期望值 → 在 unit 里临时加 `Environment=DY_LICENSE_ALLOW_DOWNGRADE=1`（确认新表只被新功能使用），或按 §5.2 恢复 `pre-migrate-*.db`。
3. 审计表体积大，回滚时**不要**连带恢复旧审计数据，只恢复业务表（从备份 `ATTACH` 后按表恢复即可）。
```bash
sudo ln -sfn /opt/dy-license/releases/1.0.0 /opt/dy-license/current && sudo systemctl restart dy-license && $rc db version
```

### 10.4 客户端最低版本强制升级

- 服务端在每个心跳/上报响应里带 `minClient` 与 `policy_version`。
- 客户端版本 < `MIN_CLIENT_VERSION` → 返回 `426` + 错误码 `SERVER_VERSION_UNSUPPORTED`。
- 客户端收到 `SERVER_VERSION_UNSUPPORTED` 时**停止自动回复（不扣费）**并弹升级提示，而不是继续跑旧逻辑。
- 节奏：先保持旧值跑 3–7 天（`$rc stats --days 7` 看版本分布），确认绝大多数已升级再抬高；抬升 = 改一次 `.env` + `systemctl restart`。

## 11. 故障排查手册

### 11.1 服务起不来

```bash
sudo systemctl status dy-license --no-pager -l && sudo journalctl -u dy-license -n 80 --no-pager
sudo -u dylicense node --check /opt/dy-license/current/server.js
sudo -u dylicense env $(grep -v '^#' /opt/dy-license/.env | xargs) node /opt/dy-license/current/server.js  # 前台直跑看完整堆栈
```
常见原因：`.env` 带引号/`export`（systemd 不解析）→ 去掉；`data/` 属主不是 `dylicense` → §2；端口被占 → `sudo ss -tlnp | grep 18080`；`ExecStart` 路径错 → `command -v node`；`schema newer than code` → §10.3。

### 11.2 客户端登录失败

```bash
curl -sS -X POST https://license.example.com:9443/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"demo001","password":"<测试密码>","deviceId":"test-dev"}' -i | head -20
sudo journalctl -u dy-license --since "10 min ago" | grep -E 'login\.(fail|lock)'
$rc account show --user demo001 && $rc session list --user demo001
```
常见原因：账号停用/到期；密码错 5 次锁 10 分钟；`MAX_DEVICES=1` 且另一台在线（`$rc session revoke --user demo001`）；客户端 `server` 少了 `:9443`。

### 11.3 客户端报"签名校验失败"

```bash
sudo journalctl -u dy-license --since "1 hour ago" | grep -c signature_mismatch
sudo grep '^HMAC_SECRET' /opt/dy-license/.env | sha256sum    # 与客户端打印的密钥指纹比对，必须一致
```
常见原因：两端 `HMAC_SECRET` 不一致（换机器时漏改）；刚轮换但客户端未换（§9.5）；**反代改写了响应体或加了压缩**（确认 `proxy_pass` 原样透传，Nginx 不要开 `sub_filter`）；签名覆盖 `Date` 头而两端时间不同步（§11.8）。

### 11.4 余额不扣 / 扣错（按条计费口径）

```bash
$rc ledger tail --user demo001 -n 50
sudo journalctl -u dy-license --since "2 hours ago" | grep -E 'report\.batch|charged' | head -20
sudo -u dylicense sqlite3 -readonly /opt/dy-license/data/license.db "select type,sum(amount) from ledger where account_id=(select id from account where username='demo001') group by type;"
$rc credit balance --user demo001
```
判定顺序：① **只扣成功发送的条数**——失败/被风控拦截/未命中规则**不扣**，商家说的"发了没扣"多数是这类；② **明细尚未上报**——客户端每 300 秒批量上报一次，期间余额不变属正常；③ **幂等去重**——同一 `report_id` 重复上报只扣一次（设计如此，不是漏扣）；④ **断网宽限期**——期间不发送不扣费，恢复后补报补扣，账单会集中出现；⑤ **单价刚改**——`CREDIT_PER_REPLY` 只影响之后，历史台账不动；⑥ `ledger` 与 `credit.balance` 不一致 → 用 `$rc credit grant --amount 0 --reason "对账修正"` 走显式台账修正，**绝不直接 UPDATE 余额**。

### 11.5 上报积压 / 策略下发失败

```bash
$rc stats --days 1 | grep -i backlog; $rc policy push --status
sudo journalctl -u dy-license | grep -E 'report\.(reject|dup)|policy_push_fail' | tail -20
sudo -u dylicense sqlite3 -readonly /opt/dy-license/data/license.db "select count(*),min(received_at) from usage_report;"
```
常见原因：客户端离线囤在 `pending_reports.json`，联网补报（正常）；`report_id` 冲突判重（幂等生效，正常）；**上报体超限被反代拒**（`client_max_body_size` / Caddy `max_size` 调到 4MB）；磁盘降级期间返回 `degraded:true`（§5.6）；策略下发失败多为客户端长期离线或 `policy_version` 未确认（`$rc policy show --user <名> --history` 核对）。

### 11.6 `SQLITE_BUSY` / 锁冲突

```bash
sudo journalctl -u dy-license --since "30 min ago" | grep -c SQLITE_BUSY
sudo lsof /opt/dy-license/data/license.db*
sudo -u dylicense sqlite3 -readonly /opt/dy-license/data/license.db "PRAGMA journal_mode; PRAGMA busy_timeout;"
```
常见原因：有人开着 `sqlite3` 交互式写事务不放（**排查时禁止开事务不动**）；`journal_mode` 不是 `wal`；有第二个进程/脚本在写同一个库（**单写者原则**）；`DB_BUSY_TIMEOUT_MS` 太小 → 调 `8000` 重启；清理作业用了超大事务 → 改小批（§5.5）。

### 11.7 磁盘满

```bash
df -h / && du -sh /opt/dy-license/* /var/log/journal 2>/dev/null | sort -h
du -sh /opt/dy-license/backups && ls -lt /opt/dy-license/backups | head; journalctl --disk-usage
$rc audit prune --keep-days 7 --yes && $rc db checkpoint
sudo journalctl --vacuum-size=256M
find /opt/dy-license/backups -name '*.db' -mtime +3 -delete
df -h / && $rc db check
```
清理顺序：先删**可再生的**（旧备份、journal）→ 再缩**可降级的**（审计明细）→ 最后才动业务数据。**清理前确认 `/opt/dy-license` 不是 sing-box 的目录**（sing-box 在 `/etc/sing-box`）。

### 11.8 时间不同步导致签名失败

```bash
timedatectl status; date -u +%Y-%m-%dT%H:%M:%SZ
timedatectl timesync-status 2>/dev/null || systemctl status systemd-timesyncd --no-pager
sudo timedatectl set-ntp true && sudo systemctl restart systemd-timesyncd
sudo sed -i 's/^#\?NTP=.*/NTP=ntp.aliyun.com time.cloudflare.com/' /etc/systemd/timesyncd.conf   # 默认 NTP 被机房屏蔽时换源
sudo systemctl restart systemd-timesyncd && timedatectl status
```
签名有效期窗口建议 ±300 秒，超出即拒。**不要用 `date -s` 手工改时间**，会造成签名窗口跳变，比不同步更糟。

### 11.9 排查速查表

| 症状 | 第一条命令 | 最可能原因 |
|---|---|---|
| 状态反复 `activating` | `journalctl -u dy-license -n 50` | `.env` 解析失败、端口占用、DB 权限 |
| 公网 502 / 连不上 | `sudo ss -tlnp \| grep 9443` | 反代没起、ufw 没放行 9443 |
| 登录 200 但客户端不认 | `curl -sS .../api/v1/auth/login -i` | 响应体被反代改写/压缩 |
| 心跳正常但余额不变 | `$rc ledger tail -n 20` | 明细尚未上报（300s 一轮）或全是失败未计费 |
| 商家说"发了很多但没扣" | `$rc audit usage` + `$rc stats --user <名>` | 多为失败/风控拦截，本就不计费 |
| 明细暴涨 | `$rc audit usage` | 客户端重试造成重复上报（查 `report_id` 幂等）或风控放宽 |
| 大量 `SERVER_VERSION_UNSUPPORTED` | `$rc stats --days 1` | `MIN_CLIENT_VERSION` 抬早了 |
| `SQLITE_FULL` | `df -h /` | 磁盘满，走 §5.6 降级 |

## 12. 与现有服务共存的注意事项

**前提：这台 VPS 上的 sing-box 是你的出口，它挂了你自己也上不了网。任何操作都不能以"先停了再说"为思路。**

### 12.1 资源隔离与连接数（按条计费后连接更活跃）

| 维度 | 做法 |
|---|---|
| 内存 | `MemoryHigh=320M` / `MemoryMax=384M`，Node 堆上限 256MB |
| CPU / IO | `CPUQuota=60%`、`IOWeight=50`；清理与聚合放凌晨且小批执行 |
| 磁盘 | journald 上限 512M；备份保留 14 天；审计明细按期清理；每月核对 `df -h /` |
| 带宽 | 心跳/上报每商家每分钟几 KB，可忽略；**外同步备份必须限速**：`rsync --bwlimit=5000` |

心跳仍 60 秒一次，但**上报从"顺带"变成常态**（默认 300 秒一批，突发时更频繁）。上线前后各确认一次，重点看**连接数上限**——`nf_conntrack_max` 偏小（如 65536）而并发长期接近上限时，会出现**代理侧随机丢包/新连接失败**，极易误判为"线路变差"：
```bash
sudo ss -s; sudo ss -tn state established | wc -l                  # 连接概览与已建立连接数（对比上线前）
sysctl net.core.somaxconn net.ipv4.tcp_max_syn_backlog net.netfilter.nf_conntrack_max
sudo tc qdisc show; sudo iptables -t mangle -S 2>/dev/null | head  # 是否有队列限速/流量整形
sudo ss -tnp | grep -c ':9443'                                     # 授权服务自身连接数
sudo journalctl -u sing-box --since "1 hour ago" -p warning --no-pager | tail -5
```
若确认相互影响：① 把 `REPORT_INTERVAL_SEC` 调到 `600` 降低请求频次；② 确认客户端失败重试是**指数退避**而非紧凑轮询；③ 调大 `nf_conntrack_max`（`sysctl` + `/etc/sysctl.d/` 持久化）。**不要**为了腾资源去改 sing-box 配置。

### 12.2 端口规划、网络服务与配置备份

| 服务 | 端口 | 处置 |
|---|---|---|
| sing-box Reality / Hysteria2 | 443/tcp / 8443/udp | **绝不动** |
| SSH / 授权应用 / 授权 HTTPS | 22/tcp / 127.0.0.1:18080 / 9443/tcp | 绝不动 / 新增仅回环 / 新增 |
上线前复查 `sudo ss -tulnp | sort -k5`，逐条比对。

❌ 不执行 `systemctl restart systemd-networkd`、`netplan apply`、`systemctl restart networking`、`/etc/init.d/networking restart`、`reboot`。✅ 改完防火墙只做 `sudo ufw status` 验证，无需重载网络。✅ 授权服务重启用 `systemctl restart dy-license`，只影响自己。✅ 万一必须重启网络：先确认有带外控制台（VNC/救援模式），否则可能失联。

```bash
sudo mkdir -p /root/net-backup && cd /root/net-backup && D=$(date -u +%Y%m%d)
sudo cp -a /etc/ufw /root/net-backup/ufw.$D && sudo cp -a /etc/sing-box /root/net-backup/sing-box.$D
sudo cp -a /etc/ssh/sshd_config /root/net-backup/sshd_config.$D
sudo sh -c "iptables-save  > /root/net-backup/iptables.$D.rules" && sudo sh -c "ip6tables-save > /root/net-backup/ip6tables.$D.rules"
sudo systemctl status sing-box --no-pager | head -5 && ls -l /root/net-backup/
```

### 12.3 上线全程的"代理不受影响"自查与回退

```bash
systemctl is-active sing-box
ss -tlnp | grep -q ':443 '  && echo "443 仍被监听"
ss -ulnp | grep -q ':8443 ' && echo "8443/udp 仍被监听"
sudo journalctl -u sing-box --since "10 min ago" -p warning --no-pager | tail -5
```
每个关键步骤后执行，全绿才继续。**回退顺序（从最小改动开始）**：① `sudo systemctl stop dy-license`（只停新服务，代理立刻恢复原状）→ ② `sudo ufw delete allow 9443/tcp`（撤销新增规则）→ ③ `sudo systemctl stop caddy`（或 `nginx`）→ ④ 恢复 `/root/net-backup/` 配置（仅前 3 步无效时）。**现有代理任务不要被覆盖**：`/etc/cron.d/vps-maintenance`（每 20 天自动更新 sing-box）不覆盖不删除；fail2ban 的 `sshd` jail 不要关；sing-box 升级前后各跑一次本自查。
