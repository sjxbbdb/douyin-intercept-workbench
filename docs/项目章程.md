## 一、一句话定位

> ### 一个可承载多种「专业分化工作流」的 Agent 平台。
>
> 每个专业领域（本地生活、家居、教育、房产、医美…）是**一个工作流包**：
> 它声明该领域的**线索判据、业务规则、话术策略、合规边界、成功定义**，由 **Agent 编排执行**。
> **「抖音截流自动回复」是内置的第一个工作流包，不是产品的全部。**

### 1.1 "Agent 平台"这三个字各自的含义

| 词 | 含义 | 不是什么 |
|---|---|---|
| **Agent** | 承载形态。理解商家意图 → 选择工作流 → 编排步骤 → 执行 → 汇报。**默认开启** | 不是"聊天窗口加几个按钮"；不是可选增值项；不是把规则引擎换个名字 |
| **平台** | 加一个新领域 = **加一个包**，核心代码零改动 | 不是"一套代码卖多家"；不是多租户 SaaS（那是部署形态，见 §四） |
| **工作流** | 一次完整的业务过程（识别线索 → 判断价值 → 组织话术 → 合规校验 → 发送 → 沉淀） | 不是"一个自动化脚本"；不是单步操作 |

### 1.2 "专业分化"到底指什么

这是整个定位里最容易被读空的四个字。它指的是一件很具体的事：**同一个问题，不同行业要完全不同的处理**。

例：客户问「多少钱」

| | 本地生活（团购） | 家居定制 | 教育培训 |
|---|---|---|---|
| **什么信号值得接** | "有没有优惠""几个人" | "多少钱一平""什么时候量房" | "几岁能上""多少钱一期" |
| **必须收集** | 就餐人数、时间 | 房型、面积、城市 | 学员年龄、基础 |
| **合规禁语** | 不得承诺具体折扣 | 不得承诺工期与总价 | ⚠️ **不得承诺升学/提分效果** |
| **高风险信号** | 差评、投诉 | 工期质疑 | 价格敏感 + 效果追问 |
| **话术风格** | 直接、促单 | 专业、先问需求 | 谨慎、先建立信任 |
| **成功定义** | 留下联系方式 | 约到量房 | 约到试听 |

**这六行差异就是"专业分化"的全部内容。** 平台的价值在于：**这六行由包声明，核心一行不改。**

> ⚠️ **反过来说**：如果实现结果是"每加一个行业都要改核心代码"，
> 那么无论功能做得多好，这个项目都**不是平台**，本文件 §一 的定位就没有兑现。

## 二、为什么是 Agent，而不是"规则引擎 + 界面"

这不是偏好问题，是**能力边界**问题。

| 能力 | 规则引擎 | Agent |
|---|---|---|
| "贵不贵" 与 "多少钱" 视为同一意图 | 需商家把两种说法**都**配成关键词 | 语义理解，天然同一 |
| "这条要不要回" | 无法判断（只能判断"命中了关键词"） | 可判断语义是否值得回复 |
| 从候选话术里挑更合语气的一条 | 只能随机轮换 | 可按上下文选择 |
| 商家说"南京这边问价的挑几个回，别超过 10 个" | 无法理解 | 映射为结构化查询与批次上限 |
| 抽出结构化线索（地域/预算/时间） | 只能存原文 | 可抽取为字段，供筛选与跟进 |
| **行业差异** | 每个行业重写一套规则 | 换一个包 |

**规则引擎没有被废弃，它降级为 Agent 的一个组件**：负责预筛候选、执行硬校验。
**它擅长的（确定、可测、可复现）继续由它做；它做不到的（语义、编排、跨域）交给 Agent。**

## 三、🔴 三条红线及其平台化表述

红线**一条都没有变**。定位修正后它们的**作用范围扩大**：从"约束客户端代码"扩大为
**"约束客户端代码 + 约束每一个工作流包 + 约束 Agent 的每一次决策"**。

### 红线 1：安全上限由服务端下发，客户端与工作流包都只能调低

- 权威数值在 `shared/protocol.md` §4.6 的 `tier_table`——**全系统唯一来源**
- 客户端**只能更保守**；**工作流包同样只能更保守**（详见 `plans/C-工作流包契约.md` §二 约束 3）
- 观察期（第 1–3 天）日上限为 0，**不可跳过、不可由包覆盖**
- 🆕 **平台化补充**：工作流包**无权读写**任何安全数值。
  包的声明中出现 `daily_max` / `min_interval_ms` / `content_similarity_max` / `active_hours` /
  `sending_enabled` / `circuit_*` 等键名 → **拒绝加载**（`PACK_FORBIDDEN_KEY`）

### 红线 2：只对平台确认成功的发送计费

判据不变：

```
verdict = sent_confirmed
且 confirm_signal = platform_response     ← DOM 判断不算，必须拿到平台响应体
且 platform_status_code = 0
且 未超当日策略上限
且 该 send_id 未计费过
```

- ⚠️ **空响应 = 风控拒绝**，不得标记成功
- ⚠️ `send_id` 必须在**发送前**生成并落盘（幂等键 + 计费键）
- 🆕 **平台化补充**：计费按 `action_kind` 分派（`send` / `compute` / `llm`）。
  **红线 2 的判据专属于 `send`**；`compute`（如自动剪辑）没有"平台确认成功"这个信号，
  其计费见 §五 与 `plans/C-工作流包契约.md` §七

### 红线 3：审计必须记录真实生效的策略值与决策依据

- 每次发送与配置变更留痕，审计须含**实际生效的策略版本与生效值**
- **隐私边界**：只上传哈希与计数，**绝不上传**评论原文、回复内容原文、`sec_uid` 原文
- 审计本地与服务端**双写**，客户端不可篡改服务端副本
- 🆕 **平台化补充**：Agent 参与决策后，审计还须回答
  **"这条回复是哪条工作流的哪一步、由哪个决策产生的"**，因此必须记录：
  `pack_id` · `pack_version` · `prompt_version` · `policy_version` · `model.version`

## 四、系统形态（两个程序 + 一个包仓库）

```
┌─ 商家电脑（Windows）──────────────────┐      ┌─ 厂商服务器（Linux）──────────┐
│                                       │      │                              │
│  商家已登录的专用 Chrome ◄──CDP 驱动──┐ │      │  license-server              │
│                                      │ │      │   ├ 授权 / 积分台账           │
│  client（Agent 平台客户端）           │ │ 签名 │   ├ 心跳与上报接收            │
│   ├ agent/   Agent 运行时（状态图）    │ │◄────►│   ├ 管理后台（厂商看）        │
│   ├ packs/   工作流包加载器            │ │HTTPS │   ├ 命令行（开号/充值/卡密）   │
│   ├ tools/   工具层（10 个粗粒度工具）  │ │      │   └ 策略权威（tier_table）    │
│   ├ safety/  护栏（硬闸门，代码 if）    │ │      │                              │
│   ├ platform/ 平台操作知识             │ │      │  数据：node:sqlite 单文件     │
│   ├ adapters/ 业务动作实现             │ │      │  依赖：零                     │
│   ├ core/    CDP 通道（唯一一条 WS）   │ │      └──────────────────────────────┘
│   ├ license/ 与服务端通信              │ │
│   ├ host/    单写者存储 / 队列 / 调度   │ │      ┌─ 包仓库 packs/ ──────────────┐
│   └ ui/      对话界面 + 图形界面（降级）│ │      │  _template/     新包起点      │
└───────────────────────────────────────┘      │  douyin-intercept/ 内置包 1   │
                                               │  <你的领域>/                  │
                                               └──────────────────────────────┘
```

**三条形态约束**：

| # | 约束 | 理由 |
|---|---|---|
| 1 | `license-server/` 与 `client/` **不得互相 require** | 只能通过 `shared/protocol.md` 定义的 HTTP 接口通信；两端可以独立发版 |
| 2 | 工作流包**不得包含可执行代码** | 包来源不可信是前提。声明式是唯一能同时做到"可扩展"与"可审计"的形态 |
| 3 | **服务端不装 Agent 框架** | Agent 跑在客户端；服务端零依赖是它最大的运维优势 |

## 五、计费模型（`action_kind`）

需求要求"自动回复按成功条数计费"，而**需求 5 的自动剪辑"也是消耗积分制"**——
但剪辑**没有"平台确认成功"这个信号**。直接套用红线 2 会产生两种坏结果之一：
剪辑失败也算钱，或剪辑无法计费。

**因此计费按动作类别分派**：

| `action_kind` | 适用动作 | 计费依据 | 佐证 | 本期状态 |
|---|---|---|---|---|
| `send` | 评论 / 弹幕 / 私信 | 平台响应体 `platform_status_code = 0` | `publish-verifier` | ✅ 已实现 |
| `compute` | 视频剪辑、渲染等算力动作 | **实测资源消耗** | 消耗证明（产物哈希 + 时长） | ⚠️ 只留契约 |
| `llm` | 推理类 | 上游 API 返回的 `usage` | `decision_log.usage` | ⚠️ 只留契约 |

**红线 2 的准确边界**：

> **可观测平台结果的动作**（`send`）只对平台确认成功计费；
> **不可观测平台结果的算力动作**（`compute`）按**实际消耗**计费，
> 且必须能在事后用客观证据复现该次消耗。

三者**共同的底线不变**：`action_id` 在动作开始前生成并落盘、失败一律不计费、
计费单位由**服务端**核算（客户端只上报证据，不采信客户端算出的金额）。

> ⚠️ **本节结论中"自动剪辑的定价口径"（按次 / 按秒 / 按输出时长）属商业决策，需甲方确认。**
> 本文件只保证**契约能承载**，不代替定价。

## 六、什么是"成功"（平台级定义）

平台必须能承载不同工作流对"成功"的不同定义。因此分两层：

| 层 | 名称 | 由谁定义 | 作用 |
|---|---|---|---|
| **计费成功** | `sent_confirmed` | **平台**（红线 2，不可协商） | 决定是否扣积分 |
| **业务成功** | `outcome.goal` | **工作流包** | 决定如何汇报与统计（如 `collect_contact` / `appointment_booked`） |

⚠️ **两者不得混用**：包不能自定义"什么算计费成功"，
平台也不能假定"发出去了"就等于"业务做成了"。

## 七、平台层 / 领域层 / 运维层 —— 文档与代码的共同骨架

**这是本平台最重要的结构性约定。** 13,000 行文档之所以需要治理，根本原因是
**平台知识与领域知识混在一起写**——于是每加一个领域，都要动平台文档。

| 层 | 回答什么问题 | 变化频率 | 代码位置 | 文档位置 |
|---|---|---|---|---|
| **① 平台层** | 与任何行业无关的机制：契约、计费、审计、安全、Agent 运行时、包机制 | **几乎不变** | `client/agent` `client/packs` `client/tools` `client/core` `client/host` `client/license` `shared/lib` `license-server` | `shared/protocol.md` `shared/测试策略.md` `shared/开发规范.md` `shared/安全与合规要求.md` `shared/AI协作开发指引.md` `shared/术语与选型基准.md` `docs/架构说明.md` `docs/部署指南-服务端.md` |
| **② 领域层** | 针对某个专业领域：线索判据、规则、话术、合规、成功定义 | **随领域增加** | `client/platform`（平台操作知识）`packs/<domain>` | `packs/<domain>/` 下的包文档；`docs/抖音工作流包需求规格.md` |
| **③ 运维层** | 厂商怎么卖、怎么开号、怎么部署、怎么排障 | 随商业策略 | `license-server/admin` `license-server/cli.js` | `docs/部署指南-服务端.md` `docs/合作方须知.html` |

### ⚠️ 三条分层纪律（违反即视为文档缺陷）

1. **平台层文档不得出现任何行业专有名词。**
   出现「抖音」「评论」「弹幕」「直播间」等词，说明该内容属于领域层，必须移出。
2. **领域层文档不得重复描述平台机制。**
   包的文档只说"本领域要什么"，不说"发送怎么计费、观察期多长"——那是平台的事，且会随平台改动而过期。
3. **任何文档必须在开头声明自己属于哪一层。**
   没有层声明的文档，读者无法判断"这条规则适不适用于我的领域"。

> **实现要求**：`docs/架构说明.md` 的目录树必须与本节一致；
> `README-DEV.md` §文档分层与权威边界 必须能回答"我这个问题该看哪份文件"。

## 八、明确不做的事（边界）

| # | 不做 | 理由 |
|---|---|---|
| 1 | **不做通用 Agent 框架** | 本平台面向"专业分化工作流"，不做"什么都能干"的通用体。领域知识必须显式声明，不允许靠模型即兴发挥 |
| 2 | **不做无限量发送** | 产品定位是「控制节奏，让账号活得长」。这是红线 1 的存在理由 |
| 3 | **不绕过验证码 / 滑块 / 风控** | 遇风控即熔断。不可协商 |
| 4 | **不读取导出 Cookie / Token / 密码** | 用商家已登录的浏览器，不接管其凭据 |
| 5 | **不让工作流包执行代码** | 包来源不可信。声明式是平台可扩展的前提（§四 约束 2） |
| 6 | **不把硬规则交给模型判断** | 观察期禁发、日上限、最小间隔必须是代码里的 `if`。**概率模型不承担确定性义务** |
| 7 | **不公开生成话术并直接发送** | 内容级风控拦得住字面、拦不住语义。Agent 只能**从候选池中选择** |
| 8 | **不做多租户 SaaS** | 当前部署形态是"一商家一客户端 + 一个共享授权中心"。多租户是另一件事，不在本平台范围内 |
