## 〇、重写与稳定的矛盾，以及解法

**矛盾**：完全重写会丢弃原作者的抖音 DOM 知识（可见 comment-list 判定、`scrollIntoView` 后延迟读坐标、note 帖浮层、Enter 三段式按键、`status_code:0` 判据……）。这些是**真账号真页面反复试错**换来的，重写无法凭空复现，且每次试错都消耗真实账号风险。

**解法：旧代码降级为"活参考 + 测试基线"，不删除。**

1. 旧代码整体移入 `legacy/`，**只读、不引用、不构建**，但保留在仓库里作为行为规格（behavior spec）。
2. 新实现的每一个 DOM 交互原语，**必须**在 `legacy/` 中找到对应实现并逐条对照（PR 里贴对照行号）。
3. 建**离线回归测试**：录下真实页面 HTML 快照存 `test/fixtures/*.html`，断言选择器仍能命中、坐标读取表达式仍能返回有效值。**不需要登录、不需要联网、不碰真账号**，可随时跑。
4. 选择器全部集中在一张表，附 `lastVerifiedAt`（最后人工验证日期）与 `confidence`（置信度）。抖音改版时先跑测试，定位失效自动标红。

> 这条是"稳定"从口号变成可验证指标的关键。

## 一、目标的"稳定"定义（可验收）

甲方要求"CDP 层要稳定"，但"稳定"必须落成数字，否则无法判断是否达成：

| 指标 | 定义 | 目标 |
|---|---|---|
| S-1 长稳 | 连续运行 72 小时不崩溃 | 无未捕获异常退出 |
| S-2 自愈 | 单点故障（标签页被关、Chrome 重启、网络抖动）后自动恢复 | 自动恢复率 ≥ 95%，无需人工 |
| S-3 可观测 | 任何失败都能定位到具体阶段与原因 | 每个任务有阶段化日志与失败归因码 |
| S-4 改版韧性 | 抖音改版后修复所需改动文件数 | **1 个**（选择器注册表） |
| S-5 幂等 | 进程重启、重复上报、崩溃恢复不产生重复发送或重复扣费 | 零重复 |
| S-6 隔离 | 一个账号实例故障不影响其他实例 | 故障不跨实例传播 |

**S-4 是架构约束**：如果选择器散落在多处，这条永远达不到。这是选择器注册表存在的原因。

## 三、客户端内部：一次采集/回复任务的完整路径

以"评论区命中关键词 → 自动回复"为例，展示分层职责与**失败归因点**：

```
① 调度器  scheduler
   从实例队列取任务 → 检查积分态/急停/频控/日上限
   ↓ 拒绝则记 reason: quota_exceeded | emergency_stop | credit_exhausted
② 适配器  adapters/comment
   组装"打开视频 → 展开评论区 → 找目标评论 → 激活编辑器 → 发送"
   ↓ 每步产出 StepResult{ok, stage, reason}
③ 平台层  platform
   把步骤翻译为选择器 + 交互原语（点击/滚动/输入/按键）
   ↓ 选择器未命中 → reason: selector_miss:<key>  ← S-4 的关键
④ 核心层  core/browser-host
   独占 WS，发 CDP 命令，处理超时/重连/标签页重建
   ↓ 连接断开 → 自动重建，任务回到 queued 而非 failed
⑤ 判定    platform/publish-verifier
   嗅探 comment/publish 响应体，status_code:0 才算成功
   ↓ 空响应 → 风控拒绝，熔断并暂停该实例
⑥ 结算    写本地任务状态（原子）→ 记本地统计 → 标记待上报
```

**每一层失败都带 `stage` 与 `reason`**（S-3），UI 能直接显示"卡在哪一步、为什么"。

## 四、多实例隔离模型（甲方选定的形态）

一客户端管多抖音号，隔离维度：

| 资源 | 隔离方式 |
|---|---|
| Chrome 配置 | `instances/<id>/chrome-profile/`，每实例独立 `--user-data-dir` 与 `--remote-debugging-port` |
| 数据 | `instances/<id>/*.json`（队列、历史、统计、运行态） |
| CDP 连接 | 每实例一条独立 WS，由一个 `browser-host` 实例持有 |
| 调度 | 每实例独立频控/日上限/熔断窗口 |
| 授权 | 实例归属商家账号，共用该商家的积分池 |
| 故障 | 单实例异常**不传播**（S-6）：`browser-host` 按实例隔离，崩溃只重建该实例 |

**端口分配**：基线 9222，实例 N 用 `9222 + N`（可配），启动前探测占用。

## 五、存储设计

### 服务端（node:sqlite）

```sql
-- 商家账号
CREATE TABLE account(id, username UNIQUE, pass_hash, salt, status,
                     plan_id, created_at, expires_at, max_sessions);
-- 积分余额（单一真相）
CREATE TABLE credit(id, account_id UNIQUE, balance, updated_at);
-- 流水台账（只增不改）
CREATE TABLE ledger(id, account_id, type, amount, balance_after,
                    ref, operator, created_at);   -- type: recharge|consume|grant|refund
-- 会话
CREATE TABLE session(token_hash, account_id, device_id, issued_at,
                     last_seen_at, expires_at, revoked);
-- 套餐
CREATE TABLE plan(id, name, hours, credits, price, is_default);
-- 充值码
CREATE TABLE redeem_code(code UNIQUE, plan_id, credits, used_by,
                         used_at, batch, created_at);
-- 用量上报（幂等）
CREATE TABLE usage_report(report_id UNIQUE, account_id, instance_id,
                          window_start, window_end, online_seconds,
                          sent_ok, sent_fail, leads, payload_json, created_at);
-- 日聚合（看板用）
CREATE TABLE stats_daily(account_id, day, instance_id, source,
                         leads, sent_ok, sent_fail, credit_used,
                         PRIMARY KEY(account_id, day, instance_id, source));
```

**关键约束**：扣费与流水写入必须在**同一事务**内；`usage_report.report_id` 唯一索引保证补报幂等（S-5）。

### 客户端（JSON，单写者）

保留 JSON 但**不再有多写者**：

- 只有 `host` 主进程读写实例文件；`browser-host` 与 adapters 通过 IPC 请求，不直接碰盘。
- 写入走 `store.js`：内存态 + 原子写（`.tmp-<pid>` → rename）+ 串行化队列。
- 文件头带 `schemaVersion`，为后续迁移留路。

> 这直接消灭 D-7（队列丢任务）、`live_config.json` 三写者、评论库写坏等**全部**竞态类缺陷——因为它们的根因都是"多进程无锁覆写同一个文件"，而新架构下不存在多写者。

## 六、进程模型对比

| 维度 | 现状 | 目标 |
|---|---|---|
| 进程数 | 8 个各自为政，无 IPC | host + N×browser-host，全 IPC |
| 子进程句柄 | scan 丢失句柄**无法停止**（D-10） | 全部由调度器持有，可取消 |
| 重复点击 | pipeline 静默杀掉前一次（D-13） | 幂等：已在跑则拒绝并提示 |
| 顶层异常 | `process.exit(1)` 无人重启（S-1） | 捕获 → 阶段化归因 → 任务回退 → 继续 |
| 进度卡死 | 强杀后 `running:true` 永不复位（D-11） | 内存态 + 心跳超时自动归位 |
| 控制台暴露 | `0.0.0.0` + 零鉴权 + CORS `*`（D-6） | `127.0.0.1` + 会话令牌 + CORS 白名单 |

## 七、积分协议（必须在写代码前定稿）

| 项 | 方案 |
|---|---|
| 计费触发 | "自动回复引擎处于运行态"的挂钟时长 |
| 空闲处理 | 计入，但**空闲上限**（连续 N 小时零命中 → 停扣并标记 `idle`） |
| 计费粒度 | 服务端按心跳累计，**分段计费**（满 36 分钟计 0.5，满 60 分钟计 1） |
| 心跳频率 | 60 秒 |
| 时钟可信 | **单调时钟 + 递增序号 + HMAC 签名**；客户端时间仅作参考 |
| 断网 | 宽限期（默认 24h）内继续运行但**暂停扣费**，恢复后一次性结算 |
| 上报幂等 | `reportId` 唯一，离线囤 `pending_reports.json`，恢复后补报 |
| 停机 | 余额 ≤ 0 → 服务端拒绝心跳续期 → 客户端 **1 分钟内**进入暂停态 |
| 防篡改 | 余额、流水、授权全部服务端权威；改本机任何文件无效 |
