## 一、两层骨架

**判断一份内容该放哪里，用"它是否与具体话术/业务规则绑定"来分。**

| 层 | 回答什么 | 变化频率 | 代码位置 | 文档位置 |
|---|---|---|---|---|
| **① 机制层** | 与具体话术无关的机制：契约、计费、审计、安全、Agent 运行时、工具层、护栏 | **几乎不变** | `client/agent` `client/tools` `client/core` `client/host` `client/license` `client/safety` `shared/lib` `license-server` | 本文件、`shared/protocol.md`、`shared/测试策略.md`、`shared/开发规范.md`、`shared/安全与合规要求.md`、`shared/AI协作开发指引.md`、`shared/术语与选型基准.md`、`docs/部署指南-服务端.md` |
| **② 业务层** | 抖音截流的业务知识：三来源、诉求分类、话术组织、预热曲线、平台 DOM 知识 | 随业务调整 | `client/platform`（抖音页面知识）、`client/adapters`（业务动作） | `docs/抖音截流需求规格.md`、`shared/已知陷阱与平台知识.md` |

> ⚠️ **分层纪律**：
> 机制层文档**不写具体话术**；业务层文档**不重复描述**计费与审计机制
> （重复描述会随机制改动而过期，且两处说法容易不一致）。

> ### ⚠️ 业务规则是**数据**，不是代码，也不是插件

> 话术、目标客户判据、报价策略由**商家配置 → 服务端下发**。
> 曾经设计过"工作流包"（插件）机制来承载业务知识，**已废弃**——
> "专用"修饰的是**业务领域**，不是技术能力。

## 三、Agent 层在架构中的位置（⚠️ 与工具链路的关键区别）

**Agent 层是本平台新增的、位于既有底座之上的编排层。它不替换任何底座能力。**

| 关系 | 说明 |
|---|---|
| Agent 层**只产出**工具调用请求与汇报 | 不产生发送动作、不碰 CDP、不直接写盘 |
| 工具层是**包装**，不是重新实现 | 内部只调 `adapters/` 与 `safety/` 的既有能力 |
| **发送永远由底座代码执行** | 走完整护栏。Agent 审批通过 **≠** 放松任何护栏 |
| **关闭 Agent 时系统仍可用** | 退化为图形界面的工具链路形态（**降级路径**，见 §四） |

### 3.1 一次交互的完整路径

以商家说**「帮我看看南京这边问价格的，挑几个回一下，别超过 10 个」**为例：

```
① 对话界面 → POST /api/agent/chat → agent/runtime
② runtime 从【落盘状态】重建上下文（不依赖对话历史——历史会截断、会丢）
③ Agent 调 get_account_health()  ← 现在能不能干活（不自己推断）
④ Agent 调 query_leads({intent:"price_inquiry", region:"南京", limit:50})
     ⚠️ 用闭集枚举值查询，不是模型自己"理解"意图
⑤ Agent 调 review_batch({max_items:10})
     ← 代码预筛（在工具层/底座完成）：guard 额度·间隔·时段·观察期；
        similarity 内容相似度；circuit 熔断；
        ★ complaint / irrelevant 由【代码】排除，不由模型判断
⑥ Agent 决策（一次推理覆盖整批）：approve / reject / skip + 选 draft_id
⑦ Agent 调 approve_batch({batch_id, decisions})
     ⚠️ 工具层与闸门【独立重新执行】全部安全校验，不信任 Agent 审批结果
⑧ 🔴 硬闸门（代码 if）→ 队列 → scheduler 逐条走完整护栏
⑨ core/browser-host → CDP → 平台页面操作
⑩ platform/publish-verifier 嗅探平台响应体 → 判定 sent_confirmed
⑪ 审计双写（本地 + 服务端）→ 上报 → 服务端核算计费
⑫ Agent 按包的 outcome 汇报业务里程碑
```

**每一步都带 `stage` 与 `reason`**，UI 能直接显示"卡在哪一步、为什么"。

### 3.2 🔴 硬闸门是架构元素，不是普通节点

**观察期禁发、日上限、最小间隔、相似度、包禁语**——这些必须是**代码里的 `if`**，
且在状态图上处于**固定位置、不可跳过**。

| 为什么必须是代码 | 说明 |
|---|---|
| 硬规则不能交给概率模型 | 你不可能让一个概率模型遵守硬约束——总有一定概率它不遵守 |
| 必须可单独测试 | 闸门能独立构造"应该被拦住"的输入并断言输出为 0 |
| 失败方向必须是"不放行" | 闸门失效的后果是真实发送，不可撤回 |

> ### ⚠️ 实测教训：闸门失效的方向是"放行"
>
> 用累积型 reducer 表达"清空待发列表"时，返回 `[]` 被 reduce 成"追加零个元素"，
> **观察期仍然放行了 1 条**。修复后才归零。
>
> **由此确立规范**：每一个闸门必须配一条"闸门关闭时下游收到 0 条"的测试，
> 且断言**下游**的输入，而不是断言闸门函数自己的返回值
> （缺陷恰恰可能出在闸门与下游之间的状态传递上）。
> 详见 `plans/ADR-001-Agent优先与框架选型.md` §3.3。

## 四、降级路径（Agent 不可用时系统必须仍可用）

**这不是可选项。** 商家场景是"跑一整天"，Agent 不可用的原因会有很多：
模型服务不可达、token 预算耗尽、误批率超标、商家主动关闭。

| 级别 | 触发条件 | 系统行为 | 商家能否完成工作 |
|---|---|---|---|
| **L1** | 单次模型调用失败 | 重试（有上限）；本次决策回退到 `recommended_draft_id` | ✅ |
| **L2** | 模型持续不可用 | 停用 Agent 决策，改为纯规则流水线；**图形界面仍完整可用** | ✅ |
| **L3** | token 预算耗尽 | 同上，并显示预算提示与充值入口 | ✅ |
| **L4** | 人工急停 / 误批率超标 | 停止发送（护栏仍在），仅保留采集 | ⚠️ 只采集，符合红线 1 |

**三条设计要求**：

1. **降级必须可见**——UI 显示当前级别与原因，**不许静默降级**（静默降级会让商家以为 Agent 在工作）
2. **降级不改护栏**——降级只减少"谁来做决策"，不减少"能不能发"
3. **图形界面必须保留**——`plans/B-与方案A的差异说明.md` §3.4 的四条理由全部继续成立：
   部分操作（批量配置、编辑话术池、查台账、卡密兑换）用表单比对话更精确

## 五、稳定性指标（可验收）

"稳定"必须落成数字，否则无法判断是否达成：

| 指标 | 定义 | 目标 |
|---|---|---|
| S-1 长稳 | 连续运行 72 小时不崩溃 | 无未捕获异常退出 |
| S-2 自愈 | 单点故障（标签页被关、Chrome 重启、网络抖动）后自动恢复 | 自动恢复率 ≥ 95%，无需人工 |
| S-3 可观测 | 任何失败都能定位到具体阶段与原因 | 每个任务有阶段化日志与失败归因码 |
| S-4 改版韧性 | 平台改版后修复所需改动文件数 | **1 个**（选择器注册表） |
| S-5 幂等 | 进程重启、重复上报、崩溃恢复不产生重复发送或重复扣费 | 零重复 |
| S-6 隔离 | 一个账号实例故障不影响其他实例 | 故障不跨实例传播 |

> **S-4 是架构约束**：如果选择器散落在多处，这条永远达不到。
> 这是选择器注册表存在的原因，也是 `selectors.js` 必须是唯一来源的原因。

## 六、层间禁止事项（违反即视为缺陷，应直接打回）

| # | 禁止 | 理由 |
|---|---|---|
| 1 | `license-server/` 与 `client/` **互相 require** | 两端必须能独立发版；只能走 `shared/protocol.md` 定义的 HTTP 接口 |
| 2 | 在 `client/platform/selectors.js` 之外定义选择器 | 破 S-4（改版只需改一个文件） |
| 3 | 在 `client/host/store.js` 之外写盘 | 破单写者约束，直接复活竞态类缺陷 |
| 4 | `client/agent/` 操作 CDP 或 `require('ws')` | Agent 只能通过工具层影响世界 |
| 5 | `client/agent/` 出现安全数值字面量 | 只能从 `gates.js` 读；`gates.js` 自身也只能从策略对象读，**不得有默认值** |
| 6 | 生产代码 `require` `legacy/` | 旧代码是只读行为规格，不是依赖 |
| 7 | 硬编码绝对路径 | 必须经 `REPLY_WORKSPACE` 或 `path.join` 解析 |
| 8 | 引入白名单外依赖 | 见 §九 |

## 七、多实例隔离模型

一客户端管多账号，隔离维度：

| 资源 | 隔离方式 |
|---|---|
| Chrome 配置 | `instances/<id>/chrome-profile/`，每实例独立 `--user-data-dir` 与 `--remote-debugging-port` |
| 数据 | `instances/<id>/*.json`（队列、历史、统计、运行态、决策记录） |
| CDP 连接 | 每实例一条独立 WS，由一个 `browser-host` 实例持有 |
| 调度 | 每实例独立频控 / 日上限 / 熔断窗口 |
| 授权 | 实例归属商家账号，共用该商家的积分池 |
| 故障 | 单实例异常**不传播**（S-6）：`browser-host` 按实例隔离，崩溃只重建该实例 |

**端口分配**：基线 9222，实例 N 用 `9222 + N`（可配），启动前探测占用。

> ⚠️ **实例目录含登录态，绝不可入库或进交付包。**
> `client/instances/` 已在 `.gitignore` 中；交付包构建脚本也跳过它。

## 八、存储设计

### 服务端（`node:sqlite`，唯一写入者 + 真事务 + WAL）

主要表：`account`（商家账号）· `credit`（余额，单一真相）· `credit_ledger`（流水台账，**只增不改**）·
`session` · `plan` · `redeem_code` · `usage_report`（`report_id` 唯一索引 → 补报幂等）·
`stats_daily`（看板日聚合）· `policy_ack_log`（★记录真实生效策略）· `audit_send`（★计费唯一依据）·
`instance` · `admin_user` · `admin_session` · `admin_action_log`

**关键约束**：扣费与流水写入必须在**同一事务**内。

### 客户端（JSON，单写者 + 原子写）

- 只有 `host` 主进程读写实例文件；`browser-host`、`adapters`、`agent` 通过 IPC 请求，不直接碰盘
- 写入走 `store.js`：内存态 + 原子写（`.tmp-<pid>` → rename）+ 串行化队列
- 文件头带 `schemaVersion`，为迁移留路
- 🆕 Agent 的决策记录与工具审计也经 `store.js`（保持单写者）

> 这直接消灭了旧代码的**全部**竞态类缺陷（队列丢任务、配置回退、评论库写坏），
> 因为它们的根因都是"多进程无锁覆写同一个文件"，而新架构下不存在多写者。

## 九、依赖策略

**核心原则：依赖越少越稳定，但 WebSocket 与 Agent 编排不在此列。**

| 用途 | 方案 | 为什么允许（含为什么不用替代品） |
|---|---|---|
| WebSocket 客户端 | **`ws`** | CDP 必需。自研要处理分帧、掩码、背压、ping/pong、重连、半开连接——"要求稳定"最不该自己写的一块 |
| Agent 编排 | **`@langchain/langgraph`** | 实测 **22 包 / 47.6 MB**，CommonJS 直接 `require` 无构建。项目的硬需求是"状态落盘、崩溃可续、闸门不可跳过"，检查点（checkpointer）是它的原生能力。**不用 `@mastra/core`**：实测 **152 包 / 104.4 MB** |
| 工具参数校验 | **`zod`** | ⚠️ langgraph 的 peer dependency。工具层必须校验模型传入的参数（不信任模型传参），**必须显式声明，不留隐式依赖** |
| SQLite（服务端） | **`node:sqlite`（内置）** | 已实测可用，零依赖且有真事务 |
| HTTP 服务 | **内置 `http`** | 够用，无必要引框架 |
| 密码哈希 / HMAC / 随机数 | **内置 `crypto`** | 够用 |
| 前端 | **原生 DOM，无框架** | 保持单文件交付、无构建步骤 |
| LLM 调用 | **内置 `node:https` 自研适配器** | 只是"发一个 POST、收一个 JSON"，约 60 行；便于统一超时、重试与脱敏。**不得引入模型厂商 SDK** |

**服务端依赖：零。** 此条不因任何理由放宽——零依赖是它最大的运维优势。

**明确不引入**：`puppeteer-core` / `playwright`（给浏览器打自动化指纹，且**用不上商家已登录的账号**——
这是它被禁的真正原因）、`@mastra/core`（体积与依赖树）、任何需要构建步骤的依赖、任何 ORM。

**分发影响**：客户端允许这三个依赖意味着首次运行需要 `npm install` 或随包内置 `node_modules`。
**推荐随包内置**，使商家仍是"解压即用"。`client/启动.cmd` 已含依赖自检，缺失时给出明确提示而非崩溃。

> 自检命令：`npm run check:deps`（校验允许集 / 禁止集 / 体积上限）。

## 十一、CDP 层与浏览器接管的可行性前提

**这是整个项目可行性的地基，换任何语言或框架都不会改变。**

| 决策 | 理由 |
|---|---|
| **裸 CDP，不用 puppeteer/playwright** | ① 它们默认启动**全新浏览器上下文**，**用不上商家 Chrome 里已扫码登录的账号**——而在自动化浏览器里重新登录恰是风控最敏感的特征；② 自动化指纹（`navigator.webdriver` 等）与语言无关，Playwright/Puppeteer 在 Python 与 Node 下用同一个驱动，换语言不解决 |
| **驱动商家已登录的专用 Chrome** | `--user-data-dir=instances/<id>/chrome-profile` + `--remote-debugging-port=9222+N`。登录态是商家的，我们不碰密码、不读 Cookie |
| **一个进程只持有一条 CDP WebSocket** | 由 `browser-host` 独占；其他模块经 IPC 请求。避免多路复用导致的响应错配 |
| **成功判定只认平台响应体** | CDP `Network` 域嗅探响应，`status_code === 0` 才算成功。**DOM 现象不算**——旧代码就是因此把页面崩溃记成"已发送" |
