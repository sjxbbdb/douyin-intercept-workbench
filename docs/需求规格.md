## 二、架构总览

改造后系统由**两个可独立部署的部分**组成：

```
┌─────────────────────────────┐         ┌──────────────────────────────────────┐
│   授权中心服务端（厂商运营）      │         │   客户端工作台（商家本机 Windows）        │
│   license-server/            │  HTTPS  │   client/                            │
│                              │◄───────►│                                      │
│  · 账号密码登录 / 会话令牌       │  JSON   │  · 登录界面（账号密码，不可注册）          │
│  · 积分账户与流水台账           │         │  · 现有采集能力（视频/评论/弹幕/私信）      │
│  · 授权签发与在线心跳           │         │  · 自动回复引擎（关键词+模板库）           │
│  · 用量归集与商家看板           │         │  · 本机数据看板（截流数/回复数）           │
│  · 管理后台（开号/充值/统计）     │         │  · 急停开关 + 频控 + 风控熔断             │
└─────────────────────────────┘         └──────────────────────────────────────┘
                                                       │ CDP :9222
                                                       ▼
                                             本地 Chrome（商家已登录的抖音账号）
```

**关键设计原则**

1. **积分是服务端权威数据**，客户端不存储余额、不允许本地加减积分。客户端只做展示与"欠费停机"。
2. **断网降级**：服务端不可达时，自动回复进入**暂停态**（不消耗积分、也不发送），恢复后自动续跑。**严禁本地伪造积分继续跑**。
3. **客户端零 npm 依赖**保持不变（只用 Node 内置模块）；服务端允许引入极少量依赖，但优先零依赖（见 §六）。
4. 保留现有 `REPLY_WORKSPACE` 环境变量约定，路径不写死。

## 三、功能需求明细

### FR-1 账号密码登录（替代现有扫码登录页）

| 项 | 要求 |
|---|---|
| FR-1.1 | 客户端首屏为**登录页**：账号 + 密码 + 记住账号。**不提供注册入口**，不提供自助改密。 |
| FR-1.2 | 登录成功后由服务端签发**会话令牌（token）**，客户端持久化到本地（`license_state.json`）。 |
| FR-1.3 | 令牌有效期默认 7 天，客户端每次启动静默续期；过期需重新登录。 |
| FR-1.4 | 同一账号**并发登录设备数上限可配**（默认 1 台），超限时踢掉最早会话。 |
| FR-1.5 | 登录失败需区分提示：账号不存在 / 密码错误 / 账号已停用 / 已到期。**密码错误 5 次锁定 10 分钟**。 |
| FR-1.6 | 密码在服务端以 **PBKDF2/scrypt 加盐哈希**存储，**禁止明文入库**。 |
| FR-1.7 | 抖音扫码登录（现有 `loginPanel`）**保留**，但降级为"账号状态检测/重新扫码"子页面，不再是主入口。 |
| FR-1.8 | 客户端界面显示：当前账号、剩余积分、折算可用小时数、到期时间。 |

### FR-2 自动回复引擎（评论区 / 直播间私信 / 直播间评论）

现有能力是"生成队列 → 人工点确认 → worker 串行发送"。改造为"关键词命中 → 模板渲染 → 风控校验 → 自动发送 → 回传统计"。

**FR-2.1 触发来源（三个）**

| 来源 | 现状 | 改造后 |
|---|---|---|
| 视频评论区 | `reply_worker.js` 需人工确认 | 命中关键词后自动回复 |
| 直播间弹幕 | `live_dom_collector.js` 采集，不回复 | 命中关键词后自动回复弹幕 |
| 直播间私信 | `live_dm_worker.js` 预填后停在发送前 | 命中关键词后自动发送私信 |

**FR-2.2 关键词规则与话术模板**

- 规则表结构：`关键词（多个，逗号分隔） → 话术模板（多条）`。
- 匹配方式沿用现有约定：**命中关键词中任意一个有效字符即触发**（现有 `pipeline.js` 行为），但**为降低误触发，自动回复场景改用「整词包含」匹配**并在界面显式提示差异。
- 模板变量：`{昵称}`、`{关键词}`、`{商品名}`、`{随机1-9}`、`{日期}`。
- **多条随机**：同一规则命中时，从模板池随机取一条；取过的进短期黑名单，**避免对同一用户重复同一句话**。
- **防重复**：同一用户 ID 在 `N` 小时内（默认 24）只回复一次，`N` 可配。
- 兜底：未命中任何规则时**不回复**（不做"万能回复"），并在看板记为"未命中"。

**FR-2.3 风控护栏（硬性，必须实现）**

| 护栏 | 默认值 | 可配 |
|---|---|---|
| 每日发送上限 | 50 条 | ✅ |
| 两条之间的最小间隔 | 60 秒（评论区）/ 30 秒（弹幕） | ✅ |
| 单轮任务最大发送量 | 20 条 | ✅ |
| 命中风控即熔断 | 立即停止 + 告警 | 不可关闭 |
| 全局急停开关 | 界面顶部常驻按钮 | 不可移除 |
| 验证码/滑块出现 | 停止并提示人工处理，**不做绕过** | 不可关闭 |

- 熔断判据沿用现有实现：`comment/publish` **响应体为空视为风控拒绝**，不得标记成功（见 `AGENTS.md` 第 6 条）。
- 连续失败 3 次 → 自动熔断并暂停该来源 30 分钟。

**FR-2.4 私信前置条件**

- 私信需要真实 `sec_uid`。现有 DOM 弹幕常把用户 ID 脱敏成 `*****`，导致 `not_locatable`。
- 改造要求：**优先从弹幕数据帧/接口响应中提取真实 `sec_uid`**；提取不到时**跳过并计入"因风控跳过"统计**，不报成功、不静默失败。

**FR-2.5 人工确认模式的保留**

- 提供三档模式开关：`全自动` / `半自动（自动填充，人工一键批量确认）` / `仅采集不回复`。
- **默认档位**：`半自动`（新装默认最安全，商家自行调到全自动）。

### FR-3 积分制（按小时消耗 + 充值 + 半年额度）

**FR-3.1 计价模型（服务端实现，客户端只展示）**

- 单价：`creditPerHour = 1`（默认，后台可配）。
- **计费口径**：按"自动回复引擎在线运行"的挂钟时长计费，不足 1 小时的按下取整赠送（即：满 36 分钟计 0.5 积分、满 60 分钟计 1 积分，采用**分段计费**，规则集中在服务端 `billing.js`）。
- 心跳：客户端每 **60 秒**上报一次心跳（含在线时长、本次会话 token）。服务端按心跳累计时长。
- 停机条件：余额 `≤ 0` → 服务端拒绝心跳续期 → 客户端自动回复**立即进入暂停态**，界面弹提示"积分不足，请联系客服充值"。
- 低余额提醒：剩余可用小时数 `< 24 小时` 时客户端界面变黄并提示。

**FR-3.2 充值**

- 本期实现**两种方式**：
  1. **管理后台手工充值**（甲方在后台给商家账号加分，必做）。
  2. **充值码兑换**（甲方批量生成卡密，商家在客户端输入兑换，必做）。
- 在线支付对接（微信/支付宝）**本期不做**，留接口。
- 充值必须写**不可变更的流水台账**（`credit_ledger`）：时间、类型（充值/消耗/赠送/退款）、数量、余额快照、操作人。

**FR-3.3 首次购买半年额度**

- 甲方开号时选择套餐，后台提供**套餐预设**：`半年套餐 = 可用小时数 × creditPerHour`（默认 1 积分/小时 × 180 天 × 24 小时 = 4320 积分，但实际按商业策略配置）。
- 提供"套餐"概念而非只给裸积分：`套餐名 / 时长 / 积分 / 价格`。开号时一键发放。
- 需求原文"积分要够半年用的"→ 实现的判定为：**开号时发放的积分 ≥ 按当前 `creditPerHour` 折算的 6 个月连续运行所需积分**，后台给出校验提示。

**FR-3.4 防篡改**

- 余额、流水、授权状态**全部只存服务端**；客户端本地文件被改不影响真实余额。
- 服务端为每次心跳返回**签名响应**（HMAC），客户端校验签名，防中间人伪造"余额充足"。

### FR-4 商家数据看板（需求 4："截了多少流、有多少人回复"）

**FR-4.1 客户机侧看板（商家自己看）**

| 指标 | 口径 |
|---|---|
| 截流总量 | 三个来源命中并成功沉淀的线索合计 |
| 已回复人数 | 成功发出自动回复的**去重用户数** |
| 回复条数 | 成功发送的回复总条数 |
| 回复成功率 | 成功 / 尝试 |
| 分来源明细 | 评论区 / 直播间弹幕 / 私信 各自的命中、发送、失败 |
| 失败原因分布 | 风控拒绝 / 未找到入口 / 未命中规则 / 被跳过 |
| 积分消耗 | 本日 / 本周 / 本月消耗积分与折算小时 |
| 趋势 | 近 7 日折线（纯 CSS/Canvas，不引第三方图表库） |

**FR-4.2 服务端侧看板（甲方看全部商家）**

- 商家列表：账号、状态、余额、已用积分、在线/离线、最后心跳时间。
- 单商家下钻：上述所有指标的服务端留存副本。
- 全平台汇总：总商家数、在线数、总消耗积分、总发送量。
- 数据由客户端**定期上报**（默认 5 分钟一次，与心跳合并），离线时囤在本地 `pending_reports.json`，联网后补报（**幂等去重**，按 `reportId`）。

**FR-4.3 口径一致性**

- 同一指标在客户端与服务端必须**口径一致**，实现上共用同一份统计聚合逻辑（客户端 `stats.js` ↔ 服务端 `stats.js` 保持相同算法，并各有一份单元自测）。

### FR-5 自动剪辑（本期不做，只留接口）

- 在导航中**不放**该入口，避免空按钮。
- 但预留：
  - 服务端 `POST /api/v1/task/submit` 通用任务接口（`type: "video_edit"` 预留枚举）。
  - 积分计价表 `price_table` 中预留 `video_edit` 单价字段（默认 0，未启用）。
  - 客户端 `services/` 目录预留 `video_edit_service.js` 占位（导出未实现异常）。

## 五、AGENTS.md 重新定义方案（甲方明确要求）

旧 `AGENTS.md` 与需求 2 正面冲突，作废以下条款：

| 旧条款 | 处置 |
|---|---|
| "回复分发必须保留人工确认，不要把队列改成无确认批量自动发送" | **作废**，改为"默认半自动，允许商家显式切换全自动" |
| "不做绕过"精神 | **保留并强化**：仍然禁止绕过验证码/风控；改为"遇风控即熔断" |

新 `AGENTS.md` 的条款结构（分三块）：

1. **不可协商（红线）**：不绕过验证码/滑块/风控；不读取导出 Cookie/Token/密码；不向第三方上传商家评论与用户隐私原文；熔断机制不可被关闭；积分服务端权威，客户端禁止本地伪造余额。
2. **策略（可配置，默认安全）**：自动回复默认档位、日上限、最小间隔、熔断阈值、计费单价 —— 全部集中在配置文件中，改动需记入 CHANGELOG。
3. **工程约定**：零依赖、`node --check`、路径解析、测试命令、提交规范。

同时拆分为：
- `AGENTS.md`（根，精简索引 + 红线，≤120 行）
- `docs/架构说明.md`（模块职责、进程模型、数据流）
- `docs/需求规格.md`（本文档）
- `docs/开发规范.md`（编码约定、测试、发布流程）

## 七、缺口清单（现状 vs 需求）

| 需求 | 现状 | 缺口 |
|---|---|---|
| FR-1 账号密码登录 | 无账号体系，只有抖音扫码 | 全部新建（服务端 + 客户端登录页） |
| FR-2 自动回复 | 三来源均已能"定位并预填"，但**必须人工点确认** | 新建引擎；改造 3 个 worker 的确认环节 |

## 七之二、基线缺陷（代码考古实测，必须先修）

以下为对原始包做只读代码考古后**已逐条亲自复核**的缺陷。其中 D-1 为阻断级：在非原作者机器上部分功能**根本跑不通**。

| 编号 | 缺陷 | 证据（文件:行） | 影响 | 处置阶段 |
|---|---|---|---|---|
| **D-1** | **硬编码绝对路径**，全部指向原作者机器的 `D:\deep seek\`，而真实目录是 `D:\DeepSeek\`（大小写与空格均不同）。共 5 文件 13 处 | `pipeline.js:176,299,306`；`scan_comments.js:88,97`；`reply_worker.js:492,493`；`qr_capture.js:50`；`filter_comments.js:3,37`；`filter_full.js:16,17,46` | **阻断级**。`server.js` 用 `path.join(WORKSPACE,…)` 写请求文件，子进程却从 `D:\deep seek\` 读 → 视频采集、增量扫描在本机**必然读不到请求**；回复去重历史静默写失败（异常被 `catch {}` 吞掉），导致**同一评论可能被重复回复** | **P0 立即修** |
| **D-2** | 界面配置项是"空承诺"：`cooldown`（单用户冷却）与 `requireConfirm`（发送前确认）被解析后**从未被使用** | 解析于 `live_dom_collector.js:104,106`；界面下拉 `select.html:619`；写入 `server.js:261,263` | 商家以为设了冷却/确认，实际**完全无效**。这直接关系到 FR-2.3 频控护栏，必须一并落地 | **P0 立即修** |
| **D-3** | `dailyLimit` 不是限流而是**丢线索**：把 leads 数组直接 `slice` 截断 | `live_dom_collector.js:216` | 超过上限的线索被**静默丢弃**而非留待次日，商家损失线索且无感知 | P1 |
| **D-4** | 死代码：`reply_worker.js:420-424` 的超时回收分支永远不可达（419 行已把 `sending` 改回 `queued`） | `reply_worker.js:419-424` | 逻辑噪音，改造时清理 | P1 |
| **D-5** | `comment_worker.js` 无人调用（未接入界面） | 全库无引用 | 需求 2 的"评论区评论"若要落 UI，需接入 | P2 |

**D-1 的额外风险提示**：`reply_worker.js` 的去重历史写盘失败是**静默**的，意味着原开发者机器上也存在"同一人被重复回复"的可能。改造 FR-2.2 的"同一用户 24 小时只回一次"时，必须把去重存储换成服务端权威 + 本地兜底双保险，不能只依赖本地文件。

> **人工确认闸门的真实位置**（考古确认，决定改造切口）：`reply_worker.js` 内部**没有任何等待人工确认的代码**，它是"入队即自动发送"。唯一的人工闸门在**入队之前**——`select.html:1314 sendReplies()`，由用户点击「🚀 分发回复」按钮（`select.html:707`）触发 `POST /api/reply`（`select.html:1339`）写队列。
> **结论**：FR-2 的改造切口非常干净——**在入队入口接自动回复引擎即可，worker 主体逻辑（定位、Enter 发送、`status_code:0` 判据）可原样复用**，无需改动 CDP 层。

## 九、验收标准

1. 商家在客户端用厂商发的账号密码登录成功，看不到注册入口。
2. 服务端后台能创建账号、发放套餐积分、看到该商家余额变化。
3. 客户端余额归零后，自动回复在 **1 分钟内**进入暂停态并提示，不再发送任何内容。
4. 配置一条"多少钱 → 话术A/话术B"，在评论区/直播间命中后**自动发出**，且多次命中随机取不同话术。
5. 达到日上限或最小间隔时**不再发送**，界面有明确状态提示。
6. 点击急停后**立即停止**所有自动回复。
7. 看板的"截流总量/已回复人数/回复成功率"三项数字，与手工核对结果一致。
8. 修改本机任何 JSON 文件把余额改成 9999，重启后界面仍显示服务端真实余额。
9. `node --check` 全量通过；自测脚本 `node test/run.js` 全绿。
10. 断网情况下自动回复暂停且不扣积分，恢复网络后自动续跑。
11. **D-1 修复验证**：把整个包拷到任意路径（如 `E:\test\wb\`）后，视频采集与增量扫描能正常读到请求文件并跑通，不再依赖 `D:\deep seek\`。
12. **D-2 修复验证**：界面设置"单用户冷却 30 分钟"后，对同一用户 30 分钟内不再重复发送，实际生效。
