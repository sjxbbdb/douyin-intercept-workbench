## 二、架构总览

改造后系统由**两个可独立部署的部分**组成：

```
┌─────────────────────────────┐         ┌──────────────────────────────────────┐
│   授权中心服务端（厂商运营）      │         │   客户端工作台（商家本机 Windows）        │
│   license-server/            │  HTTPS  │   client/                            │
│                              │◄───────►│                                      │
│  · 账号密码登录 / 会话令牌       │  JSON   │  · 登录界面（账号密码，不可注册）          │
│  · 积分账户与流水台账           │         │  · 现有采集能力（视频/评论/弹幕/私信）      │
│  · 授权签发与在线心跳           │         │  · 自动回复引擎（关键词+模板库）           │
│  · 用量归集与商家看板           │         │  · 本机数据看板（截流数/回复数）           │
│  · 管理后台（开号/充值/统计）     │         │  · 急停开关 + 频控 + 风控熔断             │
└─────────────────────────────┘         └──────────────────────────────────────┘
                                                       │ CDP :9222
                                                       ▼
                                             本地 Chrome（商家已登录的抖音账号）
```

**关键设计原则**

1. **积分是服务端权威数据**，客户端不存储余额、不允许本地加减积分。客户端只做展示与"欠费停机"。
2. **断网降级**：服务端不可达时，自动回复进入**暂停态**（不消耗积分、也不发送），恢复后自动续跑。**严禁本地伪造积分继续跑**。
3. **客户端零 npm 依赖**保持不变（只用 Node 内置模块）；服务端允许引入极少量依赖，但优先零依赖（见 §六）。
4. 保留现有 `REPLY_WORKSPACE` 环境变量约定，路径不写死。
5. **本地存储必须有单写者仲裁**（新增 `store.js`）：现有代码有 3 处"多进程同时读-改-写同一个 JSON"的竞态（见 D-7、§七之二），已实际造成队列丢任务。任何新功能不得再沿用裸 `fs.writeFileSync` 全量覆盖；统一走原子写 + 读-改-写 + 单写者。
6. **本地控制台必须收敛暴露面**：监听 `127.0.0.1`（非 `0.0.0.0`）、加鉴权、CORS 由 `*` 收紧为白名单（见 D-6）。

## 三、功能需求明细

### FR-1 账号密码登录（替代现有扫码登录页）

| 项 | 要求 |
|---|---|
| FR-1.1 | 客户端首屏为**登录页**：账号 + 密码 + 记住账号。**不提供注册入口**，不提供自助改密。 |
| FR-1.2 | 登录成功后由服务端签发**会话令牌（token）**，客户端持久化到本地（`license_state.json`）。 |
| FR-1.3 | 令牌有效期默认 7 天，客户端每次启动静默续期；过期需重新登录。 |
| FR-1.4 | 同一账号**并发登录设备数上限可配**（默认 1 台），超限时踢掉最早会话。 |
| FR-1.5 | 登录失败需区分提示：账号不存在 / 密码错误 / 账号已停用 / 已到期。**密码错误 5 次锁定 10 分钟**。 |
| FR-1.6 | 密码在服务端以 **PBKDF2/scrypt 加盐哈希**存储，**禁止明文入库**。 |
| FR-1.7 | 抖音扫码登录（现有 `loginPanel`）**保留**，但降级为"账号状态检测/重新扫码"子页面，不再是主入口。 |
| FR-1.8 | 客户端界面显示：当前账号、剩余积分、折算可用小时数、到期时间。 |

### FR-2 自动回复引擎（评论区 / 直播间私信 / 直播间评论）

现有能力是"生成队列 → 人工点确认 → worker 串行发送"。改造为"关键词命中 → 模板渲染 → 风控校验 → 自动发送 → 回传统计"。

**FR-2.1 触发来源（三个）**

| 来源 | 现状 | 改造后 |
|---|---|---|
| 视频评论区 | `reply_worker.js` 需人工确认 | 命中关键词后自动回复 |
| 直播间弹幕 | `live_dom_collector.js` 采集，不回复 | 命中关键词后自动回复弹幕 |
| 直播间私信 | `live_dm_worker.js` 预填后停在发送前 | 命中关键词后自动发送私信 |

**FR-2.2 关键词规则与话术模板**

- 规则表结构：`关键词（多个，逗号分隔） → 话术模板（多条）`。
- 匹配方式沿用现有约定：**命中关键词中任意一个有效字符即触发**（现有 `pipeline.js` 行为），但**为降低误触发，自动回复场景改用「整词包含」匹配**并在界面显式提示差异。
- 模板变量：`{昵称}`、`{关键词}`、`{商品名}`、`{随机1-9}`、`{日期}`。
- **多条随机**：同一规则命中时，从模板池随机取一条；取过的进短期黑名单，**避免对同一用户重复同一句话**。
- **防重复**：同一用户 ID 在 `N` 小时内（默认 24）只回复一次，`N` 可配。
- 兜底：未命中任何规则时**不回复**（不做"万能回复"），并在看板记为"未命中"。

**FR-2.3 账号安全体系（硬约束，服务端下发，客户端不可绕过）**

> **背景**：本工具的价值来自"发得多"，而账号被封的原因也是"发得多"——这两个目标根本对立。因此安全机制不是可选的优化项，而是**产品的核心交付价值**（"帮你控制节奏，让号活得久"）。甲方已确认：安全上限由**服务端权威下发**，客户端只能调低不能调高。

**FR-2.3.1 账号等级与预热曲线（最有效的防封措施）**

新号满速发送是封号第一诱因。客户端**不可关闭**预热逻辑：

| 阶段 | 时长 | 日发送上限 | 其中私信上限 |
|---|---|---|---|
| 观察期 | 第 1-3 天 | 0（只采集，不发送） | 0 |
| 预热期 | 第 4-7 天 | 10 条 | 3 条 |
| 爬坡期 | 第 8-14 天 | 25 条 | 8 条 |
| 稳定期 | 第 15 天起 | 按服务端策略 | 按服务端策略 |

- 等级由服务端根据账号首次启用时间计算并下发，客户端不得自行提升。
- 界面须明确显示当前等级与"距离下一档还需 N 天"。

**FR-2.3.2 按操作类型分限额（不得使用统一上限）**

**陌生人私信的封号风险显著高于评论回复**，必须独立且低得多的上限：

| 操作类型 | 日上限（默认） | 最小间隔（默认） |
|---|---|---|
| 评论区回复 | 20-30 条 | 60-180 秒（随机） |
| 直播间弹幕回复 | 30-50 条 | 30-90 秒（随机） |
| **陌生人私信** | **5-10 条** | **300-900 秒（随机）** |

> 依据：现有 `live_dm_worker.js` 已探测到平台对陌生人私信的限制（`stranger_dm_disabled` 分支），说明平台本身就在管控该行为。

**FR-2.3.3 内容指纹去重（防内容级 spam）**

- 每条规则的模板池**至少 5 条变体**。
- 发送前做**相似度检测**（SimHash 或 n-gram），与近期已发内容相似度 **> 85% 直接拒绝发送**，提示商家补充文案。
- 变量填充须自然：禁止用 `{随机1-9}` 生成"1""2"这类明显机器痕迹，须使用自然语言变体（如"这个""这款""它"）。

**FR-2.3.4 节奏去随机化与作息模拟**

| 项 | 现状 | 要求 |
|---|---|---|
| 发送间隔 | `reply_worker.js:526` 固定 `10000 + rand(4000)` | 改为**对数正态分布**（多数偏短、偶尔长间隔） |
| 操作延迟 | 无 | 每次点击/输入前加 1-3 秒随机停顿（模拟真人反应） |
| 活跃时段 | 24 小时无休 | **仅在活跃时段工作**（默认 08:00-23:00），每天随机起止，夜间休息 |
| 响应延迟 | 弹幕命中后约 8 秒回复 | 加入人工量级的延迟，避免"秒回"特征 |

**FR-2.3.5 熔断升级（不是重试，是停更久）**

- 现状 `reply_worker.js:503` 遇验证码 sleep 60 秒继续——**不足**，风控已被触发。
- 要求：**30 分钟 → 1 小时 → 当次停到次日**的递进退避，并明确告知商家当前处于哪一级。
- 熔断判据沿用现有实现：`comment/publish` **响应体为空视为风控拒绝**，不得标记成功。
- 连续失败 3 次 → 熔断并暂停该来源。

**FR-2.3.6 硬性护栏（不可关闭、不可移除）**

| 护栏 | 说明 |
|---|---|
| 全局急停开关 | 界面顶部常驻按钮 |
| 上限硬顶 | 即使商家调高，也不得超过服务端策略上限；服务端拒绝越权配置并返回 `POLICY_VIOLATION` |
| 验证码/滑块 | 停止并提示人工处理，**不做绕过** |
| 预热曲线 | 客户端不可跳过 |
| 每日风险摘要 | 持续提示，不是签一次就完事 |

**FR-2.3.7 账号健康分（可视化，作为卖点）**

界面显示"账号健康分"：今日已发 / 上限、连续无异常天数、当前等级阶段、最近一次熔断时间。**把安全可视化的目的是让商家理解并认同节流**，而非视为限制。

**FR-2.4 私信前置条件**

- 私信需要真实 `sec_uid`。现有 DOM 弹幕常把用户 ID 脱敏成 `*****`，导致 `not_locatable`。
- 改造要求：**优先从弹幕数据帧/接口响应中提取真实 `sec_uid`**；提取不到时**跳过并计入"因风控跳过"统计**，不报成功、不静默失败。

**FR-2.5 人工确认模式的保留**

- 提供三档模式开关：`全自动` / `半自动（自动填充，人工一键批量确认）` / `仅采集不回复`。
- **默认档位**：`半自动`（新装默认最安全，商家自行调到全自动）。
- 全自动档位须在开启时**主动勾选风险确认**（不得默认勾选），并记入审计日志。

### FR-3 积分制（按成功回复条数计费 + 充值 + 半年额度）

> **计费模型变更记录**：原设计为"按小时计费"，甲方于复审时改为**按成功回复条数计费**。理由：按小时计费形成"跑得越久赚得越多、账号寿命越短"的激励冲突；按条计费使厂商利益与商家账号健康**一致**（号被封 → 发不出去 → 收不到钱），且封号后争议更小。

**FR-3.1 计价模型（服务端实现，客户端只展示）**

- 单价：`creditPerReply = 1`（默认 1 积分 = 1 条成功回复，后台可配）。
- **只对成功计费**：必须收到平台确认（`status_code: 0` 类成功判据）才计费。
- **失败、被风控拒绝、被跳过、未命中规则，一律不计费。** 此设计对商家有利，须在客户端界面明确告知。
- **绝不允许客户端"上报即计费"**：上报须带客户端生成的 `sendId`，服务端按 `sendId` 唯一索引去重，重复/补报不重复扣费。
- 心跳仍保留（60 秒），用途改为：① 在线状态；② **下发安全策略**；③ 会话续期。**心跳不再作为计费依据**（`online_seconds` 仅作运营统计，须标注"不用于计费"）。
- 停机条件：余额 `≤ 0` → 服务端拒绝心跳续期 → 客户端**1 分钟内**进入暂停态并提示"积分不足，请联系客服充值"。语义从"停止计时"变为"禁止发送"。
- 低余额提醒：剩余可用条数 `< 100 条` 时客户端界面变黄并提示。

**FR-3.2 充值**

- 本期实现**两种方式**：
  1. **管理后台手工充值**（甲方在后台给商家账号加分，必做）。
  2. **充值码兑换**（甲方批量生成卡密，商家在客户端输入兑换，必做）。
- 在线支付对接（微信/支付宝）**本期不做**，留接口。
- 充值必须写**不可变更的流水台账**（`credit_ledger`）：时间、类型（充值/消耗/赠送/退款）、数量、余额快照、操作人、关联 `sendId`（消耗类）。

**FR-3.3 首次购买半年额度**

- 套餐字段：`套餐名 / 积分(credits) / 有效天数(valid_days) / 价格`。原 `hours` 字段废弃。
- 半年套餐默认值：`credits = 稳定期日上限 × 180`（按默认稳定期日上限 25 条计 = 4500 积分；实际按商业策略配置）。
- **必须在客户端显著位置说明一个商家容易误解的点**：

  > **买了半年套餐 ≠ 半年内能无限发。** 平台的日上限才是真正的量级约束，套餐只是预付额度；额度按有效期计算，到期未用完的部分按套餐规则处理。

  此提示不得隐藏在协议里，须在购买/登录后首屏展示一次，并可在"我的套餐"页随时查看。

**FR-3.4 防篡改**

- 余额、流水、授权状态**全部只存服务端**；客户端本地文件被改不影响真实余额。
- 服务端为每次心跳与上报返回**签名响应**（HMAC），客户端校验签名，防中间人伪造"余额充足"。

### FR-4 商家数据看板（需求 4："截了多少流、有多少人回复"）

**FR-4.1 客户机侧看板（商家自己看）**

| 指标 | 口径 |
|---|---|
| 截流总量 | 三个来源命中并成功沉淀的线索合计 |
| 已回复人数 | 成功发出自动回复的**去重用户数** |
| 回复条数 | 成功发送的回复总条数 |
| 回复成功率 | 成功 / 尝试 |
| 分来源明细 | 评论区 / 直播间弹幕 / 私信 各自的命中、发送、失败 |
| 失败原因分布 | 风控拒绝 / 未找到入口 / 未命中规则 / 被跳过 |
| 积分消耗 | 本日 / 本周 / 本月消耗积分与折算小时 |
| 趋势 | 近 7 日折线（纯 CSS/Canvas，不引第三方图表库） |

**FR-4.2 服务端侧看板（甲方看全部商家）**

- 商家列表：账号、状态、余额、已用积分、在线/离线、最后心跳时间。
- 单商家下钻：上述所有指标的服务端留存副本。
- 全平台汇总：总商家数、在线数、总消耗积分、总发送量。
- 数据由客户端**定期上报**（默认 5 分钟一次，与心跳合并），离线时囤在本地 `pending_reports.json`，联网后补报（**幂等去重**，按 `reportId`）。

**FR-4.3 口径一致性**

- 同一指标在客户端与服务端必须**口径一致**，实现上共用同一份统计聚合逻辑（客户端 `stats.js` ↔ 服务端 `stats.js` 保持相同算法，并各有一份单元自测）。

### FR-5 自动剪辑（本期不做，只留接口）

### FR-6 责任边界与合规（甲方要求："怎么规避我们的责任"）

> **说明**：本节是**产品与工程层面的设计**，用于把责任划分做成可举证的事实。**不构成法律意见**——协议条款与提示文案请由律师定稿，本文档可作为给律师的需求输入。

**FR-6.1 设计原则：免责能力来自"证据"，不是来自"条款"**

只写免责条款而无可举证的事实，纠纷时基本无效。因此本项目的责任设计遵循：

> **技术限制（证明厂商已尽合理限制义务）+ 全程留痕（证明风险决策来自用户）+ 明确告知（证明用户知情）= 可举证的责任划分**

**FR-6.2 技术层：默认安全 + 不可绕过**（详见 FR-2.3）

| 措施 | 举证意义 |
|---|---|
| 默认档位 = 半自动 | 厂商默认不自动发送 |
| 预热曲线客户端不可关闭 | 厂商**主动限制**了新号风险 |
| 上限有硬顶，越权配置被服务端拒绝 | 厂商**拒绝提供**无限量能力 |
| 每日风险摘要持续提示 | 厂商持续告知，非一次性签字 |

**FR-6.3 证据层：审计留痕（本项目最重要的合规资产）**

留痕是"能不能免责"的分水岭。要求：

| 记录项 | 内容 |
|---|---|
| 发送明细 | `sendId`、时间、来源类型、目标哈希、**内容哈希**、判定结果、失败归因码 |
| **配置变更审计** | **谁、何时、把哪一项从什么值改成什么值、来源是"用户操作"还是"服务端策略下发"** |
| **策略快照** | 每次上报须携带**实际生效的策略版本号与生效值** |
| 确认记录 | 用户开启全自动档位时的主动勾选记录（时间、IP、客户端版本） |
| 熔断记录 | 触发时间、级别、原因 |

**关键约束**：

- 审计记录**本地与服务端双写**，客户端不可篡改服务端副本。
- 审计须记录**真实生效的策略值**，而非仅记录设置值。"用户设了 10、系统允许 10、实际发了 10"三者必须可交叉验证——很多工具纠纷时自证失败，正是因为只记了设置值没记执行值。
- **隐私边界**：只上传哈希与计数，**不上传评论原文、回复内容原文、用户隐私字段**。
- 服务端必须能回答："某次账号处罚之前，该账号实际生效的策略是什么？用户是否主动调高过？系统是否拒绝过越权配置？"

**FR-6.4 协议层：免责要点（供律师起草，非最终条款）**

- 明确说明本工具**降低风险但不消除**账号被封、被限流、内容被下架的可能性。
- 明确因平台判定、平台规则变更导致的账号处罚与业务损失，甲方不承担赔偿责任。
- **强烈建议使用专门账号，不要使用主号**（沿用现有 `README.md:53` 的提示并强化到协议与首屏）。
- 禁止改变工具用途（这条同时是**甲方自身**的责任边界）。
- 商家确认其使用行为符合平台规则与法律法规。

**FR-6.5 商业层：把风险变成产品价值**

- **禁止承诺"保证不封号"**——这是最容易反噬的表述，须在全部文案、销售话术、界面中禁止。
- 可承诺"**持续更新风控策略**"（这是厂商能实际做到的）。
- 建议建立**封号补偿策略**（如核实后赠送积分），把纠纷前置化解。

**FR-6.6 验收要求**

- 能在服务端导出某账号的完整审计记录（`audit export` 命令），内容可支撑纠纷举证。
- 故意把客户端配置改到超过服务端策略上限，服务端必须拒绝并留下 `POLICY_VIOLATION` 记录。
- 篡改客户端本地任意文件，无法改变服务端记录的策略与用量。

## 七之三、安全体系与责任边界（本次新增，优先级最高）

甲方指出核心风险：**回复量与私信量增加会导致账号被封**。由此新增两组需求，优先级高于其他功能：

| 需求 | 章节 | 要点 |
|---|---|---|
| 账号安全体系 | FR-2.3 | 账号等级预热、分操作类型限额、内容指纹去重、作息模拟、熔断升级、健康分可视化。**服务端下发，客户端不可绕过** |
| 责任边界与合规 | FR-6 | 技术限制 + 全程留痕 + 明确告知 = 可举证的责任划分；审计须记录**真实生效的策略值** |

**一个必须让甲方意识到的结构性矛盾**：

> 这个工具的价值来自"发得多"，而账号被封的原因也是"发得多"。

因此产品定位必须是"**帮你控制节奏，让号活得久**"，而**不能**把"发得多"当卖点。若以量为卖点，等于亲手把客户送进封号队列，且纠纷时自身也无法举证已尽合理限制义务。

**计费模型已据此调整**：从"按小时"改为"**按成功回复条数**"。原因是按小时计费形成"跑得越久赚得越多、账号寿命越短"的激励冲突；按条计费使厂商与商家利益**一致**（号被封 → 发不出去 → 收不到钱），且封号后争议更小。

## 九、验收标准

1. 商家在客户端用厂商发的账号密码登录成功，看不到注册入口。
2. 服务端后台能创建账号、发放套餐积分、看到该商家余额变化。
3. 客户端余额归零后，自动回复在 **1 分钟内**进入暂停态并提示，不再发送任何内容。
4. 配置一条"多少钱 → 话术A/话术B"，在评论区/直播间命中后**自动发出**，且多次命中随机取不同话术。
5. 达到日上限或最小间隔时**不再发送**，界面有明确状态提示。
6. 点击急停后**立即停止**所有自动回复。
7. 看板的"截流总量/已回复人数/回复成功率"三项数字，与手工核对结果一致。
8. 修改本机任何 JSON 文件把余额改成 9999，重启后界面仍显示服务端真实余额。
9. `node --check` 全量通过；自测脚本 `node test/run.js` 全绿。
10. 断网情况下自动回复暂停且不扣积分，恢复网络后自动续跑。
11. **D-1 修复验证**：把整个包拷到任意路径（如 `E:\test\wb\`）后，视频采集与增量扫描能正常读到请求文件并跑通，不再依赖 `D:\deep seek\`。
12. **D-2 修复验证**：界面设置"单用户冷却 30 分钟"后，对同一用户 30 分钟内不再重复发送，实际生效。

**安全体系验收（FR-2.3）**

13. 新账号首次启用后处于**观察期**，界面显示"第 1-3 天，仅采集不发送"，且**确认无法通过任何界面操作跳过**。
14. 把客户端配置改成日上限 999，服务端心跳响应必须拒绝并返回 `POLICY_VIOLATION`，且该次越权尝试**被记入审计日志**。
15. 连续两次发送内容相似度 > 85% 时，第二次**被拒绝发送**并提示商家修改文案。
16. 私信与评论使用**不同的日上限与最小间隔**，私信默认上限显著低于评论。
17. 触发验证码后，退避时间为 **30 分钟级**（而非现有的 60 秒），界面明确显示当前熔断级别。
18. 夜间（活跃时段之外）不发生任何发送行为。

**计费与责任边界验收（FR-3 / FR-6）**

19. 一次**被风控拒绝**的发送，服务端**不扣积分**，且流水台账中无该笔消耗记录。
20. 同一条 `sendId` 重复上报 10 次，积分**只扣 1 条**。
21. 服务端可导出某账号完整审计记录，其中能看出"该账号实际生效的策略值"与"用户是否主动调高过配置"。
22. 客户端界面明确展示"买了半年套餐 ≠ 半年内能无限发"的提示，且不隐藏在协议中。
23. 全部销售文案与界面中**不出现"保证不封号"类表述**。
