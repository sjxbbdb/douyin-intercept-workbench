# 可复用资产审计

> **本文档的目的**：把"我们调研过 GitHub、确认哪些能复用、哪些不能"这件事固化下来。
> 避免三个月后开发方再问一遍"为什么不直接用 XX 项目"。
>
> 调研日期：2026-09-18 ｜ 调研范围：抖音自动化、浏览器自动化、拟人化库、授权计费平台
> 全部结论均经实际核实（读取 README、调用 GitHub API 查许可证与仓库状态）

---

## 零、一句话结论

**自动化层没有可直接复用的项目，但这不意外——有的话，这个项目就不该做了。**

**拟人化算法的思路可以借用（MIT 许可），代码可以照着重写。**

**授权计费层有成熟设计可参考，但许可证与依赖不匹配，建议借设计不借代码。**

## 二、自动化层：为什么没有能用的

四条技术路线全部核实过，**没有一条能同时满足我们的三个约束**（用商家已登录的浏览器 / 精细防封节流 / 完整审计留痕）：

### 路线 1：官方 API ❌

[抖音开放平台的角色与权限文档](https://partner.open-douyin.com/docs/resource/zh-CN/developer/introduction/type-and-permission)显示，评论管理能力**要求企业认证（蓝V）账号**。

**旁证**：`pen9un/douyin-chatgpt-bot` 用的是官方接口，它的 README 明确写着"需要抖音账号是企业认证（蓝V）账号及其员工号，**普通账号已不支持**"，且"视频评论自动回复功能已暂停服务（不能使用）"。

**结论**：官方 API 这条路对普通账号是死的。**这反过来说明我们的 CDP 方案不是"绕路"，而是普通账号唯一可行的路径。**

### 路线 2：逆向 API / 抓包重放 ❌

2026-06 的[抖音 Web 签名体系逆向结论](https://github.com/mafqla/douyin-api)显示，接口需要**三件套签名**：

| 参数 | 来源 | 缺失后果 |
|---|---|---|
| `a_bogus` | bdms（JSVMP 虚拟化混淆） | 403 |
| `timestamp` | 时间戳 | 403 Sign Invalid |
| `x-secsdk-web-signature` | securitySDK | 403 Sign Invalid |

**关键约束**：`x-secsdk-web-signature` 依赖 localStorage 里的 **ECDSA P-256 私钥**，且**服务器校验 cookie 与密钥来自同一浏览器会话**（`uifid` 由 `web_runtime_security_uid` 派生）。

**这意味着**：
- ❌ **抠 cookie 到别处用** → 签名对不上会话 → 403
- ❌ **录包重放** → 签名含 timestamp 且会话密钥会变 → 403

**结论**：直接构造请求不可行。但**签名交给实时浏览器**是可行的（见第四节）。

### 路线 3：Playwright / Selenium 系 ❌

所有基于 Playwright 的项目（MediaMate、douyin-creator-tools、Douyin_Curation_Assistant）都有同一个问题：

**它们启动自己的浏览器实例，用不上商家已扫码登录的那个 Chrome。**

具体两种做法，都不合我们的红线：

| 做法 | 项目 | 问题 |
|---|---|---|
| 持久化 profile 目录 | `douyin-creator-tools` 复用 `.playwright/douyin-profile` | 可行，但要求商家在**它的浏览器**里扫码登录，凭据落在它管理的目录 |
| 从 `.env` 注入 Cookie | `Douyin_Curation_Assistant` 用 `DY_COOKIES` | ⚠️ **正是我们红线禁止的做法**——Cookie 一旦落到配置文件，就可能进日志、进备份、被传出去 |

另外 Playwright / Patchright 会注入 `navigator.webdriver` 等自动化指纹。**Patchright 是"patch 掉 Playwright 的痕迹"**——这是另一条技术路线（对抗检测），与我们"用真实浏览器 + 真实登录历史"的路线不同，不能混用。

### 路线 4：拟人化库 ⚠️ 算法可借鉴，库不可用

`HumaniPy` 与 `humanization-playwright` 都是 MIT，质量不错，但：

| 库 | 依赖 | 与我们冲突之处 |
|---|---|---|
| HumaniPy | **Selenium** | Selenium 需要 chromedriver 且与 Chrome 版本强绑定；`apply_stealth()` 是打补丁对抗检测，与我们的路线不同 |
| humanization-playwright | **Patchright**（Playwright 分支） | 同路线 3 的问题 |

**但它们提供的算法值得借鉴**（MIT 允许）：
- **贝塞尔曲线鼠标轨迹 + 抖动 + 中途停顿**（不是直线瞬移）
- **变速打字 + 偶尔打错再退格修正**
- **惯性滚动 + 随机停顿**
- **human_wait(min, max)** 随机人类停顿

## 三、授权计费层：`keygate` 值得学，不值得用

[`tabloy/keygate`](https://github.com/tabloy/keygate) 是**唯一工程质量达到商业级**的候选。它的四项设计对我们有直接价值：

| 设计 | 它怎么做 | 我们该怎么用 |
|---|---|---|
| **签名令牌离线验证** | Ed25519 签名令牌，离线也能验证授权 | 对应我们的"断网宽限期"——服务端签发令牌，断网时客户端用它继续验证 |
| **原子配额** | 数据库层强制，高并发下不超额 | 对应积分扣减——必须在一个事务内校验+扣减 |
| **幂等写入** | `Idempotency-Key` 请求头 | 我们已有 `send_id` 幂等，可对照它的做法补 `report_id` |
| **双层审计** | 变更留痕 + 查询留痕 | 我们的审计设计可以更完整 |

### ❌ 为什么不直接用

| 问题 | 说明 |
|---|---|
| **AGPL v3 传染性** | 比 GPL 更强（网络服务也算分发）。闭源商用有合规风险，需律师评估 |
| **必须保留品牌标识** | UI 里必须显示 "Powered by Keygate"，去掉需购买商业授权 |
| **要装 PostgreSQL** | 我们已定 `node:sqlite`（零依赖），引入 PostgreSQL 等于多一个运维负担 |
| **多一个 Go 运行时** | 与我们的 Node 单栈不符 |
| **不在本机** | 它是独立服务，我们的授权中心要集成进既有架构 |

**结论**：**借设计，不借代码。** 我们已有 `node:sqlite` + HMAC 签名的设计，只缺上面这四个具体做法。

## 四、⭐ 本轮调研最有价值的三个发现

### 发现 1：签名交给浏览器，是"抓包路线"唯一可行的形态

逆向文档列了三条路径，第三条最适合我们：

| 路径 | 做法 | 评价 |
|---|---|---|
| 1 | Node/Python 里跑完整 secsdk 栈补环境 | 工作量大，且**每次抖音改版都要重做** |
| 2 | 导出 localStorage 密钥注入我们的进程 | ❌ ticket 会过期；且**密钥外泄，违反红线 3** |
| 3 | **签名那步交给实时浏览器** | ⭐ **密钥不出浏览器，抖音改签名算法时我们不受影响** |

**路径 3 的具体形态**：

```
浏览器打开着（商家已登录）
  → 通过 CDP 让页面执行签名（页面的 JS 自己算）
  → 拿到签好的 URL
  → 发请求，或直接让页面发
```

**这条路让"采集走抓包"变得可行**，同时不碰密钥。

### 发现 2：`douyin-creator-tools` 的三个设计值得抄进我们的设计

它是**最近还在维护**（2026-07 推送）、**169 star** 的项目，虽然无许可证不能抄代码，但设计思路有参考价值：

| 它的设计 | 为什么值得抄 |
|---|---|
| **`sent_unconfirmed` 状态** | ⚠️ **直接对应我们的红线 2**。它把"发出去了但没确认"单独作为一个状态，且**不重试**。这正是我们要求的"DOM 判断不算成功" |
| **浏览器并发约束** | 用 `.openclaw-browser.lock` 串行化所有浏览器命令，报 `DOUYIN_BROWSER_BUSY` 就退出。**避免了多进程争抢同一个浏览器**——正是我们旧代码的 D-7 类缺陷 |
| **JSONL 事件流协议** | `comments:interactive` 逐条发 `comment_found` 事件，模型回写决策。**这就是我们方案 B 的 `review_batch` / `approve_batch` 的雏形**，而且它区分了 `--preview`（只生成不发送） |
| **硬约束清单** | 明确写出"只改 `replyMessage`，其他字段原样保留"、"空字符串跳过"、400 字符上限。**这类字段级约束正是我们的工具契约需要的** |

**顺带一个结论**：它把架构限死为**严格串行**（`全程最多运行一个抖音命令`）。我们也要接受这一点——**一个浏览器实例不能并行操作。**

### 发现 3：`MediaMate` 的目录隔离设计可以照搬

虽然它已停更，但它的多账号隔离设计是对的：

```
data/
├── browser/     # 保存所有账户浏览器数据，首次打开需手动登录
├── active/      # 运行中被修改的数据（当前代理、已发表文件标识）
├── logs/  upload/  download/
```

**每个账户一个独立目录 + 独立浏览器数据**——这正是我们 `instances/<账号ID>/` 的设计。

它 README 里"项目缺陷"一节还自己承认了两个我们必须避免的问题：
- ❌ "playwright 模拟手动操作有天然缺陷，**处理速度慢**，以及**网速对程序执行影响很大**"
- ❌ "**没有使用数据库**，数据容易被误删"

## 五、明确"不做"的清单

以下路线**已调研并确认放弃**，开发方不要再尝试：

| 路线 | 放弃原因 |
|---|---|
| 抖音官方开放平台 API | 要求企业认证（蓝V），普通账号无权限；且评论回复能力本身受限 |
| 抠 Cookie 到独立进程调用接口 | 签名与会话绑定，必然 403；且 Cookie 落盘违反红线 3 |
| 抓包录请求后重放 | 签名含 timestamp + 会话密钥会变，必然 403 |
| 自己实现 `a_bogus` / `x-secsdk-web-signature` | JSVMP 虚拟化混淆，逆向成本极高，且抖音改版即失效 |
| Playwright / Selenium / Patchright | 用不上商家已登录的浏览器；且注入自动化指纹 |
| 引入 `keygate` | AGPL 传染性 + 强制品牌标识 + 需 PostgreSQL |
| 引入 `HumaniPy` | 依赖 Selenium（版本绑定 + 补丁式对抗检测） |
| 复制 `douyin-creator-tools` 代码 | **无许可证**，默认保留所有权利 |
| 复制 `Douyin_Curation_Assistant` 代码 | **无许可证** |

## 六、可以复用的清单

### ✅ 可借鉴算法（MIT，可自由使用）

| 项 | 来源 | 用途 |
|---|---|---|
| 贝塞尔曲线鼠标轨迹 | HumaniPy / humanization-playwright | 点击前的人类化移动 |
| 变速打字 + 退格修正 | 同上 | 输入文案时 |
| 惯性滚动 + 随机停顿 | 同上 | 滚动评论区时 |
| `human_wait(min, max)` 随机停顿 | 同上 | 操作间停顿 |

> ⚠️ **但要按 `shared/已知陷阱与平台知识.md` 的要求改造**：这些库用的是**均匀随机**，而我们要用**对数正态分布**（见 `plans/B-工具契约与粒度设计.md` 相关章节）。均匀随机的分布形状在时序分析下仍可识别。

### ✅ 可借鉴设计

| 项 | 来源 | 落到我们的哪里 |
|---|---|---|
| `sent_unconfirmed` 独立状态 | douyin-creator-tools | 强化红线 2 的实现（"疑似送达"不与"确认送达"混） |
| 浏览器串行锁 | douyin-creator-tools | `client/core/browser-host.js` 的单实例互斥 |
| JSONL 事件流 + 决策回写 | douyin-creator-tools | 验证方案 B 的 `review_batch`/`approve_batch` 设计 |
| 离线签名令牌 | keygate | 授权中心的离线宽限机制 |
| 原子配额扣减 | keygate | 积分扣减必须在单事务内"校验+扣减" |
| 每账号独立 profile 目录 | MediaMate | `instances/<账号ID>/` |

### ✅ 可借鉴的调试方法

`Douyin_Curation_Assistant` 的"**浏览器实验室**"思路：提供动作抓包与回放脚本，专门用于**调试抖音前端交互变化**。

**这正是我们 P2 真机验证最需要的能力**——当选择器失效时，用它快速定位页面结构变化，而不是靠反复试。

## 七、对 P2 验证门的影响

**这轮调研没有降低 P2 的风险。**

| 问题 | 调研前 | 调研后 |
|---|---|---|
| CDP 能否稳定驱动抖音？ | 未知 | **仍未知**——只能真机验证 |
| 签名方案 | 未知 | ✅ 已明确：交给实时浏览器 |
| 采集能否走抓包？ | 未知 | ✅ **可行**（签名交给浏览器后） |
| 发送应该走哪条路？ | 未知 | ✅ **建议走 UI 驱动**（保留天然节流） |

**新增一条 P2 验证项**（建议加入 G-1~G-5）：

| 编号 | 验证项 | 通过标准 |
|---|---|---|
| **G-6** | **浏览器内签名可用性** | 能通过 CDP 让页面产出带 `a_bogus` + `x-secsdk-web-signature` 的完整 URL，且该 URL 请求返回 200 |

**这条决定"采集走抓包"能否实现。** 若 G-6 不通过，采集只能退回 UI 驱动（慢，但可行）。

## 八、维护指引

**本文档应在以下时点复核**：
- 每季度一次（GitHub 项目状态与许可证可能变化）
- 抖音改版导致方案调整时
- 引入任何新依赖前

**复核方法**：用 GitHub API 查仓库状态与许可证，不要只看 README（本次调研中 `pen9un/douyin-chatgpt-bot` 标着 MIT 徽章但实际无源码）。

```bash
curl -s https://api.github.com/repos/<owner>/<repo> | grep -E '"license"|"pushed_at"|"stargazers_count"'
```
