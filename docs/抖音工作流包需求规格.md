## 一、这个包是做什么的

> **帮助抖音商家自动回复视频评论、直播间弹幕、私信，并把意向客户沉淀为线索。**

它是本平台的**第一个内置工作流包**，也是目前唯一已实现的包。

### 1.1 与平台的分工

| 本包定义（领域知识） | 平台定义（不得在此重复） |
|---|---|
| 三个触发来源（评论区 / 弹幕 / 私信） | 发送上限、最小间隔、观察期 |
| 每个来源的限额**建议值**（平台权威值另在 `tier_table`） | 什么算发送成功（`platform_status_code`） |
| 关键词匹配策略与话术池组织 | 如何计费、如何审计 |
| 抖音平台的操作知识与选择器 | Agent 运行时与硬闸门机制 |
| 本领域的高风险场景（投诉、无关） | 工作流包的加载与校验规则 |
| 本领域的成功定义（留联系方式等） | — |

## 二、触发来源（三个）

现状是"生成队列 → 人工点确认 → 串行发送"。目标为"命中 → 渲染 → 风控校验 → 发送 → 回传统计"。

| 来源 | 平台接口 | 现状（基线） | 目标 |
|---|---|---|---|
| **视频评论区** | `comment/publish` | 需人工确认 | 命中后自动回复 |
| **直播间弹幕** | `live/comment/send` | 采集但不回复 | 命中后自动回复弹幕 |
| **直播间私信** | `im/send` | 预填后停在发送前 | 命中后自动发送私信 |

> ⚠️ **三个接口的响应体是整个计费的唯一证据来源**（红线 2）。
> 「能不能稳定抓到这三个响应体」是**最高风险项**，必须真机验证（见 §七 G-1）。

### FR-D1 关键词规则与话术池

- 规则表结构：`关键词（多个） → 话术模板（多条）`
- 匹配方式：**整词包含**。基线代码的行为是"命中关键词中任意一个有效字符即触发"，**误触发率高**，本包改为整词包含，并在界面显式提示差异
- 模板变量：`{昵称}`、`{关键词}`、`{商品名}`、`{日期}`
- **多条随机**：同一规则命中时从模板池随机取一条；取过的进短期黑名单，**避免对同一用户重复同一句话**
- **防重复**：同一用户 ID 在 `N` 小时内（默认 24）只回复一次，`N` 可配
- 兜底：未命中任何规则时**不回复**（不做"万能回复"），并在看板记为"未命中"

> ⚠️ **模板变量中禁止 `{随机1-9}` 这类机器痕迹**。
> 生成"1""2"这种明显不是人写的变体，是内容级风控最直接的识别特征。
> 须使用自然语言变体（"这个""这款""它"）。

### FR-D2 私信前置条件

- 私信需要真实 `sec_uid`。基线代码的 DOM 弹幕常把用户 ID 脱敏成 `*****`，导致 `not_locatable`
- 要求：**优先从弹幕数据帧 / 接口响应中提取真实 `sec_uid`**；
  提取不到时**跳过并计入"因风控跳过"统计**，不报成功、不静默失败

### FR-D3 三个来源的限额建议值

> ⚠️ **权威值不在本文件**。全系统唯一来源是 `shared/protocol.md` §4.6 的 `tier_table`，
> 由服务端下发。本节给出的是**设计依据与理由**，不是可依赖的数值。

**陌生人私信的封号风险显著高于评论回复**，必须独立且低得多的上限：

| 操作类型 | 设计依据 |
|---|---|
| 评论区回复 | 风险最低，平台本身鼓励互动 |
| 直播间弹幕回复 | 风险中等，但直播间节奏快、上限可略高 |
| **陌生人私信** | **风险最高**。基线代码已探测到平台对陌生人私信的限制（`stranger_dm_disabled` 分支），说明平台本身就在管控该行为 |

**当前生效值**（`tier_table`，稳定期）：评论区 30/天，弹幕 30/天，私信 **10/天**；
`min_interval_ms`：评论 60000–180000，弹幕 30000–90000，**私信 300000–900000**。

### FR-D4 内容指纹去重（防内容级 spam）

- 每条规则的模板池**至少 5 条变体**
- 发送前做**相似度检测**（SimHash 或 n-gram），与近期已发内容相似度 **超过阈值直接拒绝发送**（`0.85` = 超过 85% 拒绝），提示商家补充文案
- ⚠️ **方向不能写反**：是"相似度过**高**才拒绝"

### FR-D5 账号等级与预热曲线

> **这是最有效的防封措施。** 新号满速发送是封号第一诱因。客户端**不可关闭**预热逻辑。

| 等级标识 | 阶段 | 时长 | 评论/天 | 弹幕/天 | 私信/天 |
|---|---|---|---|---|---|
| `observation` | 观察期 | 第 1-3 天 | **0**（只采集，不发送） | **0** | **0** |
| `warm_up` | 预热期 | 第 4-7 天 | 10 | 10 | 3 |
| `ramp_up` | 爬坡期 | 第 8-14 天 | 25 | 25 | 8 |
| `stable` | 稳定期 | 第 15 天起 | 30 | 30 | 10 |

- 等级由服务端根据账号首次启用时间计算并下发，**客户端不得自行提升**
- 界面须明确显示当前等级与"距离下一档还需 N 天"
- **日上限合计**：观察期 0 / 预热期 23 / 爬坡期 58 / 稳定期 **70**。
  稳定期合计 70 是套餐积分的折算基数（平台层 FR-P3.4）
- ⚠️ **本表与 `shared/protocol.md` 的 `tier_table` 必须逐项一致**（已校验：`day_from`/`day_to` = 1-3 / 4-7 / 8-14 / 15+，四级上限完全对齐）。任一处调整必须同步另一处

### FR-D6 节奏去随机化与作息模拟

| 项 | 基线代码 | 要求 |
|---|---|---|
| 发送间隔 | 固定 `10000 + rand(4000)` | **对数正态分布**（多数偏短、偶尔长间隔） |
| 操作延迟 | 无 | 每次点击/输入前加 1-3 秒随机停顿（模拟真人反应） |
| 活跃时段 | 24 小时无休 | **仅在活跃时段工作**（`active_hours`，默认 `08:00–23:00`），每天随机起止，夜间休息 |
| 响应延迟 | 弹幕命中后约 8 秒回复 | 加入人工量级的延迟，避免"秒回"特征 |

> **为什么必须去随机化**：固定节奏是**最容易被识别的机器人特征**。
> 这不是优化项，是红线 1「让账号活得长」的直接手段。

### FR-D7 熔断升级（不是重试，是停更久）

- 基线代码遇验证码 sleep 60 秒后继续——**不足**，风控已被触发
- 要求：**30 分钟 → 1 小时 → 当次停到次日** 的递进退避，并明确告知商家当前处于哪一级
- 熔断判据：平台响应体为**空**即视为风控拒绝，**不得标记成功**
- 连续失败达阈值（默认 3 次）→ 熔断并暂停该来源

### FR-D8 高风险场景必须由代码排除（不得交给模型）

| 场景 | 处理 | 理由 |
|---|---|---|
| 投诉 / 负面评论（`complaint`） | **规则层直接排除**，不出现在待审批批次中 | 在负面评论下自动回复有**公关风险**，这个判断不能依赖概率模型 |
| 无关内容（`irrelevant`） | 同上 | 灌水、广告、闲聊 |
| 图文帖（note post）评论 | 面板结构特殊，标记 `note_post_panel_unsupported` 跳过 | 基线已确认 |

> ⚠️ **两层过滤不可混为一谈**：
> 第一层是**代码**排除高风险意图（在生成批次**之前**，这些项根本不会出现在 Agent 视野里）；
> 第二层是 **Agent 的否决权**（批次内因语义不匹配而 `reject`）。
> **不能因为"Agent 会 reject 掉投诉"就省掉第一层**——那等于把公关风险交给概率模型。

### FR-D9 账号健康分（可视化，作为卖点）

界面显示"账号健康分"：今日已发 / 上限、连续无异常天数、当前等级阶段、最近一次熔断时间。

> **把安全可视化的目的是让商家理解并认同节流**，而非视为限制。

## 四、抖音平台操作知识（本包的核心资产）

> **这一节的内容无法凭空复现**，是拿真账号反复试错换来的。
> 完整版见 `shared/已知陷阱与平台知识.md`；实现时必须逐条对照。

| 知识 | 说明 |
|---|---|
| **隐藏与可见两套 DOM** | 页面同时存在隐藏与可见两套列表容器，隐藏那套里按钮尺寸为 0，操作必然失败。必须筛选**可见**元素（非零尺寸 + 在视口内 + `display!=none` + `visibility!=hidden`） |
| **`scrollIntoView` 后必须延迟读坐标** | 立即读会拿到滚动前的旧坐标 |
| **Enter 才是提交主路径** | 点击发送按钮的成功率显著低于按 Enter |
| **成功判定只认响应体** | 三个接口（`comment/publish`、`live/comment/send`、`im/send`）的响应体 `status_code === 0` |
| **空响应 = 风控拒绝** | 不得标记成功 |
| **弹幕的 `sec_uid` 常被脱敏** | 需从数据帧/接口响应提取真实值 |
| **顶部评论需要先激活编辑器** | 激活失败时必须**明确放弃**，否则会发成顶级评论（错误的公开位置） |

> ⚠️ **选择器只能定义在 `client/platform/selectors.js`**，且每条须带 `liveVerifiedAt`
> （最后人工验证日期）与 `confidence`。**抖音改版时只需改这一个文件**（架构约束 S-4）。

## 五、验收标准（本包）

> 平台层验收见 `docs/平台需求规格.md` §六（27 项）。本节只列**本包特有**的。

### 基础功能

1. 配置一条"多少钱 → 话术A/话术B"，在评论区/直播间命中后**自动发出**，且多次命中随机取不同话术
2. 达到日上限或最小间隔时**不再发送**，界面有明确状态提示
3. 点击急停后**立即停止**所有自动回复
4. 三个来源（评论 / 弹幕 / 私信）都能工作，且**私信使用显著低于评论的上限**

### 安全体系

5. 新账号首次启用后处于**观察期**，界面显示"第 1-3 天，仅采集不发送"，且**确认无法通过任何界面操作跳过**
6. 把客户端配置改成日上限 999，服务端心跳响应必须拒绝并返回 `POLICY_VIOLATION`，且该次越权尝试**被记入审计日志**
7. 连续两次发送内容相似度 > 85% 时，第二次**被拒绝发送**并提示商家修改文案
8. 触发验证码后，退避时间为 **30 分钟级**（而非基线代码的 60 秒），界面明确显示当前熔断级别
9. 夜间（活跃时段之外）不发生任何发送行为
10. **投诉类评论不出现在待审批批次中**（第一层过滤由代码保证）

### 平台知识

11. `packs/douyin-intercept/` 内**不含任何 `.js` 文件**（包是声明式的）
12. 本包的 `pack.json` **不含任何安全数值键名**（那些由 `tier_table` 下发）
13. 换成本包之外的其他包运行后，`client/agent/` 与 `client/tools/` **零改动**（`git diff --stat` 证明）

## 六、本包的适用与不适用场景

### 适用

- 商家自己有抖音账号、愿意用**专用 Chrome**（独立 `--user-data-dir`）承载登录态
- 商家接受**节流**：安全上限由服务端下发，只能更保守
- 需要**按效果付费**：只有平台确认成功的回复才扣积分

### 不适用（写进售前话术，别接这类单）

| 不适用 | 原因 |
|---|---|
| 需要"无限量发" | **产品定位就是不给**（`POLICY_VIOLATION`） |
| 需要自动回复**图文帖**评论 | 面板结构特殊，标记 `note_post_panel_unsupported` 跳过 |
| 需要无人值守绕过验证码/滑块 | 明确禁止，遇风控即熔断 |
| 商家机器无法安装 Node ≥ 22.5 且不接受随包分发 | 需先解决分发形态（`docs/架构说明.md` §十二 R-7） |

> 需要理解长尾语义的场景（"这东西值不值""和别家比怎么样"）**现在属于适用范围**——
> 这正是引入 Agent 要解决的问题，也是本包与基线工具链路的根本差别。

## 七、真机验证门（本包无法用代码替代的一步）

> ⚠️ **没有真机验证，本包的页面操作功能一律标记为"仅代码完成"，不得声明完成**
> （`AGENTS.md` §六 完成定义）。

| 门 | 问题 | 通过标准 | 风险等级 |
|---|---|---|---|
| **G-1** | **三个平台的响应体能否稳定抓到？** | 连续 20 次发送，`comment/publish`、`live/comment/send`、`im/send` 三个接口的响应体都抓到且 `status_code` 可判读 | 🔴 **最高**——这是整个计费的唯一证据 |
| **G-2** | `selectors.js` 的条目是否仍然有效？ | 全部条目在真机上命中可见元素（当前所有 `liveVerifiedAt: null`） | 🔴 高 |
| **G-3** | 专用 Chrome 的登录态能否存活？是否触发自动化识别？ | 连续运行 8 小时无重新登录、无验证码 | 🔴 高 |
| **G-4** | legacy 的 DOM 技巧在新实现中是否全部复现？ | 隐藏/可见两套、延迟读坐标、Enter 提交 三条全部复现成功 | 🟡 中 |
| **G-5** | 自动回复的判定是否准确？ | 连续 20 次，不误报（把失败记成功）、不谎报 | 🟡 中 |
| **G-6** | 风控表现 | 无验证码拦截、无账号异常提示 | 🟡 中 |
| **G-7** | 🆕 包隔离 | 换包后行为随包改变、核心无改动 | 🟡 中 |
| **G-8** | 🆕 闸门强度 | 真机构造"观察期满额 + 第 N+1 条"，确认**确实没有发出** | 🔴 高 |

**前置条件**：需要一个**专门的测试小号**，不能用主号。
