# 测试策略

> **本文件定义本项目的测试分层、测试资产与验收方法。** 与 `shared/已知陷阱与平台知识.md` 配套使用。
>
> | 项 | 值 |
> |---|---|
> | 上位依据 | `docs/需求规格.md` §九（23 条验收标准）、`docs/架构说明.md` §一（S-1~S-6）、§十二（P2 验证门 G-1~G-5） |
> | 技术约束 | Node ≥ 22.5 / 纯 JavaScript（CommonJS）/ **第三方依赖仅 `ws`** / 无测试框架（用 `node:test`） |
> | 统一入口 | `node test/run.js` |
> | 完成定义 | `AGENTS.md` §6：`node --check` 通过 + `node test/run.js` 全绿 + **涉及页面操作的真机验证过** |

---

## 一、测试分层

本项目有 **6 层**测试。**层与层之间不可互相替代**——尤其不能用"单元测试全绿"替代真机验证，也不能用"真机跑通了"替代离线回归（改版后无法复现）。

| 层 | 名称 | 职责 | 覆盖对象 | 运行频率 | 耗时预期 | 需要真实账号 |
|---|---|---|---|---|---|---|
| L1 | 单元测试 | 纯函数正确性 | 计费资格、策略校验、等级推导、相似度、签名、`stableStringify`、时间校准 | 每次提交 | **< 3 秒** | 否 |
| L2 | 契约测试 | 双端对 `shared/protocol.md` 理解一致 | 字段常量、错误码闭集、枚举、字段字典 | 每次提交 | **< 2 秒** | 否 |
| L3 | **离线 DOM 回归** | 抖音改版**早期预警** | `client/platform/selectors.js` 全部选择器 | 每次提交 + 每次改选择器 | **< 5 秒** | 否 |
| L4 | 集成测试 | 服务端 API 端到端 | 登录/心跳/策略/上报/计费/卡密 | 每次提交 | **< 30 秒** | 否 |
| L5 | 真机验证 | 方案可行性的**唯一**证明 | CDP 全链路：评论/弹幕/私信 | **每个阶段交付前** | **2–4 小时** | ✅ 必需 |
| L6 | 长稳测试 | 稳定性与自愈 | 72 小时连续运行、故障注入、幂等 | 发布前 | **72 小时** | ✅ 必需 |

### 1.1 各层职责边界（⚠️ 最容易搞错的地方）

| 层 | 能回答的问题 | **不能**回答的问题 |
|---|---|---|
| L1 | "这段判定逻辑对不对？" | "抖音页面还能不能操作？" |
| L2 | "两端字段名一样吗？" | "服务端扣费算得对吗？"（L4 才能） |
| L3 | "选择器在**已录制**的页面上还能命中吗？" | "**当前**线上页面还是这个结构吗？"（L5 才能） |
| L4 | "接口行为符合契约吗？" | "客户端真的能发出评论吗？" |
| L5 | "这条路走得通吗？" | "连续跑 72 小时会不会崩？"（L6 才能） |
| L6 | "会不会自己恢复？" | "换台机器能跑吗？"（`AGENTS.md` §3 的路径约束由 L3+CI 扫描保证） |

⚠️ **L3 的定位必须说清楚**：离线 fixture 是**已经发生过**的页面快照。它能发现"**我们自己的代码改坏了**"，能发现"改版后**新录的**快照与旧选择器不匹配"，但**不能**发现"线上页面刚刚改版而我还没有新快照"。因此：

> **L3 全绿 ≠ 平台没改版。** 必须配合 L5 定期真机验证 + 运行期的"选择器连续未命中告警"（`shared/已知陷阱与平台知识.md` §6.3）三者共同构成改版防线。

## 二、⭐ 离线 DOM 回归测试

### 2.1 问题

抖音页面改版会导致选择器失效，进而自动回复全部失败。但**真机验证成本高且有封号风险**（`docs/需求规格.md` §八风险表：每次试错都消耗真实账号风险）。需要一个**不需要登录、不需要联网、不碰真账号**的回归手段。

### 2.2 方案

把真实页面的 HTML 快照存进 `test/fixtures/*.html`，用**零依赖的轻量 DOM 匹配器**在 Node 里断言"选择器仍能命中"，并断言"命中的是**可见**的那一个"。

`docs/架构说明.md` §〇 已把这条定为 P0 产出："建离线回归测试：录下真实页面 HTML 快照存 `test/fixtures/*.html`，断言选择器仍能命中、坐标读取表达式仍能返回有效值。**不需要登录、不需要联网、不碰真账号**，可随时跑。"

### 2.3 目录结构与命名规范

```
test/
├── run.js                          # 统一入口：依次跑 L1~L4
├── fixtures/                       # ⚠️ 真实页面 HTML 快照（已脱敏）
│   ├── video-page-desktop-01.html
│   ├── video-page-desktop-02.html
│   ├── note-page-desktop-01.html
│   ├── live-room-desktop-01.html
│   ├── user-profile-desktop-01.html
│   ├── search-result-desktop-01.html
│   ├── captcha-page-01.html
│   └── MANIFEST.json               # 每个 fixture 的元信息（见下）
├── lib/
│   ├── mini-dom.js                 # 零依赖 HTML 匹配器
│   └── selector-assert.js          # 选择器断言工具
├── unit/                           # L1
├── contract/                       # L2
├── dom/                            # L3
└── integration/                    # L4
```

**命名规范**：`<页面类型>-<布局变体>-<序号>.html`

| 段 | 取值 | 说明 |
|---|---|---|
| 页面类型 | `video-page` / `note-page` / `live-room` / `user-profile` / `search-result` / `captcha-page` | 与 `selectors.js` 的 `channel` 对齐 |
| 布局变体 | `desktop` / `desktop-narrow` / `mobile-h5` | 同一页面的不同视口/布局 |
| 序号 | `01`、`02`… | **同一变体的多个样本必须都留着**（改版是渐进的，A/B 实验会同时存在新旧结构） |

**`MANIFEST.json` 每条记录**：

```json
{
  "file": "video-page-desktop-01.html",
  "page_type": "video-page",
  "recorded_at": "2026-09-18",
  "recorded_by": "P2 真机验证 G-4",
  "viewport": { "width": 1920, "height": 1080 },
  "url_path": "/video/<REDACTED_ID>",
  "sanitized": true,
  "notes": "含隐藏+可见两套 comment-list，用于验证可见性判定"
}
```

⚠️ `url_path` **只保留 pathname 且 ID 已脱敏**——禁止记录 `modal_id` 等 query（可能反查用户/视频）。

### 2.4 如何录制 fixture

**步骤**（在专用 Chrome、专用小号上操作，见 §5.1）：

1. 用 CDP 在目标页面执行 `Runtime.evaluate` 取整页 HTML：

```js
// test/tools/record-fixture.js（设计示意，非本次交付文件）
const fs = require('node:fs')
const path = require('node:path')

async function record(cdp, outFile) {
  // ⚠️ 必须先用本章 §2.5 的脱敏脚本处理，不得直接落盘
  const r = await cdp.send('Runtime.evaluate', {
    expression: 'document.documentElement.outerHTML',
    returnByValue: true,
  })
  const html = r.result.value
  fs.writeFileSync(outFile, html, 'utf8')   // 仅在脱敏后
}
```

2. **脱敏**（§2.5）——**这一步不可跳过，不可"先存后脱敏"**。
3. 人工确认：文件里搜不到真实昵称/`sec_uid`/评论原文。
4. 写进 `MANIFEST.json`。
5. 跑一次 `node test/run.js` 确认新 fixture 不会让已有断言失败（如果失败，说明改版了——这正是它的价值）。

⚠️ **录制前先关掉不必要的动态内容**（如视频播放器 `src`），否则快照里会有大量无意义的 blob/base64，文件巨大且每次不同。

### 2.5 ⚠️ 必须脱敏

**`test/fixtures/` 里的 HTML 不得含**（对齐 `shared/protocol.md` §7.5 隐私边界）：

| 类别 | 处理方式 |
|---|---|
| 真实用户昵称 | 替换为 `测试用户A`、`测试用户B`…（**保持长度分布**，避免破坏布局相关断言） |
| `sec_uid` / `uid` / `data-user-id` / `data-sec-uid` 等 | 替换为固定假值（如 `SEC_UID_PLACEHOLDER_0001`），**保持格式特征**（长度、字符集），使"提取正则"的测试仍然有效 |
| 评论原文 / 弹幕正文 | 替换为语义中性的占位文本（如 `这是一条测试评论内容`），**长度相近** |
| 头像 / 图片 URL | 替换为 `https://example.invalid/avatar/0001.jpg` |
| 视频/房间/会话 ID | 替换为 `<REDACTED_VIDEO_ID>` 等占位符 |
| 手机号、微信号、二维码内容 | **删除该节点**或替换为占位符 |
| Cookie / token / 登录凭据 | **必须不存在**（`outerHTML` 不含 Cookie，但要检查内联的 `window.__INITIAL_STATE__` 等） |

**"保持长度分布"很重要**：`shared/已知陷阱与平台知识.md` §4.1 的解析规则带长度上限（昵称 ≤32/≤48、正文 ≤220/≤260）。若脱敏时把长昵称替换成 3 个字的占位符，**长度相关分支就永远测不到**。

**脱敏脚本必须可重复执行**（幂等）：同一份原始 HTML 跑两次得到同样的结果，否则 fixture 无法 diff。

### 2.6 ⚠️ 不能引入白名单外依赖：用 Node 内置能力做到什么程度

**先澄清事实**：本机实测 Node **v24.18.0** 下——

```
node -e "require('node:html')"          → ERR_UNKNOWN_BUILTIN_MODULE（不存在）
node -e "require('node:test')"          → 可用
node -e "require('node:assert')"        → 可用
```

**结论**：Node **没有**内置 HTML 解析器，`node:html` 不存在。而白名单只允许 `ws`，因此**必须自写一个最小匹配器**。

**自写匹配器的能力边界（必须诚实说明，不要假装它能替代 jsdom）**：

| 能力 | 能否做到 | 说明 |
|---|---|---|
| 按 tag / `[attr]` / `[attr="v"]` / `[attr*="v"]` 匹配 | ✅ 可以 | 正则扫描开标签即可 |
| 按 class 匹配（`.foo`） | ✅ 可以 | 从 `class` 属性拆词 |
| 取元素文本（近似 `innerText`/`textContent`） | ⚠️ 近似 | 只能取标签之间的原始文本，**不做实体解码以外的排版处理**；`&nbsp;` 需手动替换为空格 |
| **可见性判定**（`getBoundingClientRect`） | ❌ **做不到** | 快照里没有布局引擎。**这是本方案最大的局限** |
| 属性顺序无关、大小写不敏感 | ✅ 可以 | 正则加 `i` 标志 |
| 后代选择器（`A B`） | ✅ 有限支持 | 在 A 的文本区间内再匹配 B |
| CSS 伪类、`nth-child`、选择器优先级 | ❌ 不做 | 不在本项目使用范围内 |

**⚠️ 可见性怎么解决**：把"可见"这一层判定**在录制时固化进快照**。具体做法：

- 录制时由页面脚本给可见的 `comment-list` 打上标记属性（如 `data-fixture-visible="1"`），并**移除/标记隐藏的那一套**（如 `data-fixture-visible="0"`）。
- 匹配器读取该标记来模拟 `match: 'first-visible'` 语义。
- ⚠️ **必须在 `MANIFEST.json` 与测试文件里显式注明**："本 fixture 的可见性来自录制期标记，**不能**验证运行期的 `getBoundingClientRect` 判据"。

**这是"测试替身"的正当用法，但必须标注局限**——声称"L3 覆盖了可见性判定"是错的。运行期可见性判据只能由 L5 真机验证覆盖。

### 2.7 最小 DOM 匹配器（零依赖，`test/lib/mini-dom.js`）

以下为**可用实现**（CommonJS，只用 Node 内置能力）。设计原则：**先切块，再在块内匹配**，不做完整词法分析。

```js
// test/lib/mini-dom.js
// ⚠️ 仅用于离线 fixture 断言。能力边界见 shared/测试策略.md §2.6。
'use strict'

const VOID_TAGS = new Set(['br', 'img', 'input', 'hr', 'meta', 'link', 'source', 'area', 'base', 'col', 'embed', 'track', 'wbr'])

// 解析出所有标签（开标签与闭标签各成一项），便于按区间切块。
// 闭标签单独成项是必须的：否则无法正确配平同名前缀的兄弟元素（如三个连续的 <div>…</div>）。
function scanTags(html) {
  const tags = []
  // ⚠️ 属性段必须用贪婪 [^<>]*：用惰性 [^<>]*? 会在第一个空格处就收尾，
  //    导致 attrsRaw 只剩空白、所有属性匹配全部失效（本项目实测踩过）。
  const re = /<(\/?)([a-zA-Z][a-zA-Z0-9-]*)([^<>]*?)(\/?)>/g
  let m
  while ((m = re.exec(html)) !== null) {
    const name = m[2].toLowerCase()
    const isClose = m[1] === '/'
    tags.push({
      name,
      isClose,
      attrsRaw: isClose ? '' : (m[3] || ''),
      selfClosing: !isClose && (m[4] === '/' || VOID_TAGS.has(name)),
      start: m.index,
      end: m.index + m[0].length,
    })
  }
  return tags
}

// 解析属性串 → { class: 'a b', 'data-e2e': 'comment-list' }
function parseAttrs(attrsRaw) {
  const out = {}
  const re = /([a-zA-Z_:][-a-zA-Z0-9_:.]*)\s*(?:=\s*(?:"([^"]*)"|'([^']*)'|([^\s"'>]+)))?/g
  let m
  while ((m = re.exec(attrsRaw)) !== null) {
    const name = m[1].toLowerCase()
    out[name] = m[2] !== undefined ? m[2] : m[3] !== undefined ? m[3] : m[4] !== undefined ? m[4] : ''
  }
  return out
}

function decodeEntities(s) {
  return String(s)
    .replace(/&nbsp;/g, '\u00a0')   // ⚠️ 必须还原，解析规则依赖它（见平台知识 §4.1）
    .replace(/&lt;/g, '<').replace(/&gt;/g, '>')
    .replace(/&quot;/g, '"').replace(/&#39;/g, "'")
    .replace(/&amp;/g, '&')
}

// ⚠️ 本函数据 tags 的绝对下标工作：调用方必须先 scanTags(rangeHtml)，
//    再把返回下标加上区间偏移（见 queryIn）。tokens 只解析一次、全区间复用。
function findClose(tags, tokens, openIndex) {
  const open = tags[openIndex]
  if (open.selfClosing) return open.end
  let depth = 0
  for (let i = openIndex; i < tags.length; i++) {
    const t = tags[i]
    // 只配平同名标签；用提前算好的 tokens 避免对每个元素重复扫描全表
    if (tokens[i] !== open.name) continue
    if (t.isClose) {
      depth--
      if (depth === 0) return t.start
    } else if (!t.selfClosing) {
      depth++
    }
  }
  return tags[tags.length - 1].end
}

// 极简选择器：tag | .class | #id | [attr] | [attr="v"] | [attr*="v"] | 组合（如 div.foo[data-e2e="x"]）
function selectorMatches(attrs, tagName, selector) {
  const parts = selector.match(/^([a-zA-Z][a-zA-Z0-9-]*)?((?:[.#]?[\w-]+|\[[^\]]+\])*)$/)
  if (!parts) throw new Error('unsupported selector: ' + selector)
  if (parts[1] && parts[1].toLowerCase() !== tagName) return false
  const rest = parts[2] || ''
  const tokenRe = /\.([\w-]+)|#([\w-]+)|\[([^\]]+)\]/g
  let m
  while ((m = tokenRe.exec(rest)) !== null) {
    if (m[1]) {
      const cls = (attrs.class || '').split(/\s+/)
      if (!cls.includes(m[1])) return false
    } else if (m[2]) {
      if (attrs.id !== m[2]) return false
    } else {
      const cond = m[3]
      // 同时支持 [attr]、[attr=v]、[attr="v"]、[attr*="v"] 四种写法
      // （⚠️ legacy 里 [data-e2e=comment-list] 与 [data-e2e="comment-list"] 两种写法都存在）
      const am = cond.match(/^([\w-]+)\s*(?:([*^$]?=)\s*(?:"([^"]*)"|'([^']*)'|([^\s"'\]]+)))?$/)
      if (!am) throw new Error('unsupported attr condition: ' + cond)
      const name = am[1].toLowerCase()
      const value = attrs[name]
      if (am[2] === undefined) {
        if (value === undefined) return false
      } else {
        const op = am[2]
        const want = am[3] !== undefined ? am[3] : am[4] !== undefined ? am[4] : am[5]
        if (value === undefined) return false
        if (op === '=' && value !== want) return false
        if (op === '*=' && !value.includes(want)) return false
        if (op === '^=' && !value.startsWith(want)) return false
        if (op === '$=' && !value.endsWith(want)) return false
      }
    }
  }
  return true
}

class MiniElement {
  // html 始终是「完整快照字符串」，offset 是本元素在其中的绝对起始位置。
  // 这样嵌套 querySelectorAll 只需把子区间偏移回去，不需要另建作用域字符串。
  constructor(html, tag, attrs, offset, innerStart, innerEnd) {
    this._html = html; this.tagName = tag; this.attrs = attrs
    this._offset = offset; this._innerStart = innerStart; this._innerEnd = innerEnd
  }
  // 近似 textContent：剥标签 + 还原实体（不做 DOM 排版处理）
  get textContent() {
    return decodeEntities(this._html.slice(this._innerStart, this._innerEnd).replace(/<[^>]*>/g, ''))
  }
  // ⚠️ 模拟 innerText：只把 br 与块级闭合标签当换行边界；无法模拟 CSS 影响。
  // 换行后去掉行首缩进、折叠行内连续空白（对应真实 innerText 的排版行为）。
  get innerText() {
    return decodeEntities(
      this._html.slice(this._innerStart, this._innerEnd)
        .replace(/<br\s*\/?>/gi, '\n')
        .replace(/<\/(p|div|li|h[1-6]|tr|section|article|header|footer)>/gi, '\n')
        .replace(/<[^>]*>/g, '')
    ).split('\n').map((s) => s.replace(/[ \t\u00a0]+/g, ' ').trim()).filter(Boolean).join('\n')
  }
  getAttribute(name) { return this.attrs[String(name).toLowerCase()] ?? null }
  querySelectorAll(selector) {
    return queryIn(this._html, this._innerStart, this._innerEnd, selector)
  }
  querySelector(selector) { return this.querySelectorAll(selector)[0] || null }
}

// 在 [scopeStart, scopeEnd) 区间内匹配；返回的元素偏移是「完整快照」的绝对位置
function queryIn(html, scopeStart, scopeEnd, selector) {
  const rangeHtml = html.slice(scopeStart, scopeEnd)
  const tags = scanTags(rangeHtml)
  // tokens 用标签名预计算，供 findClose 复用（否则每个候选元素都要重扫全表）
  const tokens = tags.map((t) => t.name)
  const out = []
  for (let i = 0; i < tags.length; i++) {
    if (tags[i].isClose) continue
    const attrs = parseAttrs(tags[i].attrsRaw)
    if (!selectorMatches(attrs, tags[i].name, selector)) continue
    const close = findClose(tags, tokens, i)
    out.push(new MiniElement(
      html, tags[i].name, attrs,
      scopeStart + tags[i].start,
      scopeStart + tags[i].end,
      scopeStart + close,
    ))
  }
  return out
}

function parse(html) {
  return {
    querySelectorAll: (sel) => queryIn(html, 0, html.length, sel),
    querySelector: (sel) => queryIn(html, 0, html.length, sel)[0] || null,
  }
}

module.exports = { parse, queryIn, scanTags, findClose, parseAttrs, decodeEntities, selectorMatches }
```

⚠️ **实现时的三个已知妥协**（写进代码注释，不要隐藏）：

1. **不处理错位嵌套标签**。浏览器产出的 `outerHTML` 是良构的，但**手工脱敏时若破坏标签结构会导致误判**——脱敏脚本必须用 DOM 操作而不是字符串替换。
2. **`innerText` 是近似**：真实 `innerText` 受 CSS 影响（`display:none` 的内容不出现）。⚠️ 因此 `shared/已知陷阱与平台知识.md` §1.1 那条"必须先确认列表可见再做文本匹配"**在离线测试里无法被验证**。
3. **`querySelectorAll` 不做后代组合选择器**（`A B`）。如需，用嵌套调用模拟：`root.querySelectorAll('A').flatMap(a => a.querySelectorAll('B'))`。

### 2.9 离线回归还应当断言什么

| 断言 | 目的 | 对应 S 指标 |
|---|---|---|
| 每个注册表条目都有 fixture | 防止"加了选择器但没样本" | S-4 |
| 隐藏根被正确排除 | 防止最贵的那个坑 | S-4 |
| 噪音过滤规则仍命中噪音行 | 防止过滤规则被"顺手删掉" | S-3 |
| `MANIFEST.json` 与文件名一一对应 | 防止快照变成无人维护的垃圾 | — |
| fixture 体积上限（如 < 2MB） | 防止仓库膨胀 | — |
| 同一页面类型至少 2 个样本 | 防止单样本过拟合 | S-4 |

## 三、契约测试

### 3.1 目标

`shared/protocol.md` 是 600 行的双端契约。客户端与服务端由**不同的实现者**（甚至是不同的 AI 智能体）完成，最容易出错的不是逻辑，而是**对契约的理解不一致**：字段名拼写、枚举值、错误码、单位（秒 vs 毫秒）、边界语义。

### 3.2 字段常量共享：`shared/lib/protocol.js`

`shared/术语与选型基准.md` §四已固化：`shared/lib/` 是**唯一允许双端共享的代码**，其中 `protocol.js` 负责"字段常量、校验、版本"。契约测试的第一要务是**确保两端都从它取值，而不是各自写字符串字面量**。


### 3.3 错误码一致性检查

`protocol.md` §3.2 有约 40 个错误码。契约测试要断言：

1. **代码里出现的错误码字符串全部在契约表中**（防止拼错 `POLICY_VIOLATION` 为 `POLICY_VIOLENT`）；
2. **HTTP 状态码与契约表一致**（例如 `POLICY_DAILY_CAP_EXCEEDED` 是 **200** 而不是 409——这是最容易被"顺手改成 4xx"的一处）；
3. **客户端对每个错误码都有处理分支**（至少要有 `default` 兜底且归入 fail-closed）。

### 3.4 一致性自检脚本设计（`test/contract/consistency.test.js`）

**思路：把 `protocol.md` 当作可解析的测试数据**，而不是当作散文。这不是完美的方案（Markdown 表格会被人改格式），但它能在**零成本**下抓住 90% 的不一致，且**当文档改动破坏格式时会立刻失败**——这个失败本身是有价值的提醒。

```js
// test/contract/consistency.test.js
'use strict'
const { test } = require('node:test')
const assert = require('node:assert')
const fs = require('node:fs')
const path = require('node:path')
const P = require('../../shared/lib/protocol.js')

const proto = fs.readFileSync(path.join(ROOT, 'shared', 'protocol.md'), 'utf8')

// ---------- 1. 枚举与文档一致 ----------
test('契约：failure_reasons 闭集与 protocol.md §7.4 一致', () => {
  const section = proto.split('### 7.4')[1].split('###')[0]
  const documented = [...new Set(section.match(/`([a-z_]+)`/g) || [])]
    .map((s) => s.replace(/`/g, ''))
    .filter((s) => P.FAILURE_REASONS.includes(s) || /^[a-z_]{4,}$/.test(s))
  for (const r of P.FAILURE_REASONS) {
    assert.ok(section.includes('`' + r + '`'), `failure_reasons 少了 ${r}（或文档拼写不同）`)
  }
  // ⚠️ 反向：编辑器消失不是失败原因（protocol.md §7.4 明文规定）
  assert.ok(!P.FAILURE_REASONS.includes('editor_dismissed_unconfirmed'))
  assert.ok(!documented.includes('editor_dismissed_unconfirmed'))
})

test('契约：platform_endpoint 闭集与 protocol.md §4.8 一致', () => {
  const section = proto.split('### 4.8')[1].split('###')[0]
  for (const ep of P.PLATFORM_ENDPOINTS) {
    assert.ok(section.includes(ep), `platform_endpoint 白名单少了 ${ep}`)
  }
  // ⚠️ 白名单必须不含 scheme / 域名

test('契约：错误码表可解析，且 HTTP 状态码符合契约', () => {

  assert.ok(rows.length >= 30, `错误码表只有 ${rows.length} 行，可能格式被破坏`)

  const codes = {}
  for (const row of rows) {
    const m = row.match(/^\|\s*`([A-Z_]+)`\s*\|\s*(\d{3})\s*\|/)
    if (m) codes[m[1]] = Number(m[2])
  }
  // ⚠️ 这两处的状态码是最容易写错的，单独钉死

  assert.strictEqual(codes.CREDIT_EXHAUSTED, 402)
  assert.strictEqual(codes.POLICY_SENDING_DISABLED, 409)

function collectJsFiles(dir) {
  if (!fs.existsSync(dir)) return []
  const out = []
  for (const e of fs.readdirSync(dir, { withFileTypes: true })) {
    const p = path.join(dir, e.name)
    if (e.isDirectory()) {
      if (e.name === 'node_modules' || e.name === 'legacy') continue
      out.push(...collectJsFiles(p))
    } else if (e.name.endsWith('.js')) out.push(p)
  }
  return out
}
```

### 4.5 HMAC 签名与 `stableStringify`

**签名串**（`protocol.md` §5.1）：`METHOD + "\n" + PATH_WITH_QUERY + "\n" + ts_ms + "\n" + nonce + "\n" + sha256_hex(raw_body_bytes)`

**`stableStringify` 的作用**：协议规定"签名对**原始请求/响应字节**计算：服务端校验用原始 buffer，**不得反序列化后重新序列化再算哈希**"（§1.3）。因此客户端必须保证**序列化只做一次**（§5.3 注释"只序列化一次！"）。`stableStringify`（`shared/lib/stable-stringify.js`）用于**需要确定性序列化的场景**（如本地审计快照的哈希、`policy_hash` 计算），**不用于**替代请求体序列化。

| # | 场景 | 输入 | 期望 |
|---|---|---|---|
| 1 | **字段顺序无关** | `{a:1,b:2}` vs `{b:2,a:1}` | `stableStringify` 输出**完全相同**，哈希相同 |
| 2 | 嵌套对象顺序无关 | `{x:{a:1,b:2}}` vs `{x:{b:2,a:1}}` | 输出相同（**递归**稳定，不是只排顶层） |
| 3 | 数组顺序**保留** | `[1,2,3]` vs `[3,2,1]` | 输出**不同**（数组有序，不得排序） |
| 4 | 数组内的对象 | `[{b:2,a:1}]` | 对象的键被排序，数组顺序保留 |
| 5 | 特殊字符 | `{"k":"a\"b\\c\nd\te\u0000f"}` | 转义与 `JSON.stringify` 一致，且跨平台字节一致（UTF-8） |
| 6 | 中文与 emoji | `{"k":"你好🙂"}` | UTF-8 编码后哈希稳定；**不得**被转成 `\uXXXX` 与原文混用不一致 |
| 7 | `undefined` / 函数 | `{a:1,b:undefined}` | `b` 被省略（与 `JSON.stringify` 一致），且不抛异常 |
| 8 | `null` 与缺失 | `{a:null}` vs `{}` | **输出不同**（`null` 是有效值，不得与缺失混淆） |
| 9 | 数字 | `{a:1}` vs `{a:1.0}` vs `{a:1e0}` | 输出相同（JS 数字统一） |
| 10 | **签名串拼接** | `POST /api/v1/heartbeat` + ts + nonce + body | 用 `§5.3` 伪代码算出已知向量，与服务端实现**逐字节相同** |
| 11 | **无 body 的哈希** | `sha256_hex("")` | 等于 `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`（§5.1 已给出前缀 `e3b0c442...b855`） |
| 12 | **原始字节校验** | 同一 body 对象，客户端 `JSON.stringify` 一次后原样发送 | 服务端用原始 buffer 算哈希，校验通过；若服务端反序列化后重算（键序变化）→ **校验失败**，此用例用于**回归该反模式** |
| 13 | `path_with_query` 原样 | `/api/v1/policy/current?account_id=acc_1001` | 含 query、**不做 URL 重编码**、不含 scheme/host |
| 14 | ts 固定 13 位 | `Date.now() + clockSkewMs` | 字符串化为 13 位；2100 年前不会变 14 位，但需断言格式 |
| 15 | nonce 唯一性 | 连续 1000 次生成 | 长度 16–32 位小写 hex，无重复；⚠️ **批量上报每次必须新生成**（§5.4） |
| 16 | **响应验签** | `"RESP" + status + path + request_nonce + server_time_ms + sha256(body)` | 与 §5.2 一致；**错误响应（402/409/4xx/5xx）也必须签名** |
| 17 | 验签失败行为 | 篡改响应体一个字节 | `verifyResponse` 返回 `bad_sign`；客户端**必须 fail-closed**（停止发送），且**不得**解析业务字段 |
| 18 | 常量时间比较 | 长度不同的签名 | 先用长度比较短路，再用 `crypto.timingSafeEqual`；**禁止**用 `===` 直接比 |

### 4.6 时间校准 `clock_skew_ms`

**规则**（`protocol.md` §1.3 / §5.3 / §5.4）：`ts = Date.now() + clockSkewMs`；`clockSkewMs` 由最近一次 `server_time_ms` 校准；容忍窗口 `sign_ts_tolerance_ms = 300000`（±5 分钟）。

|---|---|---|---|

| 2 | 本机慢 2 分钟 | 本机 = server − 120000 | `clock_skew_ms = +120000`；请求 `X-Lic-Ts = Date.now() + 120000` |
| 3 | 本机快 10 分钟 | 本机 = server + 600000 | `clock_skew_ms = -600000`（负值必须支持） |
| 4 | **恰好 ±5 分钟边界** | 偏离 = 300000 | ✅ 接受（容忍窗口是"超过"才拒） |
| 5 | 偏离 300001 | 偏离 = 300001 | ❌ `AUTH_TS_SKEW(401)` |
| 6 | 收到 `AUTH_TS_SKEW` 后的行为 | — | 用 `server_time_ms` 重算 `clockSkewMs`，**只重试一次**；第二次仍失败 → 停止发送 |
| 7 | 网络往返延迟 | 请求发出到响应 800ms | ⚠️ 校准应使用**响应到达时刻**（或扣除 RTT/2），不得直接用请求发出时刻，否则引入单向延迟偏差 |
| 8 | 时钟回拨 | 运行中系统时间被回拨 1 小时 | 时长类计算必须用**单调时钟**（`process.hrtime.bigint()`，§1.3），不受影响；`clock_skew_ms` 会在下次心跳被重新校准 |
| 9 | `clock_skew_ms` 的用途 | — | **仅用于填写上报的 `*_ms` 字段与签名 ts**；"该值本身仅作诊断"（§1.3），**不得**用于计费时长 |
| 10 | 进程重启后 | 从磁盘恢复 `clock_skew_ms` | 使用持久化值，直到下一次心跳校准；**不得重置为 0**（否则首包必被拒） |
| 11 | 校准值与本地时长混用 | 用 `Date.now()` 差值计算"引擎运行时长" | ❌ 错误实现：时钟回拨会算出负时长；必须用单调时钟 |
| 12 | `seq` 与时间的关系 | 同 session 内 `seq` 从 1 递增 | `seq` 是**独立的防重放通道**（§5.4），与 `clock_skew_ms` 无关；各通道（heartbeat/usage/sends/config_audit）**独立计数** |

### 5.1 ⚠️ 前置条件：必须用专门小号

> `shared/术语与选型基准.md` §5.2 原文：**⚠️ 请使用专门的小号做验证，不要用主号。** 验证过程会产生真实发送行为。

**硬性要求**：

| 项 | 要求 |
|---|---|
| 账号 | **专门注册的小号**，与商家正式运营账号完全隔离 |
| 手机号 | 小号绑定的手机号不得是主号绑定的号码 |
| 设备 | 使用专用 Chrome（`--user-data-dir=dy-main`），不改动商家日常浏览器 |
| 内容 | 测试回复内容必须**明显是测试**（如"测试回复-001"），避免被真实用户当成骚扰 |
| 对象 | 优先在本方自有视频/直播间下测试；必须在他人的内容下测试时，选择无实际用户的冷门内容 |

### 5.2 G-1 登录态可用性

### 5.3 G-2 自动回复成功率（连续 20 次）

**问题**：自动回复是否能连续 20 次成功且判定准确？

⚠️ **本项包含两个独立指标，必须分开记录，不得只记成功率**：
- **真实成功率** = 人工在抖音 App/网页上确认"回复真的出现了"的次数 / 20
- **判定准确率** = 系统判定与实际一致的比例，尤其要抓 **误报（谎报成功）** 与 **漏报（真成功却判失败）**

| 项 | 内容 |
|---|---|
| **前置** | 在小号自己的视频下预置 20 条评论（或用 20 个不同视频各 1 条），每条评论内容唯一且不重复（避免命中归一化后的重复匹配） |
| **步骤 1** | 对每条评论执行一次回复，**每次记录**：`send_id`、目标评论 ID、回复文案、`verdict`、`evidence.confirm_signal`、`evidence.platform_status_code`、`evidence.risk_control_signal`、`failure_reason`、耗时 |
| **步骤 2** | 20 次完成后，**逐条人工核对**：在抖音上打开对应视频，确认回复是否真的出现 |
| **步骤 3** | 计算：真实成功数 / 20；谎报数（判 `sent_confirmed` 但实际没出现）；漏报数（判 `failed`/`sent_suspected` 但实际出现了） |
| **通过判据** | ① 真实成功率 **≥ 18/20（90%）**；② **谎报数 = 0**（这是红线 2 的底线，一次都不允许）；③ 漏报数 ≤ 2；④ 每次成功都必须有 `confirm_signal=platform_response` 且 `platform_status_code=0` |
| **额外必测项** | 中途**强制制造一次空响应**（如在 DevTools 里拦截 `comment/publish` 返回空体），确认系统判为 `failed` + `risk_control_rejected` 且**不标记成功** |
| **失败的处置** | 若定位逻辑问题（找不到按钮/编辑器）→ 定位逻辑需重做；若判定问题（谎报）→ **立即停止验证**，这是红线 2 违反，必须先修判定 |

### 5.4 G-3 风控表现

**问题**：风控表现如何？

### 6.2 故障注入方法

| # | 故障 | 注入方式 | 期望行为 |
|---|---|---|---|
| 1 | **关闭标签页** | 手工关闭正在工作的标签页（或在 Chrome 里 `Target.closeTarget`） | `browser-host` 检测到目标消失 → 重建标签页 → 任务回到 `queued` **而非 `failed`**（`docs/架构说明.md` §三 ④）。⚠️ legacy 有"标签页存活检查"（`reply_worker.js:445-460`：比对 `/json/list` 里的 `webSocketDebuggerUrl`），新实现必须保留检测思路但用 `ws` 的重连机制做 |
| 2 | **重启 Chrome** | 关闭 Chrome 进程后重新启动（同一 `--user-data-dir`，登录态保留） | 检测到 CDP 连接断开 → 指数退避重连 → 重新获取 target 列表 → 恢复。**登录态不得丢失**（登录态在 profile 里） |
| 3 | **断网** | 断开网卡 2 分钟（或阻断授权中心域名） | ① 已发生的发送明细写入 `pending_sends.json`（**发送前**已生成 `send_id`）；② 使用只减不增的影子额度；③ 恢复后补报，按 `sent_at_ms` 升序分批（`protocol.md` §9.3）；④ **断网期间不重复发送** |
| 4 | **进程被杀** | `taskkill /F /PID <pid>`（模拟商家关窗口 / 系统重启） | ① 重启后 `sending` 态任务自动回收为 `queued`（legacy 思路见 `reply_worker.js:416-427`，⚠️ 但其 `:419-424` 有死代码缺陷 D-4，新实现不得复制）；② 已生成 `send_id` 的发送不重复发起；③ 本地审计不丢 |
| 5 | 授权中心服务端重启 | 重启服务端进程 | 客户端退避重试；恢复后未 ACK 明细按**原 `send_id`** 重发，唯一索引保证只扣一次（`protocol.md` 边界用例 11） |
| 6 | SQLite 忙 | 制造并发写 | 服务端返回 `SERVER_DB_BUSY`；客户端 1 秒后重试（§6.7） |

### 6.3 故障自愈的成功判据（S-2 自愈率 ≥ 95%）

```
自愈率 = 自动恢复的故障次数 / 注入的故障总次数
```

| 项 | 定义 |
|---|---|
| "自动恢复" | **无需任何人工操作**，系统在 **5 分钟内**回到正常处理任务的状态 |
| 计入分母 | 所有已注入且**期望可自愈**的故障（上表 1/2/3/5/6） |
| 不计入分母 | 需要人工介入的故障（如验证码、登录态失效、商家手工点急停）——**这些必须停下等人工**，不是自愈失败 |
| 通过阈值 | **≥ 95%**（72 小时内注入的故障里，自动恢复的比例） |
| 额外要求 | 每次恢复都必须留下可定位的记录：故障类型、检测时刻、恢复时刻、`stage`/`reason`。**"恢复了但不知道为什么"不算通过**（S-3） |

⚠️ **反例（legacy 的错误做法）**：`reply_worker.js:508,514` 用"连续 2 次失败就把 cdp 置空重连"的粗暴策略。它确实能恢复，但**没有归因、没有退避、没有上限**，且在验证码场景下会变成"重连 → 重试 → 再被拒"的循环。新实现必须是：**检测 → 归因 → 退避策略 → 重连 → 任务回退**，五步齐全。

### 6.4 幂等性验证（S-5）

> S-5：进程重启、重复上报、崩溃恢复不产生重复发送或重复扣费 → **零重复**。

| # | 场景 | 操作 | 通过判据 |
|---|---|---|---|
| 1 | **发送前杀进程** | 生成 `send_id` 并落盘后、真正发出请求前强杀 | 重启后：该 `send_id` 仍存在，**要么继续用它发送，要么放弃**；不得生成新 `send_id` 重发 |
| 2 | **发送后、上报前杀进程** | 拿到平台响应后、写审计前强杀 | 重启后：发送明细仍在 `pending_sends.json`（先落盘再发送的必然结果）；补报后**只计费一次** |
| 3 | **重复上报** | 手工对同一批 `send_id` 连续上报 10 次 | 服务端：首次 `billed`，其余 9 次 `duplicate:true`；余额只减一次（`protocol.md` 边界用例 1） |
| 4 | **跨天补报** | 昨天离线囤 12 条，今天恢复补报 | 按每条 `sent_at_ms` 所属自然日的等级与上限核算；超额部分 `policy_exceeded` 不扣费（边界用例 7） |
| 5 | **崩溃恢复后重复发送** | 在"已发出但未记录"的窗口内强杀（步骤 2），重启后由 `queued` 恢复 | ⚠️ **这是最危险的一条**：可能真的重复发送。判据：若发生重发，**必须**由 `send_id` 幂等保证**只计费一次**；同时记录该事件并优化"先落盘再发送"的时机 |
| 6 | **服务端重启** | 重启服务端后重发未 ACK 明细 | 状态全在 SQLite，唯一索引保证只扣一次（边界用例 11） |
| 7 | **重复的 `report_id`** | 同一 `report_id` 重发聚合上报 | `duplicate:true`，回放首次结果，不重复计入看板（§4.7） |
| 8 | **重复兑换卡密** | 同一卡密并发兑换 | 只有一个成功，另一个 `CREDIT_REDEEM_CODE_USED`（§4.13，`BEGIN IMMEDIATE` + 唯一索引） |
| 9 | **同批重复 `send_id`** | 一批内出现两条相同 `send_id` | 后者按幂等处理，**不得重复计费**（§6.2） |
| 10 | 本地审计重放 | 同一 `change_id` 重发配置审计 | `duplicate:true`，键 `(account_id, change_id)`（§4.9） |

## 八、测试入口与 CI

### 8.1 `node test/run.js` 的设计

**约束**：不引入第三方测试框架（白名单只有 `ws`）。用 Node 内置 **`node:test`**（本机实测 v24.18.0 可用）与 **`node:assert`**。

```js
// test/run.js
'use strict'
const { spawnSync } = require('node:child_process')
const fs = require('node:fs')
const path = require('node:path')

const ROOT = path.join(__dirname, '..')

// 分层定义：name 用于输出，dir 用于发现测试文件，optional 表示缺目录时不算失败
const LAYERS = [
  { id: 'L1', name: '单元测试',        dir: 'test/unit' },
  { id: 'L2', name: '契约测试',        dir: 'test/contract' },
  { id: 'L3', name: '离线 DOM 回归',   dir: 'test/dom' },
  { id: 'L4', name: '集成测试',        dir: 'test/integration', optional: true },
]

function collectTests(dir) {
  const abs = path.join(ROOT, dir)
  if (!fs.existsSync(abs)) return []
  return fs.readdirSync(abs)
    .filter((f) => f.endsWith('.test.js'))
    .map((f) => path.join(abs, f))
}

function main() {
  const only = process.argv[2]              // node test/run.js L3
  const summary = []

  for (const layer of LAYERS) {
    if (only && layer.id !== only) continue
    const files = collectTests(layer.dir)
    if (!files.length) {
      if (!layer.optional) summary.push({ ...layer, status: 'EMPTY', code: 1 })
      else summary.push({ ...layer, status: 'SKIP', code: 0 })
      continue
    }
    // 用子进程跑 node:test，隔离每个测试文件的全局状态
    const r = spawnSync(process.execPath, ['--test', ...files], {
      cwd: ROOT, encoding: 'utf8', stdio: 'inherit',
    })
    summary.push({ ...layer, status: r.status === 0 ? 'PASS' : 'FAIL', code: r.status || 0 })
    if (r.status !== 0) break        // 快速失败
  }

  console.log('\n' + '='.repeat(56))
  for (const s of summary) console.log(`${s.id} ${s.name.padEnd(14)} ${s.status}`)
  console.log('='.repeat(56))
  const failed = summary.some((s) => s.code !== 0)
  console.log(failed ? '❌ 存在失败项' : '✅ 全部通过（注意：L5 真机验证与 L6 长稳不在此入口内）')
  process.exit(failed ? 1 : 0)
}

main()
```

⚠️ **入口的输出必须显式声明"L5/L6 不在此入口内"**。原因见 §1.1：`node test/run.js` 全绿**绝不能**被理解为"功能完成"。`AGENTS.md` §6 的完成定义要求真机验证，而真机验证是人工过程。

**支持按层运行**：`node test/run.js L3`（改选择器时只跑回归）、`node test/run.js L1`（改算法时只跑单元）。

### 8.3 每次提交的最低测试要求

| 改动类型 | 最低要求 | 是否需真机验证 |
