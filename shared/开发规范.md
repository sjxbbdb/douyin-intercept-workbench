## 一、代码风格与组织

### 1.1 命名约定（全项目统一）

**结论：全项目统一 `snake_case`，包括局部变量与函数名。不混用 `camelCase`。**

理由（三条，均可在上游文档中查证）：

1. **协议字段是 `snake_case` 且不可改**。`shared/protocol.md` 开头即规定"全篇 JSON 字段统一 `snake_case`"，§5 的签名串又直接拼接这些字段。若代码用 `camelCase`，每个模块都要维护一层 `camelCase ↔ snake_case` 映射，映射写错就是**签名失败或字段丢失**，而签名失败按契约是 fail-closed 停机——代价极高。
2. **术语表与数据库字段已是 `snake_case`**：`account_day_index`、`policy_version`、`min_interval_ms`、`send_id`、`applied_limits`、`user_key_hash`。混用会出现"同一个概念两个写法"，而这正是旧代码契约漂移的起点。
3. **旧代码用 `camelCase`**（`awemeId`、`commentId`、`doneAt`），新代码是重写，必须一次性斩断，不能让两代风格在 `legacy/` 对照时混淆。**在 `legacy/` 之外出现 `awemeId` 这类写法视为缺陷。**

| 对象 | 约定 | 正例 | 反例 |
|---|---|---|---|
| 变量、参数、对象属性 | `snake_case` | `daily_max`、`clock_skew_ms` | `dailyMax`、`daily-max` |
| 函数、方法 | `snake_case`，动词开头 | `settle_send_batch()`、`verify_response()` | `settleSendBatch()` |
| 类 | `PascalCase` | `class BrowserHost` | `class browser_host` |
| 常量与枚举查找表 | `UPPER_SNAKE_CASE`（值仍是小写字符串） | `const ERROR_CODES = { ELEMENT_TIMEOUT: 'element_timeout' }` | `const errorCodes = {...}` |
| 模块文件名 | `kebab-case.js` 小写 | `browser-host.js`、`page-comment.js`、`stable-stringify.js` | `browserHost.js`、`BrowserHost.js` |
| 数据库表名 | 单数 `snake_case`；SQL 关键字大写 | `send_log(account_id, send_id, verdict)` | `SendLog`、`sendLogs` |
| 协议字段 | 一律照抄 `protocol.md`，**不得改名、不得加前缀** | `sent_at_ms`、`confirm_signal` | `sentAtMs`、`p_sent_at_ms` |
| 时间字段 | 统一 `_ms` 后缀，值是 Unix 毫秒整数 | `sent_at_ms`、`cooldown_until_ms` | `sent_at`、`sentAt` |
| 金额/积分字段 | 统一 `_milli` 后缀，整数 | `balance_milli`、`charged_milli` | `balance`、`charged` |
| 哈希类字段 | 统一 `_hash` 后缀 | `content_hash`、`user_key_hash` | `content`、`userKey` |
| 布尔字段 | 用形容词/分词，**禁止 `is_`/`has_` 前缀** | `sending_enabled`、`collect_only`、`applied`、`accepted` | `isSending`、`has_applied` |
| 私有内部函数 | 前置 `_`，且不得导出 | `_normalize_text()` | — |
| HTTP 头 / DOM 属性 | 照抄原文 | `X-Lic-Sign`、`data-e2e` | `x-lic-sign` |

### 1.2 文件与模块划分

| 约束 | 数值 | 说明 |
|---|---|---|
| 单文件行数上限 | **500 行**（硬上限 600） | 超过即拆分。旧 `reply_server/server.js` 达 800+ 行、混了路由/静态服务/子进程编排/队列，是 D-13 的成因之一 |
| 单函数行数 | **≤ 60 行**；嵌套深度 ≤ 4 层 | 超限说明职责混杂，先拆再写 |
| 单文件导出 | **≤ 12 个** | 导出爆炸通常意味着该模块应拆成"原语 + 编排"两层 |
| 圈复杂度 | ≤ 15 | 本项目大量 if-else 分支应改为查表（见错误码映射表写法） |

**模块划分原则（按职责，不按技术）**：

1. **一个模块只做一件事**。`safety/guard.js` 只管限额判定，不发起请求、不写盘、不打日志到文件；它返回判定结果，由调用方决定后续。
2. **依赖方向单向**：`adapters/ → platform/ → core/`，`license/ → shared/lib/`，`host/ → 全部`。**禁止反向 require**（`core/` 不得 require `adapters/`）。
3. **`legacy/` 不得被任何生产代码 `require`**（`shared/术语与选型基准.md` 目录约束）。它是只读行为规格参考。
4. **`license-server/` 与 `client/` 不得互相 require**，只能走 HTTP 契约；共享代码只允许放 `shared/lib/`。
5. **选择器只允许定义在 `client/platform/selectors.js`**；其他文件出现 `data-e2e` 字符串视为缺陷（S-4 要求改版时只改 1 个文件）。
6. **安全数值只允许来自服务端下发的 `policy`**；代码中出现 `10`/`25`/`30`/`70`/`12600` 这类限额常量视为缺陷（红线 1）。
7. **不写"万能工具"文件**：禁止 `utils.js`、`helpers.js`、`common.js`。工具函数必须按用途命名（`stable-stringify.js`、`atomic-write.js`、`mask.js`）。

### 1.3 CommonJS require 顺序

固定四段，段间空一行，段内按**变量名字母序**排列：

```js
// 1) Node 内置模块（必须带 node: 前缀）
const crypto = require('node:crypto')
const fs = require('node:fs')
const path = require('node:path')

// 2) 白名单第三方依赖（全项目只有 ws）
const WebSocket = require('ws')

// 3) 跨目录共享代码
const { ERROR_CODES, STAGES } = require('../../shared/lib/errors')
const { stableStringify } = require('../../shared/lib/stable-stringify')

// 4) 本项目内模块（相对路径，禁止 require 绝对路径）
const { atomicWriteJson } = require('./atomic-write')
const { build_canonical_request } = require('./sign')
```

**禁止**：`require` 绝对路径（旧代码 D-1 的根因）；`require` 时执行副作用（在模块顶层读写文件、发起网络请求、启动定时器）；条件 `require` 拼路径（`require(userInput)`）；动态 `import()`。

### 1.4 禁止事项（硬性）

| 禁止 | 说明 |
|---|---|
| TypeScript / JSX / 装饰器 / 类型注解 | 纯 JavaScript（CommonJS）。无构建步骤是"解压即用"分发的前提；运行 `node --check` 必须直接通过 |
| `eval` / `new Function` / `vm` | 包括"用 eval 解析配置"。`Runtime.evaluate` 的表达式是**发给 Chrome 的字符串**，与本地 `eval` 不同，属允许，但必须来自 `selectors.js` 或页面模型，不得拼接用户输入 |
| 白名单外依赖 | 白名单**只有 `ws`**。服务端零第三方依赖。见 §8 |
| `puppeteer-core` / `playwright` | 见 §8.2 |
| 硬编码绝对路径 | 一律 `path.join(WORKSPACE, ...)`，`WORKSPACE` 由 `REPLY_WORKSPACE` 解析。旧代码 5 文件 13 处硬编码 `D:\deep seek\` 导致 D-1 阻断级缺陷 |
| `try { } catch { }` 空捕获 | 见 §2.2。**本规范最重要的一条** |
| `process.exit(1)` 作为顶层异常处理 | 见 §2.6 |
| `rejectUnauthorized: false` | 生产强制校验 TLS 证书，禁止关闭 |
| 在日志/上报中出现禁用字段 | 见 §3.3、§7 |

## 二、错误处理规范

> 本章对应稳定指标 **S-3（任何失败都能定位到具体阶段与原因）**，是本项目最关键、也最容易被违反的规范。

### 2.1 统一错误对象结构

所有跨层传递的失败，必须是同一个结构（`shared/lib/errors.js` 唯一构造）：

```js
// shared/lib/errors.js
const STAGES = {
  SCHEDULE: 'schedule',        // 调度：额度/频控/急停/熔断判定
  OPEN_PAGE: 'open_page',      // 打开目标页/切换标签页
  EXPAND_PANEL: 'expand_panel',// 展开评论面板/输入区

  VERIFY: 'verify',            // 成功判定（嗅探平台响应）
  PERSIST: 'persist',          // 本地落盘

const ERROR_CODES = {

  NET_REFUSED: { stage: STAGES.REPORT, retry: RETRY_CLASS.TRANSIENT, backoff: true },
  SERVER_DB_BUSY: { stage: STAGES.REPORT, retry: RETRY_CLASS.TRANSIENT, backoff: true, max_retry: 3 },
  // —— 协议类（签名/版本，一律 fail-closed）——

  RESP_SIGN_INVALID: { stage: STAGES.REPORT, retry: RETRY_CLASS.SECURITY, halt: true },
  RESP_TS_SKEW: { stage: STAGES.REPORT, retry: RETRY_CLASS.SECURITY, max_retry: 1 },

  EMPTY_RESPONSE: { stage: STAGES.VERIFY, retry: RETRY_CLASS.PERMANENT, circuit: 'risk_control' },
  PLATFORM_REJECTED: { stage: STAGES.VERIFY, retry: RETRY_CLASS.PERMANENT, circuit: 'platform_reject' },
  PUBLISH_NOT_CAPTURED: { stage: STAGES.VERIFY, retry: RETRY_CLASS.TRANSIENT, max_retry: 1 },

class WorkbenchError extends Error {
  constructor(code, { stage, reason, context = {}, cause = null } = {}) {
    super(code)
    this.name = 'WorkbenchError'
    this.code = code                    // 大写 UPPER_SNAKE：本栈内错误码（与契约错误码同名同义，不自造）
```

**两条不同的命名空间，不得混用**：

| 命名空间 | 形态 | 来源 | 例 |
|---|---|---|---|
| 契约错误码 `code` | 大写下划线 | 只允许照抄 `protocol.md` §3.2 | `POLICY_VIOLATION`、`AUTH_REPLAY` |
| 本地归因码 `reason` | 小写下划线 | 本地实现，可扩充，必须在 `errors.js` 登记 | `selector_miss:comment_list`、`element_timeout`、`empty_response` |

`verdict` / `failure_reason` 的值是**闭集**，只能取 `protocol.md` §7.2 与 §7.4 的枚举；未知键会导致服务端拒绝整条上报。

### 2.2 ⚠️ 禁止空 catch（本项目最贵的一次教训）

**旧代码事实**：`reply_worker.js:490-494` 用 `try { ... fs.writeFileSync('D:\\deep seek\\replied_history.json', ...) } catch {}` 写入去重历史。由于 D-1 的硬编码路径在非原作者机器上不存在，写盘**每次都失败**，而异常被 `catch {}` 静默吞掉，调用方认为"已记录"：

```js
// ❌ 旧代码（reply_worker.js:490-494）——绝对禁止复制
try {
  let hist = []
  try { hist = JSON.parse(fs.readFileSync("D:\\deep seek\\replied_history.json", "utf8")); } catch {}
  if (!hist.includes(String(item.commentId))) {
    hist.push(String(item.commentId))
    fs.writeFileSync("D:\\deep seek\\replied_history.json", JSON.stringify(hist, null, 2), "utf8")
  }
} catch {}          // ← 去重历史从未落盘；同一评论会被重复回复，且无任何日志
```

**后果**：去重历史永远为空 → 同一评论被重复回复 → 触发平台风控 → 且因为没有任何日志，排障时找不到原因。**这就是"空 catch 把功能缺陷伪装成正常运行"的典型。**

**正确写法（三选一，禁止第四种）**：

```js
// ✅ 写法 A：失败必须升级为可归因错误，由调用方决定是否降级
async function remember_replied(comment_id) {
  try {
    await store.update('replied_history.json', (data) => {
      if (!data.comment_ids.includes(comment_id)) data.comment_ids.push(comment_id)
      return data
    })
  } catch (cause) {
    // 去重历史是"防重复回复"的安全前提，写不进去就不能假装成功
    fail('DISK_WRITE_FAILED', {
      stage: STAGES.PERSIST, reason: 'replied_history_write_failed',
      context: { comment_id_hash: hash(comment_id), file: 'replied_history.json' }, cause,
    })
  }
}

// ✅ 写法 B：确属可忽略的清理动作，必须显式声明忽略理由并计数（禁止裸 catch）
async function close_tab_quietly(target_id) {
  try { await browser_host.close_target(target_id) }
  catch (cause) {
    // 关闭失败不影响业务结果：标签页泄漏由 browser-host 的定期巡检回收
    metrics.count('cleanup_error', { target: 'close_tab' })
    log.warn('cleanup_failed', { stage: STAGES.OPEN_PAGE, reason: 'close_tab_failed', cause: cause.message })
  }
}

// ✅ 写法 C：可选功能缺失（如 Python 清洗脚本），走"显式跳过"而非吞异常
function try_load_optional_python_bridge() {
  try { return require_optional('scrapling_bridge') }
  catch { log.info('python_bridge_skipped', { reason: 'python_absent' }); return null }  // 有日志、有返回值
}
```

### 2.3 错误码分层与处理方式

| 层 | 典型码 | 谁能发现 | 处理方式 |
|---|---|---|---|
| **网络** | `NET_TIMEOUT` `NET_REFUSED` `SERVER_DB_BUSY` | `license/` HTTP 层 | 不计业务失败；指数退避重试；进入离线降级；**不改变本地额度与策略** |
| **协议** | `RESP_SIGN_INVALID` `AUTH_REPLAY` `AUTH_TS_SKEW` `LOGIN_PROOF_INVALID` | `license/sign.js` | **fail-closed**：记录安全事件 → 立即暂停发送 → 退避重试登录。**绝不认为余额充足、绝不认为策略放宽**（`protocol.md` §2.3） |
| **策略** | `POLICY_VIOLATION` `POLICY_SENDING_DISABLED` `POLICY_CIRCUIT_OPEN` `QUOTA_EXHAUSTED` | `safety/guard.js` | 本地拦截，**不发起发送**；写成 `audit_config_changes` 证据（`applied=false` + `reject_code`）；按 `cooldown_until_ms` 等待 |
| **计费** | 结算响应 `billing_status` | `license/reporter.js` | 只以服务端响应为准；`billed` 才减影子额度；`unbilled_insufficient_credit` **不得重试**、不得本地补扣 |
| **平台** | `EMPTY_RESPONSE` `PLATFORM_REJECTED` | `platform/publish-verifier.js` | `verdict=failed` + `risk_control_signal="empty_response"`；**不计费**；计入熔断判据 |
| **DOM 定位** | `SELECTOR_MISS` `ELEMENT_ZERO_SIZE` `ELEMENT_TIMEOUT` | `platform/` 页面模型 | 可重试 ≤3 次；`reason` **必须带选择器 key**（`selector_miss:comment_list`），这是 S-4 改版定位的唯一线索 |
| **落盘** | `DISK_WRITE_FAILED` | `host/store.js` | 重试 3 次；仍失败则该任务回退 `queued` 并告警，**不得进入下一步** |

### 2.4 阶段 + 原因：每个失败都必须可定位

每个任务在内存里维护一条阶段轨迹，任何失败都能回答"卡在哪一步、为什么"：

```js
// adapters/reply-comment.js（节选）
const steps = []
async function step(name, fn) {
  const t0 = process.hrtime.bigint()
  try {
    const value = await fn()
    steps.push({ stage: name, ok: true, cost_ms: Number(process.hrtime.bigint() - t0) / 1e6 })
    return value
  } catch (e) {
    steps.push({ stage: name, ok: false, cost_ms: Number(process.hrtime.bigint() - t0) / 1e6,
                 code: e.code || 'UNKNOWN', reason: e.reason || 'unknown' })
    throw e                                   // 不吞、不包装成新错误丢失 stage
  }
}

await step(STAGES.OPEN_PAGE, () => page.open(video_url))
await step(STAGES.EXPAND_PANEL, () => page.expand_comment_panel())   // note 帖在此抛 NOTE_POST_UNSUPPORTED
await step(STAGES.LOCATE, () => page.locate_comment(target))
await step(STAGES.INTERACT, () => page.type_and_submit(reply_text))
const evidence = await step(STAGES.VERIFY, () => publish_verifier.wait_for_platform_response())
```

失败时日志输出 `{ task_id, source_type, stage: 失败所在步, reason, steps }`，UI 直接显示"卡在 `expand_panel`，原因 `panel_not_expanded`"。

### 2.6 ⚠️ 顶层异常不得 `process.exit(1)`

**旧代码事实**：`reply_worker.js:530` 是 `})().catch((e) => { console.error("FATAL:", e.message); process.exit(1); })`——进程退出后**没有任何人重启它**，采集/回复静默停止，商家界面还在显示"运行中"。这直接违反 S-1（72 小时不崩溃）。

**要求**：捕获 → 归因（阶段 + 原因）→ **任务回退** → 继续运行。

```js
// host/main.js 顶层兜底（三层，缺一不可）
let shutdown_requested = false

process.on('uncaughtException', (err) => {
  log.error('uncaught_exception', { stage: 'top', reason: classify(err), stack: err.stack })
  recover_running_tasks('uncaught_exception')   // 把 sending 态任务回退 queued（带 attempt_seq）
  if (is_fatal(err)) shutdown_gracefully('fatal')  // 仅端口占用、磁盘只读等无法继续的情形
})

process.on('unhandledRejection', (reason) => {
  log.error('unhandled_rejection', { stage: 'top', reason: classify(reason) })
  recover_running_tasks('unhandled_rejection')
})

async function main_loop() {
  while (!shutdown_requested) {
    try { await tick() }
    catch (e) {
      log.error('tick_failed', { ...new WorkbenchError(e.code || 'UNKNOWN', e).to_log(), stack: e.stack })
      recover_running_tasks('tick_failed')      // 崩溃恢复：sending → queued，保留同一 send_id
      await sleep(backoff_next())               // 1s→2s→…→上限 60s，成功一次即复位
    }
  }
}
```

`recover_running_tasks()` 的硬要求：**回退时不得重新生成 `send_id`**。崩溃前已落盘的 `send_id` 必须复用，否则重发无法幂等、会被重复计费（红线 2）。

## 三、日志规范

### 3.1 级别与用途

| 级别 | 用途 | 生产默认 | 例 |
|---|---|---|---|
| `error` | 影响业务结果、需人工介入或已触发熔断 | 输出 | 落盘失败、验签失败、结算被拒 |
| `warn` | 异常但已自行处理、需要关注的趋势 | 输出 | 选择器重试后成功、退避重试、影子额度剩余 < 10% |
| `info` | 关键业务事件（一次发送的完整生命周期） | 输出 | `send_started` / `send_verified` / `batch_reported` |
| `debug` | 排障细节（CDP 命令、坐标、判定中间量） | **默认关闭**，`LOG_LEVEL=debug` 打开 | `selector_matched:comment_list` |

**禁止**：用 `console.log` 打业务日志（旧代码全库如此，无级别、无结构、无法过滤）。统一走 `shared/lib/log.js`；`console.*` 只允许出现在 CLI 交互输出（`license-server/cli.js`）。

### 3.2 结构化字段（每条日志必须齐全）

```js
// shared/lib/log.js —— 只允许这一个入口
const LEVELS = { error: 0, warn: 1, info: 2, debug: 3 }
const CURRENT = LEVELS[process.env.LOG_LEVEL] ?? LEVELS.info

function write(level, event, fields = {}) {
  if (LEVELS[level] > CURRENT) return
  const line = {
    ts_ms: Date.now(),                 // 仅诊断用；上报字段必须以校准后的时间为准
    level,
    module: fields.module || 'unknown',
    stage: fields.stage || null,       // STAGES 之一，S-3 的核心字段
    event,                             // 稳定的动词式事件名：send_started / selector_miss
    ok: fields.ok ?? null,             // 结果：true/false/null(不适用)
    cost_ms: fields.cost_ms ?? null,   // 耗时（用单调时钟算：process.hrtime.bigint()）
    code: fields.code || null,         // 契约错误码（如有）
    reason: fields.reason || null,     // 本地归因码
    ctx: fields.ctx || {},             // 最小必要上下文（已脱敏）
  }
  process.stdout.write(JSON.stringify(line) + '\n')   // 一行一个 JSON，便于 grep 与采集
}
module.exports = {
  error: (event, f) => write('error', event, f),
  warn: (event, f) => write('warn', event, f),
  info: (event, f) => write('info', event, f),
  debug: (event, f) => write('debug', event, f),
}
```

必备字段：`ts_ms` `level` `module` `stage` `event` `ok` `cost_ms` `code` `reason` `ctx`。缺 `stage` 的失败日志视为缺陷（S-3 不可验收）。

### 3.3 ⚠️ 脱敏要求（硬约束）

**绝不记录**：Cookie、`token`、`sign_key`、`privacy_salt`、密码、完整手机号、`sec_uid` 原文、评论原文、弹幕原文、回复内容原文、昵称、头像 URL、`conversation_id`/`room_id`/`video_id`/`comment_id` 原文、完整 URL。

```js
// shared/lib/mask.js —— 唯一允许的脱敏入口
const crypto = require('node:crypto')

function mask_id(value) {                       // 保留首尾各 4 位，用于人工比对
  const s = String(value ?? '')
  if (s.length <= 8) return '***'
  return s.slice(0, 4) + '***' + s.slice(-4)
}

function hash_prefix(value, salt) {             // 需要关联同一对象时用哈希前缀，不可反查
  return crypto.createHmac('sha256', salt).update(String(value)).digest('hex').slice(0, 12)
}

function mask_phone(value) {
  const s = String(value ?? '').replace(/\D/g, '')
  return s.length >= 11 ? s.slice(0, 3) + '****' + s.slice(-4) : '***'
}

function mask_text(value) {                     // 正文只留长度与哈希，绝不留内容
  const s = String(value ?? '')
  return { len: s.length, sha256_8: crypto.createHash('sha256').update(s).digest('hex').slice(0, 8) }
}

function mask_headers(headers) {                // 请求/响应头白名单：只留技术性字段
  const ALLOW = ['content-type', 'x-lic-server-ts', 'x-lic-ts', 'retry-after']
  const out = {}
  for (const [k, v] of Object.entries(headers || {})) {
    if (ALLOW.includes(String(k).toLowerCase())) out[k] = String(v)
    else out[k] = '[redacted]'                  // Authorization / X-Lic-Sign / Cookie 一律 redacted
  }
  return out
}

module.exports = { mask_id, hash_prefix, mask_phone, mask_text, mask_headers }
```

```js
log.info('send_verified', { stage: STAGES.VERIFY, ok: true,
  ctx: { send_id: mask_id(send_id), source_type: 'comment', content: mask_text(reply_text),
         target_hash: target_hash, platform_endpoint: 'comment/publish', platform_status_code: 0 } })

// ❌ 错误（含禁用字段，既违规又会进审计导致整条被拒）
```

### 3.4 日志轮转与保留

| 项 | 约定 |

## 四、客户端存储规范（硬约束）

### 4.1 ⚠️ 单写者（不可协商）

**只有 `client/host/` 主进程读写实例 JSON 文件。** `browser-host`、`platform`、`adapters`、`license`、UI 一律**不得** `require('node:fs')` 去碰实例数据文件，必须经 IPC 请求 host 代为读写。

**旧代码事实**：`reply_worker.js:479-481` 用"循环开头读到的陈旧 `q`"做全量覆写抢占任务，而 `reply_server/server.js:642-661` 同时在读-改-写追加新任务 → 抢单瞬间商家入队的新任务**被静默抹掉**（D-7）。同类问题还有 `live_config.json` 三写者、`scan_comments.js` 与 `pipeline.js` 同时全量覆写同一评论库（D-10）。根因都是**多进程无锁覆写同一个文件**。

```js
// client/host/store.js —— 唯一写入口
const fs = require('node:fs')
const path = require('node:path')
const { fail, STAGES } = require('../../shared/lib/errors')

const SCHEMA_VERSION = { 'reply_queue.json': 2, 'replied_history.json': 1, 'pending_sends.json': 2, 'policy.json': 1, 'license_state.json': 1 }
const cache = new Map()          // file → 最新内存态（单写者持有的唯一真相）
const chain = new Map()          // file → Promise 链，保证同文件写入串行化

function file_path(instance_dir, file) { return path.join(instance_dir, file) }

// 原子写：先写 .tmp-<pid>，fsync 后 rename 覆盖
function atomic_write_json(abs_path, obj) {
  const tmp = abs_path + '.tmp-' + process.pid
  const fd = fs.openSync(tmp, 'w')
  try {
    fs.writeFileSync(fd, JSON.stringify(obj, null, 2), 'utf8')
    fs.fsyncSync(fd)             // 必须先 fsync 再 rename，否则断电可能得到空文件
  } finally { fs.closeSync(fd) }
  fs.renameSync(tmp, abs_path)   // 同目录 rename 是原子操作；Windows 上也会覆盖已存在文件
}

function load(instance_dir, file) {
  const abs = file_path(instance_dir, file)
  const empty = { schema_version: SCHEMA_VERSION[file] }
  let data
  try { data = JSON.parse(fs.readFileSync(abs, 'utf8')) }
  catch (e) {
    if (e.code === 'ENOENT') { cache.set(abs, empty); return empty }   // 首次运行：不是错误
    // 损坏：备份现场后重建，绝不静默当成空文件（否则等于丢数据）
    fs.renameSync(abs, abs + '.corrupt-' + Date.now())
    fail('DISK_WRITE_FAILED', { stage: STAGES.PERSIST, reason: 'json_corrupt', context: { file } })
  }
  data = migrate(file, data)
  cache.set(abs, data)
  return data
}

function migrate(file, data) {
  const target = SCHEMA_VERSION[file]
  let v = Number(data.schema_version || 0)
  if (v > target) fail('DISK_WRITE_FAILED', { stage: STAGES.PERSIST, reason: 'schema_too_new', context: { file, v, target } })
  // 迁移链：逐版本升级，每一步必须是纯函数，禁止访问网络
  for (const step of (MIGRATIONS[file] || [])) {
    if (v === step.from) { data = step.up(data); v = step.to }
  }
  data.schema_version = target
  return data
}

// 读-改-写：永远以"最新内存态"为基准，mutator 是纯函数
function update(instance_dir, file, mutator) {
  const abs = file_path(instance_dir, file)
  const prev = chain.get(abs) || Promise.resolve()
  const next = prev.then(() => {
    const latest = cache.get(abs) || load(instance_dir, file)   // ← 先取最新，绝不用陈旧对象
    const draft = mutator(structuredClone(latest))
    atomic_write_json(abs, draft)                               // ← 再整体原子落盘
    cache.set(abs, draft)
    return draft
  })
  chain.set(abs, next.catch(() => {}))                          // 失败不阻断后续写入
  return next
}

module.exports = { load, update, atomic_write_json }
```

### 4.2 读-改-写的正确姿势与反例

```js
// ❌ 反例（旧代码 D-7 的形态）：拿陈旧快照全量覆盖，期间的并发修改被抹掉
```

**回退语义（S-5 关键）**：进程重启后，`sending` 态任务必须回退为 `queued`，且**保留原 `send_id` 与 `attempt_seq`**，`attempt_seq += 1`。重新生成 `send_id` 会导致同一发送被计费两次。

### 4.3 schemaVersion 与迁移策略

### 5.1 连接与 PRAGMA

### 5.2 ⚠️ 事务边界：扣费与流水必须在同一事务内

这是 `docs/架构说明.md` §五的硬约束，也是红线 2 的落地形态。**扣减余额、写 `send_log`、写 `credit_ledger` 三者必须原子完成**——否则会出现"扣了钱没流水"（无法对账）或"有流水没扣钱"（少收钱）。

```js
// license-server/domain/billing.js（对应 protocol.md §6.4 伪代码）
function settle_send_batch(acc, batch, now_ms) {
  const unit_milli = acc.credit_per_reply_milli
  const results = []

  db.exec('BEGIN IMMEDIATE')                  // 立即取写锁，避免升级锁失败
  try {
    for (const s of sort_by_sent_at(batch.sends)) {
      const prev = find_send(acc.account_id, s.send_id)
      if (prev && prev.verdict === 'sent_confirmed') { results.push(dup_result(s)); continue }
      if (prev && !is_upgrade(prev, s)) { results.push(reject_result(s, 'AUDIT_SEND_CONFLICT')); continue }

      const quota = day_quota(acc, s.source_type, s.sent_at_ms)
      const over_limit = quota.max === 0 || quota.used >= quota.max
      const billable = s.verdict === 'sent_confirmed'
        && s.evidence.confirm_signal === 'platform_response'
        && s.evidence.platform_status_code === 0
        && !over_limit && !acc.insufficient

      insert_send_log(s, over_limit)          // 明细永远留痕（审计优先于计费）
      let charged_milli = 0
      if (billable && acc.balance_milli >= unit_milli) {
        acc.balance_milli -= unit_milli
        charged_milli = unit_milli
        // ↓ 同一事务内：扣费 + 写台账，任一步失败整体回滚
        update_credit(acc.account_id, acc.balance_milli, now_ms)
        insert_ledger(acc.account_id, 'usage', -charged_milli, acc.balance_milli, s.send_id, now_ms)
      } else if (billable) {
        acc.balance_milli -= unit_milli        // §6.5 跨零点唯一一次透支
        charged_milli = unit_milli
        acc.insufficient = true
        update_credit(acc.account_id, acc.balance_milli, now_ms)
        insert_ledger(acc.account_id, 'usage', -charged_milli, acc.balance_milli, s.send_id, now_ms)
      }
      results.push(build_result(s, over_limit, charged_milli))
    }
    if (acc.balance_milli <= 0) mark_state(acc.account_id, 'exhausted')
    db.exec('COMMIT')
  } catch (e) {
    db.exec('ROLLBACK')                        // 必须回滚，绝不"部分成功"
    throw e
  }
  return results
}
```

**事务铁律**：

1. 事务内**禁止**任何 I/O：不得发 HTTP、不得写文件、不得 `await` 网络（`DatabaseSync` 是同步 API，混入异步会长时间持锁）。需要网络的步骤放到事务外，结果作为参数传入。
2. 一律用 `BEGIN IMMEDIATE`，不用裸 `BEGIN`（避免读锁升级失败导致 `SQLITE_BUSY`）。
3. 事务必须包在 `try/catch` 里，`catch` 中显式 `ROLLBACK` 后 `throw`。禁止 `catch { }`。
4. 事务内**禁止** `process.exit`。
5. SQLite 忙返回 `SERVER_DB_BUSY`(503)（`protocol.md` §3.2），客户端 1 秒后重试最多 3 次。

## 六、网络与协议实现规范

### 6.1 时间：一律 Unix 毫秒 `_ms`

- 所有协议时间字段以 `_ms` 结尾，值是整数（`protocol.md` §1.3）。
- **客户端墙上时间不可信**：每个响应带 `server_time_ms`，客户端维护 `clock_skew_ms` 并在填写任何 `*_ms` 前校准。

```js
// license/clock.js
let clock_skew_ms = 0
function sync_from_response(server_time_ms, sent_at_wall_ms) {
  clock_skew_ms = Number(server_time_ms) - sent_at_wall_ms        // 粗略校准
}
function now_ms() { return Date.now() + clock_skew_ms }           // 用于所有上报字段
function monotonic_ms() { return Number(process.hrtime.bigint() / 1000000n) }  // 用于耗时
```

**铁律**：`clock_skew_ms` 只用于"填写上报字段"；**时长计算一律用单调时钟**（`process.hrtime.bigint()`），绝不用 `Date.now()` 差值（会被系统时间调整、NTP 跳变污染）。自然日边界（日上限、等级天数）按 `stats_tz_offset_minutes`（默认 480 = UTC+8）划分，客户端不得用本地时区自行推算。

### 6.2 金额：整数 milli `_milli`

`1000 milli = 1 积分`。**禁止浮点**参与余额、单价、扣费、套餐积分的任何计算。

```js
// ❌ 浮点误差：0.1 + 0.2 !== 0.3，几十万次累加后余额与台账必然对不上
balance = balance - credit_per_reply           // 1.1 - 0.1 = 1.0000000000000002

// ✅ 整数 milli：唯一允许的形态
const unit_milli = policy.credit_per_reply_milli      // 1000
const charged_milli = unit_milli * confirmed_count    // 整数乘法
const replies_affordable = Math.floor(balance_milli / unit_milli)
```

展示时才除以 1000，且保留一位小数（`(balance_milli / 1000).toFixed(1)`）。`credit_per_reply` 可配范围 0.1–1000、步进 0.1，落库与传输**只出现 `credit_per_reply_milli`**。

### 6.3 HMAC 签名：请求与响应都要签

```js
// shared/lib/stable-stringify.js —— 签名用的确定性序列化
function stableStringify(value) {
  if (value === null || typeof value !== 'object') return JSON.stringify(value)
  if (Array.isArray(value)) return '[' + value.map(stableStringify).join(',') + ']'
  const keys = Object.keys(value).filter(k => value[k] !== undefined).sort()   // 递归按 key 升序
  return '{' + keys.map(k => JSON.stringify(k) + ':' + stableStringify(value[k])).join(',') + '}'
}
module.exports = { stableStringify }
```

**实现要求**：递归按 key 升序、无空格、不排序数组；`undefined` 键位丢弃（与 `JSON.stringify` 一致）；不处理循环引用（遇到即 `TypeError`，这属于 bug 而非数据）；**不做**数字归一化（`1.0` 与 `1` 序列化不同，调用方必须传整数）。

注意**两套用途不要混**：请求/响应签名串是对**原始字节**算 `sha256_hex`（`protocol.md` §5.1/§5.2），**不得反序列化后重新序列化再算哈希**；`stableStringify` 只用于 `login_proof`（§4.1）这类需要跨进程一致序列化的场景。

```js
// license/sign.js（客户端）—— 请求签名与响应验签
const crypto = require('node:crypto')
const sha256_hex = (b) => crypto.createHash('sha256').update(b).digest('hex')
const hmac_hex = (k, s) => crypto.createHmac('sha256', k).update(s, 'utf8').digest('hex')

function build_signed_request(method, path_with_query, body_object, ctx) {
  const raw_body = body_object === undefined ? '' : JSON.stringify(body_object)   // 只序列化一次
  const ts_ms = now_ms()                                                          // 已校准
  const nonce = crypto.randomBytes(8).toString('hex')                             // 每次请求必须新生成
  const canonical = [method.toUpperCase(), path_with_query, String(ts_ms), nonce,
                     sha256_hex(Buffer.from(raw_body, 'utf8'))].join('\n')
  return { raw_body, headers: {
    'Content-Type': 'application/json; charset=utf-8',
    'Authorization': 'Bearer ' + ctx.token,
    'X-Lic-Ts': String(ts_ms), 'X-Lic-Nonce': nonce,
    'X-Lic-Sign': hmac_hex(ctx.sign_key, canonical),
  }, nonce, path: path_with_query }
}

function verify_response(resp, ctx) {          // ⚠️ 校验通过前不得解析业务字段
  const got = resp.headers['x-lic-sign']
  const server_ts = Number(resp.headers['x-lic-server-ts'])
  if (!got || !Number.isFinite(server_ts)) return { ok: false, code: 'RESP_SIGN_MISSING' }
  if (Math.abs(now_ms() - server_ts) > ctx.sign_ts_tolerance_ms) return { ok: false, code: 'RESP_TS_SKEW' }
  const canonical = ['RESP', String(resp.status), resp.path, resp.nonce, String(server_ts),
                     sha256_hex(Buffer.from(resp.raw_body, 'utf8'))].join('\n')
  const a = Buffer.from(hmac_hex(ctx.sign_key, canonical), 'hex')
  const b = Buffer.from(got, 'hex')
  if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) return { ok: false, code: 'RESP_SIGN_INVALID' }
  return { ok: true, body: JSON.parse(resp.raw_body) }
}
```

⚠️ **客户端必须校验服务端响应签名**（`protocol.md` §2.3、§5.4）：

- 除 `POST /auth/login` 与 `GET /client/bootstrap`（这两处不签名）外，**所有响应都要验签**，**错误响应（402/409/4xx/5xx）也必须验签**——否则无法区分"服务端说余额不足/策略收紧"与"中间人伪造"。
- 验签失败 → `fail('RESP_SIGN_INVALID', { stage: STAGES.REPORT, retry: SECURITY })` → 记安全事件 → **按网络不安全处理，立即 fail-closed 暂停发送** → 退避重试登录。**绝不认为余额充足、绝不认为策略放宽。**
- 比较必须用 `crypto.timingSafeEqual`，且**先比长度**（长度不等会抛异常）。
- `login_proof` 用 PBKDF2 派生密钥（`pbkdf2Sync(password, 'dsh-login|'+account+'|'+device_id, 100000, 32, 'sha256')`），校验范围排除 `login_proof` 自身；失败则**拒绝登录且不落盘任何凭据**。

### 6.4 幂等键：`send_id` 必须在发送前生成并落盘

```
发送前：生成 send_id → 写入 pending_sends.json（原子写、fsync）→ 状态 marked_sending → 才发起发送
发送后：拿到平台响应 → 更新同一条记录（verdict / evidence）→ 等上报 ACK 后才删除
崩溃后：重启时 sending 态记录复用原 send_id，attempt_seq += 1，绝不重新生成
```

```js
// adapters/reply-comment.js（发送前的强制顺序）
const send_id = 's-' + crypto.randomUUID().replace(/-/g, '')       // 协议允许 uuid v4 或 32 hex
await store.update(instance_dir, 'pending_sends.json', (d) => {     // ① 先落盘
  d.sends.push({
    send_id, sent_at_ms: now_ms(), source_type: 'comment',
    target_hash, user_key_hash, user_key_type: 'sec_uid',
    verdict: 'pending', is_final: false, evidence: { confirm_signal: 'none' },
    failure_reason: null, attempt_seq: 1, applied_policy_version: policy.policy_version,
  })
  return d
})
await guard.assert_can_send('comment')                              // ② 再校验额度（防越权）
const evidence = await platform_send(...)                           // ③ 最后才真的发
```

**其他幂等键**：`batch_id`（每批上报唯一）、`report_id`（聚合上报唯一）、`change_id`（配置变更唯一）、`request_id`（兑换唯一）。`seq` 是**通道内自 1 递增**，`channel ∈ heartbeat/usage/sends/config_audit`，各通道独立计数；禁止复用 nonce（会被判 `AUTH_REPLAY`）。

⚠️ **`platform_endpoint` 是契约闭集，不等于"已验证可用"**：`protocol.md` §4.8 的白名单只有 `comment/publish`、`comment/reply`、`im/send`、`live/comment/send`，其中**仅 `comment/publish` 被 legacy 真机验证过**。私信与直播弹幕的真实接口路径片段与成功码字段必须先按 `shared/已知陷阱与平台知识.md` §3.5 的手工确认流程核实，再写进注册表，**禁止凭猜测填写**（猜错会让成功判定恒为 false，表现为"像风控"，实际是关键字写错）。扩大闭集必须先上线服务端支持，再提升 `min_client_version`。

### 6.5 超时、重试与退避

| 场景 | 超时 | 重试 | 退避 |
|---|---|---|---|
| CDP 命令 | 8–10 s（`Runtime.evaluate` 等长操作 10 s） | 1 次 | 立即 |
| 平台响应等待（`comment/publish`） | 10 s | **0 次**（空响应直接判失败） | — |
| 元素出现等待 | 每步 5–8 s，总预算 30 s | ≤3 次 | 1 s / 2 s / 4 s |
| HTTP 请求（业务接口） | 15 s | 按 §2.5 决策表 | 指数 1/2/4/8/…上限 60 s，**加 ±20% 抖动** |
| 心跳 | — | 持续 | 指数，上限 60 s；连续 3 次未成功判离线 |
| 登录 | 20 s | 是 | 指数；`AUTH_ACCOUNT_LOCKED` 按 `retry_after_ms` 倒计时 |
| 离线补报 | 30 s | 是 | 恢复后立即补报，单批 ≤ `audit_batch_max`(500) |

**退避必须加抖动**，否则多实例客户端会在同一时刻同时重试形成尖峰。`AUTH_TS_SKEW` **只允许重试一次**（先校准 `clock_skew_ms`），无脑重试会一直失败。**给商家的发送间隔随机化与这里的网络退避是两件事**，不得混用（发送间隔用对数正态分布，见 `safety/guard.js`）。

## 七、安全编码规范

### 7.1 ⚠️ 本地控制台必须绑 `127.0.0.1`

```js
// client/host/api.js
const HOST = process.env.REPLY_BIND_HOST || '127.0.0.1'      // ❌ 绝不是 '0.0.0.0'
if (HOST !== '127.0.0.1' && HOST !== '::1') {
  throw new Error('本地控制台只允许绑回环地址；如需局域网访问必须走授权中心，不得直接放开本机端口')
}
http.createServer(handler).listen(PORT, HOST, () => log.info('api_listening', { ctx: { host: HOST, port: PORT } }))
```

**旧代码事实**：`reply_server/server.js:673` `listen(PORT, "0.0.0.0")` + 零鉴权 + `server.js:195-198` `Access-Control-Allow-Origin: *`（D-6）。后果：**局域网内任何人可访问控制台；任意网页可跨站调用 `POST /api/reply` 直接以商家身份发出评论**。多商家场景下这是数据泄露与账号被滥用的入口。新实现必须同时满足：绑回环 + 会话鉴权 + CORS 白名单，三条缺一不可。

### 7.2 CORS 白名单

```js
const ALLOW_ORIGINS = new Set(['http://127.0.0.1:PORT', 'http://localhost:PORT', 'null'])  // 'null' 用于 file:// 载入的本地 UI
function apply_cors(req, res) {
  const origin = req.headers.origin
  if (!origin) return                                        // 同源或非浏览器请求
  if (!ALLOW_ORIGINS.has(origin)) { res.writeHead(403); res.end(); return }
  res.setHeader('Access-Control-Allow-Origin', origin)       // 回显具体来源，绝不写 '*'
  res.setHeader('Vary', 'Origin')
  res.setHeader('Access-Control-Allow-Methods', 'GET,POST,OPTIONS')
  res.setHeader('Access-Control-Allow-Headers', 'Content-Type,Authorization')
  res.setHeader('Access-Control-Allow-Credentials', 'true')
}
```

**禁止** `Access-Control-Allow-Origin: *`；禁止同时使用通配来源与 `Allow-Credentials: true`；写操作接口必须校验会话令牌 + **一次性 CSRF token**（自定义头，浏览器跨站无法伪造）。

### 7.3 密码：`crypto.scrypt` 加盐哈希

```js
// license-server/crypto/password.js
const crypto = require('node:crypto')
const N = 16384, r = 8, p = 1, KEYLEN = 32, SALTLEN = 16

function hash_password(plain) {
  const salt = crypto.randomBytes(SALTLEN)
  const hash = crypto.scryptSync(plain, salt, KEYLEN, { N, r, p })
  return `scrypt$${N}$${r}$${p}$${salt.toString('hex')}$${hash.toString('hex')}`
}
function verify_password(plain, stored) {
  const [algo, n, rr, pp, salt_hex, hash_hex] = String(stored).split('$')
  if (algo !== 'scrypt') return false
  const expect = Buffer.from(hash_hex, 'hex')
  const actual = crypto.scryptSync(plain, Buffer.from(salt_hex, 'hex'), expect.length, { N: +n, r: +rr, p: +pp })
  return actual.length === expect.length && crypto.timingSafeEqual(actual, expect)
}
```

**禁止**：明文入库、MD5/SHA1、可逆加密、`===` 比较哈希（必须 `timingSafeEqual`）。登录失败按账号维度计数，5 次锁 10 分钟；**账号不存在 / 密码错误 / 已停用 / 已到期必须返回不同错误码**（`AUTH_ACCOUNT_NOT_FOUND` / `AUTH_PASSWORD_WRONG` / `AUTH_ACCOUNT_DISABLED` / `AUTH_ACCOUNT_EXPIRED`）。

### 7.4 敏感配置走 `.env`

| 项 | 位置 | 是否入库 | 是否入日志 |
|---|---|---|---|
| `master_secret`（签名主密钥） | `.env` | 否 | 绝不 |
| 数据库路径、端口、时区偏移 | `.env` | 否 | 可以 |
| 商家密码哈希、`sign_key` 哈希、卡密哈希 | 数据库（**只存哈希**） | 是 | 绝不 |
| `token` / `sign_key` / `privacy_salt`（客户端） | `license_state.json`（受保护目录） | 不适用 | 绝不 |

`.env` 必须进 `.gitignore`；仓库只提交 `.env.example`（键名 + 占位值 + 注释，**不含真实值**）。启动时校验必需键存在，缺失时**明确报错列出缺失键名**（不得静默用默认密钥启动）。

### 7.5 子进程调用不得拼接 shell 字符串

```js
// ❌ 拼接字符串：路径含空格/特殊字符即出错，且可被注入
child_process.exec(`node ${WORKSPACE}\\reply_worker.js ${taskId}`)

// ✅ 用 execFile / spawn + 参数数组，shell: false（默认）
const { execFile } = require('node:child_process')
execFile(process.execPath, [path.join(WORKSPACE, 'client', 'adapters', 'reply-comment.js'), task_id],
         { cwd: WORKSPACE, shell: false, windowsHide: true, timeout: 60000 }, cb)
```

其他硬要求：子进程句柄必须由调度器持有（旧代码 D-10 因丢失句柄导致扫描任务**无法停止**，只能重启整个服务）；重复启动同一任务必须**幂等拒绝并提示**（旧代码 D-13 会静默杀掉前一次）；子进程崩溃必须归因并回退任务，不得让 `running:true` 永久卡死（D-11）。

### 8.2 明确排除 `puppeteer-core` / `playwright`

| 理由 | 说明 |
|---|---|
| 自动化指纹 | Puppeteer 会设置 `navigator.webdriver = true` 等特征，抖音风控可识别。本项目走裸 CDP + `--disable-blink-features=AutomationControlled` 的更可控路径 |
| 用不上已登录的商家账号 | Playwright/Puppeteer 默认启动**全新浏览器上下文**，用不上商家 Chrome 里已扫码登录的抖音账号；在自动化浏览器里重新登录**恰是风控最敏感的特征**。登录态真实可用是方案可行性的前提 |
| 交互原语要全部重写 | 现有 DOM 定位表达式围绕裸 CDP 的 `Runtime.evaluate` 编写，换到 `page.evaluate` 模型要重写全部交互原语——而这正是最值钱的部分 |
| 版本绑定与体积 | 绑定特定 Chrome 版本，增大分发体积 |

同理不引入：任何前端框架、任何 ORM、`better-sqlite3`（需编译原生模块，环境易失败；`node:sqlite` 已够用）。WebSocket 服务端（如需要）也用 `ws`，不自研。

### 8.3 Node 版本自检

```js
// 入口第一段代码，早于任何 require 业务模块
const MIN_NODE = [22, 5, 0]
const cur = process.versions.node.split('.').map(Number)
if (cur[0] < MIN_NODE[0] || (cur[0] === MIN_NODE[0] && cur[1] < MIN_NODE[1])) {
  console.error(`本程序需要 Node.js ≥ ${MIN_NODE.join('.')}（当前 ${process.versions.node}）。`)
  console.error('服务端需要内置 node:sqlite（Node 22.5 引入）。请升级后重试。')
  process.exit(2)                      // 唯一允许的 exit：环境不满足，明确告知而非崩溃
}
try { require('node:sqlite') }
catch { console.error('当前 Node 未提供 node:sqlite，请升级到 ≥ 22.5。'); process.exit(2) }
```

`process.exit` 仅允许出现在：Node 版本/依赖自检失败、强制升级页、`cli.js` 的一次性命令。**业务运行期禁止**（见 §2.6）。

## 九、提交与协作规范

### 9.1 分支策略

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 永远可运行、可打包 | 只接受经过评审的 PR；禁止直接推送 |
| `feat/<模块>-<简述>` | 新功能，如 `feat/safety-guard-tier` | 从 `main` 拉出，短生命周期（≤5 天） |
| `fix/<缺陷号>-<简述>` | 缺陷修复，如 `fix/d7-queue-race` | 引用缺陷编号（D-1~D-14 或新编号） |
| `docs/<文档名>` | 仅文档改动 | 不得夹带代码 |
| `chore/<简述>` | 构建、脚本、依赖 | 依赖改动必须附 §8.1 报备记录 |

**禁止**：把 `legacy/` 的改动混进任何分支（它是只读存档）；把 `node_modules`、`data/`、`instances/`、`license_state.json`、二维码、Cookie、登录态（`dy-main`）提交进仓库。

### 9.2 提交信息格式（Conventional Commits，中文正文）

```
<type>(<scope>): <简短描述>

<正文：为什么改，而不是改了什么>

<验证：跑了什么命令、结果如何>
<未验证：哪些没验证、需要什么条件>
```

`type` ∈ `feat` / `fix` / `docs` / `refactor` / `test` / `chore` / `perf`。`scope` 用目录名：`client/host`、`client/platform`、`license-server/billing`、`shared/protocol`。

```
fix(client/host): 消除回复队列的全量覆写竞态

旧实现在抢单时用循环开头读到的队列快照做全量覆写，商家在该瞬间入队的
新任务会被静默抹掉（基线缺陷 D-7）。改为单写者 store.js：以最新内存态
为基准 + 纯函数改动 + 原子写（.tmp-<pid> → rename）。

验证：node --check 全部通过；node test/run.js 全绿；
      test/store-race.test.js 模拟并发入队 200 次，零丢任务。
未验证：未在真机 Chrome 上跑端到端（需抖音测试账号）。
```

**禁止**的提交信息：`update`、`fix bug`、`修改`、`111`；把多件事塞进一个提交（一个提交只做一件事，便于回滚与追溯）。

### 9.3 每次改动的最低验证要求

```bash
# 1) 语法检查（改动涉及的每个文件都要过）
node --check client/host/main.js
node --check license-server/server.js
# 或一次跑全部
node test/check-syntax.js

# 2) 自测（项目统一入口）
node test/run.js

# 3) 空 catch 门禁（必须为 0）
node test/lint-empty-catch.js

# 4) 硬编码限额门禁（必须为 0 命中）
node test/lint-hardcoded-limits.js     # 扫描 client/ 与 license-server/ 中的 10/25/30/70/12600 等限额常量

# 5) 选择器集中度检查（data-e2e 只允许出现在 selectors.js）
node test/lint-selector-centralization.js
```

**验收标准**：上述 5 条全绿才算"代码写完"。**注意区分"代码写完"与"真机验证通过"**——涉及 CDP 的改动必须用真实抖音测试账号验证（见 `shared/AI协作开发指引.md` §5），未验证的必须在提交信息与汇报中显式声明。

### 9.4 代码评审关注点清单（本项目高危点）

| # | 关注点 | 一句话判定 |
|---|---|---|
| 1 | **红线 1：限额来源** | 代码里是否存在限额常量？是否存在"客户端把上限调高"的路径？`min_interval_ms` 是否只允许调**高**、`content_similarity_max` 是否只允许调**低**、`active_hours` 是否只允许调**短**？ |
| 2 | **红线 2：计费资格** | `verdict=sent_confirmed` 是否要求 `confirm_signal=platform_response` **且** `platform_status_code=0`？有没有任何路径把 DOM 现象（编辑器消失、节点出现）判成成功？空响应是否判 `failed` + `risk_control_signal="empty_response"`？ |
| 3 | **红线 3：审计值** | `policy_snapshot` 里是**实际生效值**还是用户设置值？`audit_config_changes` 是否记录了 `applied=false` + `reject_code`？有没有字段可能带出正文或隐私数据？ |
| 4 | **幂等** | `send_id` 是否在**发送前**落盘？崩溃恢复是否复用同一 `send_id`？批内是否有两条相同 `send_id`？`seq` 是否按通道独立递增？ |
| 5 | **错误处理** | 有没有空 catch？失败是否都带 `stage` + `reason`？顶层异常是否有人接管（不是 `process.exit(1)`）？ |
| 6 | **存储** | 写实例文件的是不是只有 `host`？是否原子写（`.tmp-<pid>` → fsync → rename）？是否存在用陈旧快照全量覆盖？ |
