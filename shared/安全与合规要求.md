> **涉及安全限制、审计、隐私、计费的实现，必须先读本文件。**

## 一、为什么安全机制是本产品的核心

### 1.1 一个必须正视的结构性矛盾

> **这个工具的价值来自"发得多"，而账号被封的原因也是"发得多"。**

这两个目标**根本对立**。任何试图同时最大化两者的设计都会失败。

### 1.2 由此确定的产品定位

> **「帮你控制发送节奏，让账号活得久」**

**不是**"发得越多越好"。

这个定位直接决定销售口径：**若以发送量为卖点，等于将客户导向封号风险**，后续的客户投诉、退款与口碑损失由渠道方承担。正确的卖点是**安全、可控、有数据、可长期稳定使用**。

### 1.3 商业模型与安全的利益一致性

本产品采用**按成功回复条数计费**（而非按小时）。这使得：

```
账号被封 → 发不出去 → 厂商也收不到钱
```

**厂商与商家的利益完全一致。** 因此厂商有动力协助客户维护账号状态，而不是鼓励提高发送量。

> 这是本产品区别于同类工具的可说明之处，也是安全机制能真正落地的商业基础。

## 二、🔴 红线 1：安全上限由服务端下发，客户端只能调低

### 2.1 要求

| 项 | 要求 |
|---|---|
| 权威来源 | `shared/protocol.md` §4.6 的 `tier_table`——**全系统唯一来源** |
| 硬编码 | **禁止**。限额、间隔、阈值、套餐积分、额度文案中的全部数字必须由 `tier_table` 实时推导 |
| 客户端权限 | **只能更保守**，不能更激进 |
| 越权处理 | 服务端返回 `POLICY_VIOLATION(409)` + `detail{field, reported, allowed, policy_version}`，**并记入审计** |
| 观察期 | 第 1–3 天 `sending_enabled=false` / `collect_only=true`，日上限为 **0**，只采集不发送，**客户端不可跳过** |

### 2.2 "只能更保守"的四个判定方向

⚠️ 这是最容易实现错的地方。四个方向必须**分别**校验：

| 参数 | 方向 | 说明 |
|---|---|---|
| `daily_max` | **只能调低** | 上报值 > 策略值 → 越权 |
| `min_interval_ms` | **只能调高**，且必须落在 `min_interval_ms_range` 内 | 间隔越短越激进 |
| `content_similarity_max` | **只能调低** | ⚠️ 注意：阈值越低越严格，所以"调低"是更保守 |
| `active_hours` | **只能调短**，不得延长或新增窗口 | 默认单窗口 `08:00–23:00` |

> ⚠️ `content_similarity_max` 的方向最容易弄反。正确语义：**与近期已发内容的相似度"超过"该值即拒绝发送**。所以 `0.85` 表示"超过 85% 拒绝"；把阈值改成 `0.70` 是**更严格**（更容易拒绝），即更保守。

### 2.3 等级与放量曲线

| 等级标识 | 阶段 | 天数 | 评论/天 | 弹幕/天 | 私信/天 |
|---|---|---|---|---|---|
| `observation` | 观察期 | 1–3 | **0** | **0** | **0** |
| `warm_up` | 预热期 | 4–7 | 10 | 10 | 3 |
| `ramp_up` | 爬坡期 | 8–14 | 25 | 25 | 8 |
| `stable` | 稳定期 | 15+ | 30 | 30 | 10 |

**日上限合计**：0 / 23 / 58 / **70**。稳定期合计 70 是套餐积分的折算基数。

等级由 `account_day_index`（账号首次启用后的第几天）推导，**客户端不得自行提升**。

### 2.4 观察期的实现要求

观察期是**最有效的防封措施**（新号满速发送是封号第一诱因）。必须保证：

- `review_batch` 类接口在观察期返回**空批次**
- 发送执行层在观察期**拒绝任何发送**
- 界面明确显示"当前处于观察期，仅采集线索，第 N 天开始可发送"
- **不存在任何跳过观察期的入口**（包括隐藏入口、配置文件、命令行参数）

### 2.5 其他硬性护栏（不可关闭）

| 护栏 | 要求 |
|---|---|
| **频控** | 按渠道独立限额 + **随机化间隔**（对数正态，不得固定间隔）+ 操作延迟随机化 |
| **活跃时段** | 默认 08:00–23:00 单窗口，每天随机起止 |
| **内容相似度** | 超过阈值即拒绝发送 |
| **熔断** | 递进式：**30 分钟 → 1 小时 → 停到次日**。⚠️ 旧代码仅 sleep 60 秒继续，**不足**，风控已被触发 |
| **全局急停** | 界面常驻按钮，点击后**立即**停止所有发送 |
| **验证码** | 停止并提示人工处理，**绝不做绕过** |
| **同用户冷却** | 同一用户 N 小时内只回复一次（默认 24 小时），`N` 可配 |

## 三、🔴 红线 2：只对平台确认成功的发送计费

### 3.1 计费资格的完整判据

一条发送要计费，必须**同时**满足以下全部条件：

```
① verdict = sent_confirmed
② confirm_signal = platform_response        ← DOM 判断不算
③ platform_status_code = 0
④ 未超当日策略上限
⑤ 该 send_id 未计费过（幂等）
```

**任一不满足 → 不计费**，并在 `send_log` 中记为 `billing_status = unbilled_*`。

### 3.2 ⚠️ 为什么 `confirm_signal` 必须是平台响应

这是本项目最容易出错、后果最严重的地方。

| 判据 | 可信度 | 说明 |
|---|---|---|
| `platform_response` | ✅ **可信** | 拿到平台接口的响应体且 `status_code = 0` |
| `dom_stable` | ❌ **不可用于计费** | DOM 上"看起来发出去了"。旧代码曾用"编辑器消失"判定成功，结果**把页面崩溃记为已发送** |
| `none` | ❌ | 未取得任何确认信号 |

**实现要求**：

- 用 CDP `Network` 域**被动嗅探**平台接口响应（`Network.requestWillBeSent` 筛目标接口 → `Network.getResponseBody` 取响应体）
- **空响应 = 风控拒绝**，不得标记成功
- DOM 观察只能用于"继续下一步"，**绝不能作为成功判据**

### 3.3 `send_id` 的生成时机

> ⚠️ **必须在发送前生成并落盘。**

| 时机 | 后果 |
|---|---|
| ❌ 发送成功后生成 | 崩溃或断网后无法幂等 → **重复发送、重复计费** |
| ✅ **发送前生成并落盘** | 崩溃后重启可识别"这条可能已发出"，补报时复用同一 `send_id` |

### 3.4 余额不足时的处理

采用**部分扣费**：按 `sent_at_ms` 升序扣到耗尽，跨零点的那一条全额入账（最多透支一条），其余落 `send_log` 但 `billing_status = unbilled_insufficient_credit`，**不扣费、充值后也不补扣**。

> 理由与替代方案详见 `shared/protocol.md` §6。若改为整批拒绝，必须同步放大 `pending_sends` 上限，否则会形成重试风暴。

### 3.5 停机语义

余额 `≤ 0` → 服务端拒绝心跳续期 → 客户端**1 分钟内**进入暂停态并提示"积分不足，请联系客服充值"。

语义是**"禁止发送"**，不是"停止计时"。

## 四、🔴 红线 3：审计必须记录真实生效的策略值

### 4.1 为什么这条是责任划分的分水岭

客户账号被封后来找你，会问：**"你做了什么来防止这件事？"**

如果你答不上来，免责条款就是空的。**免责能力来自可举证的证据，不来自免责条款。**

需要能回答的三个问题：

1. 该账号在**事发当时实际生效**的策略是什么？
2. 用户是否**主动调高过**配置？
3. 系统是否**拒绝过**越权尝试？

> ⚠️ **只记录"用户设置值"无法回答这些问题。** 很多工具纠纷时自证失败，正是因为只记了设置值，没记执行值。必须记录"用户设了 10、系统允许 10、实际发了 10"三者可交叉验证。

### 4.2 两类审计上报

#### 4.2.1 发送明细（`POST /api/v1/audit/sends`）

| 字段 | 说明 |
|---|---|
| `send_id` | 幂等键与计费键 |
| `sent_at_ms` | 发送时刻（已按 `clock_skew_ms` 校准到服务端时间轴） |
| `source_type` | `comment` / `live_danmaku` / `dm` |
| `target_hash` | 目标哈希（视频/直播间/会话） |
| `user_key_hash` + `user_key_type` | 对方用户哈希与类型，**绝不上传原始 `sec_uid`** |
| `content_hash` | 回复内容哈希，**绝不上传原文** |
| `verdict` | `sent_confirmed` / `sent_confirmed_dom` / `rejected` / `skipped` / `failed` |
| `evidence` | `confirm_signal`、`platform_endpoint`（**闭集白名单**）、`platform_status_code`、`observed_at_ms` |
| `failure_reason` | 失败归因码 |
| `policy_snapshot` | **实际生效的策略版本与生效值** |
| `applied_policy_version` | 生效策略版本号 |

#### 4.2.2 配置变更（`POST /api/v1/audit/config-changes`）

| 字段 | 说明 |
|---|---|
| `change_id` | 变更 ID |
| `changed_at_ms` | 变更时刻 |
| `source` | `user` / `server_policy` / `default` |
| `actor` | 操作者 |
| `field_key` | 变更字段（如 `limits.dm.daily_max`） |
| `old_value` / `new_value` | 变更前后值 |
| `applied` | 是否实际生效 |
| `reject_code` | 被拒时的错误码（如 `POLICY_VIOLATION`） |
| `policy_version` | 当时策略版本 |

### 4.3 双写与不可篡改

- 审计记录**本地与服务端双写**
- 客户端**不可篡改服务端副本**（服务端以 `report_id` / `send_id` 幂等，接收时间为权威时间 `received_at`）
- 服务端须提供**按账号导出**能力，用于纠纷举证（`audit export` 命令）

### 4.4 服务端取证数据来源

服务端须能据以下数据重建事实：`send_log`、`audit_event`、`policy_ack_log`、`policy_history`、`ledger`、`usage_report`。

## 五、隐私边界（强制）

### 5.1 只传哈希与计数

| 可上传 | 禁止上传 |
|---|---|
| 计数类指标 | 评论原文 |
| 目标/用户/内容**哈希** | 回复内容原文 |
| 策略版本与生效值 | `sec_uid` 原文 |
| 判定结果与归因码 | 昵称、头像 URL、手机号 |
| 时间戳 | Cookie / Token / 密码 |

### 5.2 哈希与脱敏实现要求

- 使用 `crypto.createHmac` + 服务端下发的 `privacy_salt`，**不得用无盐哈希**（否则可被彩虹表反查）
- `privacy_salt` 有版本号（`privacy_salt_version`），支持轮换
- 日志同样脱敏（见 `shared/开发规范.md` §三）

### 5.3 `platform_endpoint` 是闭集白名单

只允许上报**路径片段**（如 `comment/publish`、`im/send`），**禁止完整 URL 与域名**（避免泄露会话信息）。

## 六、本地安全（客户端）

| 项 | 要求 | 理由 |
|---|---|---|
| 绑定地址 | 本地 API **必须绑 `127.0.0.1`** | ⚠️ 旧代码绑 `0.0.0.0`，导致局域网内任何人可访问控制台 |
| CORS | **白名单**，不得用 `*` | ⚠️ 旧代码用 `*` + 零鉴权，导致**任意网页可跨站调用接口代替商家发出评论** |
| 鉴权 | 本地 API 需要会话令牌 | 同上 |
| 敏感文件权限 | 令牌、签名密钥、Chrome 配置目录不可被其他用户读取 | — |
| 密码存储 | 服务端 `crypto.scrypt` 加盐哈希 | 禁止明文或可逆加密 |
| 子进程 | 不得拼接 shell 字符串 | 命令注入 |

## 七、渠道与终端客户的责任约定

> 以下为**产品层面的设计要求**，用于把责任划分做成可举证的事实。
> ⚠️ **不构成法律意见。** 正式条款请由法务或律师定稿。

### 7.1 技术层：默认安全 + 不可绕过

| 措施 | 举证意义 |
|---|---|
| 默认档位为半自动 | 厂商默认不自动发送 |
| 观察期与放量曲线客户端不可关闭 | 厂商**主动限制**了新号风险 |
| 上限有硬顶，越权被拒并留痕 | 厂商**拒绝提供**无限量能力 |
| 风险摘要持续提示 | 厂商持续告知，非一次性签字 |

### 7.2 协议层：必须明确告知的内容

- 本工具**降低风险但不消除**账号被封、被限流、内容被下架的可能性
- 因平台判定、平台规则变更导致的账号处罚与业务损失，厂商不承担赔偿责任
- **强烈建议使用专门账号，不要使用主号**
- 禁止改变工具用途
- 用户确认其使用行为符合平台规则与法律法规

### 7.3 商业层：禁止与建议

| 禁止 | 建议 |
|---|---|
| ❌ 承诺"保证不封号"（这是最容易反噬的表述，须在**全部文案、销售话术、界面**中禁止） | ✅ 承诺"持续更新风控策略"（这是厂商能实际做到的） |
| ❌ 承诺发送量 | ✅ 建立封号补偿策略（如核实后赠送积分），把纠纷前置化解 |

### 7.4 额度文案的强制展示

`quota_notice.headline` 与 `detail` **必须原样展示**在四处：**套餐展示页、充值页、首次登录弹窗、余额不足提示**。不得改写、折叠或隐藏。

核心信息：**买了套餐 ≠ 无限发送；日上限才是量级约束；未用完额度不顺延。**

## 八、禁止用途

以下行为导致授权**立即终止**，已支付费用不予退还：

| 禁止行为 | 说明 |
|---|---|
| 违法违规内容 | 诈骗、赌博、色情、传销等 |
| 骚扰与恶意刷屏 | 对同一对象反复骚扰、无差别批量骚扰 |
| 冒充他人 | 冒充他人身份、官方账号、平台工作人员 |
| 规避平台风控 | 绕过验证、破解限制、伪造客户端数据 |
| 超范围转售 | 转卖、出租、共享授权给约定范围外第三方 |
| 逆向与篡改 | 逆向客户端、破解额度校验、篡改留痕数据 |

## 九、实现自检清单

实现完成后逐项确认：

**红线 1**
- [ ] 全局搜索不到硬编码的限额/间隔/阈值字面量（测试与文档除外）
- [ ] 四个"只能更保守"方向**分别**有校验，且 `content_similarity_max` 方向正确
- [ ] 观察期返回空批次且发送层拒绝，且**无任何跳过入口**
- [ ] 越权尝试被拒并留下 `POLICY_VIOLATION` 审计记录
- [ ] 套餐积分与额度文案由 `tier_table` 实时推导

**红线 2**
- [ ] 成功判定依据是平台响应体，**不是 DOM**
- [ ] 空响应被判为风控拒绝
- [ ] `send_id` 在发送前生成并落盘
- [ ] 伪造 `confirm_signal: "dom_stable"` 的上报**不计费**
- [ ] 同一 `send_id` 重复上报 10 次只扣 1 条
- [ ] 被风控拒绝的发送不计费且台账无记录

**红线 3**
- [ ] 审计含 `policy_snapshot`（生效值 + 版本号），不只设置值
- [ ] 配置变更审计含 `source` 与 `applied`/`reject_code`
- [ ] 全部上报字段经过脱敏检查，无原文、无 `sec_uid` 原文
- [ ] 服务端可按账号导出完整审计记录
- [ ] 篡改客户端本地文件不影响服务端记录

**本地安全**
- [ ] 本地 API 绑 `127.0.0.1`
- [ ] CORS 为白名单
- [ ] 本地 API 有鉴权

**其他**
- [ ] `quota_notice` 在四处原样展示
- [ ] 全部文案中无"保证不封号"类表述
