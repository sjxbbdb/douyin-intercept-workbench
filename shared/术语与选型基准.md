## 一、术语表

> 本项目术语较多，且部分术语在旧代码与需求文档中含义不同。**实现前请统一按下表理解。**

### 1.1 账号相关（注意区分三个"账号"）

| 术语 | 英文/字段 | 含义 | 易混淆点 |
|---|---|---|---|
| **商家账号** | `account` / `account_id` | 由我方（厂商）创建并下发的**工作台登录账号**，格式为账号+密码。商家用它登录客户端。 | ⚠️ **不是**抖音账号 |
| **抖音账号** | 无固定字段名，客户端本机 | 商家自己的抖音账号，登录在专用 Chrome 中。工具以它的身份操作。 | ⚠️ **不是**工作台账号 |
| **管理员** | `admin` | 厂商侧运营人员，登录授权中心管理后台，开号、充值、看板。 | 与商家账号分离 |
| **设备** | `device_id` | 一台安装了客户端的电脑。同账号默认允许 1 台在线，超限踢最早会话。 | — |

### 1.2 安全与限额（本项目最核心的术语）

| 术语 | 字段 | 含义 |
|---|---|---|
| **安全策略** | `policy` | 服务端权威下发的限额规则集合。客户端**只能调低不能调高**。 |
| **策略版本** | `policy_version` | 策略的整数版本号。改策略即递增。所有审计记录必须携带。 |
| **账号等级** | `account_tier` | `observation` / `warm_up` / `ramp_up` / `stable`，按账号启用后的天数自动推进。 |
| **账号天数索引** | `account_day_index` | 账号从首次启用算起的第几天（从 1 开始）。等级由它推导。 |
| **观察期** | `observation` | 第 1–3 天。**日上限为 0，只采集不发送。** 客户端不可跳过。 |
| **预热期** | `warm_up` | 第 4–7 天。评论 10 / 弹幕 10 / 私信 3（每日）。 |
| **爬坡期** | `ramp_up` | 第 8–14 天。评论 25 / 弹幕 25 / 私信 8。 |
| **稳定期** | `stable` | 第 15 天起。评论 30 / 弹幕 30 / 私信 10。 |
| **等级表** | `tier_table` | 上述四级限额的完整表。**全系统唯一来源**，见 `shared/protocol.md` §4.6。 |
| **禁发标记** | `sending_enabled` / `collect_only` | 观察期下为 `false` / `true`。 |
| **最小间隔** | `min_interval_ms` | 同一渠道两次发送之间的最小毫秒数。按渠道不同（见下）。 |
| **活跃时段** | `active_hours` | 允许发送的时间窗口，默认 `08:00–23:00` 单一窗口。客户端只能调更短。 |
| **内容相似度上限** | `content_similarity_max` | 与近期已发内容的相似度**超过**该值即拒绝发送（0.85 = 超过 85% 拒绝）。⚠️ 注意方向，不得反转。 |
| **熔断** | `circuit_breaker` | 检测到异常（验证码、连续失败、风控拒绝）时自动暂停发送。分 30 分钟 / 1 小时 / 停到次日三级递进。 |
| **策略越权** | `POLICY_VIOLATION` | 客户端上报的配置**比服务端策略更激进**（上限更高、间隔更短、阈值更高、时段更长）。服务端拒绝。 |
| **急停** | `pause_engine` | 全局一键停止发送。界面常驻按钮。 |

**按渠道的最小间隔**（`shared/protocol.md` §4.6 `min_interval_ms_range`）：

| 渠道 | 允许范围 | 稳定期取值 |
|---|---|---|
| `comment` 评论 | 60000 – 180000 ms | 60000 |
| `live_danmaku` 直播弹幕 | 30000 – 90000 ms | 30000 |
| `dm` 私信 | 300000 – 900000 ms | 300000 |

> **私信的限额与间隔都远严于评论**，因为抖音对陌生人私信的管控显著更严。这不是产品设计选择，是平台规则。

### 1.3 计费相关

| 术语 | 字段 | 含义 |
|---|---|---|
| **积分** | `credit` / `balance` | 预付额度。用整数计，内部用 `_milli` 后缀表示千分之一单位避免浮点误差。 |
| **条数单价** | `credit_per_reply` | 每条成功回复消耗的积分，默认 1。 |
| **成功发送** | `sent_confirmed` | **必须**拿到平台响应且 `platform_status_code = 0`。DOM 判断不算。 |
| **确认信号** | `confirm_signal` | `platform_response`（可信）/ `dom_stable`（**不可用于计费**）/ `none`。 |
| **发送明细** | `send` / `send_id` | 一条发送记录。`send_id` 是幂等键与计费键，**必须在发送前生成并落盘**。 |
| **台账** | `ledger` | 只增不改的积分流水。 |
| **套餐** | `plan` | 名称 / 积分 `credits` / 有效天数 `valid_days` / 价格。⚠️ `hours` 字段已废弃，恒为 `null`。 |
| **额度提示** | `quota_notice` | 必须原样展示的文案对象，用于说明"套餐 ≠ 无限发"。由策略表实时生成。 |

### 1.4 采集与线索

| 术语 | 字段 | 含义 |
|---|---|---|
| **线索** | `lead` | 从互动中沉淀的意向客户记录。 |
| **命中** | `hit` | 内容命中关键词的一次事件。 |
| **三渠道 / 三来源** | `source_type` | `comment`（视频评论）/ `live_danmaku`（直播弹幕）/ `dm`（私信）。**三者限额独立**。 |
| **sec_uid** | `sec_uid` | 抖音用户的安全 ID，构造用户主页 URL 必需。⚠️ 直播弹幕 DOM 中常被脱敏为 `*****`，取不到时该线索标记 `not_locatable`。 |
| **地域精度** | `regionPrecision` | 评论 IP 归属地的精确程度。 |
| **图文帖** | note post | 抖音图文内容（`/note/<id>`），评论区是右侧小浮层。⚠️ 旧版不支持回复该类，标记 `note_post_panel_unsupported`。 |

### 1.5 CDP 与浏览器

| 术语 | 含义 |
|---|---|
| **CDP** | Chrome DevTools Protocol。通过 WebSocket 驱动 Chrome。 |
| **专用 Chrome** | 工具启动的 Chrome 实例，使用独立 `--user-data-dir`（`dy-main`），不影响商家日常浏览器。**登录态就在这里，是方案可行性的前提。** |
| **调试端口** | `--remote-debugging-port`，默认 9222。多实例时按 `9222 + N` 分配。 |
| **browser-host** | 目标架构中的模块：**独占**一条 CDP WebSocket，其他模块经 IPC 请求页面操作。 |
| **target / 标签页** | Chrome 的一个页面。旧代码有"标签页存活检查"逻辑。 |
| **可见元素** | 非零尺寸且在视口内的元素。⚠️ 页面上常同时存在隐藏与可见两套结构，**只能用可见的**。 |

### 1.6 架构术语

| 术语 | 含义 |
|---|---|
| **授权中心** | `license-server/`。厂商侧服务端。 |
| **客户端** | `client/`。商家本机程序。 |
| **实例** | `instances/<账号ID>/`。一个抖音账号对应一份隔离的数据与 Chrome 配置。客户端可管多实例。 |
| **单写者** | 同一份数据只允许一个进程写入。这是消灭旧代码竞态缺陷的根本手段。 |
| **原子写** | 写临时文件再 rename，避免写入中断产生半截文件。 |

|---|---|

## 三、技术选型与理由

### 3.1 运行时与语言

| 项 | 选型 | 理由 | 约束 |
|---|---|---|---|
| Node.js | **≥ 22.5** | 服务端需要内置 `node:sqlite`（22.5 引入）。客户端启动时**必须自检版本**并给出明确提示，不得直接崩溃 | 客户端与服务端同要求 |
| 语言 | **纯 JavaScript（CommonJS）** | 无构建步骤，便于"解压即用"分发；商家机器不需要装构建工具 | 不用 TypeScript、不用 JSX、不用装饰器 |
| 模块系统 | CommonJS（`require`） | 与服务端 `node:sqlite` 及现有代码风格一致 | — |

> **若你决定引入 TypeScript**：需要自行承担构建步骤与分发包变化，并更新本文件与 `README-DEV.md`。**不要默默引入。**

### 3.2 依赖清单（白名单）

> ⚠️ **2026-09-19 修正**：原白名单只有 `ws`，隐含理由是"引依赖需要构建步骤"。
> 实测发现 `@langchain/langgraph` 可在 CommonJS 下**直接 `require()`，无需构建**
> （其 `exports` 同时提供 `import` 与 `require` 两个条件），该理由对框架类依赖不成立。
> **白名单改为按理由维护，每条须写全三项：依赖名、用途、为什么允许它而不是替代品。**
> 依据：`plans/ADR-001-Agent优先与框架选型.md`。

**允许的依赖（客户端）**：

| 依赖 | 用途 | 为什么允许（含"为什么不用替代品"） |
|---|---|---|
| `ws` | CDP WebSocket 客户端 | 自研 WebSocket 需正确处理分帧、掩码、背压、ping/pong、重连、半开连接。这是"要求稳定"最不该自己写的部分 |
| `@langchain/langgraph` | Agent 编排（状态图 + 检查点） | 实测 **22 个包 / 47.6 MB**，CommonJS 直接可用无构建。项目的硬需求是"状态落盘、崩溃可续、闸门不可跳过"，检查点是它的原生能力，自研等同重造。**不用 `@mastra/core`**：实测 **152 个包 / 104.4 MB**，客户端要分发给商家，体积与依赖树深度直接决定供应链风险 |
| `zod` | 工具参数校验 | ⚠️ `@langchain/langgraph` 的 **peer dependency**。工具层必须校验模型传入的参数（不信任模型传参，见 `plans/B-工具契约与粒度设计.md` §三），**必须显式声明，不留隐式依赖** |

**服务端（`license-server/`）依赖：零。** 此条**不因本次修正而放宽**——服务端已用 `node:sqlite` + 原生 `node:http`，零依赖是它最大的运维优势。

**其余全部使用 Node 内置模块**：

| 用途 | 内置模块 |
|---|---|
| HTTP 服务 | `http` |
| WebSocket 服务端（如需要） | 无（用 `ws`） |
| 服务端数据库 | `node:sqlite`（`DatabaseSync`） |
| 密码哈希 | `crypto.scrypt` |
| HMAC 签名 | `crypto.createHmac` |
| 随机数 | `crypto.randomUUID` / `randomBytes` |
| 文件操作 | `fs`（写入必须用原子写，见开发规范） |
| 路径 | `path` |
| 子进程 | `child_process` |
| 压缩 | `zlib` |

> **引入任何白名单外的依赖，必须先在 `README-DEV.md` 与技术负责人处报备并说明理由。**
> 自检命令：`npm run check:deps`（校验允许集 / 禁止集 / 体积上限）。

**白名单的禁止项（附理由，不是习惯）**：

| 禁止 | 理由 |
|---|---|
| 任何需要**构建步骤**才能运行的依赖 | 客户端要在商家 Windows 上"解压即用"（`client/启动.cmd`），无构建链 |
| 服务端的任何新依赖 | 零依赖是服务端最大的运维优势 |

**⚠️ 关于 LLM 接入**：**必须用内置 `node:https` 自研极简适配器**，**不得引入任何厂商 SDK**（如 `openai`、`@anthropic-ai/sdk`、`@google/generative-ai` 等）。理由：① LLM 调用只是"发一个 POST、收一个 JSON"，自研适配器约 60 行即可；② 厂商 SDK 体积大、传递依赖多，会把商家机器的分发包撑大；③ 自研便于按 `shared/开发规范.md` 做超时、重试与脱敏。详见 `plans/B-Agent开发指导.md`。

> ⚠️ **注意区分**：本条禁止的是**模型厂商 SDK**，不是**编排框架**。
> `@langchain/langgraph` 是编排层（状态图、检查点），不绑定模型厂商，与本节不冲突。

**⚠️ 关于内网穿透 / 代理工具**：服务端与客户端之间的通信全部走 HTTP(S)，**不引入**任何隧道库；如需代理，通过环境变量 `HTTPS_PROXY` 由 `http`/`https` 模块原生支持。

### 3.2.1 前端硬约束（原 `plans/A-工具链路开发指导.md` §3.3~3.9，该文件已删，规格迁至此）

> ⚠️ 这三条是**不可动摇的**，任何前端改动都不得违反。

| # | 约束 | 理由 |
|---|---|---|
| 1 | **原生 DOM，无框架、无构建、无 CDN、无外部字体、无图标库** | 商家机器可能完全离线。任何外部资源都会让面板在**断网时变成白屏**——而它恰恰是用来排障的 |
| 2 | **界面不做任何看板算术** | 所有数字来自 `GET /api/state` 的 `dashboard`（由 `shared/lib/stats.js` 的 `buildDashboard()` 算出，**双端唯一一份实现**）。前端只负责"把返回的对象画出来"。前端再算一遍的后果是"界面说 87%、服务端说 84%"，而两只眼睛看的是同一批数据 |
| 3 | **不允许出现任何硬编码样例数字** | 旧代码 D-14 的缺陷：看板挂着演示假数据，商家看到"3 房间/18 命中"的幻觉数据。空态一律显示"暂无数据" |

**配套约定**：

- **所有颜色/间距/字号都是 `:root` 里的 CSS 变量**。散落的十六进制色值视为缺陷——它们会让"换一次主题"变成全文件搜索替换
- **`null` 一律显示 `—`**，绝不显示 `0%`，更不显示 `100%`
- **克制、正式**。商家明确反馈过"排版太花哨了"：不使用渐变背景、不使用大面积高饱和色块、不使用动画装饰。颜色只承担**语义**（正常/提醒/危险/停用），不承担装饰
- **危险动作用红色，但只有它用红色**。红色一旦泛滥，真正需要被看见的那一个按钮就看不见了
- 本地 API 仍绑 `127.0.0.1` + 会话令牌 + CORS 白名单（修复 D-6 的成果不得回退）

### 3.3 ⚠️ 明确不引入的技术（含理由）

| 技术 | 不引入的理由 |
|---|---|
| **`puppeteer-core`** | ① 会设置 `navigator.webdriver = true` 等自动化指纹，抖音风控可识别，而本项目用的是裸 CDP + `--disable-blink-features=AutomationControlled` 的更可控路径；② 现有 DOM 定位表达式是围绕裸 CDP 的 `Runtime.evaluate` 写的，换到 `page.evaluate` 模型要重写全部交互原语；③ 绑定特定 Chrome 版本，增大分发体积 |
| **`playwright`** | 同上。另外 Playwright/Puppeteer 默认启动**全新浏览器上下文**，用不上商家 Chrome 里已扫码登录的抖音账号——在自动化浏览器里重新登录恰恰是风控最敏感的特征 |
| **任何前端框架** | 保持单文件分发、无构建步骤 |
| **`@mastra/core`** | 实测新增 **152 个包 / 104.4 MB**（对照 `@langchain/langgraph`：22 个包 / 47.6 MB）。客户端要分发到商家 Windows 电脑，体积与依赖树深度直接决定供应链风险；其直接依赖含 `posthog-node`（遥测）等 36 项。功能上未见本项目必需而 langgraph 不具备的能力。**实测数据见 `plans/ADR-001-Agent优先与框架选型.md` §3.1** |
| **任何 ORM** | `node:sqlite` 直接用 SQL 更可控，且本项目表结构简单 |
| **`better-sqlite3`** | 需要编译原生模块，商家/服务器环境易失败；`node:sqlite` 已够用 |

> **关于自动化库的完整讨论**见 `docs/架构说明.md` §十二（语言决策记录）。

### 3.4 存储选型

| 端 | 选型 | 理由 |
|---|---|---|
| **服务端** | `node:sqlite` | 真事务（积分扣减与流水必须同事务）、支持聚合查询（看板）、零依赖。已实测 `BEGIN`/`ROLLBACK`/`COMMIT` 可用 |
| **客户端** | JSON 文件 | 数据量小、需可读可调试、便于单机排障。**但必须遵守单写者 + 原子写**（见下） |

**⚠️ 客户端存储的硬约束**：

1. **单写者**：只有 `host` 主进程读写实例文件。其他模块（browser-host、adapters）经 IPC 请求，**不得直接碰盘**。
   > 旧代码的核心缺陷就是多个进程无锁全量覆写同一个 JSON，导致队列丢任务、配置回退。**新架构下不得存在多写者。**
2. **原子写**：写 `.tmp-<pid>` 再 rename。
3. **schemaVersion**：每个 JSON 文件头带版本号，为迁移留路。

## 五、环境要求

### 5.1 开发机

| 项 | 要求 |
|---|---|
| 操作系统 | Windows 10/11（客户端开发必需）；Linux 或 WSL（服务端开发） |
| Node.js | ≥ 22.5（开发机已有 v24.18 可用） |
| 浏览器 | Google Chrome（较新版本） |
| 抖音账号 | **真机验证必需**，见下 |
| Python | **可选**，仅用于评论清洗脚本（`scrapling_bridge`），缺失时应自动跳过而非报错 |

### 5.2 ⚠️ 真机验证前置条件

方案 A 的 P2 阶段有一个**验证门**（Gate），必须用**真实抖音测试账号**回答以下问题。**没有测试账号就无法完成后继阶段。**

| 编号 | 问题 | 通过标准 |
|---|---|---|
| G-1 | 裸 CDP 接管专用 Chrome 后，评论区互动是否全程无需重新登录？ | 无需重新登录 |
| G-2 | 自动回复是否能连续 20 次成功且判定准确？ | 不误报、不谎报 |
| G-3 | 风控表现如何？ | 无验证码拦截、无账号异常提示 |
| G-4 | 旧代码中的 DOM 定位技巧能否全部复现？ | 全部复现 |
| G-5 | 连续运行 8 小时是否稳定？ | 无崩溃，可自愈标签页关闭 |

**⚠️ 请使用专门的小号做验证，不要用主号。** 验证过程会产生真实发送行为。

### 5.3 部署环境（服务端）

**授权中心的目标部署环境已实测确认**：

| 项 | 值 |
|---|---|
| 系统 | Ubuntu 22.04.5 LTS（kernel 5.15.0-117） |
| 配置 | 2 核 / 3GB DDR4 / 50GB NVMe |
| **已有服务** | sing-box v1.14.1 占用 **443/tcp（Reality）** 与 **8443/udp（Hysteria2）** |
| **ufw 规则** | 已放行 22/tcp、443/tcp、8443/udp |
| 授权服务端口规划 | 应用 `127.0.0.1:18080`（仅回环）+ 对外 HTTPS `9443/tcp` |

**⚠️ 硬约束**：

1. **不得改动现有 sing-box 配置**，不得重启网络相关服务
2. 防火墙规则**只加不删**，改动前先备份
3. 修改防火墙前后都要验证现有代理仍可用
4. systemd 资源限制建议 `MemoryMax=384M`、`CPUQuota=60%`，避免挤占同机代理服务

详细部署步骤见 `docs/部署指南-服务端.md`。
