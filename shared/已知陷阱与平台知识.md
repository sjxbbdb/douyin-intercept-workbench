### 1.1 视频页评论区

| 对象 | 事实 | 来源 |
|---|---|---|
| 评论列表容器 | `[data-e2e="comment-list"]` | `reply_worker.js:78,100,150,215` |
| 评论项 | `[data-e2e="comment-item"]` | `reply_worker.js:78,100` |
| 评论正文节点 | `[data-e2e="comment-content"]` | `reply_worker.js:326`（仅兜底1 里用到一次） |
| 评论区入口图标 | `[data-e2e="feed-comment-icon"]` | `reply_worker.js:160` |
| 评论区入口兜底文案 | 叶子节点 `innerText.trim() === '评论'` | `reply_worker.js:160`、`comment_worker.js:92` |
| 顶层评论输入容器 | `.comment-input-container` | `comment_worker.js:104`、`reply_worker.js:314` |

**如何判断某个评论项是"我们要回复的那条"**：不能只比对正文。legacy 用的是 **正文 + 昵称双条件**，且两边都先经过同一个归一化函数（`reply_worker.js:47-53`、`:74`）：

```js
// legacy 归一化规则（原样抄录要点）：
// 1) 去掉所有 [xxx]（表情/话题占位）
// 2) 去掉所有空白
// 3) 去掉中英文标点与符号集合：，。,.!！?？:：;；、"'“”‘’()[]{}<>《》【】（）-_=+~`@#$%^&*
// 4) toLowerCase
```

匹配逻辑（`reply_worker.js:215`）：

```js
norm.indexOf(q) >= 0 && (!n || norm.indexOf(n) >= 0 || n.length <= 1)
// q = 归一化正文, n = 归一化昵称
```

⚠️ **陷阱：昵称长度 ≤1 时昵称条件被放宽为"不校验"**（`n.length <= 1`）。这是有意的，但意味着单字昵称的场景下只靠正文匹配，**正文重复的评论必须靠滚动顺序区分**。新实现必须显式记录这个降级，并计入日志。

⚠️ **陷阱：`innerText` 依赖渲染**。`innerText` 对不可见元素返回近似 `textContent` 或空串；元素不可见时归一化结果不可靠。因此**必须先确认评论列表可见**（见 1.2）再做文本匹配。

**评论区展开：三层策略（`reply_worker.js:149-185`）**

1. 纯轮询：最多 3 轮 × 每轮 4 次 × 间隔 1200ms（`reply_worker.js:154-158`）。
2. 仍不可见 → 真实鼠标点击入口一次（`mouseMoved` → 200ms → `mousePressed` → 120ms → `mouseReleased`），入口优先 `[data-e2e=feed-comment-icon]`，其次叶子节点文案"评论"（`reply_worker.js:160-169`）。
3. 点击后**耐心等待最多 12 × 1500ms ≈ 18 秒**，期间**不再点击**（`reply_worker.js:171-174`）。

⚠️ 第 3 步的注释写得很明确："避免反复点击把面板开关来回切换"（`reply_worker.js:148`）。**反复点击会把已展开的面板又关掉**——这是重试逻辑最容易写错的地方。

### 1.2 ⚠️ 页面上同时存在隐藏与可见两套 comment-list

**这是本项目最著名的一个坑。** 抖音页面 DOM 里可能有多个 `[data-e2e="comment-list"]`，其中隐藏的那套里**所有按钮尺寸为 0**，会导致"评论找到了，但回复按钮找不到"（该现象在 `reply_worker.js:146-147` 有明确注释）。

**判断"可见"的唯一方法：容器 `getBoundingClientRect()` 的宽高均 > 0。** legacy 在 6 处使用同一判据：

```js
// 摘自 reply_worker.js:78 / :100 / :150 / :215 / :288 / :293（同一段内联逻辑，共 6 次复制）
var __lists = Array.from(document.querySelectorAll('[data-e2e="comment-list"]'));
var __root = null;
for (var __L = 0; __L < __lists.length; __L++) {
  var __lr = __lists[__L].getBoundingClientRect();
  if (__lr.width > 0 && __lr.height > 0) { __root = __lists[__L]; break; }
}
if (!__root) __root = document;
```

⚠️ **legacy 的兜底是错的，不要照抄**：`if (!__root) __root = document;` 会在找不到可见列表时**退回全文档搜索**，而隐藏列表就在文档里。`reply_worker.js:215` 的查找表达式与 `:78` 的按钮坐标表达式是**两份互相独立的内联代码**，两处对"哪个是可见列表"的判定可能落在**不同**的元素上，从而出现"在这个列表里找到评论，去那个列表里点按钮"。更严重的是 `pipeline.js:369`、`scan_comments.js:166`、`comment_worker.js:85` 用的是裸的 `!!document.querySelector('[data-e2e="comment-list"]')`，**完全没有可见性判定**，无法区分隐藏与可见。

**新实现的正确做法**：

1. 提供一个**唯一的** DOM 原语 `findVisibleRoot(selector)`，全项目只此一份，内部实现：

```js
// client/platform/page-comment.js 建议实现（示意）
function findVisibleRoot() {
  const lists = Array.from(document.querySelectorAll(SELECTORS.commentList.candidates[0]));
  const visible = lists.find((el) => {
    const r = el.getBoundingClientRect();
    return r.width > 0 && r.height > 0;
  });
  return { root: visible || null, candidateCount: lists.length };
  // ⚠️ 找不到可见列表时返回 null 并报 selector_miss，绝不 fallback 到 document
}
```

2. **同一次 `Runtime.evaluate` 内完成"定位评论 → 滚入视口 → 取按钮坐标"**，不要跨两次调用（原因见 §2.1）。
3. 把"候选数量"与"选中索引"写进阶段化日志，这样面板结构变化时可定位。

| 事实 | 来源 |

| 容器类名 `.note-detail-container` | `reply_worker.js:178,228,265` |

**判定表达式的原文（`reply_worker.js:178` / `:228` / `:265` 三处完全相同）**：

```js
(!!document.querySelector('.note-detail-container')) || location.pathname.indexOf('/note/') >= 0
```

**为什么必须跳过而不是硬试**：legacy 的注释说明得很清楚——"图文帖(note)的可见评论区是右侧小浮层，深评论常因虚拟列表回收而找不到；统一按'跳过'处理并写明原因，避免把平台布局差异当成失败刷屏"（`reply_worker.js:225-226`），以及"避免反复失败、污染队列"（`reply_worker.js:263`）。

**新实现的要求**：

- 保留 `note_post_panel_unsupported` 这个**跳过**语义，但**不要**复用 legacy 的字符串错误文案；应改为结构化 `StepResult{ok:false, skip:true, stage:'open_comment_panel', reason:'note_post_panel_unsupported'}`，便于 S-3 归因统计。
- 该跳过**必须**在 `usage_report` 里记为 `skipped`（`protocol.md` §7.1），**不得**计入 `failed`，更不得计入任何成功口径。
- 若将来要支持 note 帖，属于**新的 P2 真机验证项**，必须先在 `test/fixtures/` 里有 note 帖快照，再动代码。

### 1.4 回复按钮与内联编辑器

**回复按钮的判定（`reply_worker.js:83-92`）**：

```js
// 候选集合
var els = Array.from(items[i].querySelectorAll('button,[role="button"],a,div,span'));
// 过滤条件（必须全部成立）
t === '回复'                                  // innerText/textContent 去掉所有空白后严格等于"回复"
&& r.width > 0 && r.height > 0                // 有尺寸
&& r.bottom >= 0 && r.top <= innerHeight      // 与视口有交集
&& s.visibility !== 'hidden' && s.display !== 'none'
// 排序：优先 BUTTON/[role=button]（+10 分权重），其次按面积大者优先
return (bs + br.width * br.height / 1000) - (as + ar.width * ar.height / 1000);
```

⚠️ **"回复"按钮在弹幕里也存在**。legacy 的兜底1 显式排除了父元素 className 含 `danmaku` 的候选（`reply_worker.js:338`）。新实现必须保留这个排除，否则会点到直播弹幕的回复按钮上。

**内联编辑器的判定（`reply_worker.js:305`）**：三条件同时成立

```js
norm.indexOf(q) >= 0            // 该 comment-item 含目标正文
&& (!n || norm.indexOf(n) >= 0 || n.length <= 1)   // 含目标昵称（同上放宽规则）
&& t.indexOf('回复中') >= 0      // ⚠️ 关键：编辑器激活后该评论项出现"回复中"标记
// 然后取 items[i].querySelector('[contenteditable=true]')
```

⚠️ **"回复中"是判定内联编辑器已激活的唯一可靠信号**。legacy 后续的发送按钮兜底（`reply_worker.js:395`）也**同时**要求 `t.indexOf('回复中') >= 0`，即"发送按钮必须出现在处于回复态的评论项内"。新实现若丢掉这个条件，会在错误的评论项里找发送按钮。

**编辑器激活后的点击坐标（`reply_worker.js:305`）**：

```js
ed.focus();
var r = ed.getBoundingClientRect();
return { x: Math.round(r.x + Math.min(100, Math.max(20, r.width / 2))), y: Math.round(r.y + r.height / 2) };
// ⚠️ 故意不点正中心：x 偏移被夹在 [20, 100] 之间，避开编辑器中间的占位文案/图标
```

**兜底链（共 2 级，`reply_worker.js:313-355`）**：

| 级别 | 做法 | 来源 |
|---|---|---|
| 级别 0 | 在匹配到的 comment-item 内直接找 `[contenteditable=true]` | `:304-311` |
| 级别 0.5 | 探测"内联编辑器渲染在评论项之外"：找所有可见 `[contenteditable=true]`，**排除 `.comment-input-container` 内的**（那是顶层评论框，不是回复框）；找到则 `ed.focus()` | `:314-320` |
| 兜底1 | 先点一下该评论的 `[data-e2e="comment-content"]` 正文（无则退化为整个 item），再全局找文案严格为"回复"的叶子节点并点击，然后重新探测编辑器 | `:322-354` |

⚠️ **级别 0.5 的排除条件极其重要**：`.comment-input-container` 是**发新评论**的输入框。若不排除，就会把回复写到"给视频发新评论"的框里——文案发出去了，但发到了错误的位置，且**接口仍是 `comment/publish`、`status_code` 仍是 0，计费判定会认为成功**。这是会造成"计费了但回复对象错了"的静默错误。

**激活重试次数**：内联编辑器查找最多 3 次（`reply_worker.js:284`），每次之间 `sleep(1500)`；点击"回复"后固定 `sleep(2500)`（`:280`、`:301`、`:347`）。

### 1.5 发送按钮（⚠️ 硬编码品牌色）

legacy 的发送按钮兜底（`reply_worker.js:395`）用**抖音品牌红**定位图标：

```js
var svgs = items[i].querySelectorAll('svg');
for (var s = 0; s < svgs.length; s++) {
  var p = svgs[s].querySelector('path[fill="#FE2C55"]');   // ⚠️ 硬编码颜色
  if (p) { var clickable = svgs[s].parentElement || svgs[s]; /* ... */ clickable.click(); }
}
```

⚠️ **风险明确**：`#FE2C55` 是抖音品牌红，一旦换肤/改版/A-B 实验换色，该兜底**静默失效**——而它只在 Enter 主路径失败后才执行，所以失效表现是"偶发发送失败"，很难定位。

**新实现的正确做法**：

1. Enter 是**主路径**，发送按钮是**兜底**（`reply_worker.js:385-400` 的顺序），不得颠倒。
2. 兜底候选必须写成**多候选数组**放进选择器注册表：优先语义化属性（如 `data-e2e`），把 `path[fill="#FE2C55"]` 降级为**最低置信度候选**，并标注 `lastVerifiedAt` 与 `confidence:'low'`。
3. 兜底命中时必须记一条**独立的诊断码**（如 `sent_via_fallback_button`），以便统计"Enter 主路径的实际成功率"。若主路径成功率长期偏低，说明键盘事件参数需要重新验证（见 §2.4）。

### 1.6 直播弹幕容器（⚠️ 全项目最脆弱的选择器）

legacy 用 **7 个模糊 class/属性匹配**，逐个 `querySelectorAll` 后合并、去重、过滤可见（`live_dom_collector.js:349-372`）：

```js
var selectors = [
  '[data-e2e*="chat"]',
  '[data-e2e*="comment"]',
  '[class*="webcast-chatroom"]',
  '[class*="chatroom"]',
  '[class*="danmu"]',
  '[class*="bullet"]',
  '[class*="message"]'
];
selectors.forEach(function (selector) {
  try { nodes = nodes.concat(Array.from(document.querySelectorAll(selector))); } catch (e) {}
});
```

⚠️ **为什么最脆弱**：

1. 7 个选择器全是**子串模糊匹配**（`*=`），命中集合极大。`[class*="message"]` 会命中私信、系统提示、客服浮层等**一切**带 message 的节点。
2. 去重键是 `user + "|" + text`（`live_dom_collector.js:368`），**不是** DOM 节点的身份，因此**同一用户发相同文案的两次弹幕会被误判为重复而丢一条**。
3. 结果依赖 `parseRow` 的启发式解析（§4.1），而 `parseRow` 返回 null 时会**静默丢弃**该节点，没有"疑似弹幕但解析失败"的计数。
4. legacy 提供了一个诊断字段 `diagnostics.selectorCandidates`（`:385`）与 `diagnostics.parsedRows`（`:386`），**这是唯一可观测手段，新实现必须保留并加强**。

**新实现的正确做法**：

- 选择器注册表里为"弹幕行"维护**有序候选数组**，`data-e2e` 类选择器优先，模糊 class 匹配放最后并标 `confidence:'low'`。
- 用**节点级去重**（Node 引用或 `data-*` 稳定键）取代 `user+text` 去重；无稳定键时按 `protocol.md` §7.1 的退化口径处理（5 分钟窗内只计一次）。
- **必须上报三个诊断计数**：候选节点数、解析成功数、解析失败数。三者比例突变即告警（这是发现改版的**唯一早期信号**）。

1. **不能靠 URL 判断页面是否加载成功**。`Page.navigate` 返回后 URL 可能已变成 `jingxuan?modal_id=`。判断依据必须是 **DOM 就绪**（`[data-e2e="comment-list"]` 出现且可见），不是 URL。
2. **标签页复用必须按"是不是抖音页面"判定，不能按完整 URL 相等判定**。legacy 在 `reply_worker.js:464` 用 `(t.url || "").includes("douyin.com")`、在 `scan_comments.js:119` 也用 `includes("douyin.com")`；而 `live_dom_collector.js:426-434` 的 `sameRoom` 则比较 hostname + pathname（去掉尾部 `/`）。两种粒度各有用途，**不要混用**。
3. `/user/<sec_uid>` 的 sec_uid 可能被 URL 编码，比较前必须解码（`live_dom_collector.js:291,302` 用 `decodeURIComponent`）。

## 二、⚠️ 时序陷阱

> 本节每一条都是 legacy 用"拿不到坐标 / 点不到按钮 / 发送无效"换来的。**逐条给出原因与正确做法。**

### 2.1 `scrollIntoView` 之后必须延迟再读按钮坐标

**现象**：评论区是虚拟列表，`scrollIntoView()` 触发滚动后**列表会重渲染**，同步读取的 `getBoundingClientRect()` 返回 `0×0`（元素已被回收或替换为新节点）。

**legacy 的解法（`reply_worker.js:72-114, 237-260`）——两步走**：

1. `btnCoordsExpression(q, n)`（`:75-94`）：在**同一次 `Runtime.evaluate` 内**完成"遍历 comment-item → 归一化匹配 → `scrollIntoView({block:'center'})` → 立即读候选按钮坐标"，注释原文："合并成一次同步调用，避免两次调用之间评论节点被虚拟列表回收，导致「评论找到了但按钮找不到」"（`:72-73`）。
2. 若第 1 步返回 null，**先 `sleep(1200)` 让虚拟列表完成重渲染**，再用 `replyBtnFindExpression`（`:97-114`，只读坐标、**不滚动**）读一次。注释原文："合并调用已把评论滚入视口；等虚拟列表重渲染后再读一次按钮坐标（同步读会拿到 0×0）"（`:255`）。

**重试结构（`:240-260`）**：最多 **6 次**；从第 2 次起先做"轻微上滚"（`scrollTop -= 600`）→ `sleep(1200)` → 滚到底 → `sleep(1500)`，促使列表重新渲染出该评论。

**新实现的正确做法**：把"找到 → 滚入 → 等重渲染 → 读坐标"封装成**一个原语**（如 `locateReplyButton(target)`），内部固定包含那次 `sleep`；**禁止**在平台层之外再写"先滚动再读坐标"的分步代码。延迟值不得小于 1000ms，并作为**注册表可配项**（改版后可能需要调整，属 S-4 允许的单文件改动）。

### 2.2 评论区必须等"真正可见"才能操作按钮

节点存在 ≠ 面板已展开。隐藏时容器 `display:none`，内部所有按钮尺寸为 0（`reply_worker.js:146-147`）。

**做法**：见 §1.2。补充一条 legacy 的**失败态处理**：`panelReady` 为 false 时先做 note 帖判定（`:176-184`），是 note 就 skip，否则返回 `comment panel not visible`。**新实现不得把"面板未展开"直接计入平台失败**，它是环境/布局类失败，应归到 `element_timeout`（`protocol.md` §7.4）并触发熔断计数。

面板就绪后 legacy 固定 `sleep(1500)` 再继续（`:186`）——**这一步不要省**，面板展开后的首批渲染仍在进行。

### 2.3 搜索页在长期复用的标签页里会退化

**事实**（`AGENTS.md` 重要实现细节 1）："搜索页在长期复用的标签里会退化（加载不出结果），必须用**新标签页**搜索。"

**legacy 的做法**：`pipeline.js:223-231` 为每个并行 worker **新建** 标签页（`createTab("https://www.douyin.com/search/...")`），最多 4 个（`parallelTabs = Math.min(4, Math.max(1, Number(req.parallelTabs) || 4))`，`:180`），搜索阶段结束后**关闭**这些标签页（`:308-309`），评论爬取阶段**另建**一批（`:435-440`）。

**新建标签页的等待协议（`reply_worker.js:55-70` / `pipeline.js:126-141` 完全一致）**：

```js
const { targetId } = await sendT(browser, "Target.createTarget", { url }, 15000);
await sleep(1200);                          // 先固定等一会儿
for (let i = 0; i < 20; i++) {              // 再轮询最多 20 × 500ms = 10s
  const list = await getJson("http://127.0.0.1:" + PORT + "/json/list");
  const tab = list.find((t) => t.type === "page" && t.id === targetId);
  if (tab && tab.webSocketDebuggerUrl) {
    try { await sendT(browser, "Target.activateTarget", { targetId }, 8000); } catch {}
    return new CDP(tab.webSocketDebuggerUrl);
  }
  await sleep(500);
}
throw new Error("tab not ready");
```

⚠️ `live_dm_worker.js:101-109` 的 `waitForTarget` 是 30 × 500ms = 15s，**没有** 1200ms 的初始 sleep。两处不一致，新实现统一为"先等、再轮询"或因由明确的单一实现。

### 2.4 Enter 三段式按键与标签页必须在前台

**事实**：Enter 发送**要求标签页处于前台**。`reply_worker.js:122` 注释原文："bring tab to front (Enter-send requires active tab)"，`comment_worker.js:144-152` 在按键前也显式 `await activateTab(cdp)`。

**三段式按键（`reply_worker.js:386-388`，`comment_worker.js:154-156` 同）**：

```js
await sendT(cdp, "Input.dispatchKeyEvent", { type: "rawKeyDown", key: "Enter", code: "Enter", windowsVirtualKeyCode: 13, nativeVirtualKeyCode: 13 }, 5000);
await sendT(cdp, "Input.dispatchKeyEvent", { type: "char",      key: "Enter", code: "Enter", text: "\r", windowsVirtualKeyCode: 13 }, 5000);
await sendT(cdp, "Input.dispatchKeyEvent", { type: "keyUp",     key: "Enter", code: "Enter", windowsVirtualKeyCode: 13 }, 5000);
```

⚠️ **三个细节都不能省**：① `rawKeyDown`（不是 `keyDown`）；② `char` 事件必须带 `text: "\r"`；③ 两个 `windowsVirtualKeyCode` / `nativeVirtualKeyCode` 必须为 **13**。缺少 `char` 段时某些框架的富文本编辑器（DraftJS）收不到输入。

**激活标签页的正确姿势（`reply_worker.js:123-129`）**：

```js
const version = await getJson("http://127.0.0.1:" + PORT + "/json/version");
const bws = new CDP(version.webSocketDebuggerUrl);          // 浏览器级 WS
const tlist = await getJson("http://127.0.0.1:" + PORT + "/json/list");
const myTab = tlist.find((t) => t.type === "page" && t.webSocketDebuggerUrl === cdp.ws.url);
if (myTab) await sendT(bws, "Target.activateTarget", { targetId: myTab.id }, 8000);
```

⚠️ **用的是浏览器级 WebSocket（`/json/version` 的 `webSocketDebuggerUrl`），不是页面级**。`Target.activateTarget` 只存在于浏览器级连接。legacy 在 4 个文件里各自重复了这套逻辑（`reply_worker.js:123-129`、`comment_worker.js:71-80`、`pipeline.js:324-333`、`scan_comments.js` 无），新实现必须收敛成 `core/browser-host.js` 的一个方法。

⚠️ 这段 legacy 代码**整个被 `try{}catch(e){}` 包住**（`reply_worker.js:123-129`），激活失败会被静默吞掉，然后 Enter 打空、最终报"reply POST not captured（可能被风控拦截）"——**把"标签页没在前台"误报成"风控拒绝"**。新实现必须把激活结果纳入 `StepResult`，激活失败要单独归因。

### 2.5 页面加载等待：事件 + 兜底超时

`reply_worker.js:139-145` 的模式：

```js
const loaded = new Promise((resolve) => {
  const fn = () => { cdp.off("Page.loadEventFired", fn); resolve(true); };
  cdp.on("Page.loadEventFired", fn);
  setTimeout(() => { cdp.off("Page.loadEventFired", fn); resolve(false); }, 20000);
});
await loaded;   // ⚠️ legacy 忽略了返回值 true/false
```

⚠️ **legacy 丢弃了 `loaded` 的布尔值**，因此"超时未加载完"与"正常加载完"走同一条后续路径。新实现必须区分：`loaded === false` → 记 `page_load_timeout`，进入重试或归因，而不是继续往下操作。

**导航本身带一次重试（`reply_worker.js:130-138`）**：

```js
try { await sendT(cdp, "Page.navigate", { url }, 15000); }
catch (e) { await sleep(1500); await sendT(cdp, "Page.navigate", { url }, 25000); }
```

注释原文："导航带一次重试：瞬时超时（浏览器繁忙/刚重启）不应直接判失败"。⚠️ 第二次超时放大到 25s。新实现保留"一次重试 + 放大超时"的结构，但重试次数要**由调度器控制**（避免适配器内隐藏重试导致实际尝试次数与上报的 `attempt_seq` 不一致，`protocol.md` §4.8 要求 `attempt_seq` 从 1 开始如实计数）。

**评论区出现的等待**（`pipeline.js:367-372` / `scan_comments.js:165-169` / `comment_worker.js:84-97`）：轮询 8 次 × 2000ms，判据是 `!!document.querySelector('[data-e2e="comment-list"]')`（⚠️ 无可见性判定，见 §1.2），命中后再固定 `sleep(3000)`。

### 2.6 评论查找需要滚动加载：⚠️ 40 轮 vs 报错文案 30

**legacy 的滚动查找（`reply_worker.js:194-223`）**：

| 参数 | 值 | 来源 |
|---|---|---|
| 循环上限 | **40 轮** | `:203` `for (let round = 0; round < 40; round++)` |
| 每轮滚动方式 | `Input.dispatchMouseEvent` `mouseWheel` `deltaY:2000` @ `(900,500)`；再把所有 `overflowY: scroll/auto` 且 `scrollHeight > clientHeight + 200` 的容器 `scrollTop = scrollHeight` | `:196-202` |
| 每轮等待 | `sleep(2500)` | `:205` |
| 展开回复线程 | 每 2 轮一次（`round % 2 === 0`）：点所有文案匹配 `/^展开[0-9]+条回复$/` 且 `children.length === 0` 的节点，**单轮最多 15 个**，点击后 `sleep(2000)` | `:207-213` |
| 进度日志 | 每 5 轮打印一次 `count` | `:220` |
| **失败文案** | `"comment not found after 30 scroll rounds"` | `:234` |

⚠️ **不一致就在这一行**：循环是 40 轮，报错文案写的是 **30** 轮。这是必须避免的缺陷——**新代码不得出现循环上限与错误文案不一致**。正确做法是两者由**同一个常量**推导（例如 `MSG = \`comment not found after ${MAX_SCROLL_ROUNDS} scroll rounds\``），并在测试里断言该常量被两处引用。

**"展开N条回复"的正则与限制**：

```js
var btns = Array.from(document.querySelectorAll('*')).filter(function (e) {
  var t = (e.innerText || '').trim();
  return /^展开[0-9]+条回复$/.test(t) && e.children.length === 0;
});
// 每次最多点 15 个（reply_worker.js:209）；scan_comments.js:176 是 12 个且最多 4 轮；pipeline.js:380 是 10 个且最多 3 轮
```

⚠️ **三个文件的展开上限各不相同（15/12/10）与轮数（每 2 轮 / 4 轮 / 3 轮）**。新实现必须统一为**一个**注册表参数，并说明取值理由（过多点击会触发风控节奏异常）。

**滚动位置的注意事项**：`reply_worker.js` 用 `(900, 500)`，`pipeline.js:165` 用 `(1150, 550)` 且 `deltaY:2200`。坐标不同是因为要滚动的容器不同（视频页右侧评论栏 vs 搜索/视频页）。**新实现要把滚动锚点也放进注册表**，不要散落硬编码坐标。

## 三、⭐ 发送成功判定（最关键的一节）

> 这一节直接对应 `README-DEV.md` **红线 2** 与 `protocol.md` §7.2 的四级口径。**全项目最不能出错的地方。**

### 3.1 用 CDP `Network` 域被动嗅探（不是 `Fetch` 域）

**legacy 的正确做法（`reply_worker.js:371-408`）**：

```js
const netHits = [];
const onReq = (p) => {
  if (p.request.method === "POST" && p.request.url.includes("comment/publish"))
    netHits.push({ requestId: p.requestId, url: p.request.url, postData: p.request.postData || "" });
};
const onResp = async (p) => {
  const h = netHits.find((x) => x.requestId === p.requestId);
  if (h) {
    h.status = p.response.status;
    try { const b = await sendT(cdp, "Network.getResponseBody", { requestId: p.requestId }, 8000); h.body = b.body; } catch {}
  }
};
cdp.on("Network.requestWillBeSent", onReq);
cdp.on("Network.responseReceived", onResp);
// ... 发送动作 ...
cdp.off("Network.requestWillBeSent", onReq);
cdp.off("Network.responseReceived", onResp);
```

**为什么必须是 `Network` 而不是 `Fetch`**：

- `Fetch.enable` 会**拦截并暂停**请求，需要客户端显式 `Fetch.continueRequest`，一旦漏发就会让页面请求永久挂起——这在"页面是商家的真实登录窗口"的场景下会直接卡死页面。
- `Network` 域是**纯监听**（`Network.enable` 后自动上报），不改变页面行为。legacy 在 4 处都用 `Network.enable`（`reply_worker.js:469`、`comment_worker.js:248`、`pipeline.js:214,226`、`scan_comments.js:146`），**全库没有一处 `Fetch.enable`**。

⚠️ **监听必须先于发送动作注册**（`reply_worker.js` 在 Enter 之前就 `cdp.on`，`comment_worker.js:149-151` 也是先注册再 `activateTab` 再按键）。若先发送再监听，响应可能已经到达而捕获不到。

⚠️ **`Network.getResponseBody` 必须在响应体被丢弃前调用**。legacy 是在 `responseReceived` 回调里立刻取（`reply_worker.js:380`）或很快取（`scan_comments.js:195`），并带 8s 超时且 `catch{}` 容忍失败。**取失败要当作"未拿到平台响应"，不得当作成功。**

### 3.2 判定条件（必须同时满足）

```js
const okPost = netHits.find((h) => h.status === 200);      // ① HTTP 200
if (!okPost) return { ok: false, error: "reply POST not captured (可能被风控拦截)" };
const bodyText = okPost.body || "";
const success = /"status_code"\s*:\s*0/.test(bodyText);     // ② 响应体匹配 status_code: 0
if (!success) return { ok: false, error: "publish 被拒绝: " + (bodyText.slice(0, 80) || "(空响应，疑似风控/验证码)") };
return { ok: true, sent: text.slice(0, 30), confirmed: true };
```

| # | 条件 | 说明 |
|---|---|---|
| ① | `status === 200` | HTTP 层成功 |
| ② | 响应体匹配 `/"status_code"\s*:\s*0/` | 平台业务层成功 |

⚠️ **正则必须允许冒号两侧有空白**（`\s*`），legacy 用的是 `/"status_code"\s*:\s*0/`，不要简化成 `"status_code":0`。

### 3.3 ⚠️ 空响应 = 风控拒绝，不得标记成功

legacy 的错误文案已经写明了这一点：`"(空响应，疑似风控/验证码)"`（`reply_worker.js:407`）。

**映射到新契约（`protocol.md` §7.2 / §7.4）**：

| 观测 | `verdict` | `evidence.confirm_signal` | `evidence.risk_control_signal` | `failure_reason` | 计费 |
|---|---|---|---|---|---|
| HTTP 200 + `status_code:0` | `sent_confirmed` | `platform_response` | `null` | `null` | **是** |
| HTTP 200 + 非 0 业务码（有 body） | `failed` | `none` | `null` | `content_rejected` | 否 |
| **HTTP 200 + 空 body** | `failed` | `none` | **`empty_response`** | **`risk_control_rejected`** | 否 |
| 未捕获到 `comment/publish` 请求 | `failed` | `none` | `null` | `element_timeout` 或 `network_error` | 否 |
| 拿到了响应但 `Network.getResponseBody` 失败 | `failed` | `none` | `null` | `unknown` | 否 |

⚠️ `failure_reasons` 是**闭集**（`protocol.md` §7.4），未知键会**拒绝整条上报**。并且该节明确写：**`editor_dismissed_unconfirmed` 不是失败原因**，它对应 `sent_suspected`。

### 3.4 ⚠️ DOM 判断不算成功（红线 2）

**新架构硬性要求**：计费资格必须满足 `confirm_signal === "platform_response"`（`protocol.md` §6.1 ②）。

| 判定方式 | 允许的 `verdict` | 计费 | 计入"已回复人数" |
|---|---|---|---|
| 平台响应体 `status_code:0` | `sent_confirmed` | **是** | 是 |
| 回复节点稳定存在 ≥3000ms（连续 3 次 1 秒轮询仍在且文本一致） | `sent_confirmed_dom` | 否（`bill_dom_confirmed=false`） | 否（单列展示） |
| 编辑器/输入框消失、节点出现后立刻消失、超时且无明确失败信号 | `sent_suspected` | 否 | 否 |
| 明确失败信号（平台错误码 / 空响应 / 发送按钮报错 / 元素未出现） | `failed` | 否 | 否 |

**必须写进代码注释的事实**：legacy 的 `comment_worker.js:188-197` 的 `verifyPublish` 里**混入了一条纯 DOM 判据**：

```js
// comment_worker.js:195 —— ⚠️ 反面教材，绝不允许在新代码中出现
if (cleared === "") return { ok: true, note: "输入框已清空（推断发送成功）" };
```

"输入框已清空 ⇒ 发送成功"是**推断**，不是平台确认。在 `comment_worker.js` 里它发生在"未捕获到 `comment/publish` 请求"的分支（`:189`），也就是说：**请求根本没发出去，却因为框空了而返回成功**。新实现中该情形只能是 `sent_suspected`。

同理，`live_dm_worker.js:210-213` 的私信判定也要重写：

```js
// live_dm_worker.js:211 —— ⚠️ 反面教材
if (!composer.hasEditor || (!composer.editorText && String(composer.bodyText || "").includes(task.text))) {
  await markSent(leadId, "message_detected");
}
```

`!composer.hasEditor`（编辑器消失）被直接判为已发送，**页面崩溃也会被记为成功**（`docs/需求规格.md` D-12 已确认此缺陷）。新实现必须是 `sent_suspected`，且 `source_type='dm'` 必须走**不同的平台接口白名单**（见 §3.5）。

### 3.5 私信与弹幕发送的接口关键字（⚠️ 必须先确认真实接口名，不要猜）

`protocol.md` §4.8 给出的 `platform_endpoint` **闭集白名单**只有四个值：

```
comment/publish      comment/reply      im/send      live/comment/send
```

| 渠道 | legacy 实际验证过的关键字 | 状态 |
|---|---|---|
| 视频评论**回复** | `comment/publish`（`reply_worker.js:374`，且 `comment_worker.js:147` 用大小写不敏感正则 `/comment\/publish/i` 二次确认） | ✅ 已验证 |
| 视频**新评论** | `comment/publish`（`comment_worker.js:147`） | ✅ 已验证（与回复同接口） |
| 私信 | **无**。`live_dm_worker.js` 只做预填，全程未发请求、未监听 Network | ❌ 未验证 |
| 直播弹幕 | **无**。`live_dom_collector.js` 只读 DOM，`collect.js` 路径从未发送 | ❌ 未验证 |

⚠️ **实现者必须做的第一步不是写代码，而是确认真实接口名**：

1. 打开专用 Chrome，用 DevTools 的 Network 面板**手工**发一条私信/弹幕；
2. 记录真实请求 URL 的**路径片段**（不是完整 URL——`protocol.md` §4.8 明确"禁止完整 URL 与域名"）；
3. 确认成功响应的成功码字段与值（是否为 `status_code: 0`，或别的字段名）；
4. 确认空响应的表现；
5. 把结果写进选择器/接口注册表，并**更新 `protocol.md` 的闭集白名单**（闭集扩充必须先上线服务端支持，见 §8.2）。

**⚠️ 绝对禁止**：凭猜测写 `im/send` 或 `live/comment/send` 然后"反正失败了会报错"。错误的 endpoint 会让"发送成功判定"永远为 false，看起来像风控，**实际是自己写错了关键字**，会浪费大量真机验证配额。

## 四、弹幕解析知识

### 4.1 弹幕行的"昵称换行 + 正文换行"结构

**legacy 的解析链（`live_dom_collector.js:310-347`）**：

```js
function getLines(el) {
  var raw = String(el && (el.innerText || el.textContent) || "").split(/\n+/);
  var out = [];
  raw.forEach(function (line) {
    var value = line.replace(/\u00a0/g, " ").replace(/\s+/g, " ").trim();
    if (value && out.indexOf(value) < 0) out.push(value);   // ⚠️ 去重也在这里，见下
  });
  return out;
}

function parseRow(el) {
  var lines = getLines(el);
  // 退化路径：只有一行时，尝试 "昵称: 正文" / "昵称：正文"
  if (lines.length < 2 && lines.length === 1) {
    var m = lines[0].match(/^(.{1,32})[:：]\s*(.{1,220})$/);
    if (m) lines = [m[1].trim(), m[2].trim()];
  }
  if (lines.length < 2) return null;                       // ← ⚠️ 静默丢弃
  var user = lines[0].replace(/^@/, "").trim();            // 第 1 行 = 昵称（可带 @ 前缀）
  var text = lines.slice(1).join(" ").trim();              // 第 2..n 行合并 = 正文
  if (!user || !text || user.length > 48 || text.length > 260) return null;  // ← ⚠️ 静默丢弃
  // ... 噪音过滤（见 4.2）、属性提取（见 4.3）...
}
```

**必须理解的三个设计点**：

1. **`\u00a0`（不换行空格）必须先替换成普通空格**，抖音的弹幕里有大量 `&nbsp;`。legacy 在 `cleanText`（`:35-40`）、`getLines`（`:314`）、`textOf`（`:264`）**三处**都做了这个替换。
2. **`getLines` 顺带做了行内去重**（`out.indexOf(value) < 0`）。副作用：**正文里重复出现的行会被吃掉**（例如昵称与正文相同、或正文是"666"而昵称也是"666"）。
3. **退化正则的两条长度上限**：昵称 `1..32` 字符、正文 `1..220` 字符（`:322`）；`parseRow` 末尾还有第二道闸：昵称 ≤48、正文 ≤260（`:328`）。两道阈值不一致（32/48、220/260），**新实现必须统一到注册表参数**，不要保留这种"双重标准"。

### 4.2 需要过滤的噪音

**正文开头噪音（`live_dom_collector.js:329`，行首锚定）**：

```js
/^(进入直播间|加入了直播间|点赞了|关注了主播|分享了直播间|送出|赠送|来了|拍了拍)/
```

**昵称位置噪音（`live_dom_collector.js:330`，行首锚定）**：

```js
/^(直播间|全部评论|互动消息|在线人数|发消息|说点什么)/
```

⚠️ **两条正则都是 `^` 锚定的"整行以…开头"**，不是包含匹配。不要改成 `includes`——那会把"我刚刚点赞了这个视频"这类**真实用户弹幕**误杀。

⚠️ 漏网之鱼：`protect`/`加入粉丝团`/`送出小心心` 等变体在 legacy 中**没有覆盖**。新实现应把噪音词表做成**可配置列表**（注册表项），并按"未命中任何关键词的弹幕占比"做统计，用于发现新噪音类型。

### 4.3 `sec_uid` 的提取顺序

**legacy 的三级回退（`live_dom_collector.js:282-309`）**：

| 级别 | 做法 | 来源 |
|---|---|---|
| 1 | 行元素自身的属性：`data-sec-uid` → `data-secuid` → `data-sec-open-id`（`attr()` 按顺序取第一个非空值） | `:283`、`:275-281` |
| 2 | 行元素**后代** `a[href]` 中匹配 `/\/user\/([^/?#]+)/i` 的**第一个**；命中则 `decodeURIComponent(m[1])` 作为 secUid，并用 `new URL(href, location.origin)` 构造 profileUrl | `:285-294` |
| 3 | 从行元素**向上最多 4 层祖先**，取 `href` / `data-profile-url` / `data-user-url` 属性再匹配同一正则 | `:296-306` |

**用户 ID 属性（与 sec_uid 分开，`live_dom_collector.js:332`）**：

```js
var rawUserId = attr(el, ["data-user-id", "data-uid", "data-sec-uid", "data-sec-open-id"]);
```

⚠️ 注意 `data-sec-uid` **同时出现在两处**（`profileInfo` 的 sec_uid 提取与 `rawUserId` 提取），因此 `row.userId` 与 `row.secUid` 可能相同。新实现要明确 `user_key_type`（`protocol.md` §7.3 要求 `sec_uid` > `conversation_id` > `uid_short`，且**同一账号内不得混用类型**，混用记 `audit_flag:"user_key_type_mixed"`）。

### 4.4 ⚠️ DOM 弹幕常把用户 ID 脱敏为 `*****`

**事实**（`shared/术语与选型基准.md` §1.4）："直播弹幕 DOM 中常被脱敏为 `*****`，取不到时该线索标记 `not_locatable`。"

**legacy 的处置（`live_dom_collector.js:200-207`）**：

```js
existing.locatable = Boolean(existing.secUid && existing.profileUrl);
if (!existing.locatable && !["sent", "skipped", "failed"].includes(existing.dmStatus)) {
  existing.dmStatus = "not_locatable";
  existing.dmReason = "未从弹幕 DOM 取得 sec_uid 或主页链接";
} else if (existing.locatable && !existing.dmStatus) {
  existing.dmStatus = "pending";
}
```

**新实现的要求（`docs/需求规格.md` FR-2.4 原文）**：

> 改造要求：**优先从弹幕数据帧/接口响应中提取真实 `sec_uid`**；提取不到时**跳过并计入"因风控跳过"统计**，不报成功、不静默失败。

**⚠️ 三条硬性约束**：

1. **不得**用昵称哈希冒充用户标识去发私信——昵称可改、可重复。
2. **不得**把 `not_locatable` 计入 `failed`；它是 `skipped`（`protocol.md` §7.1：跳过 = 命中但没有发起回复）。
3. **绝不上传原始 `sec_uid`**（`protocol.md` §7.3）：一律 `user_key_hash = hmac_sha256(privacy_salt, user_key_source)`，`privacy_salt` 由登录响应下发、每账号固定。

### 4.5 弹幕采集的其他实测参数

| 项 | 值 | 来源 |
|---|---|---|
| 行片段截断 | `rows.slice(-100)`（只保留最后 100 行） | `live_dom_collector.js:382` |
| 弹幕行必须"可见" | `rect.width && rect.height && rect.bottom >= 0 && rect.top <= innerHeight` 且 `display!=='none' && visibility!=='hidden' && opacity!=='0'` | `:268-274` |
| ⚠️ 可见性包含视口判断 | 意味着**只采当前视口内的弹幕**，滚出视口的行**采不到** | `:271` |
| 房间标题 | `h1` 或 `title`，正则剥掉尾部 `\s*[-|｜]\s*抖音.*$`，截 80 字 | `:375,380` |
| 在线人数 | 正文匹配 `/(?:在线人数\|在线\|观看\|人气)\s*[:：]?\s*([0-9.,万千]+)/` | `:376` |

⚠️ **`opacity !== '0'` 这个条件只在弹幕的 `visible()` 里有，评论区的可见性判定里没有**（`reply_worker.js:78` 只判 `width/height`）。新实现需明确取舍：弹幕用三条件，评论区用两条件——并把差异写进注册表说明，否则后人会"顺手统一"而踩坑。

## 五、风控与验证码

### 5.1 验证码识别

**两套识别表达式（内容不同，新实现应合并为一个超集）**：

```js
// reply_worker.js:188-192（评论区回复用）
var t = document.title || '';
var b = document.body ? document.body.innerText : '';
return (t.indexOf('验证码') >= 0 || b.indexOf('验证码中间页') >= 0 || b.indexOf('请输入验证码') >= 0);

// pipeline.js:317（采集用，多两个词）
var CAPTCHA_EXPR = "JSON.stringify((function(){ var t=(document.title||''); var b=(document.body?document.body.innerText:''); return (t.indexOf('验证码')>=0 || b.indexOf('验证码中间页')>=0 || b.indexOf('请输入验证码')>=0 || b.indexOf('安全验证')>=0 || b.indexOf('拖动滑块')>=0); })())";
```

**并集关键词**：`验证码`（标题或正文）、`验证码中间页`、`请输入验证码`、`安全验证`、`拖动滑块`。

### 5.2 ⚠️ 遇到验证码必须停下等人工处理，绝不做绕过

这是 `README-DEV.md` §四保留并强化的红线（"仍禁止绕过验证码/风控，改为'遇风控即熔断'"）。

**legacy 有两个不同的处置，都不够**：

| legacy 行为 | 位置 | 问题 |
|---|---|---|
| 立刻 `sleep(60000)` 后**自动重试** | `reply_worker.js:500-503` | `docs/需求规格.md` FR-2.3.5 明确指出"**不足**，风控已被触发"。且重试期间**没有熔断状态**，界面上看不出发生了什么 |
| 暂停全部抓取，最多等 **30 分钟**（1800000ms）人工完成，每 3 秒轮询一次是否已消失；超时则停止流程 | `pipeline.js:335-355` | 方向正确（等人工），但**无递进退避**、无级别提示 |

**新实现的正确做法（FR-2.3.5）**：

```
30 分钟 → 1 小时 → 当次停到次日    （三级递进退避）
```

并且：

- **必须把当前熔断级别显示在界面上**（FR-2.3.5 原文："并明确告知商家当前处于哪一级"）。
- 检测到验证码时，**必须把 Chrome 窗口激活到前台**（legacy 在 `pipeline.js:341` 调了 `activateTab(c)`，因为"请你在 Chrome 窗口完成验证"要求窗口可见）。
- **不得自动提交验证**、**不得使用打码服务**、**不得注入脚本模拟拖动**。
- 熔断状态机应在 `client/safety/circuit.js`（三层递进），检测点在平台层，**不要把熔断逻辑写在适配器里**。

⚠️ **多标签页共享熔断**：`pipeline.js:315-336` 用一个 `captchaWait` 布尔量让**任一标签页遇到验证码就暂停全部标签页**（`holdForCaptcha` 里 `if (captchaWait) { while (captchaWait) await sleep(2000); return; }`）。多实例架构下这个状态必须**按实例隔离**（S-6：故障不跨实例传播），但**同实例内三个渠道（评论/弹幕/私信）必须共享**——一个渠道被风控，另两个渠道继续发是明显的危险行为。

### 5.3 内容级风控

| 信号 | 判定 | 来源 |
|---|---|---|
| `comment/publish` **空响应** | 视为被拒 | `reply_worker.js:407`、`protocol.md` §7.2 |
| 平台业务码非 0 | `failed` + `content_rejected` | `protocol.md` §7.4 |
| 未捕获到 publish 请求 | ⚠️ 需区分"被拦截"与"按键没生效/标签页不在前台"，legacy 一律报"可能被风控拦截"（`reply_worker.js:404`） | 见 §2.4 |

**熔断触发条件（`docs/需求规格.md` FR-2.3.5）**：连续失败 3 次 → 熔断并暂停该来源。

⚠️ **必须区分三类失败对熔断的贡献**（否则会把环境问题当成风控，误伤可用性）：

| 类别 | 例子 | 是否计入熔断 |
|---|---|---|
| 风控类 | 空响应、业务码拒绝、验证码 | **计入**，且权重最高 |
| 内容类 | 相似度超限本地拦截 | 不计入（本地拦截根本不该发起请求） |
| 环境类 | 标签页不在前台、元素超时、网络错误 | 计入但**独立计数**；连续环境失败优先重连而不是熔断 |

### 5.4 陌生人私信被禁用

`stranger_dm_disabled` 分支（`live_dm_worker.js:124-125,133`）——见 §1.7。补充：

- 该分支在 legacy 中会**跳过整个线索**（`:193-195`）。
- ⚠️ 但要区分两种情形：① 平台对该用户永久禁止（`仅关注的人可私信`）；② 当前**本账号**被临时限制。legacy 无法区分。新实现应把②归入**账号级风控**并触发熔断（因为它是账号异常信号），①才归入 `skipped/blocked_by_target`。

## 六、⭐ 选择器注册表要求

### 6.1 为什么必须集中在一张表

`docs/架构说明.md` §一给出 **S-4 改版韧性**：抖音改版后修复所需改动文件数 = **1 个**（选择器注册表），并明确"**S-4 是架构约束**：如果选择器散落在多处，这条永远达不到"。

**反证（legacy 的实测代价）**：同一条"只用可见 comment-list"的逻辑，在 `reply_worker.js` 里**被内联复制了 6 次**（`:78, :100, :150, :215, :288, :293`）；`[data-e2e="comment-list"]` 这个字符串在 5 个文件里出现；`data-e2e=comment-list` 存在**两种写法**（带引号与不带引号，见 `reply_worker.js:78` vs `:150`、`comment_worker.js:85`）。抖音改一次版，等于要改十几处，且很容易漏。

### 6.2 注册表条目结构（`client/platform/selectors.js`）

```js
// client/platform/selectors.js —— 选择器唯一来源（示意，字段为硬性要求）
module.exports = {
  commentList: {
    key: 'commentList',
    name: '视频评论区列表容器',
    channel: 'comment',
    candidates: ['[data-e2e="comment-list"]'],   // 有序：多候选回退
    match: 'first-visible',                       // 匹配方式：first-visible | first | all
    required: true,                               // 缺失即视为页面不可用
    lastVerifiedAt: '2026-09-18',                 // 最后人工验证日期（ISO 日期）
    verifiedBy: 'P2 真机验证 G-4',
    confidence: 'high',                           // high | medium | low
    fixture: 'video-page-desktop-01.html',         // 对应离线 fixture
    notes: '⚠️ 页面可能同时存在隐藏与可见两套；必须用 rect.width>0 && rect.height>0 的那个',
  },
  commentItem: {
    key: 'commentItem', name: '评论项', channel: 'comment',
    candidates: ['[data-e2e="comment-item"]'], match: 'all', required: true,
    lastVerifiedAt: '2026-09-18', confidence: 'high', fixture: 'video-page-desktop-01.html',
    notes: '',
  },
  // ... replyButton / inlineEditor / sendButton / danmakuRow / profileDmButton ...
};
```

**硬性字段说明**：

| 字段 | 类型 | 要求 |
|---|---|---|
| `key` | string | 唯一；日志与告警中出现的就是它（`selector_miss:<key>`，见 `docs/架构说明.md` §三） |
| `channel` | enum | `comment` / `live_danmaku` / `dm` / `shared` |
| `candidates` | string[] | **有序**，逐个尝试，第一个命中即止；优先语义化属性，模糊匹配置后 |
| `match` | enum | `first-visible`（默认，必须做可见性判定）/ `first` / `all` |
| `required` | bool | `true` 时未命中 → 该步骤失败并计入 S-3 归因 |
| `lastVerifiedAt` | string | **最后人工验证日期**，不是最后修改日期 |
| `confidence` | enum | `high` / `medium` / `low`；**`low` 的选择器命中时必须额外记诊断码** |
| `fixture` | string | 对应离线 fixture 文件名；**没有 fixture 的选择器不得标 `high`** |
| `notes` | string | 踩坑说明，写清"为什么是这个选择器" |

### 6.3 选择器连续未命中告警

**要求**：连续 N 次未命中即告警（N 建议 3，可配）。

**实现要点**：

1. **按 `key` 维度统计**，不是按任务维度。同一任务里 `commentList` 命中但 `replyButton` 连续未命中，说明是按钮改版而不是面板改版。
2. **"连续"必须是跨任务连续的**：一个任务内重试 6 次全失败，只能算**1 次未命中**（否则 `reply_worker.js:240` 的 6 次重试会在一个任务内就把阈值打满，产生误告警）。计数器在**该 key 成功命中一次时清零**。
3. 达到阈值后：
   - 在 UI 上把该来源标红并提示"页面结构可能已变化"；
   - 写审计事件（本地），**不阻塞**其他来源；
   - **自动降低该 key 的 `confidence`**（内存态即可），后续命中都带诊断码。
4. 告警必须带足够定位信息：`key`、`candidates` 试过的每个值、`match` 方式、当时 URL 的 **pathname**（⚠️ 不要带 query，可能含 `modal_id` 等可反查信息）、候选节点数量（legacy 的 `diagnostics.selectorCandidates` 是这个思路，`:385`）。

### 6.4 明确禁止

**除 `client/platform/selectors.js` 外，任何地方出现 `data-e2e` 等选择器字符串一律视为缺陷。**

| 检查项 | 做法的示例 | 依据 |
|---|---|---|
| 源码扫描 | `grep -rn "data-e2e" client/ \| grep -v "client/platform/selectors.js"` 必须为空 | `shared/术语与选型基准.md` §四 |
| 事件表达式 | `Runtime.evaluate` 里出现的 `document.querySelector(...)` 只能通过注册表注入，禁止内联字面量 | 同上 |
| CSS 类名 | `.comment-input-container`、`.note-detail-container` 等同样入表 | `comment_worker.js:104`、`reply_worker.js:178` |
| 品牌色/样式常量 | `path[fill="#FE2C55"]` 入表并标 `confidence:'low'` | `reply_worker.js:395`，见 §1.5 |
