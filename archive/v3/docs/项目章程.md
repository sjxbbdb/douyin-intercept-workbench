## 一、一句话定位

> ### 一个专门做「截流 + 自动回复」的 Agent。
>
> 它只干这一件事，但要在这一件事上**足够专业**：读懂客户的真实意图、
> 判断谁值得跟、该说什么、什么时候跟进，并把意向客户沉淀成线索。
>
> **业务规则（话术、目标客户判据、报价策略）由商家配置、服务端下发，不写死在代码里。**

### 1.1 "专用"修饰的是什么

**"专用"修饰的是业务领域，不是技术能力。**

| 是 | 不是 |
|---|---|
| 只做截流与自动回复**这一个领域** | ❌ 不是"什么都能聊"的通用助手 |
| 在该领域内具备**专业深度**（能读懂行话、能多轮跟进、能判断价值） | ❌ 不是"命中关键词就回一句模板" |
| 业务规则可由商家按自己的打法配置 | ❌ 不是"支持加载多个行业"的平台 |
| 一个固定的 agent，把一件事做到位 | ❌ 不是可插拔框架，不做包机制 |

> ### ⚠️ "专业"不体现在能装几个行业，而体现在**同一个问题处理得对不对**
>
> 客户问「多少钱」，需要的是：
> 判断他是在**比价**还是在**探底**；他之前问过什么；这句该给价格还是该先问需求；
> 他有没有留联系方式的价值；上一句回完他会不会走。
>
> **这些判断的深浅，就是"专业分化程度"的实际含义。**

### 1.2 两种做法的实际差别

同样一句评论：**「这个能便宜点吗？我在南京，预算3000左右」**

| | 关键词规则 | 本 Agent |
|---|---|---|
| 是否响应 | 只有商家把"便宜""南京""3000"**都**配成关键词才命中 | 识别为「议价 + 地域 + 预算」三类信号 |
| 线索记录 | 整条原文存下 | `{诉求:议价, 地域:南京, 预算:3000}`，可按维度筛选跟进 |
| 回复内容 | 从模板池随机取一条 | 按"议价"场景从该场景的候选池中选 |
| 后续跟进 | 人工翻记录 | 可按诉求 + 地域筛出"高意向未成交"名单 |
| 多轮 | 发一条即结束 | 可追问"您是想要哪个型号" |

**右边这些不是"配置得多"，是判断得对。** 这就是引入 Agent 的理由。

## 二、这个 Agent 具体做什么

```
① 采集        从评论区 / 直播间弹幕 / 私信拿到互动内容
② 理解        识别诉求（询价/问功能/购买意向/售后/投诉/无关），抽取关键信息
③ 判断        这条值不值得回？是不是目标客户？有没有风险？
④ 组织回复    从该诉求场景的候选话术里选一条最贴切的
⑤ 合规校验    禁语、相似度、投诉场景、观察期——🔴 由代码强制，不经模型判断
⑥ 发送        走完整护栏（频控、随机间隔、活跃时段、熔断）
⑦ 确认        只认平台响应体。DOM 现象不算
⑧ 沉淀        线索入库，按诉求/地域/预算可筛；计费按确认成功的条数
```

**②③④ 是 Agent 的价值所在，⑤⑥⑦ 是代码的职责所在。这条分界线不能移动。**

### 2.1 为什么硬规则不能交给模型

| 硬规则 | 为什么必须是代码 |
|---|---|
| 观察期禁发、日上限、最小间隔 | **你不可能让一个概率模型遵守硬约束**——总有一定概率它不遵守。而这个概率的后果是账号被封 |
| 什么算发送成功 | 必须是平台响应体。模型"觉得发出去了"没有任何举证价值 |
| 投诉评论不自动回复 | 公关风险不能交给概率模型判断 |
| 禁语 | 合规底线，不接受概率 |

**Agent 只能审批代码预筛过的候选，不能构造发送目标、不能自己写文案直发、不能改任何安全参数。**

## 三、业务规则可配（这是"不写死"的具体含义）

**业务知识是数据，不是代码，也不是插件。**

| 配什么 | 配在哪 | 谁改 |
|---|---|---|
| 目标客户判据（哪些诉求值得跟、排除哪些） | 商家界面 → 服务端下发 | 商家 |
| 话术池（按诉求场景分组，每场景多条） | 商家界面 | 商家 |
| 报价策略与必问信息（如必须问到"房型""面积"） | 商家界面 | 商家 |
| 成功定义（什么算拿到线索） | 商家界面 → 服务端下发 | 商家 |
| 安全上限、间隔、观察期 | **服务端策略（`tier_table`）** | **厂商，商家只能调低** |
| 计费单价 | 服务端 | 厂商 |

> ⚠️ **前四行与后两行的区别是红线级的**：
> 业务规则商家随便改（那是他的生意）；
> **安全数值只能厂商定，商家只能往更保守的方向调**（那关系到账号能不能活）。

### 3.1 为什么不做插件/包机制

曾经设计过"工作流包"机制（可加载多个行业）。**已废弃**，理由：

| 理由 | 说明 |
|---|---|
| 定位不是平台 | 本项目只做截流自动回复一件事。支持"加载任意行业"是另一件事，会拖慢真正的目标 |
| 抽象会吃掉正确性 | 为了让"任意行业"能表达，包契约不得不做成通用声明式语言——而通用声明式的表达力**一定弱于**为截流场景专门设计的配置 |
| 没有证据表明需要 | 没有任何真实客户要求过"接入第二个行业"。为假设需求付出的抽象成本是确定的，收益是想象的 |
| 可配置已经够了 | 商家要改的是**话术和判据**，那用配置就能解决，不需要"加载代码之外的能力" |

**将来真的要做第二个平台（如快手），那是那时的决定，不是现在的设计约束。**

## 四、🔴 三条红线

红线**没有变过**，两次定位修正都没有动它们。

### 红线 1：安全上限由服务端下发，客户端只能调低

- 权威数值在 `shared/protocol.md` §4.6 的 `tier_table`——**全系统唯一来源**
- **禁止在任何地方硬编码**限额、间隔、阈值
- 客户端**只能更保守**：`daily_max` 只能调低、`min_interval_ms` 只能调高且在区间内、`content_similarity_max` 只能调低、`active_hours` 只能调短
- 越权上报 → 服务端返回 `POLICY_VIOLATION(409)` 并拒绝，并记录该次尝试供举证
- **观察期（第 1–3 天）日上限为 0**，只采集不发送，**不可跳过**

### 红线 2：只对平台确认成功的发送计费

```
verdict = sent_confirmed
且 confirm_signal = platform_response     ← DOM 判断不算，必须拿到平台响应体
且 platform_status_code = 0
且 未超当日策略上限
且 该 send_id 未计费过
```

- ⚠️ **空响应 = 风控拒绝**，不得标记成功
- ⚠️ `send_id` 必须在**发送前**生成并落盘（幂等键 + 计费键）
- 失败、被风控拒绝、被跳过、超上限的发送**一律不计费**

### 红线 3：审计必须记录真实生效的策略值与决策依据

- 每次发送与配置变更留痕，审计含**实际生效的策略版本与生效值**，而不只是商家设置值
- 原因：纠纷时须能回答"该账号当时实际生效的策略是什么、商家是否主动调高过、系统是否拒绝过"。**只记设置值无法自证**
- **隐私边界**：只上传哈希与计数，**绝不上传**评论原文、回复原文、`sec_uid` 原文
- 审计本地与服务端**双写**，客户端不可篡改服务端副本
- 🆕 **Agent 参与决策后**还须记录：`prompt_version` · `policy_version` · `model.version` · `usage`
  —— 否则模型或提示词一更新，历史决策无法复现，举证能力就没了

## 五、系统形态（两个程序）

```
┌─ 商家电脑（Windows）──────────────────┐      ┌─ 厂商服务器（Linux）──────────┐
│                                       │      │                              │
│  商家已登录的专用 Chrome ◄──CDP 驱动──┐ │      │  license-server              │
│                                      │ │      │   ├ 授权 / 积分台账           │
│  client（截流自动回复 Agent）         │ │ 签名 │   ├ 心跳与上报接收            │
│   ├ agent/   Agent 运行时（状态图）    │ │◄────►│   ├ 策略权威（tier_table）    │
│   ├ tools/   工具层（粗粒度业务工具）   │ │HTTPS │   ├ 业务规则下发              │
│   ├ safety/  护栏（硬闸门，代码 if）    │ │      │   ├ 管理后台（厂商看）        │
│   ├ platform/ 抖音页面知识             │ │      │   └ 命令行（开号/充值/卡密）   │
│   ├ adapters/ 业务动作实现             │ │      │                              │
│   ├ core/    CDP 通道（唯一一条 WS）   │ │      │  数据：node:sqlite 单文件     │
│   ├ license/ 与服务端通信              │ │      │  依赖：零                     │
│   ├ host/    单写者存储 / 队列 / 调度   │ │      └──────────────────────────────┘
│   └ ui/      对话界面 + 图形界面（降级）│ │
└───────────────────────────────────────┘
```

**三条形态约束**：

| # | 约束 | 理由 |
|---|---|---|
| 1 | `license-server/` 与 `client/` **不得互相 require** | 只能通过 `shared/protocol.md` 定义的 HTTP 接口通信；两端可独立发版 |
| 2 | **服务端不装 Agent 框架** | Agent 跑在客户端；服务端零依赖是它最大的运维优势 |
| 3 | **Agent 不直接操作浏览器** | 它只能调工具层；CDP 由 `core/browser-host` 独占 |

## 六、明确不做的事（边界）

| # | 不做 | 理由 |
|---|---|---|
| 1 | **不做通用助手** | 只做截流自动回复。问它"今天天气"应当被拒绝，不是能力不足，是定位 |
| 2 | **不做多领域平台 / 插件机制** | §3.1。可配置已覆盖真实需求 |
| 3 | **不做无限量发送** | 产品定位是「控制节奏，让账号活得长」。这是红线 1 的存在理由 |
| 4 | **不绕过验证码 / 滑块 / 风控** | 遇风控即熔断，不可协商 |
| 5 | **不读取导出 Cookie / Token / 密码** | 用商家已登录的浏览器，不接管其凭据 |
| 6 | **不把硬规则交给模型判断** | §2.1 |
| 7 | **不公开生成话术并直接发送** | 内容级风控拦得住字面、拦不住语义。Agent 只能**从候选池中选择** |
| 8 | **不做多租户 SaaS** | 当前形态是"一商家一客户端 + 一个共享授权中心" |

## 七、"专业"如何被验收

**这是本项目的核心指标。定位说"专业"，就必须有办法证明它专业。**

| # | 验收项 | 怎么测 |
|---|---|---|
| 1 | **意图识别准确率 ≥ 85%** | 用真实评论做的评估集（≥200 条脱敏样本），出混淆矩阵 |
| 2 | **`complaint`（投诉）召回率 ≥ 95%** | ⚠️ 漏判为询价会导致在投诉下自动回复，风险最高 |
| 3 | **相对关键词基线的增益可量化** | 同一份评估集跑关键词规则作对照，例如询价类召回 55% → 91% |
| 4 | **线索结构化字段可用** | 地域/预算/诉求能抽出来并按维度筛选，不是只存原文 |
| 5 | **误批率 < 5%**（硬门槛 ≤ 8%） | 已发送条目中不该回复的比例，需人工抽检 |
| 6 | **每条成本占单价 < 15%** | token 成本 ÷ 成功回复单价 |

> ⚠️ **第 3 条是整个项目的花钱决策点。**
> 若增益不足（例如询价召回只提升 5 个百分点），说明关键词已够用，
> **不应继续上 LLM**。这个结论在花钱之前就能得到，代价只是一份评估集。

## 八、文档分层（单领域下的简化版）

**只分两层。** 上一版设计过"平台层 / 领域层 / 运维层"三层加包机制，随插件机制一并废弃。

| 层 | 回答什么 | 变化频率 | 文档 |
|---|---|---|---|
| **① 机制层** | 与具体话术无关的机制：契约、计费、审计、安全、Agent 运行时、护栏 | 几乎不变 | `docs/平台需求规格.md`、`docs/架构说明.md`、`shared/protocol.md`、`shared/开发规范.md`、`shared/测试策略.md`、`shared/安全与合规要求.md`、`shared/AI协作开发指引.md`、`shared/术语与选型基准.md`、`docs/部署指南-服务端.md` |
| **② 业务层** | 抖音截流的业务知识：三来源、诉求分类、话术组织、预热曲线、平台 DOM 知识 | 随业务调整 | `docs/抖音截流需求规格.md`、`shared/已知陷阱与平台知识.md` |

> **仍然保留的纪律**：机制层文档不写具体话术；业务层文档不重复描述计费与审计机制
> （重复描述会随机制改动而过期，且两处说法容易不一致）。

### ⚠️ 两次修正的共同教训

> **不要把"用户说的一个词"直接翻译成一个架构。**

- 第一次：把"要做 agent"实现成了"加一层 agent"（默认关闭、界面为主入口）
- 第二次：把"专业分化程度较高"读成了"要支持多个行业"，于是设计了插件机制

**两次都错在同一个地方：把注意力放在"技术上能不能扩展"，而不是"用户到底要什么"。**
第一次的正确答案是"agent 是主入口不是附加层"；
第二次的正确答案是"专业 = 在这个领域判断得准"。

**这条应写进 `shared/AI协作开发指引.md`：定位类词汇（专用、平台、通用、智能）
在被翻译成架构之前，必须先问清楚它修饰的是业务领域还是技术能力。**
