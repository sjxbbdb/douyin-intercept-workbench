## 二、系统组成

```
┌─ 厂商侧 license-server（Linux）──┐        ┌─ 商家侧 client（Windows）──────┐
│  账号密码登录 / 会话令牌           │ HTTPS  │  Agent 编排（默认开启）          │
│  积分账户与流水台账                │◄──────►│  业务规则下发                    │
│  授权签发与在线心跳                │ 签名   │  业务动作执行 + 安全护栏          │
│  策略权威（tier_table）           │ JSON   │  平台页面操作（CDP）             │
│  用量归集与厂商看板                │        │  本机数据看板                    │
│  管理后台（开号/充值/卡密/策略）    │        │  急停 + 频控 + 熔断              │
└─────────────────────────────────┘        └─────────────────────────────────┘
```

> **需求 2 的具体来源（评论区 / 直播间 / 私信）属②业务层，不在本文件。**
> 本文件只约束"任何来源都必须遵守的机制"。

### 关键设计原则

1. **积分是服务端权威数据**。客户端不存余额、不允许本地加减积分，只做展示与"欠费停机"
2. **断网降级**：服务端不可达时进入**暂停态**（不消耗积分、也不发送），恢复后自动续跑。**严禁本地伪造积分继续跑**
3. **单写者 + 原子写**：只有 `client/host/store.js` 碰盘；统一原子写 + 读-改-写。任何模块不得裸 `fs.writeFileSync` 全量覆盖
4. **本地控制台收敛暴露面**：监听 `127.0.0.1`（非 `0.0.0.0`）、会话令牌鉴权、CORS 白名单
5. **路径不写死**：经 `REPLY_WORKSPACE` 或 `path.join` 解析
6. 🆕 **Agent 不得绕过硬规则**：Agent 只能审批代码预筛过的候选，发送永远由代码执行（见 FR-P2）

## 三、平台功能需求

### FR-P1 账号密码登录

| 项 | 要求 |
|---|---|
| FR-P1.1 | 客户端首屏为**登录页**：账号 + 密码 + 记住账号。**不提供注册入口**，不提供自助改密 |
| FR-P1.2 | 登录成功后由服务端签发**会话令牌（token）**，客户端持久化到本地（`license_state.json`） |
| FR-P1.3 | 令牌有效期默认 7 天，客户端每次启动静默续期；过期需重新登录 |
| FR-P1.4 | 同一账号**并发登录设备数上限可配**（默认 1 台），超限时踢掉最早会话并记录被踢设备 |
| FR-P1.5 | 登录失败需区分提示：账号不存在 / 密码错误 / 账号已停用 / 已到期。**密码错误 5 次锁定 10 分钟** |
| FR-P1.6 | 密码在服务端以 **scrypt 加盐哈希**存储，**禁止明文入库**。CLI 建号时密码只经 `--password-stdin` 或静默提示输入，**不得进 argv** |
| FR-P1.7 | 客户端界面显示：当前账号、剩余积分、到期时间 |
| FR-P1.8 | 客户端 ↔ 服务端全部请求与响应**双向 HMAC 签名**（`shared/protocol.md` §5）。未签名的 401/403 响应带 `X-Lic-Unsigned: auth` 标识 |

### FR-P2 Agent 编排与硬闸门（🆕 本项目新增的核心需求）

> **背景**：D6 将项目定位为 Agent 平台。Agent 负责理解意图与编排步骤，
> 但**硬规则绝不可交给概率模型**——你不可能让一个概率模型遵守硬约束，总有一定概率它不遵守。

| 项 | 要求 |
|---|---|
| FR-P2.1 | Agent **默认开启**。关闭后退化为图形界面的工具链路形态（**降级路径**，见 FR-P2.6） |
| FR-P2.2 | **Agent 永远不直接发送**。它只能审批系统预筛过的队列：调用 `review_batch` 看到候选 → `approve`/`reject`/`skip` + 从候选池选 `draft_id` |
| FR-P2.3 | **硬闸门必须是代码里的 `if`**，位于状态图固定位置、不可跳过、可单独测试：观察期禁发、日上限、最小间隔、内容相似度、包禁语 |
| FR-P2.4 | **不信任 Agent 的审批结果**。`approve_batch` 必须**独立重新执行**全部安全校验，任一不过则该条 `blocked` 且不发送 |
| FR-P2.5 | **工具清单里不得存在**：细粒度操作（`click`/`type`/`scroll`/`evaluate`）、修改安全策略、急停、自由生成话术直发 |
| FR-P2.6 | **降级必须可见**：L1~L4 四级（见 `docs/架构说明.md` §四），UI 显示当前级别与原因，**不许静默降级** |
| FR-P2.7 | 决策记录落盘，含 `prompt_version` / `policy_version` / `model.version` / `usage`（红线 3 的扩展） |
| FR-P2.8 | ⚠️ **每个闸门必须配一条断言测试**：闸门关闭时**下游**收到 0 条。断言对象是下游输入，不是闸门自己的返回值 |
| FR-P2.9 | 任务状态**落盘**，不依赖对话历史（对话历史会截断、会崩溃、会因上下文超限丢失） |

### FR-P3 积分制（按成功条数计费 + 充值 + 半年额度）

> **计费模型变更记录**：原设计为"按小时计费"，甲方复审时改为**按成功回复条数计费**。
> 理由：按小时计费形成"跑得越久赚得越多、账号寿命越短"的激励冲突；
> 按条计费使厂商利益与商家账号健康**一致**（号被封 → 发不出去 → 收不到钱），且封号后争议更小。

#### FR-P3.1 计价模型（服务端实现，客户端只展示）

- 单价：`credit_per_reply_milli = 1000`（1 积分 = 1 条成功回复，后台可配）
- **只对成功计费**：必须收到平台确认（平台响应体 `platform_status_code = 0`）才计费
- **失败、被风控拒绝、被跳过、超上限、未命中，一律不计费**。此设计对商家有利，须在客户端明确告知
- **绝不允许客户端"上报即计费"**：上报带客户端生成的 `send_id`，服务端按 `send_id` 唯一索引去重，重复/补报不重复扣费
- 心跳保留（60 秒），用途：① 在线状态；② **下发安全策略**；③ 会话续期。**心跳不作为计费依据**（`online_seconds` 仅作运营统计，须标注"不用于计费"）
- 停机条件：余额 `≤ 0` → 服务端拒绝心跳续期 → 客户端**1 分钟内**进入暂停态并提示"积分不足，请联系客服充值"。语义是**禁止发送**，不是"停止计时"
- 低余额提醒：剩余可用条数低于阈值（默认 100 条）时界面变黄并提示

#### FR-P3.2 计费按 `action_kind` 分派（🆕 需求 5 的接口预留）

> **背景**：需求 5 的自动剪辑"也是消耗积分制"，但剪辑**没有"平台确认成功"这个信号**。
> 红线 2 的判据（平台响应体）是为"发送"设计的，套不到"渲染出一个视频"上。
> 直接复用会产生两种坏结果之一：剪辑失败也算钱，或剪辑无法计费。

| `action_kind` | 适用 | 计费依据 | 本期 |
|---|---|---|---|
| `send` | 发送类动作 | 平台响应体 `platform_status_code = 0` | ✅ 已实现 |
| `compute` | 算力类动作（剪辑、渲染） | **实测资源消耗** + 消耗证明 | ⚠️ 只留契约 |
| `llm` | 推理类动作 | 上游 API 返回的 `usage` | ⚠️ 只留契约 |

**三者共同底线**：`action_id` 在动作开始前生成并落盘；失败一律不计费；
计费单位由**服务端**按 `price_table` 核算，**不采信客户端算出的金额**。

**消耗证明**（`compute` 类计费的必要条件）：

```
action_id · kind · started_at_ms · finished_at_ms · outcome
evidence: { output_bytes, output_sha256, cpu_ms, wall_ms }
```

> `output_sha256` 是"确实产出了产物"的客观证据，防止"空跑也计费"。

⚠️ **`compute` 类的定价口径（按次 / 按秒 / 按输出时长）属商业决策，需甲方确认。**
本文件只保证**契约能承载**，不代替定价（见 `docs/架构说明.md` §十二 R-10）。

#### FR-P3.3 充值

本期实现**两种方式**：
1. **管理后台手工充值**（甲方在后台给商家账号加分，必做）
2. **充值码兑换**（甲方批量生成卡密，商家在客户端输入兑换，必做）

在线支付对接（微信/支付宝）**本期不做**，留接口。
充值必须写**不可变更的流水台账**（`credit_ledger`）：时间、类型（充值/消耗/赠送/退款）、数量、余额快照、操作人、关联 `send_id`（消耗类）。

#### FR-P3.4 首次购买半年额度

- 套餐字段：`套餐名 / 积分(credits) / 有效天数(valid_days) / 价格`
- 半年套餐默认值：`credits = 稳定期日上限合计 × 180`（= **12600** 积分）；年套餐 = **25550** 积分。
  **实际按商业策略配置**，且必须由 `tier_table` 运行时推导，**禁止硬编码**（`shared/protocol.md` §4.14）
- ⚠️ `min_plan_credit()` 是**绝对值**（180 天的量），**不随套餐天数缩放**。设置低于该值的套餐会被拒绝（`PLAN_QUOTA_BELOW_MIN`）
- **必须在客户端显著位置说明一个商家容易误解的点**：

  > **买了半年套餐 ≠ 半年内能无限发。** 平台的日上限才是真正的量级约束，套餐只是预付额度。

  此提示不得隐藏在协议里，须在购买/登录后首屏展示一次，并可在"我的套餐"页随时查看

#### FR-P3.5 防篡改

- 余额、流水、授权状态**全部只存服务端**；客户端本地文件被改不影响真实余额
- 服务端为每次心跳与上报返回**签名响应**（HMAC），客户端校验签名，防中间人伪造"余额充足"

### FR-P6 业务规则可配（🆕 定位的直接需求）

> **定位**：这是一个**专门做截流 + 自动回复的 Agent**。
> "专用"修饰的是**业务领域**，不是技术能力——所以业务知识是**数据**，不是插件。

**FR-P6.1 分工（这是红线级的区别）**

| 配什么 | 配在哪 | 谁改 | 变化后 |
|---|---|---|---|
| 目标客户判据（哪些诉求值得跟、排除哪些） | 商家界面 → 服务端下发 | 商家 | 立即生效，无需发版 |
| 话术池（按诉求场景分组，每场景多条） | 商家界面 | 商家 | 立即生效 |
| 报价策略与必问信息 | 商家界面 | 商家 | 立即生效 |
| 成功定义（什么算拿到线索） | 商家界面 → 服务端下发 | 商家 | 立即生效 |
| **安全上限、间隔、观察期** | **服务端 `tier_table`** | **厂商；商家只能调低** | 服务端统一调整 |
| **计费单价** | 服务端 | 厂商 | 服务端统一调整 |

> ⚠️ **前四行与后两行不得混为一谈。**
> 业务规则商家随便改（那是他的生意）；
> **安全数值只能厂商定，商家只能往更保守的方向调**（那关系到账号能不能活，见红线 1）。

**FR-P6.2 业务规则的校验要求**

| 项 | 要求 |
|---|---|
| FR-P6.2.1 | 商家配置的目标客户判据**只能收窄**平台的默认范围，不得扩大（尤其是**不得移除对投诉类意图的排除**） |
| FR-P6.2.2 | 话术池每条规则**至少 5 条变体**；保存时校验，不足则拒绝保存并提示 |
| FR-P6.2.3 | 业务规则变更必须**记入审计**（谁、何时、改了什么、从什么改成什么）——红线 3 |
| FR-P6.2.4 | 业务规则**不得携带任何安全数值**。配置中出现 `daily_max` / `min_interval_ms` / `content_similarity_max` / `active_hours` / `sending_enabled` 等键名 → **拒绝保存** |
| FR-P6.2.5 | 话术池不得包含 URL 或外链（防止把流量导去平台外的可疑地址） |

> ⚠️ **不做插件/包机制**。曾设计过"工作流包"（可加载多个行业）并已废弃，
> 四条理由见 `docs/项目章程.md` §3.1。
> **将来真要做第二个平台，那是那时的决定，不是现在的设计约束。**

### FR-P7 责任边界与合规

> **说明**：本节是**产品与工程层面的设计**，用于把责任划分做成可举证的事实。
> **不构成法律意见**——协议条款与提示文案请由律师定稿，本文件可作为给律师的需求输入。

#### FR-P7.1 设计原则：免责能力来自"证据"，不是来自"条款"

只写免责条款而无可举证的事实，纠纷时基本无效。因此遵循：

> **技术限制（证明厂商已尽合理限制义务）+ 全程留痕（证明风险决策来自用户）+ 明确告知（证明用户知情）= 可举证的责任划分**

#### FR-P7.2 技术层：默认安全 + 不可绕过

| 措施 | 举证意义 |
|---|---|
| 预热曲线客户端不可关闭 | 厂商**主动限制**了新号风险 |
| 上限有硬顶，越权配置被服务端拒绝 | 厂商**拒绝提供**无限量能力 |
| ⚠️ **不得以"发得多"为卖点** | 若以量为卖点，等于亲手把客户送进封号队列，且纠纷时无法举证已尽合理限制义务 |
| 每日风险摘要持续提示 | 厂商持续告知，非一次性签字 |

> ⚠️ **原 FR-6.2 中的"默认档位 = 半自动"已作废**（2026-09-19）。
> Agent 定位下默认开启全自动编排，但**受硬闸门约束**——
> 举证意义由"默认不自动发"转为"厂商主动限制 + 全链路留痕 + 闸门不可跳过"。
> 若要保留半自动档位，须作为**商家可选项**而非平台默认值。

#### FR-P7.3 证据层：审计留痕（本项目最重要的合规资产）

留痕是"能不能免责"的分水岭。要求：

| 记录项 | 内容 |
|---|---|
| 发送明细 | `send_id`、时间、来源类型、目标哈希、**内容哈希**、判定结果、失败归因码 |
| **配置变更审计** | **谁、何时、把哪一项从什么值改成什么值、来源是"用户操作"还是"服务端策略下发"** |
| **策略快照** | 每次上报须携带**实际生效的策略版本号与生效值** |
| 熔断记录 | 触发时间、级别、原因 |
| 🆕 **Agent 决策记录** | `decision_id`、输入摘要、候选数、`decisions[]`、`prompt_version`、`model.version`、`usage`、`latency_ms` |

**关键约束**：

- 审计**本地与服务端双写**，客户端不可篡改服务端副本
- 审计须记录**真实生效的策略值**，而非仅记录设置值。"用户设了 10、系统允许 10、实际发了 10"三者必须可交叉验证——很多工具纠纷时自证失败，正是因为只记了设置值没记执行值
- **隐私边界**：只上传哈希与计数，**不上传内容原文、用户隐私字段**
- 服务端必须能回答："某次账号处罚之前，该账号实际生效的策略是什么？用户是否主动调高过？系统是否拒绝过越权配置？"

#### FR-P7.4 协议层：免责要点（供律师起草，非最终条款）

- 明确说明本工具**降低风险但不消除**账号被封、被限流、内容被下架的可能性
- 明确因平台判定、平台规则变更导致的账号处罚与业务损失，甲方不承担赔偿责任
- **强烈建议使用专门账号，不要使用主号**（须在协议与首屏强化提示）
- 禁止改变工具用途（这条同时是**甲方自身**的责任边界）
- 商家确认其使用行为符合平台规则与法律法规

#### FR-P7.5 商业层：把风险变成产品价值

- **禁止承诺"保证不封号"**——这是最容易反噬的表述，须在全部文案、销售话术、界面中禁止
- 可承诺"**持续更新风控策略**"（这是厂商能实际做到的）
- 建议建立**封号补偿策略**（如核实后赠送积分），把纠纷前置化解

#### FR-P7.6 验收要求

- 能在服务端导出某账号的完整审计记录（`cli.js audit` 命令），内容可支撑纠纷举证
- 故意把客户端配置改到超过服务端策略上限，服务端必须拒绝并留下 `POLICY_VIOLATION` 记录
- 篡改客户端本地任意文件，无法改变服务端记录的策略与用量

|---|---|
| NFR-1 依赖 | 客户端：`ws` + `@langchain/langgraph` + `zod`（每条白名单须写"为什么不用替代品"，见 `shared/术语与选型基准.md` §3.2）。**服务端零依赖**，此条不放宽。**明确不引入** `puppeteer-core`/`playwright`/`@mastra/core` |
| NFR-2 Node 版本 | 客户端与服务端均要求 **≥ 22.5**（`node:sqlite` 需要）。客户端启动须自检 Node 版本并给出明确提示，而非崩溃 |

| NFR-4 校验 | 每次改动至少 `node --check`；统一自测入口 `node test/run.js` |

## 五、基线缺陷（设计反面教材 · 已全部在新架构中规避）

以下为对原始包做只读代码考古后**已逐条亲自复核**的缺陷。
甲方后续决定**完全重写**，因此本节不再是"待修复清单"，而转为**设计反面教材**——
每一条都对应新架构中的一项硬性约束。**新实现不得重犯。**

| 编号 | 缺陷 | 对应新架构约束 |
|---|---|---|
| **D-1** | **硬编码绝对路径**指向原作者机器，共 5 文件 13 处。子进程读不到请求文件；去重历史写盘失败被 `catch {}` 吞掉，导致**同一评论可能被重复回复** | 路径必须经 `REPLY_WORKSPACE`/`path.join`；**空 catch 视为缺陷** |
| **D-2** | 界面配置项是"空承诺"：`cooldown` 与 `requireConfirm` 被解析后**从未被使用** | 配置项必须有消费点，且纳入审计 |
| **D-3** | `dailyLimit` 不是限流而是**丢线索**（`slice` 截断） | 超限应留待次日，不得静默丢弃 |
| **D-4** | 死代码：超时回收分支永远不可达 | — |
| **D-5** | `comment_worker.js` 无人调用（未接入界面） | — |
| **D-6** | **控制台监听 `0.0.0.0` + 零鉴权 + CORS `*`**。局域网内任何人可访问；**任意网页可跨站调用接口代替商家发出评论** | `127.0.0.1` + 会话令牌 + CORS 白名单 + Host 校验（NFR-9） |
| **D-7** | **队列丢失竞态**：抢占用循环开头读到的陈旧数据做全量覆盖写，同时另一路径在读-改-写追加 | `store.js` 单写者 + 原子写 + 读-改-写 |
| **D-8** | 同 D-2/D-3（另一文件中的同类问题） | 同上 |
| **D-9** | 年份硬编码 `2026` | 禁止硬编码时间常量 |
| **D-10** | 并行标签页逻辑实际无效；两处可同时全量写同一评论库；无进程句柄**无法停止** | 子进程句柄必须由调度器持有，可取消 |
| **D-11** | 进度文件卡死：进程被强杀后 `running:true` 永不复位 | 内存态 + 心跳超时自动归位 |
| **D-12** | **"已发送"判定过宽**：编辑器消失即判成功 | **只认平台响应体**（红线 2） |
| **D-13** | 重复点击**静默杀掉**正在跑的任务 | 幂等：已在跑则拒绝并提示 |
| **D-14** | 前端演示假数据在接口返回全空时**不会被清除**，商家看到幻觉数据 | 接口权威；空结果必须清空展示 |

> **D-1 的额外风险提示**：去重历史写盘失败是**静默**的，意味着原开发者机器上也存在"同一人被重复回复"的可能。
> 实现"同一用户 N 小时只回一次"时，必须用**服务端权威 + 本地兜底双保险**，不能只依赖本地文件。

## 六、验收标准（平台层）

### 基础

1. 商家用厂商发的账号密码登录成功，看不到注册入口
2. 服务端后台能创建账号、发放套餐积分、看到该商家余额变化
3. 客户端余额归零后，自动回复在 **1 分钟内**进入暂停态并提示，不再发送任何内容
4. 修改本机任何 JSON 文件把余额改成 9999，重启后界面仍显示服务端真实余额
5. `node --check` 全量通过；`node test/run.js` 全绿
6. 断网情况下自动回复暂停且不扣积分，恢复网络后自动续跑
7. 看板的"截流总量/已回复人数/回复成功率"三项数字，与手工核对结果一致

### 计费与责任边界

8. 一次**被风控拒绝**的发送，服务端**不扣积分**，且流水台账中无该笔消耗记录
9. 同一条 `send_id` 重复上报 10 次，积分**只扣 1 条**
10. 服务端可导出某账号完整审计记录，其中能看出"该账号实际生效的策略值"与"用户是否主动调高过配置"
11. 客户端界面明确展示"买了半年套餐 ≠ 半年内能无限发"的提示，且不隐藏在协议中
12. 全部销售文案与界面中**不出现"保证不封号"类表述**
13. 🆕 伪造 `action_kind=compute` 的 `billed_units` → 服务端按自己的 `price_table` **重算**，不采信客户端
14. 🆕 `action_kind=video_edit` 且单价为 0 → 不计费且返回 `BILLING_KIND_NOT_ENABLED`

### Agent 与硬闸门（FR-P2）

15. 🆕 构造"观察期 + 有候选"的输入 → **下游收到 0 条**（断言下游，不是断言闸门返回值）
16. 🆕 构造 `daily_max + 1` 条候选 → 下游收到 **=== daily_max** 条
17. 🆕 手工篡改 `draft_id` 为候选池外的值 → 必须 `blocked`，不发送
18. 🆕 同一 `batch_id` 重复提交 → 返回首次结果，**不重复发送**
19. 🆕 关闭 Agent → 图形界面仍能完成全部工作（降级路径可用）
20. 🆕 模型不可用时 → UI 显示当前降级级别与原因，**不静默降级**

### 业务规则可配（FR-P6）

21. 🆕 商家在界面改话术池 → **无需发版即生效**
22. 🆕 话术池某规则少于 5 条变体 → **拒绝保存**并提示
23. 🆕 商家配置试图**移除对投诉类意图的排除** → 拒绝（判据只能收窄）
24. 🆕 业务规则里出现 `daily_max` 等安全数值键名 → **拒绝保存**
25. 🆕 话术池含 URL / 外链 → 拒绝保存
26. 🆕 业务规则变更**记入审计**（谁、何时、从什么改成什么）
27. 🆕 商家把日上限调到超过服务端策略 → `POLICY_VIOLATION` 且**记入审计**（与业务规则可配是两回事）
