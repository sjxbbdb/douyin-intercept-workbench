环境：Windows 11 + Chrome 153（CDP 9222，商家手动登录）+ Node 22 · 零 npm 依赖 · 不逆向签名 / 不绕风控

五步链路

阶段动作关键实现点（决定成败的地方）
1 搜视频关键词 → waterfall_item_<awemeId>每次开新标签页（复用旧标签会搜不出结果）；先整串匹配，不中再分词 + 顺序无关匹配
2 抓评论拦 Network.responseReceived不抓 DOM：URL 含 comment 的响应体里才有 cid / 时间 / 地域 / sec_uid（私信必需）
3 严格筛选三种匹配模式phrase＝字面包含（推荐）；char＝单字命中，噪音极大；纯数字关键词不切分
4 评论回复定位 → 点「回复」→ 输入 → 回车 → 校验定位+点击必须原子化（同一次 evaluate）；发送以 comment/publish 的 status_code:0 为唯一判据
5 私信触达主页 → 私信 → 输入 → 回车 → 双校验输入框只在 im-dialog 内找；私密账号直接跳过；判定＝输入框已清空 且（对话区出现文案 或 message/send 200）

定位三原则（踩坑总结）

①只认可见节点：页面上常同时存在隐藏/可见两份（两个 comment-list、两个 im-dialog），querySelector 可能拿到隐藏那份（宽度 0）→ 取宽度最大者。
②原子操作：找元素 → 滚入视口 → 点击 → 检测结果，必须在同一次 Runtime.evaluate 内完成；分两次会被虚拟列表回收。
③DOM click 兜底：几何定位失败时直接 element.click()，不要求元素在视口内。

文本匹配三坑

坑现象修法
零宽字符昵称/正文带 U+200B–U+200F、U+034F，比对永远不等两侧都剔除；昵称只作优先项，不作硬条件
表情标记目标文本把 [流泪] 整段删掉，页面文本只删方括号 → 对不上页面侧同样整段删 [xxx]
多条同文评论复制粘贴党导致 XPath 兜底可能匹配到别人XPath 文本兜底仅在唯一命中时采用，歧义即放弃
