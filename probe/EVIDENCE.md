## 5. 🔴 请求证据：私信发送请求不可观测

发送期间同时挂在页面 target 的 `Network` 域上录制，结果：

| 观测项 | 结果 |
|---|---|
| HTTP POST（**不限域名**，仅排除静态资源） | **0 个** |
| WebSocket **发送**帧（带内容） | **0 个**（仅观测到 2 字节应用层心跳） |
| WebSocket **接收**帧 | 多个二进制帧，内容含 `x_frontier_received_time` / `frontier_arriverate` |

⇒ 私信走 **frontier IM 长连接**，且**发送动作在 CDP 可观测范围内没有留下痕迹**。

因此本仓库 `AGENTS.md` 安全红线 3 所要求的「**服务端/平台确认的合法业务结果**」
**在该通道当前无法直接取得**。探针采用的证据分级如下（**已刻意保留不确定状态**）：

| 级别 | 判据 | 强度 |
|---|---|---|
| `sent_confirmed` | 平台响应码 `0` | 最强 —— **本通道不可得** |
| `sent_dom_confirmed` | 文案出现在会话列表（数据来自服务端，但仍经页面渲染） | 强 |
| `submitted` | 输入框被清空 | **弱，属 DOM 表象** |

> 按红线 3「**DOM 表象必须保留为不确定状态**」，`submitted` 与 `sent_dom_confirmed`
> 均**不应**被当作可扣积分的确定成功。这是需要上游决策的开放问题，不是探针能自行解决的。

## 7. 真机修正的问题（均已在源码注释留档）

1. **输入框误命中顶栏搜索框** —— 原先取「页面第一个可见输入框」，实际拿到 `[data-e2e=searchbar-input]`，
   会把私信文案打进搜索栏，而 `filled` 判定仍返回 True（**静默错误**）。
   改为按 `[class*=messageEditor]` 容器限定作用域。
2. **发送键是无文字 SVG 图标** —— 按 `innerText === "发送"` 永远找不到，改为按类名 `e2e-send-msg-btn` 定位。
3. **验证码误报** —— 原先只匹配正文里的「验证码」三个字，被一条视频简介
   （「…手机号是收不到验证码的」）误判并中止全链路。改为「标题 / 验证码 DOM 容器 / 完整强提示句」三级判定。
4. **评论正文混入元信息** —— 正文与时间/地区/点赞是兄弟节点，直接取 `innerText` 会把
   「14小时前·山东 0 分享 回复」一并写入变量。改为排除链接内、排除时间/纯数字/固定标签后取最长候选。
5. **窗口遮挡导致点击丢失（静默降级）** —— Chrome 窗口被完全遮挡时页面
   `document.visibilityState === "hidden"`，**点击事件不送达渲染进程**，
   `Input.dispatchMouseEvent(mouseWheel)` 挂到超时，懒加载不触发。
   同关键词实测：可见 83 条视频 vs 被遮挡 9 条，**且不报错**。
   注意 CDP 的 `Page.bringToFront` / `Target.activateTarget` **改不了 Windows 的遮挡判定**，
   必须真正置前窗口（`ShowWindow` + `SetForegroundWindow`，见 `winfocus.py`）。

### 11.4 发送键为什么用颜色判定（这是本次最有价值的发现）

三个候选图标都不带任何可读属性，无法用语义类名区分。用**「有文字 vs 无文字」的 computed style 对比**测出：

| 位置 | 有文字时 | 清空后 |
|---|---|---|
| 左 | `opacity 0.44`，`fill rgba(255,255,255,0.6)` | 消失 |
| 中 | `opacity 0.44`，灰 | `opacity 0.44`，灰 |
| **右** | **`opacity 1`，`fill rgb(254,44,85)`** | 变灰 `0.44` |

采用颜色判据带来两个好处：

1. **比类名稳** —— 不依赖平台混淆后的 class 名；
2. **天然获得"空内容不发送"保护** —— 内容为空时它不是品牌红，定位器直接返回 `send_button_inactive`，**不会误点**。

⚠️ 实现细节：外层容器 `div` 也包含同一个红色 `path`，因此必须按**面积最小**选取图标叶节点；
按"最右"选会选中外层容器，其中心点落在图标**外面**，点击落空。（该缺陷由离线用例捕获。）

### 11.5 虚拟列表：必须先滚入视口再读坐标

实测某条评论的「回复」按钮坐标 `y = -1415` —— **已滚出视口**。直接按坐标点击会点到别处。

采用（沿用 legacy `reply_worker.js` 的既有做法）：

```
定位行 -> 若按钮不在视口内 -> scrollIntoView -> 等虚拟列表重渲染 -> 重新读取坐标 -> 再判定
```

定位器在按钮不在视口时返回 `scrolled_into_view` 并**不返回坐标**，由 Python 侧重试（最多 4 次）；
重试期间页面由虚拟列表完成重渲染。**绝不使用"滚动前的旧坐标"。**

### 11.9 评论区两阶段闭环（公开回复 → 私信）

**为什么必须分成两阶段。** 平台规则要求：对方回复或关注你之前，只能发送一条文字消息。
一次触达的机会只有一条，一旦阶段一（公开回复）结果不确定就贸然进入阶段二，
丢失的不是一次点击，而是这个客户。所以阶段二的前置条件被写成状态机规则，而不是调用方的自觉。

**状态规则（全部由 `comment_flow.CommentQueue` 强制执行）**：

| 阶段一状态 | 含义 | 能否进入阶段二 | 能否重试阶段一 |
|---|---|---|---|
| `sent_confirmed` | 捕获到 `comment/publish` 且平台状态码为 0 | ✅ 唯一放行态 | 不重试（已确认成功） |
| `unknown` | 无响应、或响应无法绑定到本次点击 | ❌ **两阶段均拒绝** | ❌ **绝不盲重试** |
| `failed` | 平台明确拒绝（状态码非 0） | ❌ | ✅ 受 `maxPublicAttempts` 预算约束 |
| `blocked` | 缺话术、命中风控等需人工介入 | ❌ | ❌ 停下等人 |

`unknown` 之所以在两个方向上都拒绝，是因为它既不能证明送达、也不能证明未送达：
重试会造成重复触达，放行会造成无依据的私自触达。两种错误的代价都不可逆，因此 fail-closed。

**实现要点**：

- 计划一经冻结即不可变：后续 `comment_plan` 传入的新策略被忽略，
  `plan.policySource` 如实回报策略实际来源（当前为 `builtin_default` —— 见下方未验证边界）。
- 阶段二写入独立的 `private_json` 列，**不会覆盖**阶段一状态。
- `comment_result` 的输出中**不含** `charged` / `price` / `balance`：
  积分是服务端的唯一权威，sidecar 连表达它的字段都不提供。

**离线验证**：`comment_flow` 状态机 29/29 断言通过，覆盖空队列不建批次、
过期批次不复用（`ensure_active` 抛 `batch_expired`）、仅 `sent_confirmed` 放行、
`unknown` 在 `maxPublicAttempts=99` 下仍被两阶段拒绝、`failed` 遵守重试预算、
缺任一阶段话术即 `blocked`、`mark_private` 不污染阶段一状态。

**仍未验证（不得声称可用）**：

- ❌ 未在真机跑通任何一次两阶段闭环；`comment_batch` 只有离线夹具证据。
- ❌ 阶段一的 `sent_confirmed` 依赖 `comment/publish` 响应捕获，
  **该捕获尚未在真机上观测到过一次真实响应**。
- ❌ 策略目前由调用方传入（`policySource: builtin_default`）。
  按安全红线 2，策略必须由服务端下发；接线前 `comment_batch` 不得开启自动发送。
